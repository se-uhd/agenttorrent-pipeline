# Take a GHS retrieval

## Context

`1_download_ghs.py` starts the sampling stage with a retrieval of the SEART GitHub Search (GHS) dataset. The GHS search result is a JSON file of repositories matching the configured query. The script stores the retrieval in the cache of retrievals (`ghs_cache.py`) and names it in `../data/sampling/ghs_retrieval.json` for later steps. It runs unattended, bounds the attempts for each GHS request, and states the reason for every failure. The cache index records the resolved query, counts, and every attempt.

The query is the config's `query` block plus the sampling window, which requires that a repository was created at least <!--s:parameters.1_sampling.config.ghs_download.window.created_before_months-->18<!--/s--> months before the window's end date and has a last commit in the <!--s:parameters.1_sampling.config.ghs_download.window.committed_within_months-->6<!--/s--> months before it. GHS has no update cycle to align the window with (`docs/refresh.md`). GHS's crawl job goes through its <!--s:retrieval_2026_10_05.ghs_languages-->44<!--/s--> languages one after another. For each language, it crawls the repositories pushed between the language's own checkpoint and <!--s:ghs.crawl_lag_hours:words-->one<!--/s--> hour before the crawl, and after the last language, the job pauses for <!--s:ghs.crawl_pause_hours:words-->six<!--/s--> hours (`CrawlProjectsJob.java:77`, `application.properties:169` of GHS v1.17.1). GHS updates a repository only when the crawler reaches a push to it. By default, the window therefore ends on the oldest crawl date of GHS's languages. GHS has recorded every push before that date, and its data is complete for a window that ends there.

## Key decisions

- **Language:** Python 3.14, in the single script `1_download_ghs.py`, with `requests` for HTTP, `pyyaml` for the config and `ghs_cache.py` for the cache. The suite stubs `requests` and `yaml` when they are absent
- The config defaults to `config/ghs_download.yaml` beside the script, which contains the query. Without a query, the GHS search result would contain every repository that GHS has
- The config uses GHS's own parameter names. `query` uses the names of `dto/SearchParameterDto.java:35-82`, and the download rejects any other name. GHS ignores a parameter that it does not define and returns the results of the rest of the query, so a misspelled filter would widen the sample without an error. The sampling window sets `createdMax` and `committedMin`, and the download rejects both in `query`
- The end date is a date or `crawl_date`. With `crawl_date`, the end date is the oldest crawl date of the languages. The crawl date of a language is the latest `lastCommit` date that GHS has in that language, not later than today. The search for a crawl date sorts by `lastCommit`, because GHS's search cannot sort by `pushedAt` (`GitRepoController.java:95-109`), and `lastCommit` is the field that `committedMin` compares against (`SearchParameterDtoToSpecificationConverter.java:237-240`). The search sends `committedMax=<today>`, which excludes the commits dated in the future that GHS records for some repositories. The download reads only the day, because GHS writes every hour on a 12-hour clock without AM/PM (`JacksonConfig.java:28`). A crawl date more than `max_crawl_lag_days` (<!--s:parameters.1_sampling.config.ghs_download.window.max_crawl_lag_days-->30<!--/s-->) days old means that the crawler stopped for the language, and for a language that the previous sampling frame kept, the retrieval then fails
- Only the languages that the previous sampling frame kept are held to `max_crawl_lag_days` and need a crawl date before the download of the GHS search result. Before its first request, whatever the end date, the download reads them from the values of the filter's step `languages` in the `_metadata` of `../data/sampling/ghs_filtered.json` (`kept_languages`). The filter removes every row of a language outside the most common languages of the new retrieval (`step_languages` in `4_filter_ghs.py`). A crawler that stopped for such a language, or a search that never returns its crawl date, therefore leaves the sampling frame complete. If the download held every language to the limit, every later download would fall back to the same sampling frame
- A language outside the kept set with a crawl date more than `max_crawl_lag_days` old does not hold the window back either. The download leaves it out of the end date and logs a warning that names the language and its crawl date (`stalled_outside`). After the download, it decides from the rows of the GHS search result whether the filter would keep the language (`check_left_out`, below). A language outside the kept set within the limit still counts for the end date. When no crawler stopped, the end date is the oldest crawl date of all languages. On 2026-10-12, for example, it was the crawl date of Ruby, a language that the filter does not keep
- The languages that the previous sampling frame kept are usually the languages that a new sampling frame keeps. In each of the three usable retrievals of the cache on 2026-10-19, the ten most common values of GHS's `mainLanguage` were the same ten languages, with the tenth at least <!--s:retrieval_sizes_2026_10_19.tenth_language_lead_min-->2,205<!--/s--> rows ahead of the eleventh. The filter leaves out every language that the end date left out (`filter-ghs-spec.md`). A language that enters the kept set in the month in which its crawler stopped would otherwise give the sampling frame rows for which GHS lacks the latest pushes
- After the download, `check_left_out` checks every language that the end date left out, with its crawl date or without one, against the rows of the GHS search result. With a list of kept languages, these are languages outside the list, because a language on the list needs a recent crawl date before the download. When the filter would keep one of them, the download takes the retrieval and logs a warning. The warning names the language and its crawl date or the lack of one, and it states that the filter will leave the language out. A fallback would add no row and would only keep the window from moving, every month while the crawler stays stopped. The filter leaves the language out of the new sampling frame (below), and the previous sampling frame lacks the language as well, because its filter did not keep it
- When no sampling frame or no list of kept languages is on disk, as at the first Start or for the sampling frame of March 2026, the download leaves out of the end date, with a warning, every language with a crawl date more than `max_crawl_lag_days` old or without one after the attempts and rounds. When the filter would keep one of these languages, the retrieval fails, and the reason names the language's crawl date or states that it has none. The download then falls back, or the run exits 1 when there is no earlier retrieval, as at the first Start on an empty data root. Otherwise, a crawler that stopped for a language that the filter keeps, or a failed search for its crawl date, would drop the language from the first sampling frame (`docs/refresh.md` gives the decision and its grounds)
- The languages that the filter would keep are the `top_n_languages` most common values of `mainLanguage` over the rows of the GHS search result with a license that the filter's license step keeps, judged by GHS's `license` (`licensed_rows`). As in the filter's step `languages`, a tie in count goes to the name that sorts first (`would_keep`). The download loads `4_filter_ghs.py` by its path and applies the license step with the filter's own config, SPDX list and review of licenses (`allowed_licenses`). Of the filter steps before the step `languages`, the license step removes the most rows, and it is the only one that needs no response from GitHub. In the three usable retrievals of the cache on 2026-10-19, the tenth language led the eleventh by at least <!--s:retrieval_sizes_2026_10_19.tenth_language_lead_min-->2,205<!--/s--> rows over every row of the GHS search result and by at least <!--s:retrieval_sizes_2026_10_19.tenth_language_lead_licensed_min-->677<!--/s--> over the rows that the license step keeps. In the two of them with GitHub's responses, the same ten languages led over the rows that reached the filter's step `languages`
- The number of languages is the filter's `--top-languages` when a step argument sets it, and otherwise the `top_n_languages` of the filter's config (`filter_top_languages`). The sampling stage passes that step argument to the download as well (`run_sampling.share_top_languages`). When the filter's config sets `filter_languages: false`, lacks `top_n_languages` or cannot be read, the download counts every language as one that the filter keeps, so that it leaves out no language that the filter could keep. When the filter's config skips the license step, or when the SPDX list or the review cannot be read, the download counts every row. It logs a warning for an SPDX list or a review that it cannot read, because the filter cannot run then either
- The index row contains the crawl dates and the end date. The filter takes a language with a crawl date before the end date, or without a crawl date, as a language that the end date left out, and its step `languages` ranks only the languages that the end date covers. Such a language can still rank within the filter's number of languages: after the warning above, after the filter steps that need GitHub's responses, or with a larger `--top-languages` over the same retrieval. The filter then leaves the language out with a warning and keeps the next most common language that the end date covers. It records the language that it left out, and the README of the release names it (`filter-ghs-spec.md`)
- A search for the crawl date that returns HTTP 200 without a repository gives the language no crawl date. For a language that the previous sampling frame kept, such a search counts as a failed request and gets the attempts and rounds of any other failed request. Without a crawl date, the language would no longer hold the end date back, and the window could end after the crawl date of a language that the sampling frame keeps. Without a list of kept languages, such a search counts as a failed request through the attempts of a round, so that one empty response for a language that the filter keeps does not leave the language out of the end date. After these attempts, the language gets no crawl date, with a warning, and the download decides from the rows of the GHS search result whether the filter would keep it (`check_left_out`). The download waits for no further round for such a language, because GHS's search responds, and more rounds would not change the outcome of that check. A language outside the kept set gets no crawl date at once, with a warning, and the download does not request it again
- The bounds count back by calendar months, with the day clamped to the target month. `2026-03-16` gives `createdMax=2024-09-16` and `committedMin=2025-09-16`, the window of the March sampling frame. Both bounds are closed and resolve to midnight UTC (`util/Ranges.java:110-111`), and `createdMax=2024-09-16` therefore excludes the repositories created later that day
- The download does not send `sort`. GHS's download endpoint ignores the parameter (`GitRepoController.java:175-182` passes `Sort.unsorted()`) and returns the rows in ascending GHS id
- The download sends short requests first: GHS's version (`/api/version`), its languages (`/api/l`), the crawl dates and the number of repositories that match the query (`/api/r/search` with `size=1`, field `totalItems`). When GHS returns no response, the download therefore finds out before a <!--s:release_2026_03.ghs_export_minutes-->74<!--/s-->-minute stream rather than after it. Each request has `probe_attempts` (<!--s:parameters.1_sampling.config.ghs_download.retries.probe_attempts-->5<!--/s-->) attempts, `probe_wait_seconds` (<!--s:parameters.1_sampling.config.ghs_download.retries.probe_wait_seconds-->60<!--/s-->) apart. When every attempt at a short request fails, the download waits for each wait of `probe_round_wait_minutes` in turn and makes the attempts again before it falls back. An outage of GHS or of the network can last hours, and a fallback keeps the previous sampling window until the next run. The count after the download is a short request as well, with these attempts and rounds, separate from the attempts at the download, and a count that fails does not download the GHS search result again
- With a date as the end date, the download requests neither the languages nor the crawl dates, and the index has no crawl date. No crawl date bounds such a window. A crawl date that GHS cannot return would otherwise hold the run for the attempts and rounds, or fail a retrieval with a window that does not depend on it
- The crawl dates are one short request per language, and an attempt at them keeps the dates that GHS returned. The attempt requests every language that the earlier attempts left without a date. It fails at the end and names the languages still without one, so that the next attempt requests only these languages. If each attempt requested every language again, an attempt would need a response to each of its requests, and a few failed requests could use up the attempts and the rounds
- An attempt at the crawl dates ends after `CRAWL_FAILURES_IN_A_ROW` (<!--s:parameters.1_sampling.1_download_ghs.CRAWL_FAILURES_IN_A_ROW:words-->three<!--/s-->) failed requests in a row and counts the languages that it did not request as failed. One or two failures in a row end no attempt. A response with HTTP 200, with or without a repository, shows that the search responds and resets the count. GHS's search can fail for every language while the version page and the language list respond, such as when a search times out after `READ_TIMEOUT` (<!--s:parameters.1_sampling.1_download_ghs.READ_TIMEOUT.minutes:words-->five<!--/s--> minutes) or a proxy returns HTTP 504 for it. With the shipped attempts and rounds, attempts over every language without a date would then send <!--s:ghs_download.crawl_cost.searches_without_bound-->1,320<!--/s--> requests, about <!--s:ghs_download.crawl_cost.hours_without_bound-->118<!--/s--> hours before the fallback. With the bound on failed requests in a row, the download sends at most <!--s:ghs_download.crawl_cost.searches_with_bound-->90<!--/s--> requests and falls back after about <!--s:ghs_download.crawl_cost.hours_with_bound-->16<!--/s--> hours of timeouts and of the waits of `probe_round_wait_minutes` and `probe_wait_seconds`
- Each attempt requests first the languages that the attempts requested least, in the order of the list. GHS's language list is alphabetical. Three languages with a search that fails every time, ahead of the rest in the list, would otherwise end every attempt before the languages after them were requested. A monthly download would then fall back, or the first download exit 1, at every Start. Moving the languages that an attempt requested behind the languages that it did not request would not be enough. A language after the three that failed in its one request would then sort behind them again and never be requested again
- When languages are still without a crawl date after the last round, the retrieval fails if the previous sampling frame kept one of them. Otherwise, the download leaves them out of the end date with a warning that names them, and it decides from the rows of the GHS search result whether the filter would keep them
- The language list ends on the page that returns `"last": true`. An attempt reads at most `LANGUAGE_PAGES_MAX` (<!--s:parameters.1_sampling.1_download_ghs.LANGUAGE_PAGES_MAX:words-->ten<!--/s-->) pages of `LANGUAGE_PAGE_SIZE` (<!--s:parameters.1_sampling.1_download_ghs.LANGUAGE_PAGE_SIZE-->100<!--/s-->) languages and then fails, and the next attempt starts again on the first page. A GHS that ignored `page`, or never returned `"last": true`, would respond to every request with HTTP 200. Without the bound, neither the attempts nor the fallback would then end the first step of an unattended run. GHS's <!--s:retrieval_2026_10_05.ghs_languages-->44<!--/s--> languages fit on the first page, and the bound leaves room for a list ten times as long as one page
- A short request to which GHS responds with HTTP 200 and JSON that the download cannot read counts as no response and gets another attempt, as a response that is not JSON does. Such JSON is a body that is not an object, a language list without an `items` list of names, or a count without a `totalItems` number. When the repository that a search for a crawl date returns has a `lastCommit` that does not start with a date, the search counts as a failed request for that language, because the window and the filter read each crawl date as a date. Without these checks, such a response would end the step with an exception and exit 1 instead of falling back to the previous sampling frame
- The download attempts the GHS search result `attempts` (<!--s:parameters.1_sampling.config.ghs_download.retries.attempts-->3<!--/s-->) times, waiting `wait_minutes` (<!--s:parameters.1_sampling.config.ghs_download.retries.wait_minutes.0-->5<!--/s-->, then <!--s:parameters.1_sampling.config.ghs_download.retries.wait_minutes.1-->30<!--/s-->) between the attempts. An attempt fails on a connection error or a timeout, on HTTP 408, 429 or 5xx (a `Retry-After` longer than the wait is honored, up to <!--s:parameters.1_sampling.1_download_ghs.retry_after_max_seconds.hours:words-->one<!--/s--> hour), on a body that is not a whole gzip stream, on a body that is not JSON or not an object with `items` and `parameters`, and on a GHS search result with an item count outside the counts. The download writes the compressed stream to `<id>.json.gz.part` in the cache and removes the file however the attempt ends. A Stop of the container or a kill ends the process before it can remove the file. The next download therefore removes every `*.json.gz.part` in the cache before its download and logs the name of each file that it removes, because no download reads the file of another download. In the container, the entrypoint removes these files as well, before it measures the free space (`docs/deploy.md`)
- A GHS search result can be short and look whole. GHS writes it through a JSON generator that a `finally` block closes (`GitRepoController.java:190`). An exception on the server in the middle of a GHS search result therefore ends in HTTP 200 with valid gzip and valid JSON with a short `items` list (inferred from the source and Jackson's auto-close defaults). The download detects a short GHS search result by its item count, which has to lie between the counts taken before and after the stream, widened by `completeness_slack` (<!--s:parameters.1_sampling.config.ghs_download.completeness_slack.percent-->0.1%<!--/s-->). The download of the GHS search result reads one snapshot of GHS's database (`@Transactional(readOnly = true)`, InnoDB's default isolation), and each count reads another. The count for this query grew between March and October 2026, and it can grow while the stream runs
- A retrieval of the same query counts as a failed download when it has far fewer rows than the retrieval that the stage read before (`smaller_than_previous`): fewer than `MIN_SHARE_OF_PREVIOUS` (<!--s:parameters.1_sampling.1_download_ghs.MIN_SHARE_OF_PREVIOUS-->90%<!--/s-->) of that retrieval's rows, or fewer than `MIN_LANGUAGE_SHARE_OF_PREVIOUS` (<!--s:parameters.1_sampling.1_download_ghs.MIN_LANGUAGE_SHARE_OF_PREVIOUS-->75%<!--/s-->) of a language's rows in a language with at least `LANGUAGE_ROWS_MIN` (<!--s:parameters.1_sampling.1_download_ghs.LANGUAGE_ROWS_MIN-->1,000<!--/s-->) rows in that retrieval, by the `mainLanguage` of GHS's rows. The counts before and after the download read the same database as the GHS search result and cannot show that GHS lost rows, such as after a restore of part of its database. If the stage took such a retrieval, the cloning step would delete the trees of every repository that left the sample, and the next collection would clone them again. The run falls back as when GHS returns no response, and the reason in the index, the report and the warning names both counts. The index row of the refused GHS search result has the number of its rows in `item_count`, and the report has it in `failed_item_count`. `docs/refresh.md` gives the measurements behind the shares
- When the previous sampling frame names its kept languages, the download compares only these languages, and otherwise every language. The filter removes the rows of every other language. When the crawler stops for such a language, its rows leave the moving window month by month, and a check of every language would refuse every later retrieval once the language's rows fell below the share
- The download does not compare a retrieval taken with another query (`same_query`). Another query means other parameters sent (`query`), apart from the window's two dates, or other window lengths, that is, other numbers of months from the end date back to `createdMax` and to `committedMin`, as after a change of `created_before_months` or `committed_within_months`. The comparison reads the parameters sent rather than GHS's echo, because a GHS upgrade that adds a parameter to the echo runs the same query, and `unapplied` has checked that GHS applied every parameter sent
- `--accept-smaller` takes a GHS search result that the size check refuses, for one run, with a warning, and the report contains the reason under `accepted_smaller`. After GHS has lost rows for good, every later download would otherwise fall back to the same retrieval. Deleting the pointer would not help, because the run then compares the GHS search result with the newest usable retrieval, which is the same retrieval. In the container, `--step-arg ghs_download:--accept-smaller` in `command:` passes the option for one Start (`docs/deploy.md`)
- GHS has to apply every parameter that it was sent. The GHS search result echoes the query in its `parameters` block, with dates as epoch milliseconds at midnight UTC. A parameter missing from the echo or echoed with another value means that GHS ran a different query, and the run ends with exit 1 and no fallback
- A query that GHS rejects is a defect of the config. The count and the download of the GHS search result are the two requests that carry the config's query. For these requests, HTTP 400 and the other 4xx statuses except 408 and 429 end the run with exit 1, without a fallback, because another attempt would get the same response. The version page, the language list and the crawl dates carry no parameter of the config, and GHS cannot reject the config through them. A client error in response to one of these requests counts as no response
- A file that the run cannot write or read on this host is no failure of GHS. Examples are the file of the GHS search result on a full disk (`ENOSPC`), over a quota (`EDQUOT`), on a read-only file system (`EROFS`) or in a cache that the run may not write. Such a failure ends the run with exit 1, without another attempt and without a fallback. Another attempt would get the same error, and a fallback would run the stage over the previous sampling frame with exit 0 while the fault on the host stays unnoticed. The message names the file and the free space of its file system, and the download records the failed retrieval in the index when it can still write the index. `requests` raises its own exceptions for a failure of the network. The download therefore counts any other `OSError` of the stream as an error of this host (`FileSystemFailure`), except gzip's `BadGzipFile` for a body that is not gzip. A failed write of the rows, the index, the pointer or the report ends the run in the same way. When the write error, such as a full disk, names no file, the message states the free space of the cache of retrievals
- The rows, the index, the pointer and the report are each written through a temporary file that is synced to disk before the rename, and the directory is synced after it (`ghs_cache.py`, `caches.replace_file`). Without the sync, a power loss after a rename had reached the disk but before the data had would leave an empty or truncated file under the name. An empty index or pointer would stop every later download, and an empty report would keep the runner from reading the outcome
- When GHS returns no response within the attempts, the stage continues over the previous sampling frame (`on_failure: previous_sampling_frame`). The download records the failure as a `failed` row of the index with its attempts and reason. It writes the pointer again, naming the retrieval that the pointer already named (`retrieval_before`). With no pointer, the run falls back to the newest usable retrieval. A pointer that cannot be read, such as an empty or truncated file after a power loss, or that names a retrieval that the index does not have, counts as no pointer, with a warning, because the run writes the pointer again. When the cache lacks the rows of the retrieval that the pointer names, the download takes the next older usable retrieval with its rows instead and logs a warning, because without rows the run could neither compare a GHS search result nor fall back
- After a fallback, the report contains `fallback`, `window_moved` set to false, and how many downloads in a row fell back (`fallbacks_in_a_row`), counted as the `failed` rows of the index that name a fallback since the newest usable retrieval. The warning in the log states the count from the second such download on. The runner copies the report into the pipeline execution state. At the end of every Start in which the download fell back, the entrypoint logs a warning that names the reason and the count, and the release states the fallback among the evidence limits of its README (`docs/steps/release.md`). With `on_failure: fail`, or with no earlier retrieval, the run exits 1
- The download verifies the certificate against the trust store and the shipped intermediates. `seart-ghs.si.usi.ch` sends its own certificate without the intermediate that issued it (Let's Encrypt `YR1` on 2026-10-02), which Python does not fetch. `certs/lets-encrypt-intermediates.pem` contains every intermediate that Let's Encrypt publishes, and `write_ca_bundle` puts them after the trust store of `requests` in a temporary CA file. The download does not retry a certificate that fails verification. The run falls back, and the reason in the report names the file to extend (`0_README.md` gives the commands). `requests` raises the same `SSLError` for a certificate that does not verify and for a connection that the server or the network dropped in the handshake (`SSLEOFError`). A TLS failure therefore counts as a failed verification only when `ssl.SSLCertVerificationError` is in its chain of exceptions (`caused_by`). Any other TLS failure gets another attempt, as a failed connection does
- The GHS search result stays in memory while it is parsed. The download writes it into the cache as `<id>.ghs.jsonl.xz`, in the order in which GHS sent it

## Script: `1_download_ghs.py`

### CLI interface

```
python3 1_download_ghs.py [--config CONFIG] [OPTIONS]
```

| Flag | Default | Description |
|------|---------|-------------|
| `-c, --config` | `config/ghs_download.yaml` beside the script | The YAML config |
| `--end-date` | the config's | The end date of the sampling window, a date `YYYY-MM-DD` or `crawl_date` |
| `--dry-run` | off | Compute the sampling window and count the matching repositories, without downloading or writing anything. Exit 1 when a request or a check fails |
| `--cache-dir` | `../data/sampling/ghs_retrievals/` | The cache of retrievals |
| `--pointer` | `../data/sampling/ghs_retrieval.json` | The file that names the retrieval that the stage reads |

| `--sampling-frame` | `../data/sampling/ghs_filtered.json` | The previous sampling frame, which names the languages that it kept, the languages held to `max_crawl_lag_days` and compared with the previous retrieval |
| `--accept-smaller` | off | Take a GHS search result that the size check refuses, for one run |
| `--top-languages` | the filter's config | How many of the most common languages the filter keeps, which the sampling stage passes from a step argument `--top-languages` of the filter (`run_sampling.share_top_languages`) |

### Function structure

**`load_settings(path, end_date)`**: the config, checked, as a `Settings`. Unknown parameters, window parameters in `query`, values of the wrong type, a bad end date, too few waits and an unknown failure mode are rejected

**`months_before(day, months)`**, **`lagging(settings, crawl_dates, today)`**, **`stalled_outside(settings, crawl_dates, today, kept)`**, **`resolve_window(settings, crawl_dates, today, kept, left_out)`**, **`describe_window(window, left_out)`**, **`parameter_text(value)`**, **`query_parameters(settings, window)`**: the window, which leaves out a language outside the kept languages with a crawl date older than the limit and the languages that the download decides from the rows of the GHS search result, its log message `The sampling window ends on ...`, and the parameters as sorted strings

**`unapplied(params, server)`**: the parameters that the echo of the GHS search result does not contain with the value sent

**`write_ca_bundle(directory)`**, **`caused_by(error, kind)`**, **`check_status(response, what, carries_query)`**, **`request(path, params, ca_bundle, what, stream, carries_query)`**, **`with_retries(action, attempts, waits, what, record)`**: the requests to GHS, with their failures sorted into `Retryable`, `Refused` and `CertificateFailure`, and the bounded attempts, which raise `NoResponse`. `retrieve` makes the attempts of a short request again after each round wait

**`ghs_version(ca_bundle)`**, **`languages(ca_bundle)`**, **`is_day(text)`**, **`CrawlSearches`**, **`crawl_dates(names, ca_bundle, today, searches, kept)`**, **`count(params, ca_bundle)`**, **`download_once(params, ca_bundle, temp_path)`**: the short requests and the download of the GHS search result, the language list read within `LANGUAGE_PAGES_MAX` pages, what the attempts at the crawl dates found and how often they requested each language, the languages that the attempts requested least first, a search without a repository counted as a failed request for a language that needs a crawl date, and a search with a `lastCommit` that does not start with a date counted as a failed request for any language. A response that is not the object that the download reads raises `Retryable`, and a file of the GHS search result that this host cannot write or read raises `FileSystemFailure`

**`free_space(path)`**, **`upper_first(text)`**: the free space of the file system that holds a path, for the message of a failure of this host, and a reason with its first letter capitalized, for a log message that starts with it

**`retrieval_before(paths)`**: the retrieval that the stage read before the run, which a failed run falls back to and a new retrieval is compared with, with an unreadable pointer read as none and a retrieval without its rows replaced by the next older retrieval that has its rows

**`same_query(params, settings, previous)`**, **`smaller_than_previous(data, params, settings, previous, cache_dir, kept)`**: whether the GHS search result was taken with the previous retrieval's parameters, apart from the window's two dates, and its window lengths, and why it has too few rows to replace that retrieval, overall or in a kept language, or ""

**`kept_languages(path)`**, **`fallbacks_in_a_row(cache_dir)`**: the languages that the previous sampling frame kept, and how many downloads in a row fell back

**`filter_top_languages(path, top)`**, **`filter_script()`**, **`licensed_rows(items, path)`**, **`would_keep(items, top)`**, **`without_crawl_date(undecided, settings, today)`**, **`check_left_out(items, undecided, top, settings, today, kept)`**: how many languages the filter keeps, by its `--top-languages` or its config, the filter's script loaded by its path, the rows of the GHS search result with a license that the filter's license step keeps, the languages that the filter would keep over them, what each language left out of the end date lacks, and the check whether the filter would keep one of them, which fails the retrieval when there is no list of kept languages and logs a warning when there is one

**`remove_interrupted_downloads(cache_dir)`**: removes every `*.json.gz.part` that a stopped download left

**`fall_back(settings, paths, rid, record, reason, previous)`**, **`failed_dry_run(reason)`**, **`retrieve(settings, paths, dry_run, accept_smaller, top_languages)`**, **`write_report(path, report)`**, **`main(argv)`**: a run

### Processing pipeline

1. Read and check the config
2. Name the retrieval by the UTC time of its start
3. Read the languages that the previous sampling frame kept, request GHS's version and, with the end date `crawl_date`, its languages and their crawl dates, resolve the sampling window, and count the repositories that match the query, each short request with its attempts and rounds
4. With `--dry-run`, log the window, the count and the parameters, and stop. A dry run that a failed request or check stops logs the reason as an error, writes nothing and exits 1
5. Remove the partial GHS search results that stopped downloads left, download the GHS search result, check the echo, count again as a short request, and check the counts, downloading again within the bound. When the filter would keep a language that the end date left out, fail if there is no list of kept languages, and log a warning if there is one
6. Compare the rows of the GHS search result, overall and per language that the previous sampling frame kept, with the retrieval that the stage read before, when both were taken with the same query and window lengths, and fall back when they are far fewer, unless `--accept-smaller` takes the GHS search result
7. Write the rows into the cache, the index row, the pointer and the report

### Output

The download writes `../data/sampling/ghs_retrievals/<id>.ghs.jsonl.xz` and a `retrieved` row of `../data/sampling/ghs_retrievals/index.csv` (`ghs-cache-spec.md` lists its columns). It writes `../data/sampling/ghs_retrieval.json` as `{"retrieval_id": "<id>"}`, and `../data/sampling/ghs_retrieval_report.json` with `outcome` (`retrieved` or `fallback`), `retrieval_id`, `window` and `window_moved`. After a retrieval, the report also contains `item_count`, `previous_retrieval_id` and, when `--accept-smaller` took the GHS search result, `accepted_smaller`. After a fallback, it contains `failed_retrieval_id`, `reason`, `fallbacks_in_a_row` and, for a GHS search result that the size check refused, `failed_item_count`.

## Error handling & edge cases

| Scenario | Behavior |
|----------|-----------|
| The config is missing or unreadable, or names a parameter that GHS does not have | `ERROR ghs_download: Could not read the config ...`, exit 1 |
| A short request fails <!--s:parameters.1_sampling.config.ghs_download.retries.probe_attempts:words-->five<!--/s--> times | The attempts are made again after each of `probe_round_wait_minutes`. After the last round, the retrieval fails: fallback, or exit 1 |
| The version page, the language list or a crawl date returns a 4xx | No response: another attempt |
| The language list does not end within <!--s:parameters.1_sampling.1_download_ghs.LANGUAGE_PAGES_MAX:words-->ten<!--/s--> pages | Another attempt from the first page. After the last round, the retrieval fails: fallback, or exit 1 |
| The language list or the count returns HTTP 200 with JSON that is not an object, a language list without an `items` list of names, or a count without a `totalItems` number | No response: another attempt. After the last round, the retrieval fails: fallback, or exit 1 |
| The repository of a search for a crawl date has a `lastCommit` that does not start with a date | A failed request of the language |
| A TLS connection that the server or the network dropped in the handshake | Another attempt |
| The count after the download fails | Retried as a short request. The GHS search result is not downloaded again |
| The crawl date of a language that the previous sampling frame kept is more than <!--s:parameters.1_sampling.config.ghs_download.window.max_crawl_lag_days-->30<!--/s--> days old, or every crawl date is | The retrieval fails: fallback, or exit 1 |
| The crawl date of a language that the previous sampling frame did not keep is more than <!--s:parameters.1_sampling.config.ghs_download.window.max_crawl_lag_days-->30<!--/s--> days old | `WARNING ghs_download: The crawl dates of ...`, the download leaves the language out of the end date and decides from the rows of the GHS search result whether the filter would keep it (below) |
| A language that the previous sampling frame did not keep has no crawl date after the last round | `WARNING ghs_download: GHS returned no crawl date for ...`, the download leaves the language out of the end date and decides from the rows of the GHS search result whether the filter would keep it (below) |
| The search for the crawl date of a language returns HTTP 200 without a repository | A failed request for a language that the previous sampling frame kept, through the attempts and rounds. Without a list of kept languages, a failed request through the attempts of a round, and then `WARNING ghs_download: GHS found no repository for the crawl date of ... in the attempts of a round`, no further round, and the download decides from the rows of the GHS search result. For another language, `WARNING ghs_download: GHS found no repository for the crawl date of ...`, and the download leaves the language out of the end date |
| A language that the end date left out, by a crawl date more than <!--s:parameters.1_sampling.config.ghs_download.window.max_crawl_lag_days-->30<!--/s--> days old or none after the last round, outside the kept languages | When the language is among the `top_n_languages`, or the filter's `--top-languages`, most common languages of the rows of the GHS search result under a license that the filter keeps, `WARNING ghs_download: ... The filter will leave ... out of the sampling frame, as it did from the previous one. Took the retrieval.`, because the filter leaves the language out and the previous sampling frame lacks it as well. Otherwise `INFO ghs_download: Left ... out of the end date of the sampling window. ... is not among ...`, and the retrieval is taken |
| A language that the end date left out, by a crawl date more than <!--s:parameters.1_sampling.config.ghs_download.window.max_crawl_lag_days-->30<!--/s--> days old or none after the last round, without a list of kept languages | The retrieval fails after the download when the language is among the `top_n_languages`, or the filter's `--top-languages`, most common languages of the rows of the GHS search result under a license that the filter keeps: fallback, or exit 1. Otherwise `INFO ghs_download: Left ... out of the end date of the sampling window. ... is not among ...`, and the retrieval is taken |
| A date as the end date | No request for the languages or their crawl dates, and no language left out of the end date |
| The stream breaks, the body is cut short or not JSON, the server returns 408, 429 or 5xx | Another attempt after the wait. After <!--s:parameters.1_sampling.config.ghs_download.retries.attempts:words-->three<!--/s-->, the retrieval fails |
| The GHS search result has fewer items than the counts allow | Another attempt. After <!--s:parameters.1_sampling.config.ghs_download.retries.attempts:words-->three<!--/s-->, the retrieval fails |
| The certificate does not verify | No retry. The retrieval fails, and the reason names the file of intermediates |
| The crawl dates of some languages fail | Another attempt requests only those languages, the languages that the attempts requested least first |
| <!--s:parameters.1_sampling.1_download_ghs.CRAWL_FAILURES_IN_A_ROW:Words-->Three<!--/s--> requests for crawl dates fail in a row, without a response with HTTP 200 between them | The attempt ends, and the error counts the languages that it did not request as failed |
| The GHS search result for the same query has fewer than <!--s:parameters.1_sampling.1_download_ghs.MIN_SHARE_OF_PREVIOUS-->90%<!--/s--> of the previous retrieval's rows, or fewer than <!--s:parameters.1_sampling.1_download_ghs.MIN_LANGUAGE_SHARE_OF_PREVIOUS-->75%<!--/s--> of a language's rows in a language with at least <!--s:parameters.1_sampling.1_download_ghs.LANGUAGE_ROWS_MIN-->1,000<!--/s--> there | The retrieval fails, and the reason names both counts: fallback, or exit 1 |
| The pointer is empty, truncated or names a retrieval that the index does not have | `WARNING ghs_download: ... Ignored the pointer until it is written again.`, and the download writes it again |
| The cache lacks the rows of the retrieval that the pointer names | `WARNING ghs_download: The cache of retrievals lacks the rows of ...`, and the download takes the next older usable retrieval with its rows instead |
| `--accept-smaller` and a GHS search result that the size check refuses | `WARNING ghs_download: Retrieval <id> would fall back, because .... Took it under --accept-smaller.`, and the retrieval is written |
| A partial GHS search result that a Stop or a kill left, `<id>.json.gz.part` | Removed before the next download, with an INFO line naming it |
| GHS returns 400, or another 4xx except 408 and 429, for the count or the download of the GHS search result, or the GHS search result does not echo a parameter | `ERROR ghs_download: Retrieval <id> failed. ...`, a `failed` index row, exit 1, no fallback |
| The retrieval fails with an earlier retrieval in the cache and `on_failure: previous_sampling_frame` | A `failed` index row naming the fallback, the pointer on the previous retrieval, `fallback` and the number of downloads in a row that fell back in the report, exit 0 |
| The retrieval fails with no earlier retrieval, or `on_failure: fail` | A `failed` index row, exit 1 |
| The file of the GHS search result cannot be written or read on this host, such as on a full disk, over a quota, on a read-only file system or in a cache that the run may not write | `ERROR ghs_download: Retrieval <id> failed. ...` naming the file and the free space, a `failed` index row when the index can be written, exit 1, no fallback |
| The rows, the index, the pointer or the report cannot be written | `ERROR ghs_download: Could not write the retrieval (...)` naming the free space of the file's file system, or of the cache of retrievals when the error names no file, exit 1, no fallback |
| The cache cannot be read | `ERROR ghs_download: The cache of retrievals cannot be used. ...`, exit 1 |
| A dry run gets no response, meets a certificate that does not verify or a refused query, or finds a crawl date beyond the limit that would fail a retrieval | `ERROR ghs_download: Dry run failed, nothing written. ...`, exit 1, without an index row, a pointer, a report or a fallback |

## Tests

See `test_download_ghs.py`, which uses the standard library's `unittest` and loads the script by path through `_script_loader.py`. A run is tested against a fake GHS that responds to `/version`, `/l`, `/r/search` and `/r/download/json` as GHS does and fails on demand. Every repository of its GHS search result has a license that the shipped review keeps. The fake responds to a bounded number of requests for pages of the language list and then stops the test, so that a download that never stops paging fails rather than hangs. The previous sampling frame is a file in the temporary directory with the `_metadata` of its step `languages`. The filter's config is a file there as well, which keeps the two most common languages for a first download and three for a monthly download. When the filter runs over a retrieval of a monthly download, it reads GitHub's responses that the test writes into the cache, with GHS's `mainLanguage` as GitHub's primary language. A host that cannot write the file of the GHS search result is simulated by a stand-in for `open` that raises the error of a full disk, a quota, a read-only file system or a denied permission. `time.sleep` is replaced, and every write goes to a temporary directory. ## Known limitations

- The stage is irreproducible, because a retrieval is GHS's state at one time. The cache keeps each retrieval
- Because GHS refreshes a repository only on a push, its archived flag, license and stars can be months old. `2_query_github.py` queries GitHub for the current values
- GHS filters `committedMin` on commit dates but crawls by push dates, and a repository pushed recently with an old commit date falls outside the window (GHS issue #813)
- The crawl date of a small language can lag only because nothing recent was pushed in it. The end date then moves back by that lag, and the window moves forward less
- The download counts the languages that the filter would keep over GHS's `mainLanguage` and `license`, without the filter steps that need GitHub's responses. The filter counts GitHub's values after those steps, and a language near the tenth place can rank differently there. When the filter ranks a language that the end date left out among the languages that it keeps, it leaves the language out and keeps the next most common language, and the release names the language among its evidence limits
