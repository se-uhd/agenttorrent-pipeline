# Query GitHub for a retrieval

## Context

`2_query_github.py` is the second script of the sampling stage. For every row of the retrieval that `../data/sampling/ghs_retrieval.json` names, it queries GitHub for the repository as it is now and writes the responses into the cache of retrievals beside GHS's rows (`ghs-cache-spec.md`). The filter then reads GitHub's values where GitHub returned them (`filter-ghs-spec.md`).

GHS cannot supply these values. GHS refreshes a repository only when it crawls a push of that repository. The archived, disabled and locked flags, the license and the stars therefore stay as they were at the last push, and an archived repository is never pushed again. A renamed or transferred repository gets a second row under its new name while the row under the old name stays. The GHS search result of March contains <!--s:release_2026_03.created_at_head_pairs-->54<!--/s--> pairs with equal creation time and HEAD, such as `pagehelper/mybatis-pagehelper` and `pagehelper-org/Mybatis-PageHelper`. GHS's `id` is its own database id (`model/GitRepo.java:52-55`), not GitHub's. GHS also writes every timestamp on a 12-hour clock without AM/PM (`JacksonConfig.java:28`), and all four timestamp fields of the GHS search result of March contain only the hours <!--s:release_2026_03.timestamp_hour_min-->1<!--/s--> to <!--s:release_2026_03.timestamp_hour_max-->12<!--/s-->.

## Key decisions

- **Language:** Python 3.14, in the single script `2_query_github.py`, with `requests` for HTTP, `concurrent.futures` for the requests in flight, `ghs_cache.py` for the cache, `agentcontext.credentials` for the GitHub access tokens and `agentcontext.github_api` for their pool and the reading of a rate limit. The suite stubs `requests` when it is absent
- The query covers every row of the retrieval, so that the filter's cleanup, its duplicates step and its median thresholds all read current values
- The query uses GraphQL with <!--s:parameters.1_sampling.2_query_github.BATCH_SIZE-->50<!--/s--> repositories a request, each under an alias, `r0: repository(owner: $o0, name: $n0)`, with the owner and the name as variables so that no name has to be escaped. GitHub ends a query that runs longer than <!--s:github.graphql_timeout_seconds:words-->ten<!--/s--> seconds with HTTP 502, and the batch size keeps a request within that limit. In a test on 2026-10-05, a request for <!--s:parameters.1_sampling.2_query_github.batch_size_max-->100<!--/s--> repositories looked up by name, the largest batch that `--batch-size` accepts, finished in time with no field but the id and the name, and each further field, such as `isEmpty`, added to its time. With the default branch's HEAD among the fields, every request for <!--s:parameters.1_sampling.2_query_github.batch_size_max-->100<!--/s--> ran out of time, and a request for <!--s:parameters.1_sampling.2_query_github.BATCH_SIZE-->50<!--/s--> finished in time. A request queries `databaseId`, `nameWithOwner`, `description`, `createdAt`, `pushedAt`, `updatedAt`, `isArchived`, `isDisabled`, `isLocked`, `isFork`, `isPrivate`, `isMirror`, `licenseInfo { spdxId name }`, `primaryLanguage { name }`, `stargazerCount` and `defaultBranchRef { name target { oid ... on Commit { committedDate } } }`, none of which is a connection. It also queries `rateLimit { cost remaining resetAt }`, from which the query takes the cost of the run for the index. `flatten` turns the response into one record per repository
- Each repository is `found`, `not_found` or `blocked`. GraphQL reports a missing repository as an error of type `NOT_FOUND` with the alias in its `path`. It reports a repository that GitHub blocks access to, after a DMCA takedown, as `FORBIDDEN` with "Repository access blocked". Any other error gets another attempt
- When GraphQL does not find a repository, the query looks it up once more through REST. `GET /repos/{owner}/{name}` follows the redirect that GitHub keeps for a renamed or transferred repository. The query sends the name that REST returns to GraphQL as it sends any other name, whether it is a new name or the same name, because REST returns only a repository that exists. A response under a new name contains `redirectedTo`. After a 404, a 451 (blocked after a DMCA takedown) or a 403 "Repository access blocked" (blocked for a terms-of-service violation), the row is `not_found` with `restChecked`. A REST response with HTTP 200 that names no repository, such as the HTML page of a proxy, shows nothing about the repository and counts as a failed attempt, as a GraphQL response that is not a JSON object does. A row stays unchecked when its REST request fails or when GraphQL does not find the repository that REST returned, and a later round checks it again
- The query sends the rows that the first pass leaves without a response or without a REST check again in further rounds, after each of the waits of `ROUND_WAITS`, which grow from minutes to hours. GitHub's errors and an outage of the network come in spells. Within one pass, a repository gets only the attempts below, and without the rounds, a spell that outlasts them would end the run. A row is **unresolved** when no round settles it: GitHub returned no response for it in any round, or GraphQL did not find it and no REST check showed whether GitHub has it. When the unresolved rows are at most `UNRESOLVED_MAX_SHARE` of the retrieval's rows, rounded up, or a single row in a retrieval too small for the share to allow one, the query records each of them with the status `unresolved`, logs a warning and exits 0. The stages after it then run, and the filter removes these rows as unresolved (`filter-ghs-spec.md`). Above that share, the query exits 1 and keeps the responses in the partial file, and the next run queries the rest. A later run does not query a retrieval with unresolved rows again, because the retrieval has its responses
- A pass ends early when `NO_RESPONSE_BATCHES` batches or REST checks in a row get no response for any repository, which is three for each of the default `WORKERS`. The rows that the pass has not queried wait for the next round. Without the early end, a failure that every request meets, such as a refused connection, HTTP 503 or a field that GitHub removed from the schema, would spend the attempts and waits of every batch of the retrieval in every pass. The query would then hold the run lock for months before it reached the last round. A spell in which every worker gets no response for about three batches ends the pass, and a shorter spell does not. Before a worker sends a request, it checks whether the pass has ended, so that the other workers stop too
- A failure while the responses are recorded, such as Ctrl+C or a full disk, ends the pass as well, and `pass_pool` cancels the batches and REST checks that have not started. A batch or a REST check that waits for a paused account ends its wait and sends nothing (`TokenPool.take` with the pass's `ended`). If they were sent, nothing would record their responses, and the next run would send them again
- `QUERY_SECONDS` after its start, a run sends no further request, starts no further round and makes no further check of the GitHub access tokens. A failure that leaves some responses in every pass, such as one in which half of the batches fail, ends no pass early, and the time limit ends the query instead. The limit is well beyond a first pass and the waits of `ROUND_WAITS` together, and it therefore ends only a query that GitHub keeps failing. The query then handles the rows that are left as after the last round. It records them as unresolved within the share, or leaves them to the next run, which resumes from the partial file
- The query handles a failure by its cause, and every failure is bounded. It attempts a request <!--s:parameters.1_sampling.2_query_github.ATTEMPTS:words-->four<!--/s--> times, waiting <!--s:parameters.1_sampling.2_query_github.WAITS.0-->10<!--/s-->, <!--s:parameters.1_sampling.2_query_github.WAITS.1-->30<!--/s--> and <!--s:parameters.1_sampling.2_query_github.WAITS.2-->60<!--/s--> seconds. It splits a batch in half, down to single repositories, when GitHub ended the batch because the query took too long: with HTTP 502 or 504, or with HTTP 200, no data for any repository and an error of the whole query that names a timeout (`timed_out`). A repository that GitHub cannot return in time then leaves only itself without a response. The query sends the repositories that came back with an error in a batch again in a batch of their own. A batch that fails in any other way through its attempts, such as one in which every repository came back with an error, waits for the next round without a split. When a failure meets every request, each part of a split batch would spend the attempts and waits again, down to single repositories, and one batch would take hours
- A 403 or 429 is a rate limit only when GitHub marks it as one, with `Retry-After`, with `X-RateLimit-Remaining: 0` or with "rate limit" in the message (`rate_limit_wait`). Any other 403 is a failed attempt. Read as a rate limit, the 403 of a repository blocked for its terms would pause the GitHub access token for good. A secondary rate limit applies to the account behind a GitHub access token. The query therefore pauses every GitHub access token of that account for `Retry-After` or <!--s:parameters.agentcontext.github_api.rate_limit_default_wait_seconds-->60<!--/s--> seconds, with a single warning that names the account, and the GitHub access tokens of the other accounts continue. With every account paused, the run waits for the first pause to end. If each request waited out the limit on its own, the other requests in flight would get the limit as well
- A rate limit, an exhausted rate limit and a rejected GitHub access token do not count as a failed attempt, up to `MAX_PAUSES` (<!--s:parameters.agentcontext.github_api.MAX_PAUSES-->30<!--/s-->) pauses of one request. A limit that does not end has another cause, and each pause beyond `MAX_PAUSES` counts as a failed attempt. GraphQL reports an exhausted hourly rate limit with HTTP 200 and an error of type `RATE_LIMITED`. The query then sets the GitHub access tokens of that account aside until `X-RateLimit-Reset` and sends the request with a GitHub access token of another account
- When a GraphQL request or a REST lookup returns HTTP 401, the query checks the GitHub access token again against `/rate_limit` (`Query.rejected`). It drops the GitHub access token only when the check returns HTTP 401 as well, because one response is not enough to drop a GitHub access token for the rest of the run. When the check does not return HTTP 401, the request counts as a failed attempt. When GitHub rejects every GitHub access token, in the check before the first request or later in the run, the query checks them all again after each of the waits of `ROUND_WAITS` and continues with the GitHub access tokens that GitHub accepts. It exits 1 when GitHub accepts none after the last wait. GitHub can reject valid GitHub access tokens for a while, and a run that ended on a rejection at its start would leave the stages after it idle until the next Start. A spell of such rejections after GitHub has served a request starts the waits from the first again. The rejections come in spells, as GitHub's errors do, and several short spells would otherwise use up the waits of one long spell between them and end the query with exit 1. The time limit of the run bounds all spells together, because the query makes no check after it
- The GitHub access tokens come from `GITHUB_TOKENS`, comma-separated, from `GITHUB_TOKEN` and from `credentials.csv` at the repository root, in that order without repeats (`docs/credentials.md`). `--credentials` names another file. Before the first request, the query checks each GitHub access token against `/rate_limit`, leaves out each GitHub access token that the check rejects, and rotates the requests through the others. The check rejects a GitHub access token only on HTTP 401. The query makes a check that fails on the network, or that returns HTTP 5xx or a rate limit, again after each of the waits of `CHECK_WAITS`. It keeps a GitHub access token that no check reaches, because such a failure shows nothing about the GitHub access token. GitHub's hourly GraphQL rate limit of <!--s:github.graphql_hourly_points-->5,000<!--/s--> points applies to the account, and the pool therefore tracks it per account, with <!--s:parameters.agentcontext.github_api.RESERVE-->50<!--/s--> points in reserve. When every account has reached its rate limit, the run waits for the earliest reset. GitHub access tokens from the environment have no account, and each counts as an account of its own
- The query saves the requests and the cost so far in the index every <!--s:parameters.agentcontext.logs.PROGRESS_SECONDS.minutes:words-->ten<!--/s--> minutes and when the run fails. A stopped run therefore keeps its requests and cost, and the next run adds to them
- A stopped run resumes. The query appends every batch of responses to `<id>.github.partial.jsonl` in the cache with the position of each row, and the next run queries only the rest. It queries again the rows of a last line that a stop cut short, and a response without a field that the query requests. When every row has a response and a check, the query writes the responses as `<id>.github.jsonl.xz` in GHS's order, writes the counts, the requests and the GraphQL points spent into the index, and removes the partial file. A run stopped between writing the responses and writing their SHA-256 into the index leaves responses that the index does not list. The next run queries GitHub again and keeps the responses in the partial file rather than stopping on the failed checksum. Before a run reads the partial file, it truncates the file to its last whole line. A line that a stop cut inside a character of UTF-8 would otherwise fail on the bytes that cannot be decoded, in that run and in every run after it. A response appended to a line cut short would make one line that does not parse, and every response after it would be requested again
- The query skips a retrieval that already has GitHub's responses, and a second run of the step over the same retrieval sends nothing. Responses without a field that the query requests, such as the description in the responses of 2026-10-05, do not count, and the step queries GitHub again. The filter therefore never writes a sampling frame without the field

## Script: `2_query_github.py`

### CLI interface

```
python3 2_query_github.py [OPTIONS]
```

| Flag | Default | Description |
|------|---------|-------------|
| `--cache-dir` | `../data/sampling/ghs_retrievals/` | The cache of retrievals |
| `--pointer` | `../data/sampling/ghs_retrieval.json` | The file that names the retrieval |
| `--batch-size` | <!--s:parameters.1_sampling.2_query_github.BATCH_SIZE-->50<!--/s--> | Repositories per GraphQL request, <!--s:parameters.1_sampling.2_query_github.batch_size_min-->1<!--/s--> to <!--s:parameters.1_sampling.2_query_github.batch_size_max-->100<!--/s--> |
| `--workers` | <!--s:parameters.1_sampling.2_query_github.WORKERS-->4<!--/s--> | Concurrent requests |
| `--credentials` | `credentials.csv` at the repository root, or `AGENTCONTEXT_CREDENTIALS` | The credentials file with the GitHub access tokens that the query uses after the environment's |

### Function structure

**`flatten(repository)`**, **`batch_query(names)`**, **`classify(names, body)`**, **`timed_out(body)`**: the request and its response, and whether GitHub ended the query for its time limit in a response with HTTP 200. The pool of GitHub access tokens, `TokenPool`, and the reading of a response, `rate_limit_wait`, `blocked` and `rate_limited`, are imported from `agentcontext.github_api`

**`post(token, document, variables)`**, **`rest_name(token, name)`**: one GraphQL request and one REST lookup, with their failures sorted into `Transient`, `PermissionError` (HTTP 401) and the rest. A GraphQL response with `data` that is not a JSON object is `Transient`. `post` returns `errors` as a list of objects and turns each entry that is not an object, such as a proxy's text, into the message of one. GraphQL's specification defines `errors` as a list of objects, and every reader of the errors expects objects. Read as an object, such an entry would raise `AttributeError` in a worker, and every run that resumes the query would exit 1 at the same batch

**`check_token(value)`**, **`accepted_tokens(tokens, sleep)`**, **`paused(tokens, token)`**: the check of one GitHub access token against `/rate_limit` with its verdict, the GitHub access tokens that GitHub does not reject, and what a pause sets aside, written as the start of a sentence of a log message

**`Query`**: one run, with `fetch(names)` for the retries and the split, `resolve(name)`, `rejected(token)` for the check after an HTTP 401, `record(rows)` to the partial file, and `begin_pass()`, `responded()`, `failed(last)` and `over()` for the early end of a pass and the time limit of the run

**`read_partial(path)`**, **`end_partial(path)`**, **`query_rows(...)`**, **`resolve_renames(...)`**, **`unsettled(count, received)`**, **`unresolved_allowed(count)`**, **`unresolved(position, name, received)`**, **`settle(...)`**, **`run(...)`**, **`main(argv)`**: a run, with the first pass and the further rounds in `settle`

### Output

`../data/sampling/ghs_retrievals/<id>.github.jsonl.xz`, one line per GHS row in GHS's order: `ghsName`, `status` (`found`, `not_found`, `blocked`, `unresolved`), `repository` for a found repository with `id`, `name`, `description`, `createdAt`, `pushedAt`, `updatedAt`, `isArchived`, `isDisabled`, `isLocked`, `isFork`, `isPrivate`, `isMirror`, `license`, `licenseSpdxId`, `primaryLanguage`, `stargazers`, `defaultBranch`, `headSha`, `headCommittedAt`; `error` for a repository not found or unresolved; `restChecked` and `redirectedTo` where they apply. The query also writes the `github_` columns of the retrieval's index row. `github_not_found` counts the repositories that GitHub did not find or blocks, and `github_unresolved` counts the unresolved rows, which no response shows to be gone from GitHub.

## Error handling & edge cases

| Scenario | Behavior |
|----------|-----------|
| No pointer, or a cache that cannot be read | `ERROR github_query: The cache of retrievals cannot be used. ...`, exit 1 |
| No GitHub access token in `GITHUB_TOKENS`, `GITHUB_TOKEN` or the credentials file | Exit 1 before any request |
| GitHub returns a repository with a field that it could not resolve: null, with an error that names the field below the repository in its path, as on a timeout of the field or a failure of the storage that it reads | The query queries the repository again in the attempts and the rounds, as it does a repository without a response (`UNRESOLVED_FIELDS`), because a null license or language would remove the repository from the month's sampling frame. After the last round, the query records the latest such response with the field empty and logs a `WARNING` (`Query.take_incomplete`), and the row does not count as unresolved. A field that GitHub fails for one repository every time therefore cannot end every run. The query does not write such a response to the partial file, and a run that then exits 1 leaves the repository to the next run. The same holds for a repository that GraphQL did not find under its GHS name, that REST checked, and that GraphQL returned with such a field under the name that REST returned (`Query.returned`). The query does not record a response without the repository's name (`NAME_FIELD`), and the row counts as unresolved, because the filter and the stages after it identify a repository by GitHub's name, which the filter reads from every row. Attempts in which GitHub returned only such responses do not count toward the early end of a pass |
| GitHub rejects every GitHub access token (HTTP 401) before the first request | Every GitHub access token is checked again after each of `ROUND_WAITS`, and the query exits 1 when none is accepted after the last |
| The check of a GitHub access token fails on the network, or returns HTTP 5xx or a rate limit | Checked again after each of `CHECK_WAITS`, then kept with a warning |
| A request returns HTTP 401 | The GitHub access token is checked against `/rate_limit` and dropped only when the check returns HTTP 401 too. With none left, every GitHub access token is checked again after each of `ROUND_WAITS`, and the query exits 1 when none is accepted after the last |
| GitHub rejects every GitHub access token again after it has served a request | A new spell: the waits of `ROUND_WAITS` start again from the first |
| The partial file ends in a line that a stop cut short, also inside a character of UTF-8 | The line is removed before the file is read, and its row is queried again |
| A batch takes too long: HTTP 502 or 504, or HTTP 200 with no repository and a timeout error of the whole query | Split in half, down to single repositories, so that a repository that GitHub cannot return in time stays unresolved alone |
| A batch fails in another way, such as a refused connection, HTTP 503 or an error for every repository | Attempted <!--s:parameters.1_sampling.2_query_github.ATTEMPTS:words-->four<!--/s--> times without a split, then left to the next round |
| A REST check returns HTTP 200 with a body that names no repository | A failed attempt, and after the attempts the next round checks the row again |
| A rate limit | Waited out, or the request is sent with another GitHub access token |
| A repository without a response after <!--s:parameters.1_sampling.2_query_github.ATTEMPTS:words-->four<!--/s--> attempts, or a `not_found` row without a REST check | Queried again in the next round, after the next wait of `ROUND_WAITS` |
| `NO_RESPONSE_BATCHES` batches or REST checks in a row without a response | A `WARNING` with the last error, the pass ends, and the next round queries its other rows |
| The run reaches `QUERY_SECONDS` from its start, or the next round or check of the GitHub access tokens would start after it | No further request, round or check, a `WARNING`, and the rows left are handled as after the last round |
| Rows still without a response or a REST check after the last round, at most `UNRESOLVED_MAX_SHARE` of the rows, rounded up, or one row | Recorded as `unresolved`, a `WARNING` that names their number, exit 0 |
| More rows than that still without a response or a REST check after the last round | The responses so far stay in the partial file, exit 1, and the next run queries the rest |
| The retrieval already has GitHub's responses | Nothing is sent, exit 0 |

## Verification

1. After a run, the retrieval's index row has `github_rows` equal to `item_count`, and `github_found`, `github_not_found` and `github_unresolved` add up to it
2. `github_cost` is about <!--s:retrieval_2026_10_05.github_points_per_request:words-->one<!--/s--> GraphQL point per request, the least that GitHub charges for a call, and a rate limit that the run waited for is a `WARNING github_query:` line of the log
3. Each further round, a pass that ended early, the time limit and the unresolved rows are `WARNING github_query:` lines of the log, and the filter's step `gone` records the number of unresolved rows in `values.unresolved`

## Known limitations

- GitHub's responses describe the repository when the query ran, up to a few hours after the download of the GHS search result. The counts that only GHS has, the commits, contributors, issues, pull requests and watchers, are GHS's
- GitHub reports a private repository as not found to a GitHub access token without access to it
- When GitHub rejects every GitHub access token, the responses of the requests that finish in the same pass are not recorded, and the next pass requests them again. The repeated requests cost requests and GraphQL points, but no row is lost, because a row without a recorded response stays unsettled
