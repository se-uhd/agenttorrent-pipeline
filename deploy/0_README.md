# The pipeline as a container

This directory contains the files that you need to run the pipeline's five stages unattended on a machine with Docker and on the Synology that the authors' mining project `jaws26-loop-engineering` deploys to, arranged as that project arranges its deployment. The image contains the code, and a project folder on the host contains the run's files. A change to the code therefore takes effect on the machine only through a new image. You import the image, create the project from `compose.yaml` and start the container, as the section [Import, create, start](../docs/deploy.md#import-create-start) of the runbook `../docs/deploy.md` describes.

| File | What it is |
|---|---|
| `Dockerfile` | The image: the base image `python:<release>-slim` of the release of Python that `mise.toml` pins, named by digest, with the git, rsync and 7zz that `mise.toml` pins, the Python distributions of the dependency lock `locks/pipeline.txt`, which pip installs in hash-checking mode, and the tracked code that the stages run from at `/opt/pipeline` |
| `install_tools.sh` | Fails when the interpreter of the base image is not the release of Python that `mise.toml` pins, then installs the git, the rsync and the 7-Zip that `mise.toml` pins into the image and the development image with mise, and links `git`, `rsync` and `7zz` into `/usr/local/bin` |
| `entrypoint.py` | The first process in the container. It checks the mounts and the revisions of `compose.yaml` and of the data root, records the machine, runs `run_pipeline.py` over the data root and packs the handover when the run ends. The section [The entrypoint](../docs/deploy.md#the-entrypoint) of the runbook explains its design |
| `compose.yaml` | The Container Manager project: the image, the container's name, which the scheduled tasks start whatever the project's name, `credentials.csv`, the data root and `handover/` mounted, the NAS's `/etc/localtime` mounted read-only at `/etc/host-localtime`, the stop grace period, and its revision in `AGENTCONTEXT_COMPOSE_REVISION`, which the entrypoint compares with the revision that it requires ([Mounts](#mounts)) |
| `credentials.csv.example` | An example of the `credentials.csv` that you write beside `compose.yaml`, one GitHub access token or OpenRouter API key per row under `service,account,credential`, mounted read-only. The entrypoint passes its path to the run, and in its pre-checks, the runner selects the first GitHub access token that passes validation as `GITHUB_TOKEN`. Your copy is gitignored |
| `build_image.sh` | Builds the image from the tracked files, for the NAS as a tarball that DSM imports with its tag, or for this machine with `--local` |
| `make_nas_bundle.sh` | Builds the zip from which you create the project folder: `compose.yaml`, `credentials.csv.example`, the runbook, and the data root and `handover/`, both empty |
| `../docs/deploy.md` | The runbook, copied into the bundle as `deploy.md` |
| `test_container.py` | The suite, which CI runs in the workflow step `Run container suite` of `pipeline-tests.yml` |

## Development container

`Dockerfile.development` supplies the Python distributions of the dependency lock
`locks/development.txt`, which a development machine installs into its `.venv`, and the
development tools, on the base image of the production image. `build_development_image.sh`
builds it for Linux x86-64, or for arm64 with the argument `arm64`. The source code, input data and results are mounted at
runtime. [The development workflow](../docs/development.md#linux-x86-64-development-container)
gives the commands for selected tests, complete verification and the pipeline.

## Mounts

The data root is the volume. Every stage derives the default path of each file that it reads and writes from the data root, which the entrypoint sets in `AGENTCONTEXT_DATA_ROOT` and starts the runner in. `os.replace` rewrites the caches. A rename over a file bind mount fails, and a rename over a symlink replaces the symlink with a file in the container's own layer, which the next start does not see. The host's `data/` is therefore mounted whole at `/app/data`, the path that the repository gives it, so that a path in a log names the same file on the host. A run reads the code and the heuristics from the image. The volume contains no code, and editing it changes nothing that a run does. The bundle contains an empty data root, and at the first start, the runner fills it, from the download of the GHS retrieval to the figures. The section [Key decisions](../docs/deploy.md#key-decisions) of the runbook lists the alternatives, which were checked against the code.

After the runner exits, the entrypoint packs the run's archive into the second mount, `handover/`. After a completed run, the archive contains the data root without the clones in progress, under its repository path, and `7zz x -snld` over a checkout therefore puts every file where the repository keeps it ([development](../docs/development.md#handover-working-copy)). After a Stop, a failed step or a killed runner, the archive contains the pipeline execution state and logs and the data of the sampling, classification and analysis stages. Of the collection, it contains `finished_repositories.jsonl` with the records of the collection in progress and of the last collection that ended, the collected and validated lists, the caches, the output CSVs, `deletion.csv`, `data/workflows/` and `data/imported/`. The collected and validated trees go into a second archive when the handover volume has room for them and no archive in `handover/` contains them unchanged. When a Stop reaches a completed run before the packing, the entrypoint packs the first of these archives without the second, because 7zz over the whole data root can take longer than the stop grace period, and it packs the data root at the next start. No archive contains a directory named `@eaDir`, which DSM writes and changes at any time. After a start that the runner refused before any step ran, the entrypoint writes no archive. At every start that passes its checks, it also writes `run_logs/machine.json` under the data root, which contains the processor, the container's CPU quota, the memory, the volume and the image. The archive contains that file.

The NAS's `/etc/localtime` is mounted read-only at `/etc/host-localtime`. DSM's Task Scheduler starts the container at a time of the NAS's zone, and the entrypoint reads that zone from the file when it decides, by the calendar month, whether to begin the next monthly run at a Start. The entrypoint logs the zone at each start. The container's own local time stays UTC. A mount at `/etc/localtime` would replace the zone file of UTC that the image's `/etc/localtime` links to, and the commit times that the cloning step writes in UTC would then be the NAS's local time. The entrypoint runs no step when `TZ`, `/etc/localtime` or the zone file of UTC gives an offset other than zero, and `TZ=UTC` passes. The section [A run every month](../docs/deploy.md#a-run-every-month) of the runbook gives the details.

Container Manager keeps the `compose.yaml` from which you created the project when you import a new image and build the project again. A new image can then run under the `compose.yaml` of an earlier bundle. `compose.yaml` therefore sets `AGENTCONTEXT_COMPOSE_REVISION`, which is <!--s:parameters.deploy.entrypoint.COMPOSE_REVISION-->3<!--/s--> for the current file. Under any other value, or without the variable, the entrypoint runs no step and logs one ERROR line that names the file to copy from the bundle. Whenever you change `compose.yaml` in a way that the entrypoint or the scheduled tasks depend on, such as a mount, an environment variable, the stop grace period or the container's name, raise `AGENTCONTEXT_COMPOSE_REVISION` in `compose.yaml` and `COMPOSE_REVISION` in `entrypoint.py` by one in the same commit. `test_container.py` fails when the two differ. A change to a comment or to `command:` needs no new revision.

The data root has a revision too, the revision of the formats in which the image stores its files there: the pipeline execution state, the caches, such as the cache of GHS retrievals, and the records of the steps and of the entrypoint. At the first start over a data root without a pipeline execution state, the entrypoint writes `run_logs/data_root.json` with the revision of the image, <!--s:parameters.deploy.entrypoint.DATA_ROOT_REVISION-->3<!--/s--> for the current `DATA_ROOT_REVISION` in `entrypoint.py`. A start over a data root of an earlier revision converts its stored files to the image's revision before any step runs, where `CONVERSIONS` in `entrypoint.py` has a conversion from each revision in between. The conversion from revision 1 renames the count and the limit of the linked pages in the decisions of the cache of labels from `pages` to `linked_pages`, and the outcome `preflight_failed` of the pipeline execution state to `pre_checks_failed`. The conversion from revision 2 names the digest of each input of a recorded cloning step in the pipeline execution state, and of a cloning step that exited 0 before the runner recorded it (`exited`), and writes `finished_repositories.ended-collection.json`, the record of the collection that the step ended, both rebuilt from `collected_under` and `collection` in the lines of `finished_repositories.jsonl` and from the sample, and only where their hash is the inputs part of the record of the step (`convert_cloning_records`). It writes that record also for a cloning step that closed its collection before the runner wrote `exited`, which the pipeline execution state still names as `running_step`, where every repository in the sample has a line, the latest collection wrote lines only for repositories in the sample, and that collection wrote one during the start that `running_step_started_at` names, by the time at which it began or by the `scanned_at` of a row. The record lists the repositories in the sample that the collection took over from an earlier collection: those with a latest line that names an earlier collection and records neither `head_no_response` nor a clone that the size bound or the time bound stopped. The conversion writes each converted file beside its original, replaces the originals once every converted file is written, and records the new revision last, so that a start after a kill finishes it ([The entrypoint](../docs/deploy.md#the-entrypoint)). The record then names the image that converted the data root, with the revision and the image that it converted from. A conversion rewrites the stored files once, and the code reads only the current formats. Over a data root of any other revision, or over a pipeline execution state without the record, the entrypoint runs no step and logs one ERROR line before it removes, packs or writes anything. The line names a clean run in an empty project folder as the remedy ([A clean run](../docs/deploy.md#a-clean-run)), and over a record of another revision also the image in the record, or another image of that revision, as the import that resumes the run. The first log line of every start names the image's revision after its build record, and `build_image.sh` writes it into `BUILD_INFO.txt` as `data_root_revision`, so that you can tell before an import whether the runner of an image resumes the run in a project folder. Raise `DATA_ROOT_REVISION` by one in every commit that changes a stored format, such as the columns of a cache, the keys of the pipeline execution state or the layout of a step's records. Where the files of the earlier revision have a known conversion, such as a renamed key, add it to `CONVERSIONS` in the same commit, with a test in `test_container.py` that converts a data root of the earlier revision, so that the next image continues the run. Without a conversion, the entrypoint of a new image refuses the data root of an earlier image, instead of a step stopping with an error that names a column. A change that leaves every stored file readable needs no new revision.

## Building

```bash
bash deploy/build_image.sh              # linux/amd64 for the NAS: agentcontext-pipeline.tar.gz and BUILD_INFO.txt here
bash deploy/build_image.sh --local      # this machine's platform, loaded into the local Docker, for a container on this machine
bash deploy/make_nas_bundle.sh          # agentcontext-nas-bundle.zip here
```

The build context is what git lists under `TRACKED` in `build_image.sh`, not the working directory: `mise.toml`, which pins the interpreter, git, rsync and 7-Zip, `pyproject.toml`, `run_pipeline.py`, the package, `heuristics/`, the entrypoint, `deploy/install_tools.sh`, which installs the pinned git, rsync and 7-Zip into the image, `locks/build.txt` and `locks/pipeline.txt`, the dependency locks that the image installs, and the code directories of the other stages, minus the test modules, the fixture of the analysis suites and `2_classification/config/parameter_digests.csv`, which only a test reads. The image contains no data. `BUILD_INFO` contains the commit, with `-dirty` when a tracked file differed from it, and the entrypoint logs it as the container's first line with the data root revision. `BUILD_INFO.txt` beside the tarball also contains that revision, which the script reads from `DATA_ROOT_REVISION` in the entrypoint of the build context. A build fails before Docker runs when its entrypoint does not set that revision to an integer exactly once. After either build, the script runs the image once with the zone file of Europe/Berlin from this machine's zone database mounted where `compose.yaml` mounts the NAS's zone file. The script fails unless `date` under `TZ=UTC` prints `+0000`, a commit made at 12:00 UTC reads as 12:00 in the cloning step's format, the entrypoint reads Berlin, and the entrypoint's check of the container's own zone passes. The tarball build writes `agentcontext-pipeline.tar.gz` and `BUILD_INFO.txt` only after the tag check and the zone check pass, and it first removes the files of an earlier build, so that a failed build leaves neither file. Both Dockerfiles name their base image by the digest of the release that `mise.toml` pins, because Docker Hub moves a tag such as `python:3.14-slim` to every new build, and `test_tech_stack.py` fails a Dockerfile whose tag names another release than `mise.toml`. Docker pulls the digest without reading the tag, so `install_tools.sh` fails the build of either image when the interpreter of the base image is not the release that `mise.toml` pins. `BUILD_INFO.txt` and the image's `BUILD_INFO` name the release that the interpreter of the image reports. The `container image` workflow runs the same two scripts on a GitHub-hosted runner, where the NAS platform is native, and uploads the tarball and the bundle as workflow artifacts. The tarball that the NAS imports comes from there.

## The subsample run over the local mirrors

Because the container runs every stage, a run of the image needs the network for GHS and GitHub and an OpenRouter API key for the classification's default model. To run the collection stage over the subsample's mirrors instead, with no GitHub access token and every clone redirected to `file://`, run `python -m agentcontext mirror-run` in a checkout ([docs/tools/mirror_run.md](../docs/tools/mirror_run.md)).

## Tests

Prepare the test environment with the [macOS, Linux or container development workflow](../docs/development.md).
These hosts are for development, and deployment to the NAS follows `../docs/deploy.md`.

```bash
cd deploy && python3 -m unittest test_container -v
```

The suite uses the standard library only and needs git, tar, shasum, 7zz, zip and unzip on PATH. It skips the handover tests without 7zz, the bundle tests without zip and unzip, and the build script tests without git and shasum. Nothing here builds an image.
