# Run the data collection pipeline end to end

## Context

This runner runs the <!--s:parameters.agentcontext.runner.CORE_STEPS:words-->twelve<!--/s--> core steps in order as one command. With `--with-commit-reclassification`, it also runs the `commit_reclassification` step right after repository cloning, and the <!--s:parameters.agentcontext.runner.COMMIT_RECLASSIFICATION_STEPS:words-->two<!--/s--> checks over the commit CSVs of the cloning step. `commit_reclassification` applies the current commit heuristics to the commit logs that the cloning step kept. The other four runners are lists of steps that run through this runner: `1_sampling/run_sampling.py`, `2_classification/run_classification.py`, `4_data-analysis/run_analysis.py` and `run_pipeline.py` at the repository root. Each uses the `Step` dataclass, the pre-checks, the pipeline execution state and the loop that this module defines, with its own `run_logs/`. The runner handles step order, stops on failure, and resumes after interruptions, avoiding a full restart of a collection that can take days. The file history step uses its cache and clones only to repair missing history.

The runner orders the steps, selects their interpreters, checks the declared prerequisites and outputs, and records completion fingerprints. It does not interpret configuration or commit heuristics. It records a step as complete in `run_logs/state.json` only when the step exits 0 and has written its declared outputs.

A later invocation skips a recorded step while its completion fingerprint still matches. An
`flock` on `run_logs/run.lock` prevents concurrent invocations. Before the first pending step
starts, the pre-checks verify the prerequisites of the pending steps and of the steps that an
earlier step of the run can make pending. A missing `7zz`, for example, is reported before the
collection begins.

## Key decisions

Progress messages name the steps with the noun phrases of `logs.step_name`, such as Repository
cloning, Collected file cleanup, Detection and Release. Step keys identify the steps in `--from`,
`--step-arg` and the completion fingerprints. Step identifiers and command names use the nouns that
the glossary defines, and old commands, module paths and completion keys have no aliases or
migrations. The runner records outcomes in its logs and its state file and sends no push
notifications.

The pre-checks try the distinct configured GitHub access tokens in order until one passes
validation, and they set that GitHub access token as `GITHUB_TOKEN` for repository cloning and the
file history step. They log the position of each GitHub access token that failed validation and of
the GitHub access token that these steps will use. The GitHub access token is selected at startup,
and repository cloning does not rotate GitHub access tokens during an active step. API commands
such as `snapshot validation` and `measure sizes` rotate through their own pools of GitHub access
tokens because of GitHub's rate limits.

- **Language:** Python 3.14 (a single script, `agentcontext/runner.py`), with no dependencies outside the standard library
- **Steps declare their requirements and outputs:** The runner checks those declarations and the completion fingerprints without interpreting what the step does with the data. Exit `0` alone does not establish completion
- **Long options by their full names only:** Every runner's parser is `cli.ArgumentParser`, which refuses an abbreviation, such as `--fro release` or `--step repository_cloning:--fresh`, with a usage error and exit `1`. The steps' parsers do the same. By default, argparse accepts an abbreviation of a long option as the option. The container's entrypoint recognizes the arguments for one Start in `command:` by their full names, and it passes an argument that it does not recognize at every Start. A `--fro release` that the runner took for `--from release` would then run the release again at every Start ([deployment](deploy.md#deployment-options))
- **Step arguments:** Steps use their defaults unless the step list supplies an input path or a reporting policy. `commit_attribution_validation` reads `output/all_ai_commits.csv` and `output/other_ai_commits.csv`. `unmatched_paths_report` and `deleted_files_report` log their findings without stopping the unattended run
- **Five stages of steps.** The pipeline has five stages: sampling, classification, collection, publication and analysis. Each stage is a sequence of steps, the `Step` objects of this module. The pipeline execution state records each step, and a run resumes at a step, because a collection stopped after days has to resume at its own step, from `finished_repositories.jsonl`. The runner adopts a GHS download that is already on disk instead of taking it again. A step names its stage in `stage`. `--list` shows the steps under their stage, and `--from` takes a stage to mean all of its steps and whatever is computed from them. The scripts stay separate, and only the list groups them
- **Resume from completion fingerprints:** Depending on the step's completion policy, the fingerprint covers its code, its code and its inputs, or its output. `repository_cloning` is recorded by its output, because its result is a snapshot that cloning again cannot reproduce. `--from` runs steps again explicitly, and `--mark-complete` records verified output obtained separately. All five runners validate these flags through `run`. The four that take `--mark-complete` refuse it together with `--repo-csv` or `--step-arg` through `refuses_mark_complete`. They do so before they fold those two flags into the steps, where `run` can no longer detect them
- **A new image keeps the labels and the collection:** A labeling that the runner runs again after a change to the code of the classification completes its finished run without a README request when the current rules derive each decision unchanged, unless the run left repositories without a decision and no collection over its sample has begun. The cloning step continues its collection over a sample that lacks only repositories that GitHub no longer serves. After the cloning step has exited 0, a change of the collector's code, the path heuristics or the import heuristics runs the step, which continues the collection that ended and collects again the repositories that the change reaches, or begins a new collection where no collection over the list is in progress or ended, as after `--mark-complete`. Another version of git alone keeps the step recorded, with a `WARNING` that names the change (`kept_on`), because the step would collect every repository again. A new run of the labeling and a new collection would otherwise follow any fix to the classification or the collector, and the new collection would clone again every repository with a head that moved. `--from repository_cloning` takes a new snapshot ([a new image during or after the collection](#a-new-image-during-or-after-the-collection))
- **One state file, written atomically and durably:** The completions and the run's provenance are stored in `run_logs/state.json`. The runner writes the file to a temporary name, syncs it to the disk and renames it, and it syncs the directory after the rename (`caches.replace_file`). Two files, such as completion markers beside a provenance manifest, could disagree after a kill between the two writes. A rename alone is atomic but not durable. After a power loss, a rename that reached the disk before the data would leave an empty or truncated `state.json`, and every later start would stop at `read_state`
- **A step's completion is recorded with the hash of the script that produced it:** A resume can then check whether the code behind a result is still the code on disk. A changed script invalidates the completion of its own step and of everything computed from it. The fingerprint is per step, so that an edit to the detection script does not force the cloning step to clone the sample again, as one hash over the whole pipeline would
- **The hash covers the code that runs, not the bytes of the file:** `code_digest` hashes the syntax trees of the code without docstrings and log statements, through `fingerprints.code_fingerprint`, in the way that the cloning step records the collector. For a step that runs a module of the package, the code is the module's closure. For a step that runs a script, it is the script, and where the step sets `package_code`, as the analysis steps do, also the package modules that the script and its code inputs import (`fingerprints.imports_closure`). The sampling and the classification steps do not set it, and an edit to a module of the package runs them again only through the code inputs that they name. Comments, docstrings and log messages are left out because no step writes them into its outputs. Every step imports `agentcontext/logs.py`, and with a hash of the bytes, an edit to one of its comments would run every step again, from the collected file cleanup through the archive of the sample to the analysis. A file that is not Python, such as a prompt among the code inputs, or a file that does not parse, is hashed by its bytes, because every edit to it can change what the step does
- **An unreadable state file is a hard stop:** Malformed JSON, an invalid state format or a filesystem read error stops the runner. The runner replaces the file only after its temporary file reached the disk, and an interrupted write or a power loss alone does not establish that the file was truncated. Treating an unreadable state as empty would discard the completion information. In the container, the entrypoint refuses a start over such a state before the runner starts, and it logs how to recover the state from the handover ([deployment](deploy.md#entrypointpy))
- **One run at a time:** `run_logs/run.lock` is an `flock` held for the life of the process, as in `snapshot.py`. The kernel releases the lock of a dead holder (e.g., after a crash, a `kill -9` or a reboot), and there is no stale state to detect. The file names the process and the host that hold the lock and the time since which they hold it, and the runner never reads it to test whether the holder is alive. A pid in the file, checked with `os.kill(pid, 0)`, does not work in a container, where the runner is pid 1 on every start. A hard stop would leave a file that names a process that is always alive, and every restart would refuse to run
- **Pre-checks before any step:** The pre-checks verify up front the binaries, each pending step's module and declared imports under the step's own interpreter, that interpreter's Python minor version against `mise.toml`, the declared environment variables, the `lingua` import for `detection`, the collection input CSV, the GitHub access token and the API key of the service that serves the labeling's model. They check these for the pending steps and for the steps that an earlier step of the run can make pending (`may_become_pending`), and for no other step. They check the free disk space at every start, and against the whole `MIN_FREE_DISK_GB` only when a step that clones is pending or can become pending. When a step in `LABELING_STEPS` is pending or can become pending, and the step's model is an OpenRouter model, the pre-checks read the credit of the first OpenRouter API key through a request that costs nothing. For an OpenAI model that a `--step-arg` names, they send one minimal request to OpenAI's Responses API instead. Without the check, a revoked key would be found only after the sampling stage. A key without credit gives a warning, because the labeling waits for credit. In a monthly run, for example, the labeling becomes pending only after the GHS download and the filter have run again. When a step in `CLONING_STEPS` is pending or can become pending, the pre-checks try the configured GitHub access tokens in order through authenticated `GET /rate_limit` requests. Missing credentials, or credentials that GitHub rejects with HTTP 401, stop the pre-checks before the cloning steps run. A check that returns no verdict, such as a request that cannot reach GitHub or a server error, is repeated after the pauses of `GITHUB_CHECK_WAITS`. When no attempt returns a verdict, the pre-checks keep the GitHub access token, because a short failure of the network would otherwise stop a monthly run before its first step. `--no-github` skips the check for a run with clones that never reach github.com, and such a run must have no GitHub access token. A missing `7zz` must not block a run that never reaches `collected_files_archive`. The `lingua` check gives a warning and no error, because `agentcontext/steps/detection.py` runs without the package and records `n/a` for every language. Failing the run would block an offline regeneration of everything else over a package that the other steps never load. A missing `lingua` costs the language of every row, because the detection step reads the language of every row in every run
- **A stop is forwarded to the step and ends the pipeline:** The runner installs its own handlers for `SIGTERM` and `SIGINT`. A plain `except KeyboardInterrupt` covers only Ctrl+C at a terminal, which the kernel delivers to the whole process group. Under `kill`, a systemd stop or a `docker stop`, nothing would reach the step, and the runner would exit and leave the step orphaned and still cloning
- **A stopped run exits 128 plus the signal's number, not 1:** An interruption is not an ordinary failure. The runner exits `130` for `SIGINT` and `143` for `SIGTERM`
- **A signaled step is never recorded, whatever it returned:** A step that finishes its work in progress on a stop can exit `0` with every path that it declares present. Recording that step would make the next run skip a partial result
- **`engineered_project_selection` runs under bare `python3`:** It uses the stdlib `csv` module and nothing else. The pre-checks import each pending step's module with that step's interpreter. A third-party import added to the module would therefore stop the run before any step starts wherever bare `python3` is not the interpreter that runs the runner, such as when the runner runs as `.venv/bin/python` from a shell in which `.venv` is not active
- **`detection` runs under an interpreter that has `lingua`:** It is the one step with a third-party dependency. The runner starts it with `DATA_COLLECTION_PYTHON` when that is set, and otherwise with the interpreter that runs the runner itself: on a development machine the one of `.venv`, which holds the distributions of `locks/development.txt`, and in the image the interpreter of the base image, which holds those of `locks/pipeline.txt`. The runner looks for no virtual environment at a path of the checkout, because such an environment holds distributions that no dependency lock lists. The runner starts `repository_cloning`, `commit_reclassification` and `file_history` the same way. This choice costs nothing and keeps these four steps on one interpreter
- **Each step runs as a child process of the runner, never in the runner's own process:** The step's interpreter can differ from the runner's. The runner reads the output of the step, and of the programs that the step starts, from a pipe and copies each line to the console and to the step's log. On a stop, the runner signals the step and records it as interrupted. The cloning step and the file history step end on a stop with `os._exit`, which in the runner's own process would end the runner before it records the step
- **Nothing here is specific to the collection stage once a step names its own directories.** `Step.root` names the directory that a step runs in, relative to the data root. Every data path that a step declares resolves against that directory. `Step.code` names the directory of the step's script and its `code_inputs`, relative to the repository root. The runner starts the script by its full path. The code stays in the repository, and what the step writes goes to the data root. `run(steps, ...)` takes any list and the place to keep its pipeline execution state. The other runners import it from the package and pass it their lists. Each keeps its pipeline execution state under its stage's data directory, and `run_pipeline.py` keeps the pipeline execution state of the whole pipeline under the data root
- **Two flags for a snapshot, and a third completion policy for a figure.** With `completion=COMPLETION_OUTPUT`, the runner records a step by what it produced. With `inputs_of`, which `repository_cloning` names, it also records the step by the other inputs that decide it. With `irreproducible=True`, the runner also adopts an output already on disk at the start of a run, unless the pipeline execution state lists the step under `unfinished`. The GHS download sets this flag. `repository_cloning` does not, because a reconstructed sample is recorded on purpose with `--mark-complete`. With `completion=COMPLETION_INPUTS`, the runner records a hash of the script and of the contents of `inputs`. An analysis step then runs again exactly when a CSV that it reads or its own script changed. The runner computes such a step's fingerprint again just before the run would skip the step. For a step recorded by its output and by `inputs_of`, it computes again the part of the record that `inputs_of` gives (`changed_during_run`). A step therefore runs again, with everything computed from it, when an earlier step of the same run rewrote one of its inputs. The GHS download rewrites the pointer that the sampling steps read, for example, and the labeling and the selection rewrite the list of repositories by which `repository_cloning` is recorded. Without the check of `inputs_of`, a new image that changed the labels would run the labeling, the selection and the release, and the release would publish the new labels over the collection of the old sample. Apart from this recomputation, the runner decides the set of completed steps before the run begins. The runner records the steps of this list that read a heuristics file the same way, by the heuristics files that they declare. `collected_file_cleanup`, `detection`, `import_detection`, `output_cross_check`, `unmatched_paths_report`, `deleted_files_report` and `release` declare `config_path_patterns.csv`. `collected_file_cleanup` and `detection` also declare `vendored_dirs.txt`, `planning_document_patterns.csv` and `local_state_paths.csv`. `detection` and `import_detection` also declare `import_patterns.csv`, which decides where Claude Code reads a `.claude/AGENTS.md`. The `inputs_of` of `import_detection` gives a checksum manifest of the imported tree, which no list of paths can name. `release` also declares `ai_commit_patterns.csv`, `other_ai_commit_patterns.csv`, `import_patterns.csv`, `not_imports.csv` and `planning_document_patterns.csv`, which the release contains. The two checks of the AI commits declare `ai_commit_patterns.csv`, and `commit_attribution_validation` also declares `other_ai_commit_patterns.csv`. `commit_reclassification` declares both commit heuristics files and, through `inputs_of`, the `classified_by` digest. `unmatched_paths_report` and `deleted_files_report` declare `not_configuration.csv`, and `unmatched_commits_report` declares `not_ai_commits.csv`. Without these declarations, an image that changed only a heuristic would run nothing again, and the run of a Start with that image would publish the old classification under the new heuristics
- **What a step needs is declared on it.** `binaries`, `imports` and `env` name the executables that the step needs, the packages that its interpreter has to import and the environment variables that it needs. The pre-checks verify them for the pending steps, together with the map `BINARY_REQUIREMENTS`, which names the binaries of the collection's steps. An `env` entry that names alternatives with `|`, such as `GITHUB_TOKENS|GITHUB_TOKEN`, needs one of them set
- **A step can record what its exit code cannot express.** `report` names a JSON object that the step writes. The report of the step's last run stays on disk until the step writes a new one, and a run that fails therefore leaves the report beside the outputs that it describes. A `--mark-complete` of the step or an adoption of its outputs records that report, and the release names it among its inputs. If a run removed the old report first, the release would be recorded without that input and would run again at every Start. The runner reads the report before it records the step, and copies it into the step's entry of `steps` in `state.json`. A step that exits 0 without writing the report that it declares fails in the same way as a step that left an output unwritten. The runner tells a new report from the report of the last run by the signature that the file had before the step. A report that is not a JSON object fails the step too. The GHS download's report states whether it took a retrieval or fell back to the previous retrieval
- **Commit reclassification and checks are opt-in:** `--with-commit-reclassification` adds `commit_reclassification` after repository cloning, and the `commit_attribution_validation` and `unmatched_commits_report` checks as the last steps of the collection, before the publication. The release publishes `output/commit-reclassification.json`, and a run without the flag stops at the release unless an earlier run wrote that file. `commit_attribution_validation` exits 2 when a row of the commit CSV differs from the result of the current heuristics. The run then stops before the archive and the release, because a release must not contain commit rows that the heuristics do not give. `unmatched_paths_report` runs without `--fail-above`, and `deleted_files_report` runs with `--report-only`, because a pattern that no heuristic explains is a reading task, not a defect of the data. `commit_reclassification` exits 0 with `complete: false` in `output/commit-reclassification.json` while the repositories with incomplete evidence stay within what the cloning step accepts. The run then continues to the release, which names those repositories among its evidence limits. The step exits 2, which stops the run, only when these repositories exceed the cloning step's limit ([the commit step](steps/commit_reclassification.md)). Reclassification requires commit logs. Extracted CSVs support the checks of the messages but cannot replace missing evidence of identities and histories
- **The state file is written after every step,** not only at the end. The state of a run in progress records the steps completed so far

## `agentcontext/runner.py`

### Architecture

#### Step list

Every step is a frozen `Step` dataclass with these fields:

- `key`: the step identifier, which is the key in `state.json`, the name of the `.log` file, and what `--from`, `--step-arg` and `--mark-complete` match on
- `interpreter`: the Python to run the step with
- `args`: the argv after the interpreter, which is `-m` and a module of the `agentcontext` package, or a script, followed by its flags
- `produces`: paths relative to the step's `root` that this run must have written by the time the step exits zero, empty for a step that writes no file
- `consumes`: the steps that this step is computed from
- `mutates`: the steps with outputs that this step modifies in place
- `reads`: paths relative to the step's `root` that the step opens and that no step of a plain run necessarily writes, such as the tracked caches. The pre-checks require them to be on disk or produced by a pending step
- `completion`: what a finished run records for the step, `COMPLETION_SCRIPT`, `COMPLETION_OUTPUT` or `COMPLETION_INPUTS`
- `root`: the directory that the step runs in, relative to the data root, empty for the collection stage's directory, `STAGE_DIR`
- `code`: the directory of the step's script and its `code_inputs`, relative to the repository root, empty for a module of the package, or for a script in `root`, as a test's stand-in has
- `irreproducible`: marks a step recorded by its output that is adopted from output on disk rather than run again
- `inputs`: the data files that the `COMPLETION_INPUTS` policy hashes beside the script, relative to `root`. An entry can name alternatives with `|`, and each alternative can be a glob. The hash covers every file that the first alternative on disk matches, and every 7-Zip archive or volume that a later alternative matches (`input_paths`). An archive holds the file that an earlier alternative names, and a reader of that file compares it with the archive that git tracks beside it ([archives](archives.md)). A changed archive therefore runs the step again. Any other later alternative is read only when the first is absent, as `output/repos.csv` makes the entry of `collection_summary` present when no commit reclassification wrote its record. It is not hashed, because it adds nothing that the step reads, and hashing it would change the fingerprint that a finished run recorded for `collection_summary` and run the step and the release again on a new image
- `code_inputs`: the modules and the configuration that the same policy hashes, relative to `code`, as `<code>/<path>`
- `package_code`: whether the fingerprint of a script's code also covers the modules of the package that the script and its `code_inputs` import, set for the analysis scripts and not for the sampling and the classification
- `heuristics`: the files under `heuristics/` that the same policy hashes, as `heuristics/<name>`
- `binaries`, `imports` and `env`: what the pre-checks verify for the step. An `env` entry can name alternatives with `|`
- `extended`: outputs of `produces` that a later step changes in place, which `COMPLETION_OUTPUT` records by their presence
- `may_be_empty`: outputs of `produces` that the step rightly leaves empty, such as the imported tree of a collection in which no import reaches a file
- `inputs_of`: a function of the step that returns the other inputs by which the runner records the step, as pairs of a label and a digest. For a step recorded by its output, these pairs count beside the output, and for a step recorded by its inputs, beside the inputs
- `report`: a JSON object that the step writes, which the runner copies into the step's entry of the pipeline execution state
- `stage`: the stage of the pipeline that the step belongs to, which is sampling, classification, collection, publication or analysis

`detection` reads `file_history.csv` and `ai_authorship.csv`. The step declares them in `reads` and not in `consumes`, because their producer, `repository_cloning`, does not run in a regeneration over an earlier collection, where both files are already on disk. Undeclared, they would be the one input that the pre-checks never verify. `file_history` reads the collected list, `data/collected/repos.csv`, which `repository_cloning` writes too. It keeps the rows of the two caches at the heads that the list contains ([caches](caches.md#the-rows-that-the-two-caches-keep)).

`__post_init__` rejects an unknown `completion`. It also rejects `COMPLETION_OUTPUT` on a step with no `produces`, because such a step would fingerprint to the empty string. The empty string is also the fingerprint of a step with a missing script, and such a step would count as done for as long as the record survived. `Step` is a dataclass, not a tuple, because a tuple has no named place for `produces`, `consumes`, `mutates` and `completion`. `Step` is frozen, so that `apply_step_overrides` cannot write an override back into the module-level lists that every run shares.

`CORE_STEPS` contains <!--s:parameters.agentcontext.runner.CORE_STEPS:words-->twelve<!--/s--> `Step`s in pipeline order: `engineered_project_selection`, `repository_cloning`, `collected_file_cleanup`, `detection`, `file_history`, `import_detection`, `output_cross_check`, `unmatched_paths_report`, `deleted_files_report`, `collection_summary`, `collected_files_archive`, `release`. `engineered_project_selection` comes first because it writes the sample list that the collector reads, so that a run over an empty data root derives that list instead of receiving it. The step is the last step of the classification stage, and `2_classification/run_classification.py` has the same step after the labeling. `run_pipeline.py` takes the step from that list. `COMMIT_RECLASSIFICATION_STEPS` adds `commit_attribution_validation` and `unmatched_commits_report`, the <!--s:parameters.agentcontext.runner.COMMIT_RECLASSIFICATION_STEPS:words-->two<!--/s--> checks over the commit CSVs of the cloning step.

`repository_cloning.produces` names `ai_authorship.csv` beside `file_history.csv`. The history query of each copied path fills both files, and the detection step reads both next. `produces` does not name the commit CSV, `other_ai_commits.csv`, the unmatched attributions, the mentions, `ai_commits-repos.csv` or the shards. The runner records the step by a checksum manifest of what it declares, and the detection step rewrites the commit CSV in place. `--mark-complete` can record `repository_cloning` from outputs restored from a handover, while the evidence of the commit histories is validated separately. The completion record therefore does not show whether the commit histories were read, and `ai_commits-repos.csv` does. [docs/commits.md](commits.md) explains the completion record of the commit histories, and `test_reading_the_commit_history_is_outside_the_collect_manifest` checks both parts.

The runner assembles the list of each run from the core steps. With `--with-commit-reclassification`, it inserts `COMMIT_HEURISTICS_STEP` after `repository_cloning` and `COMMIT_RECLASSIFICATION_STEPS` before the steps of the publication, which keeps the collection's steps together. It then applies the `--repo-csv` and `--step-arg` overrides. `apply_repo_csv(steps, repo_csv, step_key="repository_cloning")` appends `--repo-csv VALUE` to the cloning step through the override path. The pre-checks keep working unchanged, because they read `--repo-csv` back out of that step's argv to check that the file exists. The override reaches `repository_cloning` alone. A run that names another sample list still runs `engineered_project_selection`, which writes the default path that the collector then ignores. That run is still correct, because `engineered_project_selection` writes nothing else. The wasted work is the cost of keeping the override in one place.

#### Declared outputs

In `produces`, each step names the files that the next step reads, not everything that it writes. When a step exits zero without writing them, the runner fails the step as if it had exited non-zero. It records nothing, and the pipeline stops. The runner checks that this run wrote the files, not only that they exist. It reads each declared file's signature before the step starts and again after it exits, and a file that has not changed counts as unwritten. The check finds a step that did nothing and exited 0. Without it, the next step would read whatever the previous run left on disk, and every CSV downstream would mix two passes with nothing to show it.

| `unmatched_commits_report` | `output/unmatched-commits.csv` |

The paths of the mechanism CSVs come from `MECHANISM_OUTPUTS`, which derives them from `heuristics.csv_filenames()` instead of repeating them. `PLANNING_OUTPUT` takes the name of the planning documents' CSV from `planning_schema.CSV_NAME`. `RELEASE_OUTPUTS` is derived the same way from `release.RELEASE_FILES`, which is also what the checksum manifest covers and what the published README describes. `RELEASE_OUTPUTS` drops only the archive of collected files, because `produces` is what the step itself must have written, and `release` checks that file without writing it.

`file_history` rewrites the output CSVs that `detection` wrote and writes no files of its own. The CSVs are there before the step runs, and their presence afterward shows nothing. The declaration is still a complete check, because the check compares each file with its state before the step started, and a rewrite in place changes the file. Every mechanism CSV must be declared. If `detection` declared only `output/repos.csv` and `output/context-files.csv`, a run that exited 0 after writing those two files and none of the other mechanism CSVs would pass without notice. `commit_attribution_validation` names each output after its input, `<stem>-validated.csv`. Its `produces` spells out the names for the two inputs that its command line pins, `output/all_ai_commits.csv` and `output/other_ai_commits.csv`.

#### Dependency graph

`consumes` names the steps that a step is computed from. It is a dependency, not a list position, and the two are different sets:

| Step | `consumes` | `mutates` |
|-------|-----------|-----------|
| `engineered_project_selection` | none | none |
| `repository_cloning` | none | none |
| `commit_reclassification` | `repository_cloning` | none |
| `collected_file_cleanup` | `repository_cloning`, and `commit_reclassification` when enabled | none |
| `detection` | `collected_file_cleanup`, and `commit_reclassification` when enabled | none |
| `file_history` | `detection`, `collected_file_cleanup` | `collected_file_cleanup` |
| `import_detection` | `repository_cloning`, `collected_file_cleanup`, `detection`, `file_history` | none |
| `output_cross_check` | `detection`, `file_history` | none |
| `unmatched_paths_report` | `detection`, `file_history` | none |
| `deleted_files_report` | `detection`, `file_history` | none |
| `collection_summary` | `repository_cloning`, `detection`, `file_history`, `import_detection` | none |
| `collected_files_archive` | `collected_file_cleanup` | none |
| `release` | `detection`, `file_history`, `import_detection`, `output_cross_check`, `unmatched_paths_report`, `deleted_files_report`, `collection_summary`, `collected_files_archive`, and in the whole pipeline also `repository_filtering` and `repository_labeling`, because it declares their sampling frame and labels among its inputs | none |
| `commit_attribution_validation` | `repository_cloning`, `detection` | none |
| `unmatched_commits_report` | `repository_cloning`, `commit_reclassification` | none |

`consumes` names the direct producer of everything that a step reads, not merely the step before it. For example, `file_history` and `collected_files_archive` both open `data/validated/`, which `collected_file_cleanup` produces, and both name `collected_file_cleanup`. `collected_files_archive` has an explicit prune list and reads nothing under `output/`. It does not consume `detection`, and an edit to the detector or the path heuristics does not cause a full copy of the validated tree and a 7z of the sample. `mutates` is a separate relation and never implies `consumes`. `file_history` prunes `data/validated/`, but it does not produce the tree.

`repository_cloning` is the one deliberate omission. It reads the list that `engineered_project_selection` writes and still names no producer. An edge would put `repository_cloning` in `invalidated_by("engineered_project_selection")`. An edit to `agentcontext/steps/engineered_project_selection.py` that writes the same list would then drop `repository_cloning` from the recorded set and run it over a tree that is already exactly what the step wrote. The runner records the step by the list's content instead, as one of its inputs (`collection_inputs`). A new list runs the step, and an unchanged list does not. One test checks that `repository_cloning.consumes` is empty, and another that `invalidated_by(CORE_STEPS, "engineered_project_selection")` does not contain `repository_cloning`.

`invalidated_by(steps, key)` returns `key` plus every step computed from it, transitively, in pipeline order. `--from` uses it instead of a slice by position, which would confuse "runs after" with "depends on". `--from output_cross_check` drops `output_cross_check` and `release`, which consumes it, from the record. `collected_files_archive` runs after `output_cross_check` but reads nothing that `output_cross_check` writes, and running `output_cross_check` again does not run `collected_files_archive` again.

With `--with-commit-reclassification`, `collected_file_cleanup` also depends on `commit_reclassification`. After
the reclassification, the validated tree must be rebuilt before detection, because an earlier
`file_history` run may have pruned it. The cleanup rebuilds the tree from the collected files
already on disk, and the dependency does not invalidate the collection.

#### Steps that modify an earlier step's output

`file_history` is the only step with a non-empty `mutates`. `agentcontext/steps/file_history.py` deletes from `data/validated/` the whole directory of a repository that git reports as gone, with the clone outcome `clone_failed`. A repository with a clone stopped by a timeout, a size bound or a network failure keeps its directory. So does a repository in which every miss was a row that is blank in the cache, which the step only retried. The step does not delete single files without commit history, and it keeps a published row with a file that has no history at the recorded commit. `data/validated/` is `collected_file_cleanup`'s output, and `file_history` never writes it back. Once `file_history` has run, a detection that runs again over `data/validated/` reads a smaller tree than the pipeline specifies and writes a different `output/repos.csv` without a warning. Only `collected_file_cleanup` restores the tree, by deriving `data/validated/` again from the untouched `data/collected/`.

`file_history` also rewrites in place the mechanism CSVs that `detection` wrote, and this rewrite is deliberately not a `mutates` edge. `mutates` names an output that a later step would read as something other than what its producer wrote. A CSV with its git columns filled is the completed CSV. Both steps therefore declare the same paths in `produces`, and `output_cross_check` names both steps in `consumes`. `data/validated/` is the only output that comes back smaller than its producing step declared.

`modified_input_problems(steps, pending, completed, modified)` reports every pending step that directly consumes a step with an output that an earlier run has modified, unless the run rebuilds that step too. The check looks at direct consumers, not transitive ones. Every step downstream depends on `collected_file_cleanup` eventually, but its state affects only the three steps that open `data/validated/`: `detection`, `file_history` and `collected_files_archive`. `deleted_files_report` opens the tree too and names no edge to `collected_file_cleanup` on purpose. By the validated list, which the file history step leaves unchanged, it tells the file history step's prune apart from a deletion that the collected file cleanup did not record, and it reads a pruned tree correctly (`docs/checks/deletions.md`). In the whole pipeline, the analysis stage's content quality step opens the tree as well. `run_pipeline.py` names the file history step as the tree's producer for the content quality step, because the content quality step reads the files that the file history step's CSVs list, in the tree as the file history step leaves it. `output_cross_check` reads `output/` and nothing else. Running it alone again against an already written `output/repos.csv` is correct, and the check does not report it.

`run` calls `modified_input_problems`. When the check reports a step, `run` runs the damaged step again in the same run, with every step computed from it, as `--from` with the damaged step does. It logs an `INFO runner:` line that names the damaged step, the mutator and the affected steps. A refusal would leave an unattended run stopped at its Start. Its remedy, a `--from collected_file_cleanup` in `command:`, would keep the entrypoint from beginning the monthly run (`monthly_argv`, [deployment](deploy.md#a-run-every-month)). After a new image that changes only `agentcontext/steps/file_history.py`, the runner therefore rebuilds the validated tree, runs the detection and the file history step again, and publishes. The rebuild collects nothing again, because the cleanup derives the tree from the untouched collected tree. The runner does not take a new snapshot without the operator, because a new snapshot can take days, and it is not the snapshot that the other steps read. When the damaged step is recorded by its output, `run` therefore refuses the run and names the `--from` that repairs it. The recorded completions stay untouched, the lock is released, and the state file records `modified_inputs`. No step of the current lists modifies a snapshot.

The check does not report a consumer that the step list puts after the mutator when the mutator is recorded and is not pending. In a run that nothing interrupts, such a consumer reads the output as the mutator left it. It reads the same output in a run that resumes after a failure or a stop between the two steps. `collected_files_archive` is such a consumer. A failure of `output_cross_check` or `commit_attribution_validation`, or a Stop during the 7z of the archive, leaves every step through `file_history` recorded, and at the next Start the runner resumes at the step that did not finish. Without the exception, the runner would rebuild the validated tree at that Start and run the detection and the file history step again for nothing. The check still reports a consumer listed before the mutator, such as `detection`. It also reports a consumer after a mutator that runs again, because the mutator would then modify an output that it has already modified.

The check reads the raw recorded set, that is, every step that the state file names, before `--from` drops anything and before `completed_steps` drops a step with a changed fingerprint. The run that pruned the tree changed it, and neither kind of drop undoes that change. The check also reads `modified`, the `modified` object of the pipeline execution state (`MODIFIED`). For each damaged step, that object lists the mutators that started since the damaged step last ran. The runner adds a mutator there before the mutator starts, and removes the names only when the damaged step runs again and is recorded. From the raw recorded set alone, the check would miss a mutator that pruned the tree and then failed or was stopped, because such a step is not recorded. It would also miss a mutator with a record that `--from` removed, as the monthly `--from repository_cloning` removes the record of the file history step. Without `modified`, after a file history step that pruned the tree and then failed, the runner would run the detection over the partly pruned tree at a Start with a new image that changed the detection step, and the detection would drop its rows without a message.

Both kinds of drop can remove the same step, and the check has to hold for both. `--from detection` on a finished run drops `file_history`, because `file_history` is computed from `detection`. Editing `agentcontext/steps/detection.py` drops `file_history` for the same reason, through `completed_steps`. If the check read the set filtered by fingerprints, it would report the run after `--from detection` and miss the run after the edit. `detection` would then run again over the `data/validated/` that `file_history` had pruned and write a different `output/repos.csv`.

#### Resume model

`run_logs/state.json` contains `completed`: one entry per finished step, mapping its key to what the step fingerprinted to when it finished. `run` skips a step that is in it and logs `INFO runner: <step name> skipped, because it is already complete. Run --from <key> to run it again.` A resumed run runs nothing again that already succeeded.

Beside each record, `completed_by` holds how the step was recorded, when, and the commit of the code that recorded it (`record_completion`). The line that `run` logs when it skips the step, the skip line, names them, as in `INFO runner: Repository cloning skipped, because it is already complete. Finished on 2026-10-27 at 18:41 UTC with the code of commit <commit>. Its log is run_logs/repository_cloning.log. Run --from repository_cloning to run it again.` A Build in Container Manager creates the container again and discards its log, and with it the lines of the invocation that ran the step. The skip line then names the commit of the image that the step ran under and the log with the step's own lines, because `run_step` writes the log of a step anew only when the step runs. For a step recorded from its exit after a kill (`exited`), `completed_by` holds the time at which the step exited and the commit of the code that it ran with. For a step that the runner adopted, the skip line says `Recorded from its output on disk`, and for a step that `--mark-complete` recorded, it says `Recorded by --mark-complete`. Each entry of `completed_by` names the fingerprint of its record, and the runner reads the entry for the skip line only while `completed` holds that fingerprint (`completion_origin`). After a hand edit of the record, the skip line leaves out how, when and with which code the step was recorded, because the entry describes the record before the edit.

A recorded step stops counting as done when it no longer fingerprints to what was recorded. `completed_steps` drops it *and everything computed from it*, because those results were derived from output that the step no longer produces. It logs which steps it dropped and why.

After its pre-checks, the runner prefixes the record of every step that the run is going to run with `stale:`. When the runner finds during the run that a step recorded by its inputs, or by its output and `inputs_of`, has to run again, it does the same for that step and the steps that read it. When a step succeeds, the runner replaces the record with the step's fingerprint. When the step fails or is stopped, the record keeps the prefix, and the next run runs the step again and logs `INFO runner: <key> did not finish its last run after one of its inputs changed`. The runner keeps the record instead of removing it, because the check for modified inputs tests whether a step ever ran. Without the prefix, a step that failed after its producer was recorded again would keep its old record, which still matches its unchanged script. At the next Start, the runner would skip that step and every step after it and exit 0. After a failed `commit_attribution_validation`, the run would then reach the release without the check.

When a step joins the run, the runner also drops the records of its consumers, even when their
fingerprints match. When you enable `--with-commit-reclassification` on an existing run, the
run must reclassify, rebuild the validated tree and compute the published outputs again.
Otherwise a consumer could keep its old completion record after its new producer changed
the input.

The field `completion` of a step names its completion policy.

**`COMPLETION_INPUTS`** hashes the step's code, its declared `inputs`, `code_inputs` and `heuristics`, and what its `inputs_of` names, if it names anything. A step without `inputs_of` hashes its code and its declared inputs alone. A step's code is the module closure of its module (`fingerprints.module_closure`), without the imports under `if TYPE_CHECKING:`, which never run. A Python module among the `code_inputs` is hashed by its code, as the script is, and every other declared input by its bytes. In the collection pipeline, `collected_file_cleanup`, `detection`, `import_detection`, `output_cross_check`, `unmatched_paths_report`, `deleted_files_report`, `collection_summary`, `release`, `commit_reclassification`, `commit_attribution_validation` and `unmatched_commits_report` use this policy.

`commit_reclassification` repeats the names of the cloning step's outputs instead of importing the cloning step. The closures of the reclassification and of the checks after it then leave out the collector, `reuse.py` and the cloning step's module, and an edit to these modules runs none of these steps again. `commit_reclassification` names `commits.CLASSIFIED_BY` (`classified_by_input`), the digest that it writes into every per-repository commit record and into its report. The digest hashes the columns of the two commit heuristics files that the classification reads (`commits.CLASSIFICATION_COLUMNS`) and the code of `commits.py` and `heuristics.py` without their comments, docstrings and log calls (`fingerprints.code_fingerprint`). `snapshot write` copies the digest from the report, and the release refuses a snapshot with a digest other than its own. Recorded by its code and the heuristics files alone, the step would stay complete after an image that changes the digest in another way, and the release would refuse at every Start.

The analysis stage's content quality step names the files of the validated tree that the mechanism CSVs list, the files that the markers among them name, and every file of their repositories that the collected file cleanup keeps even when it is empty (`collected_file_cleanup.kept_when_empty`): the files that GitHub Agentic Workflows import, the prompt files of the agent actions, the planning documents with their anchors and the CLAUDE files that decide whether Claude Code reads an AGENTS.md. No fixed list of paths can name these files. Declared in `reads` alone, the tree would be required on disk but covered by no fingerprint, and a tree that changed under the same CSVs would leave the step recorded as done. The sampling stage's GitHub query, comparison and filter name the files of the cache of retrievals that they read, under the names that the retrieval gives them. The comparison also names the retrieval before it. It does not name the collected list that it reads, because the cloning step rewrites the list later in the same run (`1_sampling/run-sampling-spec.md`).

**`COMPLETION_SCRIPT`**, the default, hashes the code of a standalone script, or of a package module and its transitive package imports, without comments, docstrings and log statements (`code_digest`). `engineered_project_selection`, `file_history` and `collected_files_archive` use this policy. It fits a step with output that can be derived again from its input, which is still on disk. A changed script means that the result no longer matches the code that would produce it, and running the step again is both possible and correct.

**`COMPLETION_OUTPUT`** is a checksum manifest of everything that the step declares in `produces`, recorded as `output:<sha256>`. `repository_cloning` and the sampling stage's `ghs_download` use it, because the result of each is a snapshot of data that the pipeline does not control. The cloning step reads GitHub on a given day, and the download reads GHS. No edit to a script reproduces the day that the script read, and running the step again takes a new snapshot instead of reproducing the old one. Under the script policy, the first edit to `agentcontext/steps/repository_cloning.py` would mark `repository_cloning` as not done and invalidate `collected_file_cleanup` and everything after it. A resumed run would then run the collector again over every repository in its input list, all rows of `repos_annotated_included.csv`, on top of a tree that is already on disk and is still exactly what the step wrote. The cloning step reads the sample list, not the smaller validated population.

Under the output policy alone, a change to the tree would invalidate the record, but an edit to the collector, a change to the path heuristics or a new sample list would leave it valid. At a Start after any of these changes, the runner would skip the step. The run would keep the collection of a sample that the classification had replaced, and no record would name what the tree was collected under. `repository_cloning` therefore names an `inputs_of`, `collection_inputs`, which gives the inputs that `reuse` checks before the step takes a repository over from the tree:

- the collector's code, that is, the files that `reuse.collector_files` names, as `reuse.collector_fingerprint` digests them, without their docstrings, log statements and exception texts, and without the modules that only schedule the run or the package files `agentcontext/__init__.py` and `agentcontext/git/__init__.py` (`reuse.PACKAGE_FILES`)
- the version of git, as `git --version` prints it, on which `created_at`, `#commits` and `first_commit_sha` depend (`docs/git.md`). After an image with another git alone, the runner keeps the step with a `WARNING` where its record names the digest of each input, and runs it otherwise. When git prints no version after the tries of `clone.git_version`, the runner stops the run with exit 1. Read as an absent input, the version would count the step as not done, and the run would start the collection and mark every step after it to run again
- the path heuristics, as `reuse.heuristics_sha` digests them, over the columns that decide what is copied, the vendored directories, the path and the match mode of each heuristic of the planning documents, and the places of the tools' local state (`heuristics/local_state_paths.csv`), which the step does not copy
- the import heuristics, over the columns that decide what is copied to the imported tree, with the fingerprint of the code of the imports (`reuse.import_heuristics`), which the collector's code leaves out
- the list that `--repo-csv` names, read from the step's arguments as the step's parser reads them, the last occurrence in either form, `--repo-csv FILE` or `--repo-csv=FILE` (`_flag_value`)

The record is `output:<sha256>+inputs:<sha256>`, and a change to either part runs the step, with one exception. `completed_by` names the digest of each input beside the record (`record_completion`). After a change of the version of git alone, the runner keeps the step recorded (`kept_on`, `changes_kept`), because every line of a collection records the version of git, and the step would collect every repository again, each at the head that it has now, which is a new snapshot of the sample. The runner then logs a `WARNING` that names the change, the reason and `--from repository_cloning`, which takes the new snapshot. The history columns stay those of the earlier version of git until then. The same holds when the runner reaches the step during the run (`changed_during_run`), until another input changes. A change of the collector's code, the path heuristics or the import heuristics runs the step, also beside another version of git, and the runner logs an `INFO` line that names what changed. The step continues the collection in progress, or the last collection that ended over its list or over its list without repositories that GitHub no longer serves (`resume.open_collection`). It then queries no head of a repository that the collection collected or confirmed and collects again the repositories that the change reaches (`reuse.outdated`). Where no collection over its list is in progress or ended, as after `--mark-complete`, the step begins a new collection, which queries the head of every repository again and collects again every repository with a head that moved. If the runner kept the step after such a change, the steps after it would publish the rows of the new heuristics over the tree that the earlier heuristics collected, with no row for a file that a new path heuristic matches. A record of a runner that named no digests, such as the runner of the image with the backup providers, gets them at a start under unchanged inputs (`name_recorded_inputs`), and until then a change of any input runs the step. The container converts such a record once, with the record of the collection that the step ended, at the first start of an image of data root revision <!--s:parameters.deploy.entrypoint.DATA_ROOT_REVISION-->3<!--/s--> ([deploy](../deploy/0_README.md)). The runner computes the inputs right before the step runs (`inputs_before`) and records the step under them once the step exits 0. The record contains the inputs part that the step ran under and needs no git after the step. The cloning step closes its collection when it exits 0. If the runner ran `git --version` again after the step, a git that could not start would leave the step unrecorded. At the next Start, the runner would then run the step again, which continues the collection that ended, and every step after it. A git that cannot start before the step stops the run before the step begins.

The step takes over the repositories that the change does not affect and that have lines in `finished_repositories.jsonl` that record `collected_under` (`agentcontext/reuse.py`), and a run after a changed input clones only what it has to. A new log message, a page that the documentation watch read again, or an edit to the selection step that writes the same list runs nothing. The runner records the list by the repositories that the step reads from it, the digest that ties a collection to its list (`resume.open_collection`), and not by its bytes. The list carries the labels' other columns, and recorded by its bytes, a rewrite of the justifications with the same repositories would run the step again, which continues the collection that ended, and every step after it. A list that lacks only repositories that GitHub no longer serves runs the step, which continues the collection in progress or the collection that ended over it, without querying the heads again ([a new image during or after the collection](#a-new-image-during-or-after-the-collection)). When only the inputs part changed, the runner logs which inputs the step is recorded by. It does not offer `--mark-complete`, which would record the tree under inputs that it was not collected under.

The imported tree, `data/imported/`, is one of the step's outputs. When the tree is removed or changed after the step, the step counts as not done. Otherwise, the import detection step would stop at every Start, or it would give rows that are `missing` without a message. The tree is `may_be_empty`, because a collection in which no import reaches a file leaves it empty, and `--mark-complete` records such a tree. An empty collected tree, by contrast, is a failed run.

Two of the step's outputs, `file_history.csv` and `ai_authorship.csv`, are `extended`. The file history step adds the rows of the files that it measures to both and removes the rows at heads that no later step reads. The manifest therefore records that the two files are there, not what they contain. Recorded by their contents, they would make `repository_cloning` count as unfinished at every Start after the file history step had run. After a late failure, the runner would then run the collector again at the next start over every repository in `finished_repositories.jsonl`, and every step after it.

`resolve_produced` follows a `produces` entry that is itself a symlink, and only at that level. A link found while the files are listed is a configuration artifact that the collector copied out, and its target string identifies it. A `produces` entry, by contrast, is the place where a step was told to put its output, and putting a large tree on another volume and linking to it is the ordinary way to do that. Described as a link, `data/collected` would become one manifest line that names the mount point. That line would be the same whether the mount contains the sample, contains a different snapshot, or has been unmounted. The manifest keeps the declared name as its label, and moving the tree and pointing the link at an identical copy leaves the record valid.

The manifest leaves out the files named in `DISCARDED_NAMES`, because a file that the pipeline provably throws away cannot be part of what identifies a tree. `.DS_Store` is the only entry. `collected_file_cleanup.is_valid_file` rejects it as a file at any depth, and the validator deletes it with the reason `macOS Finder file`. A `.DS_Store` that the Finder writes into the collected sample therefore cannot change a published row. If the manifest counted the file, the file would invalidate the completion of `repository_cloning`, and the next run would run the collector again over its whole input list. A name is discarded only where the validator discards it, which is as a file. `is_valid_file` rejects `.claude/.DS_Store` and accepts `.claude/.DS_Store/settings.json`. The validator descends into such a directory instead of removing it, and its files reach `data/validated/`, are classified and reach a published row. The manifest describes a directory with a discarded name as any other directory, and a symlink with such a name too, because `is_dir` follows a link. Keeping a file that the pipeline would have thrown away costs one `--mark-complete`, while dropping a file that it would have kept hides a change in the sample.

The manifest and the entry count leave out the directories named in `DISCARDED_DIRECTORIES` for the same reason. `@eaDir` is the only entry. Synology DSM writes this directory into the directories that its File Station and indexing services visit, and on the NAS these include the collected tree. `collected_file_cleanup.scan_and_clean_repo` deletes every directory of that name from the validated tree with the reason `Synology DSM directory`, before any other pass reads the tree, and an `@eaDir` therefore cannot change a published row. A name of this set is discarded only as a directory, the form that the validator discards. The manifest describes a link or a file with the name as any other entry. `is_discarded` applies both sets for `manifest_lines` and `counted_entries`. The runner defines the sets itself rather than importing them from the validator, because nothing in the runner encodes what a step does. Tests assert that the validator rejects every name of `DISCARDED_NAMES` and deletes every directory of `DISCARDED_DIRECTORIES`, so that the sets and the validator cannot diverge.

`manifest_lines` builds the manifest, one sorted line per entry:

- `d <path>` for a directory, so that an emptied directory still shows
- `f <path> <sha256>` for a regular file
- `l <path> <target>` for a symlink
- `? <path>` for anything else

It lists the tree with a stack of its own, and it gives the lines in the order in which a function that calls itself for each directory would give them, so that a record written before stays valid. The collector copies a configuration directory whatever its depth, and over a directory nested deeper than the recursion limit, such a function raises RecursionError. No caller catches that error, the finished cloning step would stay unrecorded, and the runner would collect the sample again at every Start. `manifest_lines` tests for a symlink first and never follows one, because `Path.is_dir` follows a link, and a collection may include links to directories and dangling links. It describes a file by its content, not by its mtime. A tree that a tool without preserved timestamps copied, rsynced or restored is still the tree that the collection wrote. `7zz x`, the documented way to restore the tree, restores the archived times, but a copy or an rsync without `--times` does not, and a comparison of mtimes would count such a tree as changed. The runner hashes the collected tree when it checks whether to skip the collection and when it records the completion of the collection. The cost depends on the number and size of the collected files.

A declared output that is absent fingerprints to `""`. For a step under the output policy, the empty fingerprint counts as "not done", whatever the record contains, so that a recorded empty fingerprint never matches an absent output and skips the step. Absent means that nothing is at the end of the path, including a link that points at nothing.

A declared output that exists but cannot be read raises `UnreadableOutput` instead, and each caller reports it in its own words. On a resume, `step_fingerprint_or_stop` turns it into the `ERROR runner:` line that ends the run. Reporting "not done" there would run the step again over a result that is on disk, which for `repository_cloning` means running the collector again over its whole input list. `--mark-complete` runs no step and writes its own `ERROR runner:` line, which names the output that it could not read. When the runner records a step that has just finished, it reports a failed step instead. The existence check is inside the same `try`. `entry_kind` calls `os.lstat`, not `Path.exists`, and raises again every errno other than `ENOENT`, `ENOTDIR`, `EBADF` and `ELOOP`. The other errnos are the errors of a mount that is present but not working, such as `EACCES`, `EIO`, `ESTALE`, `ENOTCONN` and `ETIMEDOUT`. Outside the `try`, those errors would escape to `run`'s `except OSError`, which announces a failure to write the state file and names the sample as the file that it could not write. The runner catches that hard stop in one place, where a step that has just finished is recorded. A step that exits `0` with unreadable output is then reported as a failed step instead of ending the run.

Before the runner adopts the output of an `irreproducible=True` step from disk, it applies the same emptiness check as `--mark-complete`, because the adoption records the step as `--mark-complete` does, only without the flag. A check for empty directories alone would adopt a zero-length output that `--mark-complete` refuses in the same run. The adoption runs on every invocation of the five runners, without any flag. With that check alone, a download killed early would be recorded, and every later run would skip the step.

Emptiness does not show whether the step finished. The GHS download replaces the pointer only after it has written the rows of the new retrieval, and a download that fails or is stopped before then leaves the pointer to the earlier retrieval, which the runner would adopt at the next start as the result of the new download. The runner therefore lists an irreproducible step under `unfinished` in the pipeline execution state before the step starts, and removes it only when the step is recorded as complete. A failure, a stop and a kill all leave the step listed. `adopt_irreproducible` skips a listed step with a `WARNING runner:` line, and the run takes the snapshot again. `--mark-complete` records what the unfinished run left and removes the step from the list. `read_state` refuses a record with an `unfinished` that is not a list of step names.

A declared output that is gone invalidates the completion of its step, whatever the completion policy is. A check of the fingerprint alone would not be enough. A step recorded by its script fingerprints the same whether or not its output is there, and a step recorded by its inputs never reads `produces`. With such a check, deleting `output/repos.csv` after a finished run would leave every step after `collected_file_cleanup` counting as done, and the next run would skip the missing output and exit `0`.

`--mark-complete STEP` records verified output that arrived through an external
archive, without running the step. It takes the run lock and refuses missing or
empty declared outputs. It removes the `exited` entry of the same step, which a kill
after the step exited 0 left with the inputs of that run. Use it only after you have confirmed
that the complete handover was extracted, because a partial tree must not count as a completed
collection.

`--from NAME` drops `NAME` and every step computed from it from the record ([Dependency graph](#dependency-graph)). It is the only supported way to run finished work again. A record edited by hand also works, because the check for modified inputs reads the file and covers such a record too.

Each line that a step writes, and each line of the programs that it starts, goes to its log and
to the console through `logs.labeled`. `logs.labeled` keeps a log message as it is and drops an
empty line. A line printed for a person to read gets `INFO <step key>:` in front of it. Without
the labels, the container's log would show the steps' counts and tables as plain sentences
between the formatted lines, with nothing to show which step wrote them.

Each step also has its own `run_logs/<name>.log`, rewritten on every attempt. When the runner gets an `OSError` while it writes the log, such as on a full or failing volume, it ends the step. It signals the step to stop, reads the rest of its output onto the console alone, and waits for it. It then flushes what the buffer holds under the same handler, closes the log without raising again, and reports the step as failed in a line that names the log. Without this handling, the error would reach the handler written for the state file, which names that file and leaves the step running. Closing the log at the end of the block would also raise the error again. The runner reads to the end, because `repository_cloning` and `file_history` finish their work in progress on `SIGTERM` and keep writing output. If the runner stopped reading at the failure, output larger than the pipe's buffer would block the step on a print and the runner on its wait indefinitely. The wait has no bound, as it has none when your stop is forwarded, because the step has to finish the clones in flight.

#### A new image during or after the collection

The runner records the labeling by its script, its prompts and every module that `run_classification.MODULES` names, and an image that changes any of them runs the labeling again. That includes a change that decides no label, such as one to the cost record, `costs.py`. Both image updates of the run of 2026-11-03 changed modules of the classification, and a fix to any defect comes as a new image built from `main`. The labeling that runs again does not label the sampling frame again. Over the same sampling frame, model and classification parameters, it completes its finished run when the current rules derive each of its decisions unchanged. It then writes its outputs again from the cache of labels and requests no README (`complete_finished_run` in `2_classification/1_classify_repos.py`). A run that left repositories without a decision is completed only once a collection over its sample has begun, in progress or ended. Before that, missing labels are tried again by default, and the labeling labels them in a new run. After it, the labeling logs a `WARNING` with their count and `--new-run`, because a new run could change the sample of the collection. Before a collection has begun, a run with its outputs or its comparison incomplete, as after a stop, is completed first, and the same invocation then labels them in a new run, because the runner records the labeling once the invocation exits 0, and the selection and the cloning step follow. While OpenRouter's lists show that OpenRouter serves no request of the classifying model or the summary model, that new run would exit 1 before its first request at every Start. The labeling then skips that run, completes the finished run without them also before a collection has begun, and logs a `WARNING` with their count after the comparison. The next new run of the labeling tries them again. A new run that does try them stops only where any run of the labeling stops, as when the API's service or GitHub fails through every pause or the credit stays spent, and the runner then stops at the labeling until the next Start resumes the run. The selection writes the same sample, the runner records `repository_cloning` by the same list, and the collection, in progress or finished, stays.

A new run would request every README again and record each repository that GitHub has stopped serving as `not_found_or_no_access`. The selection would drop it from the sample, and the changed list would make the cloning step begin a new collection. A new collection queries the head of every repository again and collects again every repository with a head that moved, which over a sample of tens of thousands of repositories costs days, followed by every step after the cloning. Recording the labeling by fewer modules would not prevent it, because `1_classify_repos.py` holds the rules that decide a label beside code that decides none, and both image updates changed it. The labeling's own check of its decisions tells the two apart where it matters, at the labels.

A labeling still labels again after a change of a rule that derives a label differently, after a change of the classification parameters, or with `--step-arg repository_labeling:--new-run`. Such a run can drop repositories that GitHub no longer serves. The cloning step then continues the collection in progress over the smaller list, or the collection that ended when none is in progress, and does not begin a new one (`resume.open_collection`, [repository cloning](steps/repository_cloning.md)). A repository counts as no longer served when the excluded repositories beside the sample, `repos_excluded.csv`, name it `not_found_or_no_access`, or when the line of the repository in `finished_repositories.jsonl` records that outcome. The runner still runs the step, because its list changed, and the step removes the files of the dropped repositories and takes over every other repository without querying its head. The runner could instead keep the step recorded over such a list, but the collected tree and its list would then keep the dropped repositories, and the release would publish them beside labels that name them `not_found_or_no_access`. A list that adds a repository, or that drops one that GitHub still serves, belongs to another sample, and the step begins a new collection. A list with the same repositories as the collection that ended continues it, as when the runner runs the step after a change of the collector's code or of the heuristics or under a record that names no digest of each input, and what a change of the collector, git or the heuristics reaches is collected again (`reuse.outdated`).

After the cloning step has exited 0, an image that changes the collector's code, the path heuristics or the import heuristics runs the step, also beside another version of git. The step continues the collection that ended over its list, queries no head of a repository that the collection collected and collects again the repositories that the change reaches, which can be every repository. Where no collection over the list is in progress or ended, as after `--mark-complete`, the step begins a new collection, which queries the head of every repository again and collects again every repository with a head that moved. An image that changes only the version of git does not run the step, because the step would collect every repository again. The runner then logs a `WARNING` that names the change and the reason, and the collection stays as the earlier version of git collected it ([resume model](#resume-model)). `--from repository_cloning` requests the new snapshot explicitly, and so does the next monthly run, whose `--from` arguments name the step (`NEW_RUN_FROM` in `deploy/entrypoint.py`). The runner then marks the collection that ended as replaced (`resume.forget_ended_collection` in `drop_completed_from`), and the step begins a new collection whatever its list. The mark is made when the runner drops the record of the step, after the pre-checks, so that a stop before the step starts keeps the request. It also keeps the labeling of a monthly run whose GHS download fell back to the previous retrieval from counting the collection of the previous month as a collection over its sample (`collection_over`), so that the labeling tries the repositories without a decision again. A collection in progress that never ended is resumed, because it has not taken its snapshot yet. A continued collection that a stop, a kill, a power loss or any exit other than 0 left in progress is the earlier snapshot. Its record has the key `continued_after_end` (`resume.CONTINUED`), and the runner removes that record and marks the collection as replaced too.

#### Stopping

`run` installs `forward_stop` for `SIGTERM` and `SIGINT` after the `--list` check and restores the previous handlers in its `finally`. A handler never outlives the call that installed it, which matters because the module's own test suite imports the module.

The handler passes the signal to the running step and records it in `_STOPPING`. It returns instead of raising. The loop notices the stop at its next test of `_STOPPING` and ends the run cleanly, with the step that just finished still recorded. Forwarding alone would not be enough, because after the handler returns and the signaled step exits, the loop would start the next step. A stop has to end the pipeline as well as the step. A second signal that arrives while no step is running makes the runner exit immediately, and you never need `kill -9`.

For Ctrl+C, the forwarded signal duplicates what the terminal already delivered to the process group. The duplicate costs nothing, because the step is ending either way, and forwarding makes `kill -INT` on the runner alone behave the same.

`run_step` creates the step's data directory before it starts the step, because over an empty data root no stage has a data directory yet. It checks the flag again immediately after `Popen` returns. A signal delivered *inside* `Popen()`, after the loop's check and before the assignment completes, would find no child and take the branch for a stop without a running step. The child would never be signaled, and `wait()` would block for the step's full duration. The window is about a millisecond, and a signal lost in it costs hours.

The `except KeyboardInterrupt` block remains for the narrow window before the handler is installed. An ordinary Ctrl+C does not reach it.

#### Locking

`acquire_lock` opens `run_logs/run.lock`, which the first run creates, and takes a non-blocking exclusive `flock` on the descriptor. It keeps the descriptor open for the life of the process. `EWOULDBLOCK` means that another run holds the lock. This run then refuses to start and logs whatever identifier the holder wrote. A lock file that the run cannot open, such as a read-only lock file restored from a handover, gives one `ERROR runner:` line and exit 1, not a traceback. On success, `acquire_lock` writes `pid <pid> on <host> since <time>` into the file for you, and nothing reads that line back. `release_lock` closes the descriptor, which drops the lock. It runs in a `finally`, and the lock is dropped on success, failure and interrupt alike. The runner never unlinks the file. A waiter that had opened the old inode would lock a file with no name while the next run created a new file at the path, and both runs would proceed.

#### Pre-checks

`pre_checks` receives the pending steps, those not in `completed`. It checks only what they need and what the steps that `may_become_pending` names need. Those are the steps recorded as done that this run can still run and that the run computes again when it reaches them: a step recorded by its inputs, and a step recorded by its output and `inputs_of`. Such a step can become pending when a pending step before it writes a path that it reads (`read_paths`: each alternative of `inputs`, `reads`, and for `repository_cloning` the list of repositories that it collects). Every step computed from such a step joins too, until nothing more is added. A monthly run takes `ghs_download` and `repository_cloning` again. In it, the query, the comparison and the filter read the pointer that the download writes, the labeling reads the sampling frame that the filter writes, and the selection consumes the labeling. In a run after a new image that changed the labeling, `repository_cloning` reads the list that the selection writes. The pre-checks log the steps that they check this way in an `INFO pre_checks:` line.

The pre-checks check the binaries, the imports, the environment variables, the API key of the service that serves the labeling's model, the GitHub access token, the interpreters, `lingua`, the scratch directory and the free space for both sets of steps. They check the inputs on disk for the pending steps alone, because a step that becomes pending reads what the steps before it write. `BINARY_REQUIREMENTS` maps each binary to the steps that require it. When `detection`, the one step in `LINGUA_STEPS`, is pending, the pre-checks also warn if `VENV_PYTHON` cannot `import lingua`.

`repository_cloning` must find its input CSV. The pre-checks read the path out of the step's own argv, and they honor both `--repo-csv other.csv` and `--step-arg repository_cloning:"--repo-csv other.csv"`. They skip that check when a pending step declares the same path in `produces`, because the file will be there by the time `repository_cloning` opens it. `engineered_project_selection` declares exactly the default path. An unconditional check would refuse the run over an empty data root, the run that `engineered_project_selection` exists to make possible. Any other `--repo-csv` is still checked, because no step produces it.

Each pending step's interpreter must import the step's module and its declared `imports`. The step's declared `env` variables must be set, or, for a GitHub access token, an OpenAI API key or an OpenRouter API key, be in the credentials file that the runner's command line names (`docs/credentials.md`). Every pending interpreter must report the `major.minor` version that `mise.toml` pins.

`LABELING_STEPS` holds one step, `repository_labeling`. When it is pending or can become pending, `labeling_keys_accepted` checks the API key of the service that serves the step's model. An OpenRouter model has an id that names its author, such as `deepseek/deepseek-v4.1-flash` for the default DeepSeek V4.1 Flash. For such a model, `openrouter_accepts` reads the credit of the first OpenRouter API key through `openrouter_key` (`GET /api/v1/key`), a request that costs nothing. A request with the model itself would cost money at OpenRouter, and OpenAI would refuse an OpenRouter model as a model that it does not offer. HTTP 401 and 403 from `GET /api/v1/key` fail the pre-checks. A key without credit left gives a `WARNING pre_checks:` line, because the labeling waits for credit, and any other error gives a warning too. With one OpenRouter API key, the `INFO pre_checks:` line of a key with credit names it as the OpenRouter API key. With several, from `OPENROUTER_API_KEY` and the credentials file, a `WARNING pre_checks:` line names how many of them are unused, because the check and the labeling use only the first (`endpoints.api_key` of `2_classification/endpoints.py`), and the `INFO` line names the key that it checked as the first. A run labels with an OpenAI model only when a `--step-arg` names one. For such a model, when an OpenAI API key is configured, the check sends one request to OpenAI's Responses API through `openai_response`. The request uses the first OpenAI API key, which the labeling uses too, and the step's model. `labeling_model` reads the model from the last `--model` of the step's arguments, and a `--step-arg` counts. Otherwise, it reads from the script's source the `DEFAULT_MODEL` that the script assigns, because the script imports packages that the runner's interpreter lacks. The request sets `max_output_tokens` to the fewest output tokens that the API accepts and stores nothing. HTTP 401 and 403, and an error with the code or type `model_not_found`, fail the pre-checks. An error with the code or type `insufficient_quota` or `billing_hard_limit_reached` gives a `WARNING pre_checks:` line that names the cause and what to do, because a top-up ends the refusal and the labeling waits for the credit rather than failing its repositories (`classify-repos-spec.md`). A failed pre-check would stop a monthly run until the next Start. The `ERROR pre_checks:` line names the cause, the HTTP status and the model, never the key or the body of the response. Every other error, such as a server error, a rate limit, a timeout or a server that cannot be reached, gives a `WARNING pre_checks:` line. Such an error shows nothing about the key, and the step retries its own requests. A key that is not configured is the error of the `env` check above, and no request is sent. Without the request, a key that OpenAI refuses would be found only after the sampling stage, when every repository of the labeling failed with it.

When a step in `CLONING_STEPS` is pending or can become pending, the pre-checks verify each distinct configured GitHub access token in order through `github_verdict`, until GitHub accepts one. They check the GitHub access tokens of `GITHUB_TOKENS` and `GITHUB_TOKEN` first, then those of the credentials file. A problem with the file, or a value of these variables that does not have the form of a GitHub access token, is a WARNING, and the pre-checks do not check such a value. `github_verdict` calls `github_rate_limit`. Only HTTP 401, `GITHUB_REJECTED_STATUS`, rejects a GitHub access token, and the pre-checks then try the next one. Any other result gives no verdict, such as a request that cannot reach GitHub, a server error, a rate limit or a response in another format, including a JSON body without an object at `resources.core`. The pre-checks then repeat the check after each pause of `GITHUB_CHECK_WAITS`, with an `INFO pre_checks:` line before each pause, and a stop ends the pauses. When no attempt returns a verdict, the pre-checks keep the GitHub access token with a `WARNING pre_checks:` line. Such a failure shows nothing about the GitHub access token, and the cloning step's connectivity probe finds a failure of the network that lasts. Counted as a rejection, a short failure of the network would stop a monthly run before its first step. The pre-checks assign the GitHub access token that they accepted or kept to `GITHUB_TOKEN` for the child steps.

GitHub can reject valid GitHub access tokens for a while. When it rejects every candidate, the pre-checks verify them all again in their order after each wait of `GITHUB_REJECTED_WAITS`, with an `INFO pre_checks:` line before each wait. The waits grow from minutes to hours, as the steps that query GitHub wait out such a period. The pre-checks fail only when GitHub rejects every candidate in each check, or when none is configured. Failing after one rejection of each would leave an unattended run stopped, because nothing starts it again. A stop ends the wait (`_wait_unless_stopped`), because the handler of a stop returns, and a sleep of hours would hold a Stop of the container until its grace period ended in SIGKILL. The run then ends with the outcome `stopped_before_steps` (`STOPPED_BEFORE_STEPS`), one of `NO_STEP_OUTCOMES`. Every stop before the first step of a start ends the same way, whether it arrives while the runner computes the record of the collected tree, during the pre-checks whatever they found, in the loop over the steps that the start skips, or as a second signal. After a stop during the pre-checks, the pre-checks send no further request. This outcome leaves the outcome of the run before it in place. Recorded as `interrupted`, such a stop would hide a run that had failed in its analysis stage. The run of the next Start would then run the failing step again, and the entrypoint would hand over the data root a second time. With `--no-github`, the pre-checks verify no GitHub access token, and a set `GITHUB_TOKEN` is an error.

The pre-checks measure the free disk space at every start, on the volumes that contain the data root and the stage directory, each at the nearest directory that exists. When a step in `CLONING_STEPS` is pending or can become pending, they also measure it on the volume that contains the scratch directory, which the pre-checks create. A volume that holds more than one of these directories is measured once. `free_space_minimum` gives the minimum: the `--min-free-gb` of the command line when it gives one, `MIN_FREE_DISK_GB` when a step in `CLONING_STEPS` is pending or can become pending, and otherwise `MIN_FREE_DISK_GB` less `CLONES_IN_FLIGHT_GB`. `CLONES_IN_FLIGHT_GB` is the <!--s:collection.max_scratch_gib-->160<!--/s--> GiB that the clones in flight take, and a test keeps it equal to the cloning step's default number of workers times the clone bound. Without a clone in flight, the steps need only the room beside the clones, and the whole minimum refused a resume of the steps after the collection on a volume with room for those steps. Every failing check logs its own `ERROR pre_checks:` line, and the run stops before any step starts.

#### Pipeline execution state

`write_execution_state` fills and writes the provenance part of the same file: the git SHA and dirty flag of this code, the exact command, the start and finish times, the duration, the outcome, the host and the platform, and one entry per step with its status (i.e., `ok`, `skipped`, `failed` or `interrupted`) and duration. The command is quoted with `shlex.join`, so that an argument containing a space can be pasted back and run again. `write_execution_state` never replaces `completed`.

The runner calls `write_execution_state` with the outcome `running` just before the first step of a start that it does not skip and just before every step that it runs. It calls it after every step with the same outcome, and once more at the end with the final outcome. The first call covers a kill inside that step, such as a reboot during the cloning step, which no handler catches. Without the call, the file would keep the outcome of the start before, `success` after a completed run, and the entrypoint would not resume the run at the next Start. The call before a step names the step as `running_step` (`RUNNING_STEP`). It records the `started_at` of its start as `running_step_started_at`, and the step results of that start up to the step as `running_step_results`. A later call removes the three keys once its step results record a step that ran, and a kill inside the step leaves the step named. At a start with step results that record no step that ran, the runner leaves the name as the start before it wrote it. Such a start is a refused or stopped start, or a start that a check stops before its first step with the outcome `failed`, such as `collection_inputs` when git cannot start. If the runner removed the name at such a start, the record of a kill inside the first step of the start before it would be lost, and the entrypoint would hand the data root over as complete while it held part of a collection (`release_step_completed`).

While a step waits for something that a person has to do, the state shows the wait under `running_step_status` (`RUNNING_STEP_STATUS`). The labeling waits up to <!--s:parameters.2_classification.1_classify_repos.CREDIT_WAIT_SECONDS.days:words-->three<!--/s--> days for credit when OpenAI or OpenRouter refuses its requests because the credit is spent, and the state then names the service, the reason, what to do and since when (`classify-repos-spec.md`). The runner sets `AGENTCONTEXT_STEP_STATUS` in the step's environment to `run_logs/<step>.status.json` (`status_path`), and the step writes the file with `logs.step_status` and removes it when the wait ends. At each line of the step's log, the runner reads the file when its modification time or its size changed and writes the state with the status, or without it once the file is gone (`run_step`, `record_step_status`). The step writes or removes the file before it logs the line with which the wait begins or ends, so that the runner writes the state at both lines without a timer of its own. When the step ends, the runner removes the file and the key, also after a stop or a failure. `write_execution_state` removes the key too, because it writes between steps, so that the next start removes a wait that the state kept when the runner was killed. The runner reports the wait in its state and its log without a push notification service, as it reports every outcome.

At a start that ran no step (`NO_STEP_OUTCOMES`), the runner also leaves the step results (`steps`) as the start before it wrote them, as it leaves `last_run_outcome` and `last_run_steps`. The container's entrypoint reads the step results to tell whether a `--fresh` of a step took effect. The flag took effect only when its own step started, because a kill in an earlier step leaves the collection untouched ([deployment](deploy.md#deployment-options)).

Beside the outcome, `write_execution_state` records the outcome of the last start that ran steps as `last_run_outcome`, which a refusal and a `--mark-complete` leave unchanged. It records the finish time of the last start that ran a step as `last_steps_finished_at`, which a start that skipped every step also leaves unchanged. At a Start, the container's entrypoint decides from `last_run_outcome` whether to begin the monthly run, and it records `last_steps_finished_at` with the handover of a completed run (`recorded_handover`, [deployment](deploy.md#key-decisions)). The time of the state file cannot show whether a handover contains the data root as it is, because every start writes the file. A state written by a runner without `last_steps_finished_at` has no such key until the runner runs a step at a later start, and the entrypoint records the handover of such a state with null in its place.

Beside the finish time, `write_execution_state` records the step results of the last start that ran a step as `last_run_steps` (`LAST_RUN_STEPS`). A refusal, a `--mark-complete` and a check that stops the run before its first step write step results in which no step ran, and they leave `last_run_steps` as it was. The entrypoint reads the failed step from `last_run_steps`. It counts a last run that failed in a step after a release step that the run recorded as `ok` or `skipped` as a run that failed in the analysis stage. At a Start in a later calendar month than the run's retrieval, the entrypoint begins the monthly run after it (`failed_analysis_step`), also after a Start at which the pre-checks refused that monthly run. Before a run with a `--from` of `command:`, the entrypoint reads from `last_run_steps` whether the release step is done, whatever the outcome. It reads from `running_step` and `running_step_results` whether a kill came after the release step (`release_step_completed`). When a kill ended a start before any of its steps ended, `last_run_steps` stays as the start before it wrote it. At a later start that a check stops, the runner writes `steps` that end where the check stopped it.

### Output

| Path | Contents |
|------|----------|
| `run_logs/<name>.log` | That step's stdout and stderr, each line through `logs.labeled`, rewritten on every attempt |
| `run_logs/state.json` | `completed` (step key to the fingerprint that the step completed with: a code hash, `inputs:<sha256>` over code and declared inputs, or `output:<sha256>` over its output manifest), `completed_by` (step key to the fingerprint of the record, the time, the commit of the code and how the step was recorded: `ran`, `adopted` or `marked_complete`, and for a step recorded by its output and by `inputs_of`, under `inputs`, each input with its digest), `unfinished` (the irreproducible steps that a run started and did not record), `modified` (for each step with an output that a later step modifies, the mutators that started since the step last ran), `running_step` (the step that has started and not ended, while it runs, and after a kill inside it until the runner runs a step at a later start) with `running_step_started_at` (the start that named it) and `running_step_results` (that start's step results up to the step), `running_step_status` (what the running step waits for, while it waits), `exited` (the step that exited `0` and that the runner has not recorded yet, with the inputs part that it ran under and each of these inputs with its digest, the commit of the code, the step's script fingerprint and the time at which it exited), plus the run's provenance with `last_run_outcome`, `last_steps_finished_at` and `last_run_steps`. Written atomically before the first step that the runner runs at a start, before and after every step, when the running step begins or ends a wait, and by `--mark-complete` with outcome `marked_complete` |
| `run_logs/run.lock` | The `flock` of the running invocation, with an identifier for you. The lock drops when the process ends, and the file stays |

Exit codes:

- `0`: every step succeeded or was already done
- `1`: a step failed, pre-checks failed, another run holds the lock, the lock file cannot be opened, or the command line cannot be read
- `130`: interrupted with Ctrl+C
- `143`: stopped with `SIGTERM`

## Error handling & edge cases

| Scenario | Behavior |
|----------|-----------|
| A step exits non-zero | The pipeline stops there, and the runner records nothing for the step. The next run retries it, and earlier steps stay skipped |
| A step exits zero without writing a path it declares in `produces` | Treated as a failure: `ERROR runner: <step name> exited 0 after <seconds>s but did not write <paths>. Its log is <log>.`, nothing recorded, pipeline stops. The message names only the paths that this run did not write, and it names a path that is on disk but unchanged as such |

| A directory is declared in `produces` | The directory has to exist, whether this run created it or not. A `repository_cloning` that resumes from `finished_repositories.jsonl` can leave `data/collected/` complete without touching the directory entry, and a directory need not have changed. `collected_file_cleanup` rebuilds `data/validated/` completely in every run anyway. `repository_cloning` declares its list as an entry apart from the directory that contains it, so that the check still tests whether the run wrote the list |

| Lock left behind by a dead process | The kernel released its `flock` when it died. The next run takes the lock with nothing to detect |
| Lock file containing garbage, or a pid that is alive and not the holder | Never read. Only the `flock` counts |
| Lock held by another user's live process | The runner cannot take the `flock`, as with any holder, and refuses to start. A lock file that this user cannot open for writing gives one `ERROR runner:` line that names the lock, and exit `1` |

| A signaled step that finishes its work in progress and exits `0` with all its declared outputs | Still not recorded, because it is interrupted, not complete |
| A signal that arrives after the step exited and before the runner reads its exit | Not forwarded, because no step runs. The step is recorded as the one that finished, and the run ends before the next step |
| A power loss right after a step exited `0` | Before any record contains the step, the runner syncs the declared outputs of the step and its report: each file, and each directory with every file and directory below it (`sync_outputs`, `caches.sync_tree`). Steps write their outputs by a rename without a sync, and a record that reached the disk first would name the step over an empty or an earlier file. The runner syncs these paths and not the file system that holds them, because `syncfs(2)` waits for every write that is pending on the volume. On the btrfs volume of the NAS, the cloning step of the run that began on 2026-10-23 called `syncfs(2)` and did not return from it |

A step recorded by its output is recorded with the inputs part of the run that wrote it. `completed_steps` then compares that part with the current inputs, as for a step recorded on the normal path, which holds no code in its record either. The runner records a step that is recorded by its script or by its inputs this way only under the commit of the code and the step's script that it ran with. Under other code, such as after a new image, the step runs again. The cloning step closes its collection before it exits `0`. Run again, it would continue the collection that ended and take over every repository, and every step after it would run again. A new collection begins only over another list or after `--from repository_cloning`. The cloning step syncs its commit CSVs before it closes the collection. It syncs its lists and caches as it writes them, and the files that a line of the list of finished repositories describes before it writes that line. The runner's sync after the step then has little left to write, and the window in which a power loss finds the collection closed and the step not yet in `exited` is short. At the start that records such a step, the runner counts it as a step that it ran, with the status `ok`, and the pipeline execution state names the time of its last steps and no running step. The entrypoint packs a handover when that time is later than the handover that it packed, and the step changed the data root. The step stays under `recorded_from_exit` until a start's loop reaches it. When a start ends before that, by a refusal, a stop or a kill, the result is left to the next start. The runner removes `exited` only once the step is recorded or refused, so that a second stop signal during the fingerprint, which exits at once, leaves it to the next start. `--mark-complete` of the same step removes it, because it holds the inputs of the killed run. Otherwise, the runner would record the step from it at the next start over the mark and run the step again |

## Running the pipeline

Run the collection and the publication with one of the commands at the end of this section. The runner logs each step's output to `run_logs/<step>.log` and shows it on the console line by line, and a container's log shows the run. The cloning step logs a progress line after every <!--s:parameters.agentcontext.guards.PROGRESS_EVERY-->100<!--/s--> finished repositories, or after <!--s:parameters.agentcontext.logs.PROGRESS_SECONDS.minutes:words-->ten<!--/s--> minutes without one, with the counts, the rate and the time left at that rate. [Context](#context) and [Key decisions](#key-decisions) describe how the runner skips completed steps and how the other three runners and `../run_pipeline.py`, which runs the five stages as one list of steps, run their steps through the same code. The runner takes these options:

- `--with-commit-reclassification`: reclassify the commit logs after the collection, rebuild the validated tree, then run detection and its consumers. Also run the <!--s:parameters.agentcontext.runner.COMMIT_RECLASSIFICATION_STEPS:words-->two<!--/s--> checks over the commit CSVs of the cloning step, last among the steps of the collection. `commit_attribution_validation` exits 2 when a row of `output/all_ai_commits.csv` differs from the result of the current heuristics over the columns that the CSV stores. `unmatched_commits_report` writes the attributions that no heuristic explains, ranked, into `output/unmatched-commits.csv` and exits 0. Off by default. The option requires commit logs for the reclassification and the original unmatched attributions for the unmatched check. The reduced archive of the unmatched attributions that the repository tracks does not replace those inputs. See [the commit step](steps/commit_reclassification.md) and [dataset evidence limits](dataset.md).
- `--from <name>`: run a stage of the pipeline again, that is, all of its steps, or one step, together with everything *computed from* it, whatever their recorded completion. You can give the flag more than once, and the run then runs each name again with what is computed from it. A monthly run, for example, runs `ghs_download` and `repository_cloning` again, which no edge joins. `--list` shows the steps under their stage. The selection follows dependencies, not list positions. `--from output_cross_check` leaves `collected_files_archive` alone, because `collected_files_archive` reads nothing that `output_cross_check` writes.

  After a completed run, `--from detection` also runs `collected_file_cleanup` again first, because the file history step has pruned `data/validated/` ([Steps that modify an earlier step's output](#steps-that-modify-an-earlier-steps-output)). An `INFO runner:` line names the damaged step, and the cleanup derives `data/validated/` again from the untouched `data/collected/`, as `--from collected_file_cleanup` does.
- `--list`: print the stages with their steps without running anything.
- `--step-arg NAME:"args"`: append extra CLI arguments to one step for this run only, such as `--step-arg repository_cloning:"-w 10"`.
- `--min-free-gb GB`: the free space that the pre-checks require of each volume that they measure, and also the cloning step's `--min-free-gb`, so that both use one number. Without it, the pre-checks require `MIN_FREE_DISK_GB`, <!--s:parameters.agentcontext.runner.MIN_FREE_DISK_GB-->190<!--/s-->, when a step that clones is pending or can become pending, and the room beside the clones otherwise ([Pre-checks](#pre-checks)). `MIN_FREE_DISK_GB` allows <!--s:parameters.agentcontext.steps.repository_cloning.workers_default:words-->five<!--/s--> clones at the size bound in flight. A run over a short list needs less.
- `--scratch-dir DIR`: the directory where every step that clones puts its clones and where the pre-checks measure free space. The default is `_scratch/` under the stage directory, and in a container a mounted volume. The cloning step measures the same minimum again as it runs. Below the minimum, it starts no further clone, lets the clones in flight finish, and exits 3 with every finished repository in its list of finished repositories.
- `--no-github`: for a run with clones that do not reach github.com, such as a run against local mirrors. The pre-checks skip the GitHub access token and the rate-limit request, and they refuse a GitHub access token that is set.
- `--mark-complete <step>`: record a step as complete from the output already on disk, then exit without running anything. Only a step recorded by its output can be marked: `repository_cloning` in the collection's list and `ghs_download` in the sampling's list. For every other step, the recorded value is a hash of its code, or of its code and its declared inputs, and does not describe its output on disk. The runner records `repository_cloning` with its inputs as they are now, each with its digest. A later change of the list, of the collector's code or of the heuristics runs the step, which then begins a new collection, and a later change of the version of git alone keeps it with a `WARNING` (`kept_on`). It removes the records of the collection in progress and of the last collection that ended, `finished_repositories.collection.json` and `finished_repositories.ended-collection.json` (`resume.forget_collections`). `--mark-complete` refuses when any of that output is missing or empty, or when an input that the step is recorded by is absent. It also refuses to share a command line with `--list`, `--from`, `--repo-csv` or `--step-arg`, which it would otherwise ignore. Use it to record the verified collection output of a handover that you restored into a working copy. See [the working copy of a handover](development.md#handover-working-copy).

Every invocation writes `run_logs/state.json` ([Pipeline execution state](#pipeline-execution-state)), and the runner writes it atomically after every step as well as at the end. In the container, which has no `.git`, the commit in the file comes from the image's `BUILD_INFO`, and `git_dirty` from its `-dirty` suffix. To check a run on a remote machine, copy this one file instead of searching `run_logs/`.

[Resume model](#resume-model) describes how the runner records each step, and [Key decisions](#key-decisions) the reasons. After a change to the collected tree, the runner's message names `--mark-complete repository_cloning` as the way to record the tree again once you have looked at what changed.

Only one run is allowed at a time, under `run_logs/run.lock`, an `flock` that the kernel releases when its holder dies ([Locking](#locking)). Before any pending step starts, the pre-checks verify the prerequisites ([Pre-checks](#pre-checks)):

- `git`, `rsync` and `7zz` on PATH
- the cloning step's input list, on disk or produced by a pending step
- when a step that clones is pending or can become pending, a configured GitHub access token that `GET /rate_limit` does not reject
- when the labeling is pending or can become pending, an OpenRouter API key that `GET /api/v1/key` does not reject, or, when a `--step-arg` gives the labeling an OpenAI model, an OpenAI API key with which OpenAI accepts one request for it
- <!--s:parameters.agentcontext.runner.MIN_FREE_DISK_GB-->190<!--/s--> GiB of free disk, `MIN_FREE_DISK_GB`, when a step that clones is pending or can become pending, and the room beside the clones otherwise

The pre-checks also check each pending step's interpreter, and they only warn when the detection step's interpreter cannot import `lingua`, because the step runs without it and then records `n/a` as every `language` in the <!--s:parameters.agentcontext.heuristics.LANGUAGE_MECHANISMS:words-->five<!--/s--> output CSVs that have the column.

The runner forwards `SIGTERM` and `SIGINT` to the running step and then ends the run with `128 + signal` ([Stopping](#stopping)). When the cloning step is signaled, it ends its pool workers and kills the git processes that they started. A signal that ended the parent process alone would leave the workers running, and a run resumed while they run would share the scratch directory with them.

```shell
python3 -m agentcontext run
python3 -m agentcontext run --with-commit-reclassification
```

The runner tests in `tests/test_runner.py` start the command's main entry point with a cloning
step. They check that `--with-commit-reclassification` runs the reclassification immediately
after that step, and that `--list` shows the same order. They also check the complete set of
heuristics files that each step declares, and that a change to either commit heuristics file
changes the reclassification fingerprint.

The test of a failure to write the log uses a step that writes more than a pipe buffer after
SIGTERM. The step's handler sets a stop flag, and its main loop writes that output, which avoids
reentrant writes if the signal interrupts the initial output.

CI runs the sampling runner suite after it installs `agentcontext` and before it
installs any third-party step dependencies. An accidental import of a dependency
therefore fails in the environment that the runner is documented to support.

## The collection summary

`collection_summary` runs before `collected_files_archive` and `release`. It consumes the results
of repository cloning, detection, the file history step and the import detection. Its fingerprint
covers the input lists, the mechanism CSVs and `output/imports.csv`, which the snapshot's
`imports` section counts. `release` consumes `collection_summary`, and after a new collection,
the step writes the provenance again before the release is built. The snapshot summarizes the
coverage of the optional commit reclassification. A normal run of the analysis runner makes no
comparisons with the counts of earlier papers.

## Recovery

| Error | Required action |
|---|---|
| `state.json ... could not be read` or `not a pipeline execution state` | Keep the file, and restore a valid pipeline execution state from the same handover. The runner refuses to overwrite an unreadable state. Deleting the file loses the completion information and can start an expensive collection again |
| Declared output `could not be read` | Restore the mount, or correct the permissions or the storage failure that the message names. The runner does not treat existing output as absent. Do not delete a readable sample to work around a problem of the mount |
| Step exited 0 but did not write declared output | Inspect the step log and the outputs that the message names. A declared file must be created or changed, and a declared directory must exist. Correct the producer or its inputs and run it again. Do not mark outdated output complete |
| Step log could not be opened or written | Check the log path and the filesystem error that the message names. On a failure while writing, the runner signals the running step to stop and keeps the remaining console output. Resolve the cause before you resume. The step is not recorded complete |
| Pipeline execution state could not be written | Stop and keep the step outputs and logs. Correct the storage or the permissions, then inspect whether the last completed step was recorded. Use `--mark-complete` only for verified, complete declared outputs |
| Run lock is held | Locate the active pipeline process. The kernel releases the lock when its holder exits. Deleting the lock file can allow overlapping runs and is not the remedy |
| Unknown command or step | CLI command names use hyphens, such as `file-history`, and runner step keys use underscores, such as `file_history`. Check the command help and the runner's `--list` output |

After you correct the error, run the same command again over the original state and inputs. On the
NAS, start the container again: in Container Manager, open Container in the left menu, select
`agentcontext-agentcontext-1`, then choose Action, Start
([deployment](deploy.md#import-create-start)). For a refusal over modified inputs, add the `--from`
that the message names, in the container as an argument for one Start
([deployment](deploy.md#deployment-options)). A rebuild with `--from collected_file_cleanup` leaves
the collected tree untouched.
[Deployment recovery](deploy.md#recovery-from-handover-and-storage-errors) distinguishes failed
processing from a failed delivery of the handover.
