# Running the pipeline on the Synology

For development and tests across all stages, use the [x86-64 development image](development.md#linux-x86-64-development-container).
That image runs over a mounted checkout under an unprivileged user. The container that this runbook
sets up from the production image and the NAS bundle runs the five stages and packs the handover.

This runbook describes how to run the pipeline on the authors' Synology through Container Manager. The deployment follows that of the authors' mining project `jaws26-loop-engineering`. The code runs from the image, and the data and the run's files are in a project folder on the machine. A change to the code therefore takes effect on the machine only through a new image. `compose.yaml` beside this file is the project file.

You import the image, create the project and start the container once ([Import, create, start](#import-create-start)). The container's entrypoint then starts the runner, which runs every step of the five stages in order. When the runner ends, the entrypoint packs the handover. The runner downloads a retrieval of GHS, queries GitHub for its repositories, filters the sampling frame and labels it. It then collects the sample with the <!--s:parameters.agentcontext.runner.COMMIT_RECLASSIFICATION_STEPS:words-->two<!--/s--> checks over the commit CSVs of the cloning step, builds the release and writes the analysis. You edit no command between steps.

When you start the container over a project folder that a run of an image with the same data root revision has written to, the runner resumes that run and skips every step recorded complete. Over a project folder of an earlier data root revision, the entrypoint first converts the stored files where the image has a conversion from that revision, and over any other revision it runs no step ([Restarting and updating](#restarting-and-updating)). The cloning step takes over each repository in `finished_repositories.jsonl` that has an unchanged head commit and that no change of the collector, git, the path heuristics or the import heuristics has reached since its collection, except the repositories that it retries when it resumes a collection. When the cloning step resumes a collection, it takes over the repositories that the collection already collected or confirmed, without querying their heads again ([the cloning step](steps/repository_cloning.md)).

## Prerequisites

- **Container Manager and a project folder.** Put the project folder on a volume of the machine itself. The run lock and the snapshot lock are `flock`s, which a share mounted from another machine may not implement, and the entrypoint refuses to start the runner when the folder's filesystem does not implement them.
- **Mounts.** <!--s:parameters.deploy.entrypoint.MOUNTS:Words-->Two<!--/s--> mounts, both read-write: the data root `data/` and `handover/`. `compose.yaml` also mounts `credentials.csv` read-only, and the NAS's `/etc/localtime` read-only at `/etc/host-localtime`. The entrypoint reads the NAS's time zone from that file and compares calendar months in that zone ([A run every month](#a-run-every-month)). The container's own local time stays UTC. At each start, the entrypoint's `startup_problems` returns every problem with the mounts at once, and the entrypoint logs each problem and exits 1. The function checks that each of the <!--s:parameters.deploy.entrypoint.MOUNTS:words-->two<!--/s--> mounts is the host's filesystem and not the container's own layer, and that each can be written. It also checks that the data root's filesystem implements `flock`, that no other run holds the lock, and that `run_logs/` can contain the pipeline execution state. An empty data root is a first start, not a problem. A directory that is not a mount is reported alone, and so is a read-only data mount, because the later checks write into the mount. Over a broken mount, the later checks would report on the mount, not on what they check. `flock_works`, for example, would report a filesystem without `flock`, with a remedy that does not help. The checks are one function, not a sequence of checks inside `main`, so that the tests call every check through it. If each check were tested only on its own, deleting the call of a check would break no test. A check for the directory's existence alone is not enough. The entrypoint writes into `handover/` only once, at the end, and a read-only mount there would pass every other start check and lose the handover of a run that had already taken days.
- **Free space.** Keep at least <!--s:parameters.agentcontext.runner.MIN_FREE_DISK_GB-->190<!--/s--> GiB free on the volume. When a step that clones is pending or can become pending and the volume has less free, the runner refuses the start in its pre-checks. A step that clones can become pending when a pending step before it writes a file that it reads. The cloning step, for example, can become pending after an image that changes the labeling, because the labels decide the list of the repositories that the cloning step collects. A Start after such an image update therefore needs the whole minimum also after the collection has ended. Without such a step, the runner refuses a start below that minimum less the <!--s:collection.max_scratch_gib-->160<!--/s--> GiB of the clones in flight ([the runner](runner.md#pre-checks)). The cloning step measures the same minimum again as it runs. Below the minimum, the step starts no further clone, lets active clones finish and exits 3. What the run keeps is small compared with that minimum: the retrieval and the sampling frame, the cache of labels, the collected and validated trees, the output CSVs, the release archives and the figures. The scratch directory contains the clones in progress, each bounded at <!--s:parameters.agentcontext.git.bounds.DEFAULT_MAX_BYTES-->32<!--/s--> GiB, <!--s:parameters.agentcontext.steps.repository_cloning.workers_default:words-->five<!--/s--> at a time by default, which is <!--s:collection.max_scratch_gib-->160<!--/s--> GiB at most.
- **Credentials.** Write an OpenRouter API key for DeepSeek V4.1 Flash, the default model of the
  classification, and GitHub access tokens with read access to public repositories, into
  `credentials.csv` beside `compose.yaml`, one per row under `service,account,credential`. When a
  pending step needs either credential and the pre-checks find none, the runner refuses the run.
  The pre-checks treat the steps that an earlier step of the run can make pending the same way,
  such as the labeling of a monthly run, which becomes pending once the GHS download has taken a
  new retrieval. They try the GitHub access tokens in order, starting with `GITHUB_TOKENS` and
  `GITHUB_TOKEN` when they are set, and log a warning for each GitHub access token that GitHub
  rejects with HTTP 401. When a check cannot reach GitHub, or GitHub returns a server error or a
  rate limit for it, the pre-checks repeat the check after pauses. They keep a GitHub access token
  that never gets a verdict, with a warning. Repository cloning and the file history step use only
  the first GitHub access token that passes or is kept, and the log names its position. If GitHub
  rejects all of them, the pre-checks fail, and no step runs. Collection does not rotate GitHub
  access tokens during an active step. When the labeling is pending or can become pending, the
  pre-checks read the credit of the first OpenRouter API key for the labeling's OpenRouter model
  through a request that spends nothing, and the runner refuses the start when OpenRouter rejects
  the key. A key without credit gives a warning, because the labeling waits for credit, and the
  pipeline execution state shows such a wait under `running_step_status` ([Monitoring a run](#monitoring-a-run)). A server
  error, a rate limit or a timeout gives a warning.

The cost of a collection depends on the sample, the available history, the network and the
machine. Each repository's line in `finished_repositories.jsonl` contains the measured duration
and size of its clone, of the fetch of its history and of the reading of its commit history. Use
measurements from comparable inputs to estimate capacity. The configured minimum of free space
remains a separate bound on whether the collection can continue.

## Pre-deployment checks

Before you start a collection, verify the code and the inputs intended for that run:

1. Refresh the SPDX license list and review what changed. In `1_sampling/`,
   `python3 4_filter_ghs.py --refresh-spdx` names every license for which the current list
   adds or withdraws OSI approval, and exits 2 when it finds one. Filter the latest retrieval and
   run `python3 4_filter_ghs.py --check-licenses` in a scratch data root, with
   `AGENTCONTEXT_DATA_ROOT` set for both commands, as the
   [sampling stage](../1_sampling/0_README.md#4-filter-the-retrieval-repository_filtering)
   lists them. The checkout then keeps the tracked sampling frame and
   `data/sampling/ghs_licenses.csv`. The verification of step 3 stops on a sampling frame that
   differs from its archive and fails on a license table that differs from its committed version.
   Record each license that the check names in
   `1_sampling/config/licenses.csv` with its reason, source and date. The image contains the
   list, and the filter of a run on the NAS uses it.
2. Check the crawl dates of GHS. In `1_sampling/`, `python3 1_download_ghs.py --dry-run
   --sampling-frame /nonexistent/sampling_frame.csv` logs the crawl date of each language and counts
   the matching repositories, without downloading or writing anything. It exits 1 when a request
   or a check fails, such as when GHS returns no response. With a path that does not
   exist, the dry run reads no previous sampling frame, as in a clean run in a new project folder,
   and names each language that the download of such a run leaves out of the end date. That download
   exits 1 when a language that the filter
   would keep has a crawl date more than
   <!--s:parameters.1_sampling.config.ghs_download.window.max_crawl_lag_days-->30<!--/s--> days old
   at the first Start. When a language that the filter would keep is close to the limit, raise `window.max_crawl_lag_days`
   in `1_sampling/config/ghs_download.yaml` before you build the image, or plan to start the run
   with `--step-arg ghs_download:"--end-date YYYY-MM-DD"` ([A run every month](#a-run-every-month)).
3. Run the full verification on the committed revision. Follow the platform instructions
   in [development.md](development.md).
4. Run the [collection test on local Git mirrors](tools/mirror_run.md). It covers stop and
   resume, the expected incomplete reclassification after an injected history failure, and the
   repair of the file history from the full mirror. After the injected failure, the run continues
   through the publication as the runner does. Inspect every output difference against the
   reference run. A file of expected findings applies only to its own input and revision. Review
   the differences again when either changes.
5. Process a working copy of the latest complete handover with the
   [commands after the collection](development.md#continuous-improvement-from-handovers).
   Inspect every coverage outcome and correct the processing defects. Record separately the
   outcomes that you expected from missing inputs. The review does not reconstruct the input.
6. Build the production image and the NAS bundle from the verified revision. Record their
   dates and checksums. Verify the downloaded archives, compare their checksums with the build
   outputs, and check the commit embedded in `BUILD_INFO.txt`. Reject an unexpected commit or
   a `-dirty` build. Load the image and check with `--list` ([Deployment options](#deployment-options)) that it lists
   the intended steps.

Repeat the affected processing and builds when their code, heuristics or inputs change. After
these checks pass, use a new project folder to collect the whole sample again with the current
format of the evidence. You decide when to deploy and when to start the container.

## Get the image and the bundle

The `container image` workflow, run by hand from the Actions tab on any branch or by a `v*` tag, uploads two workflow artifacts. `agentcontext-image` contains `agentcontext-pipeline.tar.gz` and `BUILD_INFO.txt`, and `agentcontext-nas-bundle` contains `agentcontext-nas-bundle.zip`. Each workflow artifact downloads as a zip, and you have to unzip the bundle twice. On a laptop with Docker, `bash deploy/build_image.sh` and `bash deploy/make_nas_bundle.sh` write the same three files into `deploy/`.

The tarball uses the older docker-save layout on purpose. DSM's Docker imports the OCI layout that Docker Desktop writes without its tag, and compose then fails with `No such image`. `build_image.sh` rewrites the layout and checks that the tag is still there after a load. The image runs the git, the rsync and the 7-Zip that `mise.toml` pins, conda-forge's packages of git and rsync and the `7zz` of the 7-Zip release, which `deploy/install_tools.sh` installs with mise and every development machine runs through `mise exec` too. The cloning step takes over a repository only from a collection under the same `git --version`, so a new pin means that the next run collects the whole sample again. The image installs the Python distributions of the dependency lock `locks/pipeline.txt`, each at the version and with the hashes that the dependency lock lists, the versions that CI tests and that every development machine installs ([Python environments](development.md#python-environments)). pip installs them in hash-checking mode into the interpreter of the base image and refuses a distribution that the dependency lock does not list. The base image is the release of Python that `mise.toml` pins, the release of CI and of every development machine, named by digest, so that every build of a commit starts from the same interpreter and the same pip. Docker pulls the digest without reading the tag, so `deploy/install_tools.sh` fails the build when the interpreter of the base image is another release than the one that `mise.toml` pins, and `BUILD_INFO.txt` names the release that the interpreter of the built image reports.

Identify a build by the `commit` line of `BUILD_INFO.txt`. The entrypoint logs the same record as the container's first log line. The log of a run therefore names the commit of the code that produced the run, with `-dirty` when an input of the image, including `deploy/Dockerfile`, differed from the commit at build time. The `data_root_revision` line of `BUILD_INFO.txt` contains the image's data root revision, and the first log line names it too. From that line, you can tell before an import whether the runner of the image resumes the run in a project folder ([Restarting and updating](#restarting-and-updating)).

## The project folder

`/docker/agentcontext/`, unpacked once from the bundle, contains:

| Path | Role |
|---|---|
| `compose.yaml` | Read by Container Manager. Comes from the bundle on every deployment |
| `credentials.csv` | Written by you from `credentials.csv.example`: the header `service,account,credential` as the first line, then one GitHub access token or OpenRouter API key per row ([credentials](credentials.md#the-file)), mounted read-only. Never in the bundle |
| `deploy.md` | This file, the runbook |
| `data/` | Mounted read-write as the data root. Empty in the bundle. The run writes everything there: `sampling/` the retrieval and the sampling frame, `classification/` the cache of labels and the sample, `collection/` the collected and validated trees, the output CSVs, the caches and the release, `analysis/` the figures and tables, and `run_logs/` the pipeline execution state and logs |
| `handover/` | Mounted read-write. When the runner ends, the entrypoint packs the handover into it, one archive of everything that a checkout needs, which is the file to download |

The bundle contains `data/` and `handover/` with only a `.keep` file each, because Container Manager refuses to create a missing bind-mount source when the project is created.

The image contains the code of the five stages, the heuristics and the entrypoint, and the data is mounted. Neither the image nor the bundle contains data. The entrypoint never copies anything out of the image into the mounts. Editing the project folder changes nothing that a run does, and a new image changes nothing in the project folder. The mining project mounts its pinned `input/`, and this deployment mounts its data root. [Key decisions](#key-decisions) gives the reasons.

Never unpack a bundle over a project folder in use. The bundle contains no data, but its `compose.yaml` and this runbook belong to the image that it was built with. To update the code, import a new image, copy `compose.yaml` and this runbook out of the bundle of the same build, and build the project, as [Restarting and updating](#restarting-and-updating) describes. Container Manager keeps the `compose.yaml` of the project folder when you import an image, and `docker start` starts the container that Container Manager created from that file. `compose.yaml` therefore sets its revision in `AGENTCONTEXT_COMPOSE_REVISION`. Under a `compose.yaml` of another revision than the image requires, the entrypoint runs no step and logs one ERROR line that names the file to copy.

## Import, create, start

Every instruction in this runbook to start or stop the container, to build the project or to read the log means one of these actions in Container Manager:

- **Start.** Open Container in the left menu, select `agentcontext-agentcontext-1`, then choose Action, Start. Container Manager runs `docker start agentcontext-agentcontext-1`, which is also the command of the scheduled tasks in [A run every month](#a-run-every-month). Each start of the container is a Start: The entrypoint starts the runner over the five stages and packs the handover when the runner ends.
- **Stop.** Open Container in the left menu, select `agentcontext-agentcontext-1`, then choose Action, Stop. Docker sends `SIGTERM` to the entrypoint, and [Restarting and updating](#restarting-and-updating) describes what the entrypoint and the runner then do.
- **Build.** Open Project in the left menu, select the project, then choose Action, Build. Synology documents Build as `docker-compose up --build --no-start` ([Container Manager, Project](https://kb.synology.com/en-global/DSM/help/ContainerManager/docker_project?version=7)): Container Manager creates the container again from the `compose.yaml` of the project folder and the image `agentcontext-pipeline:latest` when either changed, and does not start it. A new image and an edit to `compose.yaml` take effect only through a Build ([Restarting and updating](#restarting-and-updating)). Wherever this runbook says to build the project, start the container after the Build.
- **The log.** Open Container in the left menu, select `agentcontext-agentcontext-1`, choose Details, and open the Log tab. It shows the lines of the entrypoint, the runner and every step as they run. `data/run_logs/<step>.log` in the project folder keeps the lines of each step.

To begin the first run:

1. Upload `agentcontext-pipeline.tar.gz` and the unpacked bundle to the machine. The bundle's `agentcontext/` folder becomes `/docker/agentcontext/`, which has to be empty or absent before you upload the folder. Write `credentials.csv` in that folder from `credentials.csv.example`: Keep the header as the first line, and remove the `#` of each example row that you fill in. A `credentials.csv` written from an earlier example begins with comment lines, which you delete, because the header has to be the first line.
2. Container Manager, Image, Import, Add from file: `agentcontext-pipeline.tar.gz`. Container Manager imports the image as `agentcontext-pipeline:latest`, and a later tarball under the same tag replaces it.
3. Container Manager, Project, Create, path `/docker/agentcontext`, under any project name. Container Manager reads `compose.yaml` from that path. Choose Next, then Done, and choose to start the project when the wizard offers it. Container Manager builds the project from the file and starts the container, and this start is the run's first Start. If you did not choose the start, start the container as above. The project's name does not matter, because `compose.yaml` names the container `agentcontext-agentcontext-1`, the name that the scheduled tasks start ([A run every month](#a-run-every-month)). Docker refuses a second container of that name, and the machine therefore holds one project from this file at a time.
4. Read the log. An ERROR line right after the build record that names `compose.yaml` or the container's local time means that the project's `compose.yaml` is not the one from the image's bundle. An ERROR line that names the data root's revision means that an image of another data root revision began the data root and that this image cannot convert that revision. In each case the entrypoint ran no step ([Recovery from handover and storage errors](#recovery-from-handover-and-storage-errors)). Otherwise the first lines are, in order:
   - the build record with the image's data root revision
   - the line about the credentials
   - after a Stop, a kill or a reboot that left clones in `data/collection/_scratch/`, an interrupted GHS download, or a partial archive or checksum file in `handover/`, the line `Removed what killed processes left (...)`, which names what the entrypoint removed
   - at the first Start of an image over a data root of an earlier data root revision that the image converts, the line `Converting the data root /app/data from revision ... to revision ...`, and then the line `Converted the data root /app/data from revision ... to revision ...`, which names the stored files that the conversion rewrote ([Restarting and updating](#restarting-and-updating))
   - a warning when `command:` still names an argument for one Start that the run of an earlier Start used ([Deployment options](#deployment-options))
   - the line `Calendar months are counted in ...`, which has to name the NAS's zone
   - at the first Start over an empty data root, the line `Recorded revision ... of the new data root ...`, which names the image's revision, <!--s:parameters.deploy.entrypoint.DATA_ROOT_REVISION-->3<!--/s--> for the image of this runbook, and `run_logs/data_root.json`
   - the machine line
   - the line about the heuristics files of the image
   - the `Running` line with the runner's command
   - the lines of the pre-checks

   When the runner has ended, the last lines name the handover and its size.

To resume a run, start the container. To resume it with a new image of the same data root revision, or of a later revision that converts the data root, import the image, copy `compose.yaml` and this runbook from its bundle, build the project and start the container, as [Restarting and updating](#restarting-and-updating) describes. At that Start, the runner resumes the run. For a fresh collection, and for a new image that cannot convert the revision of the data root, follow [A clean run](#a-clean-run).

DSM shows the notification "Container stopped unexpectedly" on any exit of a project container, including a clean end. Read the last lines of the log before you treat the exit as a failure. The line `The runner exited N (...)` gives the runner's exit code, and [The stop rule](#the-stop-rule) says what to do for each code.

## Steps in order

Each path is relative to the data root, `data/` in the project folder. A path of a collection or publication step is relative to that stage's directory, `data/collection/`.

| Step | What it writes |
|---|---|
| `ghs_download` | `sampling/ghs_retrievals/`, a retrieval of GHS, and `sampling/ghs_retrieval.json`, the pointer to it. At a later Start, the runner adopts them from disk ([refresh](refresh.md)) |
| `github_query` | GitHub's response for every repository in the retrieval, in `sampling/ghs_retrievals/` |
| `retrieval_comparison` | `sampling/ghs_changes.csv`, `ghs_collection_changes.csv` and `ghs_changes.json`, the differences from the previous retrieval |
| `repository_filtering` | `sampling/ghs_filtered.json`, the sampling frame |
| `repository_labeling` | The cache of labels `classification/labels/`, with the cost record of the run in USD, `<id>.cost.csv`, `classification/repos_annotated.csv` with its record `repos_annotated.json`, `repos_excluded.csv` and `label_changes.csv` |
| `engineered_project_selection` | `classification/repos_annotated_included.csv`, the sample list |
| `repository_cloning` | `data/collected/`, one directory per repository that has a path pattern, with `repos.csv` and `clone_failed.csv`; the three caches; `finished_repositories.jsonl`, one line per finished repository and one per retry before it starts; `collect_commits/` and `output/all_ai_commits.csv` with `other_ai_commits.csv`, the unmatched attributions, the mentions and `ai_commits-repos.csv` beside it; `data/workflows/`, `data/file_lists/` and `data/imported/`, the files that the imports reach. The step exits 3 when free space falls below the minimum and 4 when a failure ceiling is exceeded. The log shows either code in the `ERROR runner: Repository cloning exited N after ...` line, while the container exits 1. After either code, the runner resumes the step at the next Start |
| `commit_reclassification` | The commit CSVs, unmatched attributions, mentions, `ai_commits-repos.csv`, AI columns and the `#commits` of `file_history.csv`, reclassified from the kept evidence. Before the step reuses a current classification, it validates the provenance, the revision, the checksums and the coverage of the paths. `output/commit-reclassification.json` lists every requested repository and whether its evidence is complete. The step exits 0 with incomplete evidence that the cloning step accepts: the histories that the time bound or the size bound stopped, and other repositories up to the cloning step's ceiling. It exits 2 above that ceiling, and 1 when an input is missing or the assembly fails |
| `collected_file_cleanup` | `data/validated/` and its `repos.csv`, and `deletion.csv` |
| `detection` | `output/repos.csv` and the mechanism CSVs, with the git and AI columns joined from the caches. Also `output/all_ai_commits.csv`, restricted to the published repositories |
| `file_history` | The output CSVs again, with every row filled for which the cache had no values. After a collection, no such row remains |
| `import_detection` | `output/imports.csv`, the imports of the configuration artifacts with what each reaches in `data/imported/` |
| `output_cross_check` | `output/consistency-report.csv` |
| `unmatched_paths_report` | `output/unmatched-paths.csv`, the path globs in `other.csv` and in the repositories that the cleanup dropped that no heuristic explains. Exits 0, because the threshold belongs to the check run by hand and to CI |
| `deleted_files_report` | `output/deletions.csv`, the rows of `deletion.csv` per reason and repository, the files that the repositories dropped by the cleanup still contained, and what its assertions found. Exits 0 with a `WARNING` that names a failed assertion, where the command run by hand exits 2 |
| `collection_summary` | `output/snapshot.json`, regenerated from the current collection and outputs, including commit reclassification coverage |
| `commit_attribution_validation` | `output/all_ai_commits-validated.csv`. Exits 2 when a row of the commit CSV differs from the result of the current heuristics over the columns that the CSV stores |
| `unmatched_commits_report` | `output/unmatched-commits.csv`, the attributions that no commit heuristic explains, ranked. Exits 0, because no threshold exists that a real collection could meet |
| `collected_files_archive` | `release/repos_data.7z` |
| `release` | `release/`: the joined CSVs, the compressed CSVs, `imported_files.7z`, `deletion.csv.7z`, the <!--s:parameters.agentcontext.steps.release.RELEASE_FILES.heuristics_files:words-->thirteen<!--/s--> heuristics files, the provenance records, the records of the collection, the checksum manifest, the README and the citation file |
| the analysis steps | `analysis/rq2/`, `analysis/rq3/` and `analysis/dataset/`, the figures and tables, and then the reproduction check over them |
| the handover | `handover/agentcontext-handover-<time>-<outcome>.7z`, which the entrypoint packs after the runner exits. After every step finished, the entrypoint packs `-complete` with the whole data root without the clones in progress, when the handover volume has twice its size free and no Stop arrived before the packing. Otherwise it packs `-complete-without-sample` with the files that it packs after a Stop. After a Stop, that archive has no `-trees` companion and no record, and the entrypoint packs the data root at the next Start. At a Start that skipped every step, the entrypoint packs nothing when `run_logs/complete_handover.json`, the record of the last handover of a completed run, contains a `-complete` archive packed after the last start that ran a step finished, even after you deleted that archive. Without room for the data root, it also packs nothing at such a Start when the record contains a `-complete-without-sample` archive packed after that time. After a Stop, a failed step or a killed runner, the entrypoint packs `-stopped`, `-failed` or `-killed` with the pipeline execution state and logs and the data of the sampling, classification and analysis stages, without a download that the Stop interrupted, which the runner downloads again at the next Start. Of the collection, that archive contains `finished_repositories.jsonl` with the record of the collection in progress, the collected and validated lists, the caches, the output CSVs, `deletion.csv`, `data/workflows/` and `data/imported/`. The entrypoint then packs the collected and validated trees into a second archive, `-trees`, when the handover volume has room for them and no `-trees` archive in `handover/` contains them unchanged, according to `run_logs/trees_handover.json`. The sample stays in the project folder until a run completes. No archive contains a directory named `@eaDir`, which DSM writes. After a start that the runner refused before any step ran, the entrypoint writes no handover, and a killed container writes none either. A `SIGKILL` during the packing leaves a `.partial` file, which is not an archive. At the next Start, the entrypoint removes it before it measures the free space of the handover volume. Beside each archive, the entrypoint writes `<archive>.sha256` with the archive's SHA-256, which the log also names |

`docs/runner.md` describes each step and every option that the runner takes.

## Monitoring a run

The pipeline execution state and logs are under `data/run_logs/` in the project folder, `/docker/agentcontext/` in File Station, and each stage's files are in its directory under `data/`. The collection's paths below are relative to `data/collection/`:

- `data/run_logs/state.json`: which steps completed, the outcome and duration of each, and the command. While a step waits for something that a person has to do, as the labeling waits for credit, `running_step_status` names the service, the reason, what to do and since when, and the key is gone once the wait ends, the step ends or the next start begins. The runner writes it with the outcome `running` just before the first step of a start that it does not skip, and after every step. The file describes a run as of the last step that ended. The runner syncs each new version of the file to the disk before it replaces the file, and after a power loss the file holds the previous state or the new one. When the runner was killed inside a step, the file contains the outcome `running`, and the container's log shows that the runner was killed. Its `git_sha` and dirty flag come from the checkout, or from `/opt/pipeline/BUILD_INFO` in an image, and the commit is null only when neither source provides it. The container's first log line also names the build commit.
- `data/run_logs/complete_handover.json`: the name of the last handover of a completed run that the entrypoint packed, with the `last_steps_finished_at` of the pipeline execution state that the handover contains. The time is null when that state has none. A state that a runner without this field wrote has none until a start runs a step. At a Start that skips every step, the entrypoint packs nothing while the record has the time that the state has, or null while the state still has none, whether or not the archive is still in `handover/`. After a packing that failed, the entrypoint writes no record, and it packs at the next such Start. The entrypoint syncs the archive to the disk before it renames the archive, and the record before it renames the record. After a power loss, the record therefore never contains the name of an archive with bytes that were lost. At a Start that begins the next monthly run, the entrypoint packs the data root first when neither the record nor a packing earlier in the same Start provides a `-complete` archive of the previous run ([A run every month](#a-run-every-month)). It does the same at a Start with a `command:` that names a `--from` that no run has used, when one such `--from` names a stage or step before the analysis stage and the release step is done in the data root. To make the entrypoint pack the data root again at the next such Start, delete the file.
- `data/run_logs/data_root.json`: the data root revision of the data root, and the build record of the image that began it or last converted it. After a conversion, `converted_from` holds the revision and the image that the data root was converted from. At the first start over a data root without a pipeline execution state, the entrypoint writes the file before the runner starts. It writes the file again only after it has converted the data root from an earlier revision. Over a data root with a record of a revision that the image neither has nor converts, or with a pipeline execution state and no record, the entrypoint runs no step. Its ERROR line names the image in the record, and importing that image resumes the run ([Restarting and updating](#restarting-and-updating)).
- `data/run_logs/data_root_conversion.json`: during a conversion of the data root, the stored files that the converted files beside them still have to replace. The entrypoint removes the file once the converted files have replaced the stored files, and a start after a kill finishes the replacement first.
- `data/run_logs/trees_handover.json`: the name of the last `-trees` archive that the entrypoint packed, with a fingerprint of the entries that it contains: the path and the kind of each, the size and the modification time of each file, and the target of each link. At a Start that would pack the collected and validated trees, the entrypoint packs nothing while the trees have that fingerprint and the archive is in `handover/`, and the log names the archive. When Starts fail one after another, such as in a step of the analysis stage, the entrypoint therefore packs the trees once. It packs the first archive at every such Start, because that archive contains the pipeline execution state and the logs that the Start wrote. The time of a directory is not part of the fingerprint, because DSM changes it when it writes an `@eaDir` into the directory.
- The log ([Import, create, start](#import-create-start)) shows every step's output as it runs, and `data/run_logs/<step>.log` keeps the same lines. During the cloning step, an `INFO repository_cloning:` progress line appears after every <!--s:parameters.agentcontext.guards.PROGRESS_EVERY-->100<!--/s--> finished repositories, and also when a repository finishes more than <!--s:parameters.agentcontext.logs.PROGRESS_SECONDS.minutes:words-->ten<!--/s--> minutes after the last line. It gives the done and total counts, the ok and failed counts of this run, repositories per minute, the elapsed time, the time left at that rate, and the container's process and zombie counts. Fetching one repository's history or reading its commit history can take longer than that interval, and nothing prints while either runs.
- `finished_repositories.jsonl`: one line per finished repository, and one line per retry of a recorded repository, written before the retry starts. To measure the progress against the current sample list, read the latest line of each repository, because the retry lines make the count of lines misleading. When a collection begins, the cloning step keeps only the lines that the steps read, and the log says how many of them it kept ([the cloning step](steps/repository_cloning.md)). Before 2.0.0, the project folder kept its data in `1_sampling/`, `2_classification/` and `3_data-collection/`, with this list as `collect_finished.jsonl`. `compose.yaml` mounts only `data/` and `handover/`, and a Start over such a folder therefore begins a new run in `data/` and reads none of the earlier files ([A clean run](#a-clean-run)).
- `data/collected/clone_failed.csv`: the repositories with a failed clone, with the outcome, rewritten from `finished_repositories.jsonl` when the step ends.
- `output/ai_commits-repos.csv`, after the cloning step: one row per repository with the clone outcome, the commits read and the commits matched.
- Three records that the run keeps to improve the heuristics and the bounds afterward, which no step reads: `data/file_lists/`, every repository's file list at the collected commit, including the repositories from which the step copied nothing; `output/all_ai_commits-mentions.csv`, the lines naming one of the six tools in commits that no heuristic matched, grouped by phrasing; and the `measures` of each line of `finished_repositories.jsonl`, what the clone of each repository, the fetch of its history and the reading of its commit history cost in seconds and bytes. `docs/steps/repository_cloning.md` describes each. The `-complete` handover contains all three. After a run that did not complete, the entrypoint packs `finished_repositories.jsonl` and `output/` into the first archive and leaves the file lists on the volume.
- `output/deletions.csv`, after the `deleted_files_report` step, and a `WARNING deleted_files_report:` line in its log when one of the check's assertions failed: a path that the output CSVs publish and that the cleanup deleted, a `SKILL.md` that the cleanup deleted in a directory that a symlink marker of the collected tree names, or a repository directory that left the validated tree without a row. The run continues to the archive and the publication, and `docs/checks/deletions.md` says what each finding means.
- `data/run_logs/heuristics/`: the heuristics files of the image. The entrypoint copies them at every start that passes the checks, after it packed the handover of a previous run that the next monthly run replaces. The copies replace those of an earlier image, and the directory holds no file that the image lacks. `output/provenance.json` contains checksums of `config_path_patterns.csv`, `planning_document_patterns.csv`, `vendored_dirs.txt` and `local_state_paths.csv` alone. Without the copies, a handover read months later could not show which commit patterns or which of the two negatives the commits were classified under. An image built before an edit to any of these files produces data that a checkout cannot explain. The entrypoint copies the files into the run's log directory, not over the checkout's own copies, and unpacking a handover replaces none of the checkout's heuristics.
- `data/run_logs/machine.json`: the machine that the run uses, logged as one line. The entrypoint writes it at every start that passes the checks of the mounts, the lock and the directories, after the handover of a previous run that the next monthly run replaces. It contains the processor's model and count, the CPU quota of the container's cgroup, which a `cpus:` limit sets, the memory and any container limit, and the process ceilings, `pid_max`, `threads-max` and the cgroup's. It also states whether an init process is there, and contains the volume's filesystem and free space, the kernel, the image, and the versions of git, 7zz and rsync. The image installs the versions that `mise.toml` pins ([Get the image and the bundle](#get-the-image-and-the-bundle)), and git determines values in published columns. You enter nothing about the machine. You can derive the uplink from the run afterward, as repositories finished per hour since the collection started: the rows of `data/collected/repos.csv` with a `scanned_at` after the start. The name of the latest collection in the lines of `data/collection/finished_repositories.jsonl` begins with the time at which that collection started. The earliest `scanned_at` is not the start, because a repository that the collection took over keeps the `scanned_at` of the earlier collection that cloned it, which can be a month before.

## The stop rule

When the log ([Import, create, start](#import-create-start)) ends in one of the cases below, act as the case describes before you start the container again. If the container still runs, stop it first.

1. **The pre-checks failed.** The log shows `ERROR pre_checks:` lines, then `INFO pre_checks: A check failed. No step ran.`, and the container exits 1. Correct what the `ERROR pre_checks:` lines name, such as a GitHub access token or an OpenRouter API key for the labeling's default model missing from `credentials.csv`, a missing program, too little free space on the volume or a missing input. Then start the container again. Nothing needs to be reset. No step ran, and the entrypoint writes no archive for a start in which no step ran.
2. **The cloning step exited 3.** The log shows `ERROR runner: Repository cloning exited 3 after ...`, and the container exits 1. Make room on the volume until it has at least <!--s:parameters.agentcontext.runner.MIN_FREE_DISK_GB-->190<!--/s--> GiB free, such as by deleting handovers that you have downloaded and emptying the Recycle Bin ([Recovery from handover and storage errors](#recovery-from-handover-and-storage-errors)). Then start the container again, and the runner resumes the collection. The volume's free space fell below that minimum. The step started no further clone, let the clones in progress finish and recorded them.
3. **The cloning step exited 4.** The log shows a `WARNING repository_cloning:` line that names the cause, then `ERROR runner: Repository cloning exited 4 after ...`, and the container exits 1. The step stops the collection for one of these causes:
   - the connectivity probe failed, and failed again after each of its waits, which last up to <!--s:parameters.agentcontext.guards.PROBE_WAITS.4.hours:words-->four<!--/s--> hours
   - repeated `collector_error` outcomes
   - a worker that ended unexpectedly
   - missing commit logs that should have been kept
   - remaining retries above the configured ceiling

   Read the warning and the clone logs under `data/collection/clone_logs/`, one `clone_logs/<owner§repo>.log` per repository, and correct the cause that they report. Then start the container again. When the runner resumes the collection, the cloning step retries `clone_failed`, `collector_error`, and the outcomes of a repairable history or a missing directory. Check authentication and connectivity when Git's error names either problem. A successful probe does not explain individual clone failures. A worker exit does not establish an out-of-memory kill, so inspect the container's memory and process limits and the OS logs before you change the number of workers. A `collector_error` comes from an operation after the clone and includes its traceback.

   The line `N repositories remain to collect again` names the incomplete repositories. The line `No head commit from git for N repositories` names the repositories that the step kept with their earlier collection, because git returned no head commit for them. When the step resumes the collection, it queries their heads again. Before the step keeps more of them than the ceiling allows, it waits and queries them again in <!--s:parameters.agentcontext.reuse.HEAD_WAITS.length:words-->six<!--/s--> rounds, with `INFO repository_cloning:` lines that name each wait ([the cloning step](steps/repository_cloning.md)). A refusal by GitHub, `not_found_or_no_access`, `dmca_takedown` or `disabled_by_github`, stays recorded as unavailable. A `FILE_LIST_ERROR` warning alone does not stop the collection. It means that Git could not list the committed paths at HEAD. That repository then has no saved inventory or submodule metadata, and its clone log keeps the command and Git's error.
4. **Another run holds the run lock.** An ERROR line of the entrypoint or the runner begins with `Another run holds` and names the holder of `run_logs/run.lock`. Another container of this project folder is already running. Find it in Container Manager, Container, and stop it or let its run end before you start this container again. The refused start ran no step, and the entrypoint wrote no archive for it.
5. **`ERROR runner:` names a step that takes a snapshot and the `--from` that repairs it.** The line begins with `'<later step>' modified the output of '<snapshot step>' in place on an earlier run` and ends with the `--from` that produces the output again, and no step ran. Put that `--from` in `command:` for one Start ([Deployment options](#deployment-options)), then build the project. A pending step would read an output that a later step has modified in place, and the step that produced the output takes a snapshot, which the runner does not take again on its own. No step of the shipped lists modifies a snapshot.

   The `INFO runner:` line `'file_history' modified the output of 'collected_file_cleanup' in place` needs nothing from you. The file history step deletes from `data/validated/` the directory of a repository that git reports as gone. At a Start that runs the detection or the file history step again over the pruned tree, such as after a new image that changes either step, after a failed file history step or with `--from detection` in `command:`, the runner runs the collected file cleanup again first and logs that line. The cleanup rebuilds the validated tree from the untouched collected tree, and the steps after it run again without a clone. Such a Start needs nothing in `command:`. After a failure or a Stop between the file history step and the archive, the runner resumes without a rebuild, because the archive step reads the pruned tree in every run.
6. **Exit 143 or 130.** The container exits 143 or 130. These codes stand for SIGTERM and SIGINT, normally a Stop and Ctrl+C. Start the container again, and the runner resumes the run.

   Exit 137 stands for SIGKILL and exit 129 for SIGHUP. Neither code shows why the signal was sent. Before you attribute a SIGKILL to exhausted memory or reduce the workers, check whether the kernel's out-of-memory killer ended a process. In an SSH session on the NAS, `sudo dmesg | grep -i -e 'out of memory' -e 'killed process'` lists such kills, and `sudo docker inspect --format '{{.State.OOMKilled}} {{.State.ExitCode}}' agentcontext-agentcontext-1` prints whether Docker recorded one for the container. Container Manager, Log in the left menu, lists all activities of Container Manager ([Container Manager, Log](https://kb.synology.com/en-global/DSM/help/ContainerManager/docker_log?version=7)). When the runner dies from an unhandled signal, the entrypoint ends its process group and packs a `-killed` handover. The state file in that handover may describe an earlier completed step, so keep the container log. When the whole container is killed, the entrypoint may write no archive at all. A step's own exit 3 or 4 appears in the runner's error line about the step, while the container exits 1.
7. **A step failed.** The log shows an `ERROR runner:` line about a step, such as `<name> exited N after ...s. Its log is /app/data/run_logs/<key>.log.`, `<name> exited 0 after ...s but did not write ...` or `Could not open ..., the log of <key>`, and the container exits 1. `<name>` is the step's name in the log, such as `File history`, and `<key>` is its key, such as `file_history`. To resume the run:
   1. Read the step's log, `data/run_logs/<key>.log` in the project folder, which File Station shows under `/docker/agentcontext/data/run_logs/`. The same lines are in the container's log above the ERROR line. If the runner could not open or write the step's log, that file may be absent or left from an earlier attempt, and the current error is only in the container's log.
   2. Read the last recorded result in `data/run_logs/state.json`.
   3. Correct the cause that the log reports, such as a full volume, a credential in `credentials.csv` or the network. A defect in the code or the heuristics requires a new image: Update as [Restarting and updating](#restarting-and-updating) describes, and at the Start after the Build, the runner runs the failed step under the new image.
   4. Start the container again, unless the update in step 3 has already started it. The runner skips the steps recorded complete and runs the failed step again, then the steps after it that are pending.

   When the failed step is a step of the analysis stage after the release step and the next month is due, the entrypoint begins the next monthly run at that Start instead of running the failed step again. [A run every month](#a-run-every-month) describes this case and how to finish the failed analysis.

   The runner records a step only when the step finishes, and a failed step therefore stays pending. The entrypoint packs a `-failed` handover with the state, the logs, the caches and the output CSVs. It packs the `-failed-trees` companion only when the storage allows it. The collected and validated trees, the clone logs and the commit shards stay in the project folder.
8. **The file history step failed on a row with a blank `created_at`.** The log of the file history step shows a line `FAIL N measured row(s) of <file> have a blank created_at, ...`, followed by `ERROR runner: File history exited 1 after ...`. Start the container again. By default, the file history step measures a row again when the cache records it blank, and the runner resumes and repairs such rows without anything in `command:`. `verify_tables` fails a row that has `#commits` and `last_commit_sha` and not `created_at` and `first_commit_sha`. `git log --follow` produces such rows, with exit 0, for a path that a merge added and that neither parent contained, and the history query falls back to the exact query there ([git](git.md)). A clean run empties the volume first, as [A clean run](#a-clean-run) describes.

## A clean run

In a later run over the same project folder, from a step of the sampling or the classification
stage or from `repository_cloning`, the cloning step takes over each repository that has an
unchanged head commit and that the current collector, git, path heuristics and import heuristics
would collect the same way. It clones the others, including the repositories new to the sample. The step's
`Took over` line gives the count, and the line after it gives the reasons
([the cloning step](steps/repository_cloning.md)). After a change to the collector's code, the
run collects again the repositories that the change reaches, as `agentcontext/code_versions.py`
declares them, and every repository of a version of the code that the file does not name. After
a change to the format of the commit evidence, the run collects the whole sample again without a
new folder. With `--step-arg repository_cloning:"--fresh"`, the cloning step clones every
repository in any case, in its first run after you add the argument ([Deployment options](#deployment-options)). For a
clean run, use the command shipped in `compose.yaml`.

For the next full collection, keep the handover of the previous collection and its working
copy apart. Use a new, empty project folder with the verified image and bundle, and do not
restore earlier completion records or collected trees into it. If you reuse the existing project
folder, follow these steps:

1. If you still want the record of the previous run, download the archives in `handover/` in
   File Station and export the log ([Import, create, start](#import-create-start)). Deleting the folder deletes them.
2. Container Manager, Project, the project, Action, Delete. Then delete `/docker/agentcontext/`
   in File Station, including `credentials.csv`. The Recycle Bin of the shared folder keeps the
   deleted folder, with the data root and the archives, in its `#recycle` folder and frees none
   of their space. Empty it in Control Panel, Shared Folder, the shared folder of the project
   folder, Edit, Empty Recycle Bin. A snapshot of the shared folder keeps the space until its
   retention ends.
3. Import the new image and unpack the new bundle as [Import, create, start](#import-create-start) describes, write
   `credentials.csv` again, and create the project. The data root is empty, and at the Start that
   Container Manager makes when it creates the project, the runner runs every step from the
   download of the retrieval on, because the volume holds no record of a completed step.

A NAS that ran the pipeline before the dataset was renamed has the project folder
`/docker/agentconfigs/`, the container `agentconfigs-agentconfigs-1` and the image
`agentconfigs-pipeline:latest`. A new bundle leaves all three in place. Download that folder's
`handover/` and the container's log. Then delete the project, the folder, with the Recycle Bin
emptied as in step 2, and the image. In Control Panel, Task Scheduler, change every task that
starts `agentconfigs-agentconfigs-1` to start `agentcontext-agentcontext-1`. Until then, those
tasks start the old image over the old folder, and the new container gets no monthly Start.

A clean run needs no argument in `command:` beyond the shipped one, and neither does a run after
a change to the path heuristics, to the import heuristics, to the collector or to the sample list.
The runner records `repository_cloning` by a checksum of `data/collected/` and by these inputs and
the version of git, and at a Start after a change to any of them but the version of git alone, it
runs the step without an argument. The step then takes over the repositories that the change does
not reach and collects the others. The runner logs the inputs that changed, such as `The path
heuristics changed since repository_cloning ran`, or `An input of repository_cloning (...) has
changed` where its record names no digest of each input. After a change of the version of git
alone, the runner keeps the step with a `WARNING`, because the step would collect every repository
again, and `--from repository_cloning` in `command:` for one Start runs it.

## A run every month

A Start ([Import, create, start](#import-create-start)) does not by itself begin a new month's run. The runner skips
every step that a run completed with the same code, and after a completed run it would run
nothing again. At each Start, the entrypoint's `monthly_argv` decides what the run does. The next
month is due when the current calendar month is later than the month in which the last run's
GHS download started, both in the NAS's local time (`next_month_due`):

- The last run completed and the next month is due: the entrypoint begins the next month's run.
  It adds `--from ghs_download --from repository_cloning` to the command and logs the reason.
  The download takes a new retrieval with a window that ends on the oldest crawl date of GHS's
  languages. The classification labels what the new sampling frame adds or changes and reuses
  the other labels. The cloning step takes over the repositories with an unchanged head commit
  and clones the others. `--from repository_cloning` is needed as well, because a download that
  falls back to the previous sampling frame leaves the sample list unchanged, and the
  repositories with a changed head commit still have to be collected. The next run replaces the
  sampling frame, the labels, the collected and validated trees and the release of the completed
  run. Before the runner starts, the entrypoint therefore packs the data root when
  `run_logs/complete_handover.json` contains no `-complete` archive of the completed run, because
  the packing at its end failed or the data root did not fit on the handover volume. It packs
  before it writes the machine record and the copies of the heuristics files of this Start, so
  that the archive contains those of the completed run. When that packing fails, or the data root
  still does not fit, the entrypoint begins no new month, logs an error that names which of the
  two happened, and exits 1. After a Stop, it starts no packing, exits `128 + signal`, and packs
  at the next Start.
- The last run failed in a step of the analysis stage after its release step completed, and the
  next month is due: the entrypoint logs a warning that names the step of the previous month's
  analysis that failed. It begins the next month's run as after a completed run, because the
  collection and the release of the failed run are done. Without this case, a step of the
  analysis stage that fails at every Start would keep every later month from being collected,
  because the runner would resume the failed run at each Start. The handover of the failed run
  contains the state, the logs and the lists, and the record contains no `-complete` archive of
  that run. The entrypoint therefore packs its data root first. The archive is named `-complete`
  because the collection and the release of the run completed, and the pipeline execution state
  in it records the failed step.
- The last run completed and the next month is not due, as when you build the project to load a
  new image during the month: the runner continues that run and runs again only what the new code
  or heuristics change.
- The last run did not complete in any other way: the runner resumes it.

To finish the previous month's analysis on the machine instead, such as with a new image that
repairs the step, put `--from <step>` in `command:` for one Start and build the project
([Import, create, start](#import-create-start)). The entrypoint passes the argument to the run of that Start only
([Deployment options](#deployment-options)) and packs nothing before that run. Under the image that ran the failed run,
that run rewrites only `analysis/` and `run_logs/`. Under a new image, such as one that repairs
the step, the runner also runs again every step that the new code or heuristics change, and the
entrypoint packs nothing first, as at every Start with a new image ([Restarting and updating](#restarting-and-updating)).

When a run completes, or fails in a step of the analysis stage after its release step completed,
the entrypoint packs its handover and decides again, after a monthly run as after any other run.
When the next month is due by then, the entrypoint begins the next month's run in the same Start,
with `--from ghs_download --from repository_cloning`. It packs the handover of that run when the
run ends and decides again. Docker ignores the scheduled Start while the container runs. Without
these decisions, a run that passes the first of a month would make the next month's retrieval
wait for the Start a month later. Such a run can be a resumed collection, a collection again
under a new image, or a monthly run that began late in a month, such as on the 29th after you
repaired a Start at which the pre-checks failed.

After a monthly run, the entrypoint begins another monthly run only when the run that just ended
changed `sampling/ghs_retrieval_report.json`, as its download does. Otherwise the record still
contains the download before it, and the entrypoint logs a warning that names the download's log
and begins no other monthly run, so that it does not pack the data root and run again on the
same record. A check of the runner may stop the monthly run before its first step, and the state
then contains the outcome `failed` with no step that ran. The warning then says instead that the
run ran no step, whether the run before it completed or failed in the analysis stage, and the
runner's ERROR line names the check.

The entrypoint begins the next run only when a `-complete` archive contains the data root of the
run before it: the archive that the entrypoint packed at this Start, or one that the record
contains, as in the first case. It begins no next run after a Stop during the Start. When a run
failed in the analysis stage and the packing of its `-failed` archive failed, the entrypoint packs
the `-complete` archive of its data root before the next run, which then begins. That archive
contains the same pipeline execution state and logs. At one Start, the entrypoint packs the data
root of a run at most once, also when it cannot write the record.

The entrypoint reads the failed step from the step results of the last start that ran a step,
which the pipeline execution state keeps as `last_run_steps`. A Start at which the pre-checks
failed, a `--mark-complete` and a check that stops the run before its first step leave these step
results as they were. After a Start at which the pre-checks failed for a monthly run, the
entrypoint therefore begins the month again at the next Start. It does not resume the failed run,
run the failed step again or pack its data root a second time. A run that a reboot killed during
the collection delays the next month's run only until the resumed run completes. When the
pre-checks fail for the next month's run, the container exits with the runner's code, and
`handover/` has the handover of the run before it.

"The last run" is the last Start that ran steps, and the pipeline execution state keeps its outcome
as `last_run_outcome`. A Start at which the pre-checks or the check for modified inputs failed ran
nothing, and at the next Start, the entrypoint decides as if that Start had not happened. A monthly
run's labeling becomes pending only after the download and the filter have run again, and its
cloning step only after the labeling has changed the sample. The pre-checks of the Start that begins
the month therefore check the labeling's API key, the GitHub access token and the free space for both
steps before the download starts. A run that a kill ended during a step left the outcome `running`,
and the runner resumes it at the next Start. The runner writes that outcome just before the first
step that it runs at a Start. A kill in that step, such as in the cloning step, which the runner
runs again under a new version of git, leaves `running` too. The entrypoint reads the start of a
monthly run's download from `sampling/ghs_retrieval_report.json`. The file contains the retrieval
that the download took, or, when the download fell back to the previous sampling frame, the
retrieval that it attempted. When the file is missing or cannot be read after a completed run, the
entrypoint logs a warning that names the file and the `--from` arguments that begin the next month's
run, and it begins no such run. When a Stop arrives during the pre-checks of a Start that begins a
month, the runner ends the start before any step started (`stopped_before_steps`), and at the next
Start the entrypoint decides again to begin the month.

When the download falls back, the run keeps the sampling frame and the window of the run before
and completes over them with exit 0. The entrypoint therefore ends a Start in which the download
fell back with a warning as its last line. The warning names the retrieval that the run kept, the
reason, and how many downloads in a row have fallen back to that retrieval
(`warn_after_fallback`). The release README states the same as an evidence limit. When the
download refused the retrieval in its size check, because the GHS search result had far fewer
rows than the retrieval before, the warning also names `--step-arg ghs_download:--accept-smaller`.
With that argument, the download takes the smaller retrieval, for when GHS has lost those rows for
good ([Deployment options](#deployment-options)). A crawler that stays stopped for a language that the sampling frame
keeps makes every later download fall back as well, until GHS's crawler resumes or you deploy an
image that raises `window.max_crawl_lag_days` in `1_sampling/config/ghs_download.yaml`. At the
first Start on an empty data root, the download has no retrieval to fall back to, and it exits 1
instead when the GHS search result shows that the filter would keep such a language
([refresh strategy](refresh.md#the-decisions)). To start such a run without a new image, add
`--step-arg ghs_download:"--end-date YYYY-MM-DD"` to `command:` with the end date for the sampling
window of the run, such as the crawl date of the language for which the crawler stopped. The
argument is an argument for one Start: The entrypoint passes it until the download takes a
retrieval, and at every later Start it leaves it out with a warning until you remove it from
`command:` ([Deployment options](#deployment-options)).

When `command:` names a `--from` or `--mark-complete` that no run has used yet, you decide what
the run does. The entrypoint passes the arguments as they are and begins no next monthly run
before that run. A run with a `--from` writes the outputs of the steps that it runs again over the
data root of the run before it. After the `--from ghs_download --from repository_cloning` that the
warnings above name, it writes every stage's data, as a monthly run does. After a
`--from repository_cloning`, it writes the trees, the output CSVs and the release. Before the
runner starts, the entrypoint therefore packs that data root at a Start with a `--from` of a stage
or step before the analysis stage, such as `--from release`, when the release step is done in it
and no `-complete` archive contains it, as the first case above describes. It starts no runner
when the packing fails or the data root does not fit. The release step is done after a run that
completed or failed in a step of the analysis stage. It is also done after a run that a Stop or a
kill ended in the analysis stage, which the runner resumes at the next Start without the
entrypoint following it with the next monthly run, and the `-stopped` or `-killed` handover of such
a run does not contain its release. It is not done after a run that failed or was stopped before
the release step, or that a kill ended in an earlier step, such as in a cloning step that the
runner runs again under a new image. The entrypoint then packs nothing first, because an archive
of that data root named `-complete` would mark a collection as complete that is not.

When every `--from` names the analysis stage or one of its steps, such as the `--from <step>` that
finishes a failed analysis, the entrypoint packs nothing first. A second archive of the data root
would take the room of the archive that the entrypoint packs at the end of the run. Under the
image that ran the run before it, the run rewrites only `analysis/` and `run_logs/`. The handover
of the run before it contains both unless its packing failed. After a failed packing, no archive
contains the outputs of the analysis and the step logs that the run replaces. Under a new image,
the runner also runs again what the new code or heuristics change, as described above. A step of
the analysis stage after the one that failed counts as a step before the analysis stage, because
the pipeline execution state of the failed run does not list it.

Once a run has used an argument for one Start, the entrypoint leaves it out at later Starts with
a warning and decides as without it, also for the next monthly run that it begins in the same
Start ([Deployment options](#deployment-options)). Because the calendar
month alone decides, the entrypoint begins a month's run at the scheduled Start on the first of
that month, however late the previous month's run began. That run may have begun on the 20th after
you repaired a Start at which the pre-checks failed, or on the last day of the month before at the
first Start of a deployment. When a run, a monthly run included, is still running on the first of
a month, the entrypoint begins that month's run after it in the same Start, as described above.

Schedule the monthly Start on the NAS: In Control Panel, Task Scheduler, choose Create, Scheduled
Task, User-defined script. Run the task as `root`, repeated monthly on the first day of the month
at a time of that day, such as 00:00, with the command

```shell
/usr/local/bin/docker start agentcontext-agentcontext-1
```

DSM runs the task at that time in the NAS's time zone, which Control Panel, Regional Options sets.
`compose.yaml` mounts the NAS's `/etc/localtime` read-only at `/etc/host-localtime`, and the
entrypoint compares the calendar months in the zone of that file. A Start at 00:00 on the first of
a month in a zone east of UTC is still on the last day of the month before in UTC, and a comparison
in UTC would skip that month. The container's own local time stays UTC. The image's
`/etc/localtime` is a link to the zone file of UTC, and Docker mounts a file over the target of
such a link. A mount at `/etc/localtime` would then put the NAS's zone into the zone file of
UTC. The cloning step reads the commit times with `git log` under `TZ=UTC`, and every
`commit_timestamp` would then be the NAS's local time with a `Z`. At every Start, the entrypoint
logs the zone in which it compares calendar months, such as `now CET, UTC+01:00`. Without the
file, or with a file that is not a time zone file, the entrypoint compares calendar months in UTC
and logs a warning that names the file to mount. In a container created from a `compose.yaml` of
an earlier bundle, which may lack the mount, the entrypoint runs no step, because that file sets
another revision or none ([Restarting and updating](#restarting-and-updating)). The entrypoint also runs no step, and logs
one ERROR line that names the cause, when `TZ` names a zone with an offset other than zero, or when
`/etc/localtime` or the zone file of UTC gives such an offset, as after a mount at
`/etc/localtime`. `TZ=UTC` and `TZ=Etc/UTC` pass. `build_image.sh` runs each image once with the
zone file of Europe/Berlin at `/etc/host-localtime`. The build fails unless `date` under `TZ=UTC`
prints `+0000`, a commit made at 12:00 UTC reads as 12:00, the entrypoint reads Berlin, and the
entrypoint's check of the container's own zone passes.

`agentcontext-agentcontext-1` is the name that `compose.yaml` gives the project's container
(`container_name`), whatever the project's name, and the name under which its log is exported.
Without `container_name`, Compose would name the container after the project, and under a project
of another name every scheduled Start would fail with `No such container`. The command names
docker by its path, because the Task Scheduler runs a script without the `PATH` of a login shell.
`/usr/local/bin/docker` is the link to the docker command that the Docker package created when it
started, before Container Manager replaced that package in DSM 7.2. When the result of the task in
Task Scheduler says that this file is missing while Container Manager runs, run
`command -v docker` in an SSH session as `root`, and put the path that it prints in its place.

`docker start` runs the entrypoint with the `command:` of `compose.yaml`, as a Start in Container
Manager does. The entrypoint packs the handover of every run into `handover/`, and a complete
handover contains the sample. Download each month's handover in File Station, and delete the
earlier handovers before the volume fills. Empty the Recycle Bin of the shared folder after you
delete them ([Recovery from handover and storage errors](#recovery-from-handover-and-storage-errors)). The entrypoint deletes no archive. At
every start that the runner did not refuse, it logs how many archives `handover/` holds and their
size.

A reboot of the machine, such as for a DSM update, kills the container. Docker does not start it
again, because `compose.yaml` sets no `restart:` policy. The container exits at the end of every
Start, and a policy that restarts an exited container would begin another Start after each one.
Without a further task, the runner resumes the killed run at the next monthly Start, and once that
run completes, the entrypoint begins the next month's run. Create a second task, so that a
collection that a reboot killed resumes when the machine is up again, not at the next monthly
Start: In Control Panel, Task Scheduler, choose Create, Triggered Task, User-defined script. Run
the task as `root` on the event Boot-up, with the command

```shell
for attempt in $(seq 60); do /usr/local/bin/docker info >/dev/null 2>&1 && break; sleep 10; done
/usr/local/bin/docker start agentcontext-agentcontext-1
```

The loop waits until `/usr/local/bin/docker` exists and the Docker daemon of Container Manager
responds, so that the task does not depend on the order in which DSM starts the task and the
package. `docker start` does nothing to a running container, and the two tasks never start a
second run. At a Start at boot-up, the entrypoint decides as at any Start. After a completed run of
this month, the runner skips every step, and after a Stop, it resumes the stopped run. At a Start
that skips every step, the entrypoint packs no handover while `run_logs/complete_handover.json`
contains the handover of the completed run, also after you downloaded and deleted that archive,
and the reboots of a month do not fill `handover/`. Before a Stop after which the run has to stay
stopped across a reboot, disable the task in Task Scheduler.

## Restarting and updating

At a Start over a data root of the image's data root revision, which the paragraphs on updating below define, the runner resumes the run. It runs a step again only when one of these conditions holds:

- For a step of the collection, the publication or the analysis, the code of its module or of a package module that it imports changed. An edit to a comment, a docstring or a log message changes no code. The runner records a step of the sampling or the classification by its script and the code inputs that it declares alone (`package_code`, [the runner](runner.md#step-list)). A fix to a package module that such a step imports, such as `agentcontext/github_api.py`, which the GitHub query and the labeling import, therefore runs no step of the sampling or the classification again. To run such a step under the fix, put `--from <step>` in `command:` for one Start. For the cloning step, the condition is instead that the collector's code, the version of git, the columns of the path heuristics that decide what it copies, the places of the tools' local state, the import heuristics with the code of `agentcontext/imports.py` and `agentcontext/prune.py`, or its list changed. Once the cloning step has exited 0, a change of the collector's code or of the heuristics runs it, also beside another version of git. The step then continues the collection that ended over its list: it queries no head of a repository that the collection collected and collects again the repositories that the change reaches. Where no collection over its list is in progress or ended, as after `--mark-complete`, the step begins a new collection, which queries the head of every repository again and collects again every repository with a moved head. Another version of git alone does not run the step, because the step would collect every repository again. The runner then logs a `WARNING` that names the change and the reason, and the collection stays as the earlier version of git collected it until `--from repository_cloning` or the next monthly run takes a new snapshot ([the runner](runner.md#a-new-image-during-or-after-the-collection)). By this condition, an edit to the code of `agentcontext/commits.py` or `agentcontext/heuristics.py` makes the commit reclassification run again. The `classified_by` digest that the release compares covers the same code, also without comments, docstrings and log calls.
- A code input that it declares changed. The labeling declares the prompts and the modules of the classification, and the filter of the sampling stage declares `1_sampling/config/ghs_filter.yaml`, `1_sampling/config/licenses.csv` and `1_sampling/config/spdx_licenses.json`. A change of the classification parameters, such as an edited prompt or tool description, makes the labeling label every repository in the sampling frame again and send paid requests to the model for each. Any other change to the code of the labeling's script or of a module of the classification runs the labeling again too, also a change that decides no label, such as one to the cost record. Over the same sampling frame, the labeling then completes its finished run without a new run when the current rules derive each of its labels unchanged. It requests no README and writes its outputs again from the cache of labels, and the sample and the collection, in progress or finished, stay. The labeling completes a finished run that left repositories without a decision in this way only once a collection over its sample has begun. Before that, it labels these repositories in a new run, also right after it completes a run with its outputs or its comparison incomplete, as after a Stop, and after that, it logs a `WARNING` with their count and the remedy below. While OpenRouter's lists show that OpenRouter serves no request of the classifying model or the summary model, the new run would exit 1 at every Start, and the labeling then completes the run without them before a collection has begun too, logs a `WARNING` with their count and exits 0, so that the collection follows. The next new run of the labeling tries them again. A new run, after a change of the parameters or of a rule that derives a label differently, requests every README again and drops from the sample every repository that GitHub has stopped serving since. Over such a smaller sample, the cloning step continues the collection in progress, or the collection that ended, without querying the heads again, and it removes the files of the dropped repositories. When the new labels add a repository to the sample or drop one that GitHub still serves, the cloning step begins a new collection and collects every repository with a moved head again ([the runner](runner.md#a-new-image-during-or-after-the-collection)). To label the sampling frame in a new run anyway, for example to try again the repositories that the finished run left without a decision after the collection began, put `--from repository_labeling` and `--step-arg repository_labeling:--new-run` in `command:` for one Start. Remove the `--step-arg` again after that Start. The entrypoint passes it at every Start, as a setting ([Deployment options](#deployment-options)), and every later run of the labeling would then label in a new run.
- A heuristics file that it reads changed: `config_path_patterns.csv`, `vendored_dirs.txt`, `local_state_paths.csv`, `planning_document_patterns.csv`, `import_patterns.csv`, `not_imports.csv`, `ai_commit_patterns.csv`, `other_ai_commit_patterns.csv`, `not_configuration.csv`, `not_ai_commits.csv`, `not_planning_documents.csv`, `doc_hashes.json` or `doc_quotes.json` under `heuristics/`. Among the steps, only the release reads the last three, which it publishes.
- A step that it is computed from ran again.
- `--from` names it or its stage.

The cloning step itself tries a repository again, as it tries a failed clone again, when git could not start reading its commit history, when the fetch of its history failed on the network, or when its collected directory is gone while its row or its per-repository commit record shows that it copied files. The step makes up to <!--s:parameters.agentcontext.guards.RETRY_ROUNDS:words-->two<!--/s--> such rounds after a pause of <!--s:parameters.agentcontext.guards.RETRY_PAUSE_SECONDS.minutes:words-->five<!--/s--> minutes before it ends. When those rounds fail too, the next run that runs the step tries again. The step writes each retry into `finished_repositories.jsonl` before the retry starts. When more such rows than the configured failure ceiling remain at the end of a run, the step exits 4, and the runner retries them at the next Start. When fewer remain, the runner records the step as done with those rows. To retry them then, put `--from repository_cloning` in `command:` for one Start and build the project ([Import, create, start](#import-create-start)).

The step records the bound with a repository when its clone went over the size bound, when its history did not arrive within the time limit or the size bound, or when the time limit ended the reading of its commit history. To collect such a repository again, put `--from repository_cloning` in `command:` beside a larger `--step-arg repository_cloning:"--clone-timeout N"` or `--step-arg repository_cloning:"--max-clone-mb N"`, and build the project. The cloning step then clones the repository, fetches its history or reads its commit history again. Without `--from repository_cloning`, the runner records the step as done and skips it. The entrypoint passes the `--from` to one run. The larger bound is a setting, and every later run of the step applies it until you remove it from `command:` ([Deployment options](#deployment-options)). The step's last lines count these repositories: `Could not fetch the commit histories of N repositories`, `Reading the commit history timed out for N repositories` and `N repositories remain to collect again`.

The `-complete` handover of a finished run restores the whole data root. A `-stopped`, `-failed` or `-killed` handover contains the lists and not the sample, and `finished_repositories.jsonl` without the sample is not a state to resume from. The runner records the cloning step by a checksum of what it wrote and by the inputs that decide what it collects. Under a new image with the same collector and path heuristics, the runner therefore does not run the step. Under a new image that changes either while the collection is in progress, it runs the step, which resumes the collection and collects again what the change reaches. After the step has exited 0, it runs the step too, which continues the collection that ended, `finished_repositories.ended-collection.json`, and collects again what the change reaches. A new version of git alone, which reaches every repository, keeps the collection with a `WARNING`. `--from repository_cloning` in `command:` for one Start takes a new snapshot: The runner then marks the collection that ended as replaced, also when a stop, a kill, a power loss or any exit other than 0 has left the continued collection in progress, and the step begins a new collection, which queries every head again. A collection in progress that never ended is resumed instead. `--step-arg repository_cloning:"--fresh"` in `command:`, an argument for one Start, is the only way to start the collection over. The flag deletes `finished_repositories.jsonl`, the shards, the clone logs, the file lists, the workflow files, the kept path heuristics and the collected repositories. It keeps the two lists at the tree's root, which the run rewrites.

To update the code:

1. If the container is running, stop it ([Import, create, start](#import-create-start)). The entrypoint packs a `-stopped` handover.
2. Import the new tarball, as step 2 of [Import, create, start](#import-create-start) describes.
3. Copy `compose.yaml` and `deploy.md` from the bundle of the same build into the project folder, at every update. Add again what you had added to `command:` ([Deployment options](#deployment-options)).
4. Check `credentials.csv` in the project folder against the `credentials.csv.example` of the same bundle, at every update. The file needs the header `service,account,credential` as its first line, your GitHub access tokens and an OpenRouter API key for the labeling's default model, one per row ([credentials](credentials.md#the-file)). The example in the bundles of the images that ran the run that started on 2026-10-23 begins with comment lines and has no row for OpenRouter. In a `credentials.csv` written from it, delete the lines above the header and add the key as a row `openrouter,ACCOUNT,KEY`. The runner of the new image reads no credential from a file without the header as its first line. Its pre-checks then refuse every Start at which `github_query`, `repository_labeling`, `repository_cloning` or `file_history` is pending or can become pending, such as the Start that begins the next monthly run.
5. Build the project ([Import, create, start](#import-create-start)).
6. Start the container ([Import, create, start](#import-create-start)).
7. Check the `commit` line at the top of the log against the `BUILD_INFO.txt` of the build. When the line names the earlier commit, the container runs the earlier image. Check in Container Manager, Image, that `agentcontext-pipeline:latest` is the image that you imported, then build the project again and start the container.

At the Start after the Build, the runner resumes the run with the new image when the image has the data root revision that `data/run_logs/data_root.json` contains. The code comes from the image, and the update leaves the state untouched. Container Manager keeps the `compose.yaml` of the project folder when you import an image. A new image can depend on what an earlier `compose.yaml` lacks, such as the mount of the NAS's zone file, without which the entrypoint compares months in UTC and skips a month. `compose.yaml` therefore sets `AGENTCONTEXT_COMPOSE_REVISION`. Under a value other than the revision that the image requires, or without the variable, the entrypoint runs no step and logs one ERROR line that names the file to copy. A container keeps the image that it was created from, also after a newer image takes its tag, and `docker start`, which the Task Scheduler runs, would run the earlier image. A Build creates the project's container again from `compose.yaml` and the image that `agentcontext-pipeline:latest` names, under the name that `compose.yaml` gives it, `agentcontext-agentcontext-1`, and does not start it. Your start after the Build and the scheduled tasks then start the new container. The entrypoint cannot tell that a newer image has been imported, because the container has no access to Docker, and the `commit` line is therefore the check.

The data root revision is the revision of the formats in which an image stores its files in the data root, such as the pipeline execution state, the caches and the records of the steps. It is `DATA_ROOT_REVISION` in `deploy/entrypoint.py` of the image's commit. After an update in place, the runner resumes the run when the new image has the revision of the data root. A new image of a later revision converts the stored files of the data root to its own revision at the Start after the Build, before any step runs, where it has a conversion from the revision of the data root (`CONVERSIONS` in `deploy/entrypoint.py`), and the runner then resumes the run. The conversion to revision 2 converts a data root of revision 1, such as the data root of the run that began on 2026-10-23: It renames the count and the limit of the linked pages in the decisions of the cache of labels, and the outcome `preflight_failed` of the pipeline execution state to `pre_checks_failed`. The image of revision <!--s:parameters.deploy.entrypoint.DATA_ROOT_REVISION-->3<!--/s--> also converts a data root of revision 2, such as the data root of the run with the backup providers: It names the digest of each input of a recorded cloning step, or of a cloning step that exited 0 before a kill or a power loss kept the runner from recording it, and writes the record of the collection that the step ended, both rebuilt from the lines of `finished_repositories.jsonl` and accepted only where they give the inputs part of the record of the step (`convert_cloning_records`). A cloning step that closed its collection before a kill or a power loss kept the runner from writing the record of its exit leaves no inputs part. For such a step, which the pipeline execution state still names as the running step, the conversion writes the record of the collection where the lines cover the sample and the collection wrote a line during the start that the kill ended, so that a monthly run that a kill ended before its new collection began does not continue the collection of the month before. The record also lists the repositories that the collection took over from an earlier collection, and the continued collection queries none of their heads again. During the collection, the record of the collection in progress names it, and the conversion changes no file. After the collection, a later image that changes the path heuristics then runs the cloning step, which continues the collection that ended rather than begin a new one. Once converted, the data root no longer resumes under an image of revision 2. The conversion writes each converted file beside its original and replaces the originals only once every converted file is written. A Stop or a power loss during the conversion therefore leaves the original files or a record of the replacements still to make, and the next Start finishes the conversion before anything reads the data root. The entrypoint records the new revision last. The `data_root_revision` line of an image's `BUILD_INFO.txt` and the first log line of each of its Starts name its revision. Under a new image that cannot convert the revision of the data root, the entrypoint runs no step at the Start after the Build, logs one ERROR line, and changes nothing in the project folder. The line names the revision of the data root and the build record of the image that began it, both from `data/run_logs/data_root.json`. To resume the run, import that image again, or another image of that revision, copy `compose.yaml` and `deploy.md` from the bundle of its build, and build the project. To run the new image instead, download `handover/` and export the log, and follow [A clean run](#a-clean-run) with the new image and its bundle. Over a data root that has a pipeline execution state and no `data/run_logs/data_root.json`, the entrypoint of no image runs a step, and the ERROR line then names only the clean run. One such data root is that of the first run on the NAS, with a cache of GHS retrievals that has other index columns than later images read.

A Stop ([Import, create, start](#import-create-start)) sends `SIGTERM`. The entrypoint passes it to the runner, and the runner to the running step. The cloning step ends its workers and kills the git processes that they started. Its `finished_repositories.jsonl` already contains every repository that finished, and the entrypoint then packs a handover named `-stopped`. `compose.yaml` allows <!--s:parameters.deploy.compose.stop_grace_period:words-->thirty<!--/s--> minutes for all of this before Docker sends `SIGKILL`. `finished_repositories.jsonl` survives a `SIGKILL`, and an archive in progress does not. When a Stop reaches a run after its last step, the run stays complete. The entrypoint packs its handover and begins no next monthly run, which Docker would kill when the grace period ends. The entrypoint records a Stop for the whole Start, including a Stop that arrives after the runner ended, while the entrypoint measures the data root or the handover directory before it packs. After a Stop, the handover of a completed run is `-complete-without-sample`, with the pipeline execution state, the logs and the lists and without the trees. 7zz over the whole data root can take longer than the grace period, and Docker would kill it and leave a `.partial` file and no handover. The entrypoint records no handover of that run, and it packs the data root at the next Start. When a Stop arrives before the runner starts, the entrypoint starts no runner, and the container exits with 128 plus the signal, 143 after a Stop. Before a monthly run, the entrypoint then also starts no packing of the data root of the previous run, and it packs that data root at the next Start. When a Stop arrives while 7zz packs, the entrypoint kills 7zz, and that packing fails. After a run that exited 0, the container then exits with 128 plus the signal, as after a Stop during the run, and the log says that the Stop ended 7zz. When a Stop arrives just after the runner started, before the entrypoint installed the handler that passes it on, the entrypoint passes it on once that handler is installed.

## After the run

Download the handover from `handover/` in File Station, and export the log from its Log tab
([Import, create, start](#import-create-start)). The name of a handover contains the end time and the outcome:
`complete`, `stopped`, `failed` or `killed`, or `complete-without-sample`. The last outcome marks
a completed run with a data root that did not fit on the handover volume, or that a Stop reached
before the entrypoint packed its data root. Download the `.sha256` file beside the archive too,
and check the archive in the directory of the download with
`shasum -a 256 -c agentcontext-handover-<time>-complete.7z.sha256` on macOS or `sha256sum -c` on
Linux. The log names the same checksum after the line that names the packed archive. Record the
checksum and the code revision from `BUILD_INFO.txt`.

A `-complete` archive contains the data root without scratch clones: the retrieval, the
sampling frame, the cache of labels and the sample, the collected and validated trees, file lists,
output CSVs, caches, `deletion.csv`, workflows, `finished_repositories.jsonl`, per-repository
commit records and commit logs, clone logs, release files, the figures and tables, and the pipeline
execution state and logs. Symlink markers are stored as links. A `-stopped`, `-failed` or
`-killed` archive contains the pipeline execution state and logs and the data of the sampling,
classification and analysis stages. Of the collection, it contains the completion records, lists,
caches, output CSVs, deletion records and workflows. Its companion `-trees` archive contains the
collected and validated trees when the storage allows it. When an earlier `-trees` archive in
`handover/` contains the trees unchanged, the entrypoint packs none, and the log names that
earlier archive.

Keep the downloaded handover unchanged, and prepare a
[working copy](development.md#handover-working-copy) for the processing. Follow
[the review procedure](development.md#continuous-improvement-from-handovers). Review the commit
coverage, the attribution differences, the unmatched paths, the deletions and the missing
metadata. Fix the confirmed defects and add regression tests before you replace the regression
manifest with `regressions check --write`.

After you review the regenerated outputs, run `snapshot write` and `snapshot validation`.
Update the tracked unmatched attributions with `unmatched reduce`, regenerate the development
subsample and the analysis outputs, and update [dataset facts](dataset.md). Build the release and
the website from the same inputs and heuristics. Move the changelog's unreleased entries to the
new version and tag a release once its verification and the review of its inputs are complete.

## Deployment options

The entrypoint passes the `command:` line of `compose.yaml` to the runner, `run_pipeline.py`, without the arguments for one Start that a run has already used, as the rule below the table describes. A deployment uses these options:

| Option | Use |
|---|---|
| `--with-commit-reclassification` | In the shipped command: reclassification after `repository_cloning`, and the <!--s:parameters.agentcontext.runner.COMMIT_RECLASSIFICATION_STEPS:words-->two<!--/s--> checks as the last steps of the collection, before the publication. When a row of the commit CSV is not what the heuristics give, the run stops before the release |
| `--from <name>` | Redo a stage's steps, or one step, and everything computed from them. Repeat the option for more stages or steps |
| `--step-arg NAME:"args"` | Extra arguments to one step: `repository_cloning:"-w 3"` for fewer clone workers, `repository_cloning:"--fresh"` to collect everything again, `ghs_download:"--accept-smaller"` to take a retrieval that is far smaller than the one before it, `file_history:"--keep-blank"` to leave the rows that the cache records without a history as they are rather than clone again for them, `repository_labeling:"--workers 4"` for fewer repositories labeled at once, `repository_labeling:"--new-run"` with `--from repository_labeling` to label the sampling frame in a new run ([Restarting and updating](#restarting-and-updating)) |
| `--list` | Print the stages with their steps and exit. It needs no mounts, and you can therefore check a newly imported image with it |
| `--repo-csv PATH` | Another sample list, for a run over a subset |
| `--min-free-gb N` | Minimum free space for both the pre-checks and the collection. Reduce it only for a bounded local run |
| `--mark-complete STEP` | Record deliberately restored outputs without running the step |
| `--no-github` | A run over local mirrors, with clones that do not reach github.com. The pre-checks fail when a GitHub access token is set |

A deployment does not need `--scratch-dir`, because the default, `_scratch/` under `data/collection/`, is on the mounted volume.

An edit to `command:` takes effect only when you build the project ([Import, create, start](#import-create-start)), as a new image does ([Restarting and updating](#restarting-and-updating)). `docker start`, which Container Manager runs for a Start and the Task Scheduler runs for its tasks, starts the container with the command that it was created with, and a Build creates the container again from `compose.yaml`.

An argument in `command:` is either an argument for one Start or a setting:

- **Arguments for one Start:** `--from`, `--mark-complete`, and a `--fresh`, an `--accept-smaller` or an `--end-date` in a `--step-arg` value, such as `repository_cloning:"--fresh"`, `ghs_download:"--accept-smaller"` or `ghs_download:"--end-date 2026-10-12"`. Each changes what the runner has recorded, collected or retrieved, and the runbook gives each for one Start. Left in `command:`, each would take effect again at every later Start. With a `--from`, the runner would run its steps again, the entrypoint would pack another archive of the data root, and no later monthly run would begin. With a `--fresh`, the cloning step would collect the whole sample again in every monthly run, with an `--accept-smaller`, the download would take every later retrieval however many rows GHS lost, and with an `--end-date`, every later monthly run would keep the sampling window of that end date.
- **Settings:** every other argument, such as `--with-commit-reclassification`, `--repo-csv`, `--min-free-gb`, `--no-github`, and a `--step-arg` value without `--fresh`, `--accept-smaller` or `--end-date`, such as `repository_cloning:"-w 3"`, `repository_cloning:"--clone-timeout N"` or `repository_labeling:"--workers 4"`. The entrypoint passes them at every Start until you remove them. `repository_filtering:"--top-languages N"` is a setting too. The runner passes it to the filter and to the GHS download, also at the Start after a filter that failed. The filter ranks only the languages that the end date of the retrieval covers. Over the retrieval of the month, a larger N therefore leaves out a language that the end date left out and keeps the next most common language in its place, and the README of the release names the language (`1_sampling/filter-ghs-spec.md`). The download of each later month counts N languages as well. When a language that its end date left out is among them, the download names the language in a warning and takes the retrieval, because the filter leaves the language out and the previous sampling frame lacks it as well (`1_sampling/download-ghs-spec.md`).

The entrypoint recognizes the arguments for one Start by their full names, also in the form `--from=NAME`. The runner and its steps take long options by their full names only. With an abbreviation, such as `--fro release` or `--step repository_cloning:--fresh`, the runner stops the Start with a usage error, instead of the argument acting at every later Start. Write each argument in full.

The entrypoint passes an argument for one Start to the runner until a run has used it, and records it in `run_logs/one_start_arguments.json`. Before the runner starts, the entrypoint writes into the record the arguments that it passed, so that a reboot that kills the container during the run leaves what the entrypoint needs to decide at the next Start. A run has used a `--from` when the runner ran a step, or when its pipeline execution state no longer records as completed a step that it recorded before the Start. The runner takes the steps that `--from` names out of its record of completed steps after the last check that can refuse the run. It writes that record before the first step that it runs, and at a Start that resumes the run after a kill, the runner runs those steps without the `--from`. When the pre-checks or the check for modified inputs fail, the runner's record of completed steps stays as it was. It also stays when a check stops the run before that point, such as a git that cannot start while the runner fingerprints the cloning step. The entrypoint then passes the argument again at the next Start. A run has used a `--mark-complete` when the runner recorded the outcome `marked_complete`.

A run has used a `--fresh` once its step has removed the list of finished repositories, the first thing that the step deletes. A `--fresh` passed again after that would delete what the step collected since. The entrypoint counts the `--fresh` as used when the step ran, failed or was stopped, or a kill ended the runner inside it, and the list is gone or is another file than before the runner started. The runner writes into its pipeline execution state the name of the step that it has started and that has not ended ([the runner](runner.md#pipeline-execution-state)). After a kill in an earlier step, and after a cloning step that failed or was stopped before it removed the list, the `--fresh` deleted nothing, and the entrypoint passes it again at the next Start. A run has used an `--accept-smaller` or an `--end-date` only when the GHS download took a retrieval, that is, when `sampling/ghs_retrieval_report.json` records the outcome `retrieved` for a retrieval that it did not name before the runner started. A download that failed, was stopped or was killed before it wrote that record took no retrieval. Neither did a download that fell back to the previous sampling frame, which ends `ok` whatever the reason for the fallback, such as a GHS that does not respond or a crawler that stopped for a language that the sampling frame keeps. At the next Start that runs the download, the entrypoint passes the argument again, and without an `--accept-smaller`, the download would refuse the smaller export once more. After a download that failed or that a Stop or a kill ended, the runner runs the download again at the next Start. After a download that fell back, the runner records the download as complete and runs it again only in the next monthly run or at a Start with a `--from` that names the download or its stage. Alone, `--step-arg ghs_download:"--accept-smaller"` therefore takes effect at the Start of the next monthly run, and together with `--from ghs_download --from repository_cloning` at the first Start with them in `command:`.

At every later Start while `command:` still names such an argument, the entrypoint leaves it out and logs a warning that names it and says to remove it from `command:`. It decides as without the argument: the runner resumes the run, or the entrypoint begins the month that is due. A `--step-arg` value keeps its other words, which are settings. For the next monthly run that the entrypoint begins in the same Start, it also leaves out the arguments that the run before it used. At a Start with a `command:` that does not name the argument, the entrypoint removes the argument from the record, and you can then add it again for another Start.

## The entrypoint

### Context

The pipeline runs unattended on a machine with Docker, the Synology that the mining project deploys to. This deployment follows that project's, as the start of this runbook describes, and all that you do is import the image, create the project and start the container in Container Manager ([Import, create, start](#import-create-start)). The layout of the data differs. The mining pipeline wrote into fixed directories around which its code was designed. This pipeline's scripts derive every data path from the data root, keep caches in each stage's directory, and rewrite those caches with `os.replace`. A rename over a file bind mount fails. A rename over a symlink replaces the symlink with the renamed file in the container's own layer, where the next start does not read it.

`entrypoint.py` handles that difference. The data root itself is the volume, mounted from the host at the path that the repository gives it, `data/`. The script checks the mounts, records the machine, and runs the runner of the five stages, `run_pipeline.py`. After the runner exits, whether every step finished, a step failed or a Stop ended the run, the script packs what a checkout needs from the run into one archive in the second mount, `handover/`. The mining project's run writes its handover zip the same way. After a start that the runner refused before any step ran, the script packs nothing, because that start has nothing to hand over. A `SIGKILL` leaves no process to pack, and a `SIGKILL` during the packing leaves the archive under its `.partial` name. Before any of this, the script refuses a start with directories that are not mounts or with a filesystem that does not implement `flock`. Both failures stay silent until the container is removed or a lock is taken.

### Key decisions

- **Language:** Python 3.14 (`entrypoint.py`), with no dependencies outside the standard library
- **The data root is the volume.** The alternatives were checked against the code. A mount per state path needs the caches to be file mounts or symlinks. `caches.FileHistoryCache.save`, `caches.AiAuthorshipCache.save`, the cache of labels and the cloning step's own writers all write a temporary file beside the target and `os.replace` it, which works with neither. Redirecting every cache by a flag would leave the detection step, which has no path flags, reading the stage directory, and the runner's `produces` and `reads` naming files that are not there. Mounting the whole data root is the only arrangement under which everything that a run writes is stored on the host without changing a step
- **No data is built into the image or included in the bundle.** The code comes from the image: the package, the scripts of the other stages, `run_pipeline.py` and the heuristics, read from `/opt/pipeline`. A heuristic that changed in the image therefore takes effect without a copy into the volume, and the data on the volume belongs to the host. The entrypoint never copies anything from the image into the mounts. Before 2.0.0, the image contained the collection stage's tracked state, data in an image of code. The entrypoint copied it onto the volume on the first start, and replacing an input meant a rebuild. The runner in the image runs every stage. At a first start over an empty data root, it downloads its own GHS retrieval and labels its own sampling frame, and at a later start, it continues from what the previous start left on the volume
- **An empty data root is a first start.** `data/` and `handover/` come with one `.keep` file each, because Container Manager refuses to create a missing bind-mount source. Of the data root's content, the entrypoint requires only a record of its revision once a pipeline execution state is there (below). The runner checks what a step needs, in its pre-checks and its `reads`, and an earlier step that has not run yet writes it. The entrypoint refuses a `run_logs` that is a file or a link, and names it
- **Mounts are judged by device number.** Inside the container, `/app` is on the image's layer, and a bind mount has the host's device. A directory on the same device as `/app` is therefore in the container's layer, and everything in it is lost with the container. The check is the mining project's `unmounted_volumes` over the <!--s:parameters.deploy.entrypoint.MOUNTS:words-->two<!--/s--> directories, and it reports a directory that does not exist with the same message
- **The runner's lock is probed before anything is written.** Without the probe, a second container started against a project folder in use would write the machine record and the copies of the heuristics files under the running run before the runner's lock refused it. The entrypoint takes and releases a non-blocking `flock` on `run_logs/run.lock` right after the mount check. When it cannot take the lock, it refuses the start with the holder's line
- **`flock` is probed before the runner takes its lock.** The run lock and the snapshot lock are both `flock`s, and `snapshot.py` raises an error on a filesystem that refuses one. The probe takes and releases a lock on a file that it creates and removes in the data root. The refusal is then one line that names the cause, not a traceback in the middle of a run
- **The credentials are in `credentials.csv` in the project folder, mounted read-only.** You write the file, one GitHub access token or OpenRouter API key per row under `service,account,credential`. The entrypoint does not read it, because the entrypoint has to run even where the package cannot be imported. It names the file to the run through `AGENTCONTEXT_CREDENTIALS`, unless the environment names another file, and logs whether the file is there. `agentcontext/credentials.py` reads it in the runner's pre-checks and in each step that calls GitHub or OpenRouter, after `GITHUB_TOKENS`, `GITHUB_TOKEN` and `OPENROUTER_API_KEY`, which take precedence. The runner refuses a run without a GitHub access token in its pre-checks. The entrypoint therefore only reports a missing file and does not refuse the start, because a run over local mirrors has no GitHub access token on purpose. A directory at the path gives a WARNING that names it as what Docker creates for a missing bind source. The reader drops a byte-order mark, accepts CRLF line ends and refuses a file without the header. It reports a row that is not a credential of its service by its line number and never by its text, because such a row can contain a GitHub access token beside a comment
- **`--list` and `--help` need no mount.** They print and exit, and they run from an empty directory in the image when nothing is mounted. You check a newly imported image with them
- **`AGENTCONTEXT_DATA_ROOT` is the mounted data root.** The `agentcontext` package is installed from the image's copy of the repository under `/opt/pipeline`. Every stage derives the default path of each file that a run reads and writes, including the caches and the snapshot record, from the data root beside it. The heuristics stay at `heuristics/` in the image. The run's files are on the volume, and the entrypoint sets the variable to the volume before the runner starts, for the package to read. The subsample run over the mirrors does the same for its own checkout. Without the variable, such a run writes into the development repository's caches.
- **`TMPDIR` is the scratch directory on the volume.** `agentcontext/steps/release.py` builds the release under `tempfile`'s default directory, which in a container is the image's layer, while the clones already go to `_scratch/` under `data/collection/`. Setting the variable puts every temporary file of the run on the volume that the pre-checks measured
- **What killed processes left is removed before the runner starts.** A GHS download that a Stop or a kill interrupted leaves `<retrieval>.json.gz.part` in `data/sampling/ghs_retrievals/`. A kill of the release, of the cloning step or of any other step leaves its clones and temporary directories in `_scratch/`, which `TMPDIR` names. No step reads them: each download takes a retrieval of its own, and the cloning step removes a clone's directory before each attempt. After the startup checks, which establish that no runner holds the run lock, `remove_leftovers` removes them and logs what it removed. They would otherwise take free space that the pre-checks require at every later Start. The next GHS download also removes such a download before its export, which covers a run outside the container too. A file of the sample with a `.part` name stays, because only the cache of retrievals is searched. The same function removes the `.7z.partial` files that a kill during a packing left in `handover/`, and the `.7z.sha256.partial` files that a kill left while the entrypoint wrote the checksum of an archive. Left until the next packing, such a file would count as used space when the entrypoint measures whether the handover volume has twice the size of the data root free. At a monthly Start, the entrypoint would then pack the data root without the sample, exit 1 and begin no month
- **The entrypoint refuses a start over a pipeline execution state that cannot be read.** `state_problem` reads `run_logs/state.json` among the startup checks. A file that cannot be read, or that is not a JSON object, is not a missing state. Read as missing, it would make the entrypoint decide on the next monthly run as if no run had happened. The runner refuses it anyway, because a new state written over it would discard the record of every completed step. The entrypoint logs the file and its recovery from the latest archive in `handover/`, and exits 1 before it removes, packs or writes anything. The runner syncs the state to the disk before its rename, and a power loss leaves the previous state or the new one
- **The runner is a child, and the handover follows it.** This process receives the `SIGTERM` that a Stop sends and passes it to the runner, which passes it to the running step. After the runner exits, whether every step finished, a step failed or a Stop ended the run, the script packs the handover and exits with the runner's code. With `exec`, no process would remain to pack the handover. The runner leads a process group. A signal death is a runner killed by a signal that it did not handle, for which `Popen.wait` returns a negative code. Without the group, a signal death would leave its step running under the init process while the handover is packed, and the container's teardown would kill the step before it could end. The entrypoint therefore sends the group the `SIGTERM` that the runner would have forwarded, gives it `KILLED_RUNNER_DRAIN_SECONDS` to end, and then kills it. The outcome is `killed`, and the container's code is `128 + signal`, not the value that `sys.exit` makes of a negative code, such as 241 for -15. The entrypoint ends the group after any exit other than 0, because a runner that exits by an exception, such as an `OSError` on the step's log, leaves its step running the same way. A runner that ended its step leaves an empty group, which costs one signal and no log message. The handler that passes a signal on records it (`note_stop`). After a Stop, the entrypoint begins no next monthly run after the run of that Start, because Docker kills the container when the grace period ends, and a run that Docker kills leaves no handover. A runner that receives the Stop after its last step still exits 0, and the exit code cannot show the Stop. Outside the runner and 7zz, a handler that records the Stop (`note_stop_signal`) is installed for the whole start, because `run_runner` restores the handler that was there before it. With Python's default handler, a Stop that arrives while the entrypoint measures the data root or the handover directory would end the entrypoint without a handover. After such a Stop, the entrypoint packs the handover of the run that just ended, without the data root when the run completed, and starts no runner (`stopped_before_runner`) and no other packing. A Stop that arrives after the runner started and before `run_runner` installed the handler that passes it on is recorded by the handler of the whole start. `run_runner` passes it on to the runner once its own handler is installed, because Docker sends no second signal. `compose.yaml` sets `init: true`, and process 1 is Docker's init, with this script as its child. The cloning step runs every git command with maintenance off, and nothing that it starts is left without a parent. The init process reaps any other process. The script logs a warning when it runs as process 1
- **After a start that ran no step, the entrypoint packs no handover.** The entrypoint reads the pipeline execution state, `run_logs/state.json`, before and after the runner runs. A step that the runner could not start, or with a log that it could not open, counts as a step that ran and failed. The runner records it as such, and the entrypoint packs the handover. A non-zero exit that left the pipeline execution state unchanged is the runner's refusal on its lock, which writes nothing. A non-zero exit with a state that records `pre_checks_failed` or `modified_inputs` is a failure of the pre-checks or of the check for modified inputs, and the runner writes the pipeline execution state after each of them. An exit 0 with a state that records `marked_complete` is a `--mark-complete` run, which records a step and runs none. An exit 128 plus a signal with a state that records `stopped_before_steps` is a stop before any step of the start started, such as during the pre-checks. At the next Start, the entrypoint then passes its arguments for one Start again. `NO_STEP_OUTCOMES` names the <!--s:parameters.deploy.entrypoint.NO_STEP_OUTCOMES:words-->four<!--/s--> outcomes. Without this check, the entrypoint would write a `-failed` archive of an earlier run's state into `handover/` at every refused Start, as it did at refused Starts in the subsample run, and it would pack the sample as `-complete` after a `--mark-complete` run. A signal death is never a refusal. The runner writes the outcome `running` just before the first step that it runs. A runner killed earlier, such as during the pre-checks, can leave the state unchanged, as the runner's refusal on its lock does. The state on the host then describes the previous start, and the container's log records that the runner was killed
- **After a run that completed, the entrypoint packs the data root. After any other run, it packs `PARTIAL_HANDOVER_MEMBERS`, and then the collected and validated trees.** After a Stop, a step that failed or a runner that was killed, you read `PARTIAL_HANDOVER_MEMBERS` before the next Start: the pipeline execution state and logs and the data of the sampling, classification and analysis stages. Of the collection, they are `finished_repositories.jsonl` with the records of the collection in progress and of the last collection that ended, the lists of the two trees, the caches, `deletion.csv`, the workflow files, the imported tree and the output CSVs. The collected and validated trees, `data/collected/` and `data/validated/`, follow in a second archive, `-<outcome>-trees.7z`, written after the first archive. When the grace period of a Stop ends during their packing, the first archive is still complete. Without the trees, a step that failed after the collection could be examined only in its log, because only the trees contain the symlinks, the markers and the files that the cleanup deleted. The entrypoint packs the trees only when the handover volume has at least twice their size free, because the cloning step stops when the volume runs low, and packing the sample onto it would fill it. The log states when the trees are left out. The entrypoint also packs them only when no `-trees` archive in `handover/` contains them unchanged (`recorded_trees`). Otherwise, after a step that fails at every Start, such as a step of the analysis stage after a refused Start, the entrypoint would put another copy of the sample on the volume at each Start, until the pre-checks of the next monthly run fail for lack of free space. `trees_listing` lists the entries of the trees that 7zz would pack. It fingerprints the path and the kind of each entry, the size and the modification time of each file and the target of each link. After a packing, the entrypoint records the archive with that fingerprint in `run_logs/trees_handover.json`. The time of a directory is left out, because DSM changes it when it writes an `@eaDir` into the directory, and a deleted archive no longer counts. The first archive is packed at every such Start, because it contains the pipeline execution state and the logs that the Start wrote. The clone logs and the shards are packed when a run completes
- **The whole data root is packed only when it fits, only when no archive has it yet, and not after a Stop.** 7zz over the whole data root can take longer than the stop grace period. Docker kills it when the grace period ends, which leaves a `.partial` file and no handover. A Stop may arrive during the run, after its last step or while the data root was measured. After such a Stop, the handover of a completed run is `-complete-without-sample` with `PARTIAL_HANDOVER_MEMBERS` and without the trees, and `run_logs/complete_handover.json` does not contain it. The entrypoint then packs the data root at the next Start. When a Stop arrives after that check and before 7zz's handler is installed, `_run_7z` does not start 7zz over the whole data root, and the packing ends as one that a Stop ended. Before it packs the data root of a completed run, `room_for_everything` measures the data root without the scratch directory against the free space of the handover volume, by the rule of the trees, twice its size. Without that room, the archive contains `PARTIAL_HANDOVER_MEMBERS` and is named `-complete-without-sample`, so that nobody takes it for the archive of the data root. The trees follow as `-complete-trees.7z` when they fit, and the log says that the data root remains in the project folder. At a Start after a completed run with nothing changed, the runner runs no step, and packing the data root again would put a second copy of the sample on the volume at every such Start. After it packs the handover of a completed run, the entrypoint writes `run_logs/complete_handover.json` (`record_handover`). The record contains the name of the archive and the time at which the last start that ran a step finished, which the runner records as `last_steps_finished_at`. When the pipeline execution state records every step as skipped, `recorded_handover` reads the record. A `-complete` archive recorded with the time that the state has contains the data root as it is. The entrypoint then packs nothing, and the log names the archive. A state written by a runner that does not record `last_steps_finished_at` has no such time, and the record of its handover has null in its place. A null record matches a state without the time, because a start that runs a step writes the time, and such a state has run no step since the packing. Otherwise the entrypoint would pack the data root again at every start over such a state, and at the start that begins the next monthly run, it would pack the data root and then refuse the run. The time of the pipeline execution state cannot show this, because every start writes the state, including a start that skipped every step and a refused start. After one of them, every archive is older than the state, and the entrypoint would pack the data root again at every second such Start. Nor can the archives in `handover/` show it, because you delete the archives that you have downloaded. If the entrypoint packed the data root whenever its archive was gone, it would pack it again at every reboot, through the Start at boot-up, until the archives use up the free space that the pre-checks of the next monthly run require. When the packing of the completed run failed, the entrypoint wrote no record, and it packs at the next start. Without room for the data root, a recorded `-complete-without-sample` archive counts the same. It contains the pipeline execution state, the logs and the lists as they are, and another such archive with its trees would take the room that the volume lacks. The entrypoint deletes no archive, because only you know which archives you have downloaded. It logs how many archives `handover/` holds and their size, so that the log shows when the volume fills
- **No monthly run replaces a data root that no archive contains.** The next monthly run replaces the sampling frame, the labels, the collected and validated trees and the release of the run before it. Before the runner starts that run, `hand_over_before_next_month` reads the record of the last handover of a completed run. When the record contains no `-complete` archive of that run, the function packs the data root, as at a start that skipped every step. The packing at the end of the completed run can have failed, the data root can have been too large for the handover volume then, or the run failed in the analysis stage and packed its state, its logs and its lists. The archive that this packing returns counts as well as the record. So does a `-complete` archive that the entrypoint packed at the same Start after a resumed run. A record that cannot be written then neither makes the entrypoint refuse the month after a packing that succeeded nor pack the data root twice. When no `-complete` archive contains the data root afterward, the entrypoint begins no new month. It logs an error that names the cause, the error of the packing or a data root that does not fit, and exits 1, and the data root remains in the project folder. The entrypoint checks the same after the handover of each run of a Start, a monthly run included, before it begins the next monthly run that became due during that run. That run may have failed in the analysis stage, and the packing of its `-failed` archive may have failed. The entrypoint then still packs its data root and begins the month, because the `-complete` archive contains the pipeline execution state and the logs that the `-failed` archive would have contained. A small archive that failed, such as on a file that changed while 7zz read it, would otherwise hold back a month with a data root that is safe. After a Stop, the packing does not start, even when the Stop arrived while the data root was measured, because Docker kills a packing of the whole data root when the grace period ends. The entrypoint then exits `128 + signal`, and it packs at the next Start. Another `-complete-without-sample` archive would contain nothing new, and a data root that still does not fit is not packed again. The machine record and the copies of the heuristics files of the Start are written after this packing, because they describe the next run. With a `--from` in `command:` that no run has used, `monthly_argv` leaves the decision on the monthly run to you, but the entrypoint still decides on this packing. A run with a `--from` writes the outputs of the steps that it runs again over the data root of the last run. `start` therefore calls `hand_over_before_next_month` before such a run too, when the step results of the last start that ran a step record the release step as done or skipped, whatever the outcome of that start (`release_step_completed`, `from_arguments`). The release step is done after a run that completed or failed in the analysis stage. It is also done after a run that a Stop or a kill ended in the analysis stage, for which `monthly_argv` keeps the arguments, so that the runner resumes it instead of the entrypoint beginning the next month, and the `-stopped` or `-killed` handover of such a run does not contain its release. A kill before any step of its start ended leaves the step results of the start before it in `last_run_steps`. The step results of the killed start up to the step that the kill ended, which the runner keeps as `running_step_results` until a later start runs a step, then show whether that step came after the release step. After a kill in a cloning step that the runner runs again under a new image, it did not, and a data root packed then would be named `-complete` while it holds part of a collection. The packing covers every `--from` of a stage or step before the analysis stage, not only the names that take a new GHS retrieval. A `--from repository_labeling` rewrites the labels and the release of that run, a `--from repository_cloning` its trees, its output CSVs and its release, and a `--from release` its release, which the `-failed` handover of a run that failed in the analysis stage does not contain. When every `--from` names the analysis stage or one of its steps, `start` packs nothing before the run (`redoes_only_the_analysis`). Packed first, the data root would take the room of a second archive beside the archive that the entrypoint packs at the end of the run. On a handover volume with room for one such archive but not two, the handover of that run and of every later monthly run would then leave out the data root, which the entrypoint would pack first at the next Start. Under the image that ran the last run, the run rewrites only `analysis/` and `run_logs/`, which the handover of that run contains unless its packing failed. Under a new image, the runner also runs again every step that the new code or heuristics change, without a packing first, as at every Start with a new image. The entrypoint reads the steps after the release step from the step results of the last start that ran a step, which list them in the pipeline's order, because it has to run when the package cannot be imported. After a run that failed in the analysis stage, these step results end at the failed step, and before a `--from` of a later step, the entrypoint packs the data root first, as before a `--from release`. The warning after a fallback and the warning about a missing record of the GHS download name `--from ghs_download --from repository_cloning` for one Start, which would otherwise replace a data root that no archive contains. After a run that failed, was stopped or was killed before its release step completed, nothing is packed first. An archive of its data root named `-complete` would mark a collection as complete that is not, and its handover contains its state, its logs and its lists
- **The next month is due in the next calendar month of the NAS's time zone, whatever the age of the last download.** DSM's Task Scheduler runs the monthly Start at a time of the NAS's time zone. A Start at 00:00 on the first of a month in Berlin is 22:00 or 23:00 on the last day of the month before in UTC. Compared in UTC, the months of that Start and of a download earlier in the month before would be the same, and the entrypoint would skip the month at that Start. `compose.yaml` therefore mounts the NAS's `/etc/localtime`, which DSM keeps in line with its Regional Options, read-only at `/etc/host-localtime`. `month_zone` reads the zone from that file with `ZoneInfo.from_file`, and `next_month_due` compares both times in that zone. A `TZ` variable in `compose.yaml` would have to be edited for each NAS and kept in line with DSM by hand. No minimum age of the download applies. The Starts of a monthly schedule are 28 to 31 days apart, and a month can begin late, on the 20th after you repaired a Start at which the pre-checks failed, or on the last day of a month at the first Start of a deployment. With any minimum age, the entrypoint would skip the month at the next scheduled Start after such a run
- **The container's own local time stays UTC.** The zone file is mounted at a path of its own, not at `/etc/localtime`. The image's `/etc/localtime` is a link to `/usr/share/zoneinfo/Etc/UTC`, and Docker mounts a file over the target of such a link inside the container. A mount at `/etc/localtime` would therefore put the NAS's zone into the zone file of UTC, and `TZ=UTC` and `ZoneInfo("UTC")` would give the NAS's local time. The cloning step reads the commit times with `git log --date=format-local:...Z` under `TZ=UTC`. Every `commit_timestamp` in the per-repository commit records, the commit logs and the commit CSVs would then be shifted by the NAS's offset while it reads as UTC. A `TZ` variable with the NAS's zone would shift every other time that a step writes in local time. Reading the zone from a file of its own changes nothing but the decision. Without the file, `month_zone` returns UTC, and the entrypoint logs a warning that names the file to mount. A directory at the path, which Docker creates for a bind mount of the short form when the host has no file, counts as no file. A file that is not a time zone file counts as no file, with its error. `read_zone` refuses a file of version 2 or later that ends inside its last line, because `zoneinfo` reads that line up to its newline and does not return at the end of the file. `build_image.sh` runs every image once with the zone file of Europe/Berlin mounted where `compose.yaml` mounts the NAS's. The build fails unless `date` under `TZ=UTC` prints `+0000`, a commit made at 12:00 UTC reads as 12:00 in the format of the cloning step, the entrypoint puts a Start at 23:00 UTC on November 30 on December 1, and the entrypoint's check of the container's own zone passes. That check, `container_zone_problem`, runs at every Start with the check of the revision below, before anything is removed, packed or written, because an edited `compose.yaml` of the current revision can still set `TZ` or mount a file over the zone files. The entrypoint refuses a Start when the zone of `TZ`, as the C library reads it (`tz_offsets`), or `/etc/localtime` or `/usr/share/zoneinfo/UTC`, the file that `TZ=UTC` reads, gives an offset other than zero on the first of January, on the first of July or now. The two dates catch a zone with daylight saving time. A zone with offset zero all year writes the same times as UTC, and `TZ=UTC` and `TZ=Etc/UTC` pass. The C library reads `TZ` as the name of a zone file, under the zone database or absolute, and as a POSIX rule where no such file can be read, and the offsets are those that the steps would see. A file that is missing or is not a zone file passes, because the C library then takes UTC
- **`compose.yaml` sets its revision, and under another revision the entrypoint runs nothing.** Container Manager keeps the `compose.yaml` from which you created the project when you import a new image and build the project. A new image can therefore run under the `compose.yaml` of an earlier bundle. A project created from the bundle of the first run on the NAS has no mount of the NAS's zone file, and under it, the entrypoint of a new image would compare months in UTC and skip one with no more than a warning. `compose.yaml` therefore sets `AGENTCONTEXT_COMPOSE_REVISION`. The entrypoint refuses a Start when `compose_problem` finds the variable absent or different from `COMPOSE_REVISION`, before anything is removed, packed or written, with one ERROR line that names the files to copy from the bundle of the same build. A check of each thing that the entrypoint needs from `compose.yaml` would miss what nobody thought to check, while one number covers every change. `deploy/0_README.md` states when to raise it. The entrypoint cannot read the image's bundle and cannot compare `compose.yaml` itself
- **The data root records its revision, the entrypoint converts an earlier revision that it has a conversion for, and over another revision it runs nothing.** The steps read the caches and the records of the data root as the image writes them, and the project has no compatibility paths: no step reads two formats of one file. A change of a stored format with a known conversion, such as a renamed key, therefore comes with a conversion of the stored files (`CONVERSIONS`, `convert_data_root`). The entrypoint converts the data root once, at the first Start of the new image and before any step, and the code of the image reads only its own formats. Without the conversion, the change from revision 1 to revision 2 would have made the next image refuse the data root of the run that began on 2026-10-23, and a clean run would have taken the retrieval, the labels, the collection and the commit logs again. The change from revision 2 to revision 3 records how the cloning step was recorded and which collection it ended. Read at every start rather than converted once, the records of the runner of the image with the backup providers would need code that rebuilds them from the lines in every later image. The conversion writes every converted file under its name with `.converted` and syncs it, then writes `run_logs/data_root_conversion.json` with the files that it replaces, renames the converted files over the originals, removes the record and records the new revision. A start after a kill before the record converts again from the originals, and a start after a kill during the renames finishes them from the record. Before it converts a part of a run's decisions, it checks the part against the SHA-256 that the index of the cache of labels records, and it records the SHA-256 of the converted part in the converted index. A part that does not match stops the start with one ERROR line, and nothing is converted. Without a check of the revision, the runner of a later image would resume the failed labeling over the data root of the first run on the NAS. The query of GitHub would stop on the index columns of the cache of retrievals with a message that names the columns, not the remedy, and at every Start the entrypoint would pack another `-failed` archive and begin no month. At the first start over a data root without a pipeline execution state, the entrypoint therefore writes `run_logs/data_root.json` with `DATA_ROOT_REVISION` and the image's build record (`record_data_root`). It writes the record before the runner starts, so that the record exists also after a first start at which the pre-checks fail. `data_root_problem` runs among the startup checks, after the mount checks and before anything is removed, packed or written. The entrypoint refuses a data root with a record of a revision that it neither has nor converts, or with a record that cannot be read. It converts a data root of an earlier revision after these checks and after it removes what killed processes left, before it packs a handover of the previous run, so that such a handover contains the converted data root. It also refuses a data root with a pipeline execution state and no record, which an image that writes no record began. Its one ERROR line names the record, the revision and two remedies. One remedy is an import that resumes the run: of the image that began the data root, with the build record that `run_logs/data_root.json` contains, or of another image with a `BUILD_INFO.txt` that names that revision. The other is a clean run in an empty project folder with this image. For a record without a build record, the line names the revision alone. For a revision that is no whole number, or a data root without a record, it names only the clean run. The state's own problem is not reported beside it, because restoring the state from an archive leaves the data root in the formats of that revision. A check of each stored format would have to know every format of every earlier image, while one number covers every change. `deploy/0_README.md` states when to raise it. The first log line of every Start names the image's revision after its build record (`first_line`). `build_image.sh` writes the revision into `BUILD_INFO.txt` as `data_root_revision`, read from `DATA_ROOT_REVISION` in the entrypoint of the build context. It fails the build when the entrypoint does not set it to an integer exactly once. You can therefore tell before an import whether the runner of an image resumes the run, not only from an update at which the entrypoint runs no step
- **An argument for one Start takes effect in one run.** The runbook gives `--from`, `--mark-complete`, `--step-arg repository_cloning:"--fresh"`, `--step-arg ghs_download:"--accept-smaller"` and `--step-arg ghs_download:"--end-date YYYY-MM-DD"` for one Start. Left in `command:`, each would take effect again at every later Start, as [Deployment options](#deployment-options) describes. `settle_one_start_arguments` leaves out, with a warning, each such argument that `run_logs/one_start_arguments.json` records as used. `run_once` records an argument as passed before the runner starts, and as used after it when `took_effect` finds the effect in the pipeline execution state. The runner removes the steps that `--from` names from its record of completed steps only after its pre-checks. It writes that record just before the first step that it runs, or with the outcome `interrupted` after a Stop before that step. Beside the arguments that it passed, the entrypoint therefore writes into its record the steps that the state recorded as completed before the runner started (`completed_names`). It counts a `--from` as used only when the state changed during the Start, records no refusal, and either records a step that ran or no longer records as completed one of those steps. When a check of the runner stops the run before the runner takes the steps out of the record, such as `collection_inputs` when git cannot start, the runner writes the outcome `failed` with the record as it was and no step run. At the next Start, the entrypoint then passes the `--from` again, as after a refusal. At a Start after a kill, the runner resumes without the `--from` only when it had recorded its effect. A `--mark-complete` counts as used when the state records `marked_complete`. A `--fresh` takes effect when its step runs, which the step results show when the step ends. The runner writes the name of the step that it has started and that has not ended as `running_step`, and a kill inside the step leaves that name in the state. With `--fresh`, the cloning step removes the list of finished repositories first. The `--fresh` counts as used when the step results record its step or `running_step` contains it, and the list is gone or is another file than before the runner started (`finished_list_identity`, kept in the record as `finished_before`). Passed again, the `--fresh` would delete what the step collected. After a kill in an earlier step, the entrypoint passes the `--fresh` again at the next Start, and so it does after a step that failed to start, exited before it removed the list, or was stopped while its interpreter started. A start after the kill that runs no step, such as one that a check stops before its first step, leaves `running_step` as it was. `running_step_started_at` identifies the start that wrote it, and the entrypoint counts the name only for that start (`step_of_the_latest_start`). An `--accept-smaller` or an `--end-date` counts as used only when `sampling/ghs_retrieval_report.json` records the outcome `retrieved` for a retrieval that the file did not contain before the runner started (`taken_retrieval`, kept in the record as `retrieval_before`). A download that failed, was stopped or was killed before its record took no retrieval. Neither did a download that fell back, which exits 0 after a fallback for any reason, and without the argument, the download at the next Start would refuse the smaller export again. The step results do not decide it. A kill after the download exited 0 and before the runner recorded the step leaves no result, and at the next Start, the runner records the step from its `exited` record without running it. If the step results decided it, the argument would stay in `command:` and let every later download take a smaller export. The record of the passed arguments survives a reboot that kills the container, and at the next Start, the entrypoint decides from it and the state. Every other argument is a setting. Leaving the removal to the operator would make every later Start depend on an edit that nobody checks, and a `--from` forgotten in `command:` would hold back every later monthly run without a message. The entrypoint recognizes these arguments by their full names, `--from`, `--mark-complete`, `--step-arg`, `--fresh`, `--accept-smaller` and `--end-date`, also in the forms `--from=NAME` and `--end-date=DATE`. By default, argparse takes an abbreviation of a long option for the option. A runner would take `--fro release` for `--from release`, and the cloning step `--fre` for `--fresh`, and such an argument, which the entrypoint passes as a setting, would take effect at every Start. Every parser of the pipeline therefore takes long options by their full names only (`agentcontext.cli.ArgumentParser`), and at the first Start with an abbreviation, the runner stops with a usage error
- **After a fallback of the GHS download, the entrypoint ends the Start with a warning.** The download exits 0 after a fallback, the run completes over the previous sampling frame, and the pipeline execution state records a success. A GHS that stays smaller, or a crawler that stays stopped for a language that the sampling frame keeps, makes every later download fall back to the same retrieval. `warn_after_fallback` compares the record of the GHS download at the end of the Start with its bytes at the start. When a run of the Start rewrote the record with the outcome `fallback`, it logs a WARNING as the last line of the Start. The warning names the retrieval, the reason and the downloads in a row that fell back, which the download counts in the record. After the download refused a retrieval in its size check, the warning also names the `--step-arg` that takes the retrieval. After a Start that ran no download, the record is unchanged, and the entrypoint logs no such warning
- **A step of the analysis stage that fails does not hold back the next month.** The analysis reads the output CSVs that the publication wrote and writes figures and tables, which a checkout can produce again from the handover. The last run may have failed in a step after its release step, which in the pipeline's order is a step of the analysis stage (`failed_analysis_step`, checked against `run_pipeline.compose` by a test). `monthly_argv` then treats the run as completed, the entrypoint logs a warning that names the step, and the data root of the failed run is packed before the next run begins. Resuming the run first would run the failing step again at every Start, and the monthly collection would wait for a repair of the analysis. The step results are those of the last start that ran a step, which the runner records as `last_run_steps`, because a start at which the pre-checks failed writes step results in which no step ran. Read from the latest start, the step results would make the runner resume the failed run at the Start after a monthly Start at which the pre-checks failed. Running the failed step again would change the time in the record of the packing, and the entrypoint would pack the data root a second time. A step that failed before the release step, such as a check of the collection that the release does not read, leaves the run without a complete collection, and the runner resumes it at the next Start
- **A completed run's handover is the data root without the clones in progress, under its repository path.** `7zz x -snld` over a checkout then puts every file where the repository keeps it ([development](development.md#handover-working-copy)): the retrieval, the sampling frame, the cache of labels and the sample, the collected and validated trees and their lists, the output CSVs, the caches, `finished_repositories.jsonl`, the shards, the release, the clone logs, the figures and the machine record. Symlinks are stored as links, `-snl`, because the collector writes symlink markers on purpose. Without the option, 7zz stores the target's bytes and fails on a dangling marker, and the sample contains such markers. The archive is written under a `.partial` name and renamed when 7zz is done, and a `SIGKILL` during the packing leaves nothing that looks complete. The archive is synced to the disk before the rename (`sync_file`), and its directory after the rename (`sync_directory`). The record of the handover is written the same way after the archive. After a power loss, the record never contains the name of an archive with bytes that were lost, and the next monthly run never replaces a data root that only such an archive contains. A failed sync of the file fails the packing. A filesystem that refuses to open or sync a directory is left as it is, as `caches.sync_directory` leaves it. The data of the file is on the disk either way, and an error there would fail every packing on that filesystem, so that no monthly run could begin. The entrypoint leaves out of the archive the clones in progress and the GHS download that a Stop interrupted, by their paths (`HANDOVER_EXCLUDED_PATHS`). It also leaves out the files that Python and Finder write, by their names, and every directory named as in `paths.DISCARDED_DIRECTORIES`, `@eaDir`, at any depth (`seven_zip_excludes`). DSM writes and changes such directories in a shared folder at any time. One that changes while 7zz reads it makes 7zz warn, which fails the packing. No step reads such a directory: `collected_file_cleanup` deletes it from the validated tree, and the runner leaves it out of the manifest of the collected tree. The wildcard ends with a slash, and 7zz leaves out a directory and keeps a file of that name, which the runner describes as any other entry. The names are repeated in `DISCARDED_DIRECTORIES` of the entrypoint, because the entrypoint has to run even where the package cannot be imported, and a test checks that the two sets are equal. The download is left out by its path, not by its `.part` suffix, because a configuration artifact of the sample can have any name. Packing requires 7-Zip exit 0. Because a warning can mean omitted files, exit 1 fails the packing. The entrypoint removes the temporary archive, and the container log keeps 7-Zip's complete output. When the entrypoint ends 7zz on a Stop, the packing fails too (`PackingStopped`). The container then exits as after any other Stop: with the runner's code, which after a run that exited 0 is `128 + signal`, not with the 1 of a packing that failed for a cause that you correct. The name has the time and the outcome, `complete`, `stopped`, `failed` or `killed`, and the archive of a partial run is marked as partial. A `SIGKILL` leaves nothing packed, which is why the stop grace period in `compose.yaml` covers both the time that the runner needs to finish its work in progress and the packing
- **Each archive has its SHA-256 beside it.** After the entrypoint packed an archive and wrote its record, `record_checksum` hashes the archive and writes `<archive>.sha256` beside it, in the format that `sha256sum -c` and `shasum -a 256 -c` read, and the log names the checksum. A download can then be checked against the archive that the entrypoint packed before you extract it, and `docs/dataset.md` records the checksum of that archive. The hash follows the record, so that a kill during the hashing leaves the handover recorded. The file is written under a `.partial` name, synced and renamed, and a kill leaves no file with a wrong checksum. When the file cannot be written, the entrypoint logs a warning and fails no handover, because the archive is complete without it
- **The machine is recorded rather than entered by hand.** At every start that passes the checks of the mounts, the lock and the directories, the entrypoint writes `run_logs/machine.json` under the data root, after the handover of a previous run that the next monthly run replaces, and logs one line. The record holds the processor's model and count, the CPU quota of the container's cgroup, the memory and any cgroup limit, the process ceilings, the cgroup's pids limit, `pid_max` and `threads-max`, and whether an init process is there. It also holds the state volume's filesystem, size and free space, the kernel, the architecture, the hostname, the image's build record, and the first line that each of git, 7zz and rsync prints about its version. The image installs the versions of the three that `mise.toml` pins, and the record shows the versions that a run had. git determines `created_at` and `first_commit_sha` through its own rename and copy detection (`docs/git.md`). The ceilings are recorded because a run can run out of processes, and the record of the first deployment, which did, could not show which ceiling it hit. The CPU quota is recorded beside the count, because `os.cpu_count()` counts the host's processors, also in a container that a `cpus:` limit or `docker run --cpus` confines to fewer. `_cgroup_cpu_quota` divides the quota by the period, from `cpu.max` of cgroup v2 or from `cpu.cfs_quota_us` and `cpu.cfs_period_us` of cgroup v1, in which -1 sets no quota. The record contains no quota where the cgroup sets none. The machine's model is not visible from inside a container, but the processor's model is. The entrypoint does not measure the uplink, because the run itself measures it as repositories finished per hour since the collection started. The measure uses the rows of `data/collected/repos.csv` with a `scanned_at` after the start that the name of the latest collection in `finished_repositories.jsonl` gives, against the bytes per clone that the sample recorded. A row that the collection took over keeps the `scanned_at` of an earlier collection and cost no clone

### Error handling & edge cases

| Case | Behavior |
|---|---|
| A directory under `/app` is not a mount, or does not exist | One line names every such directory. Exit 1 before anything is written |
| The runner exits, with any code, after a step ran or could not be started | The handover is packed and named after the outcome. The container exits with the runner's code, `128 + signal` for a signal death |
| The runner refused before any step ran, on its lock, its pre-checks or its check for modified inputs, or recorded a step under `--mark-complete` | No archive. The pipeline execution state is unchanged, or records the refusal or the `--mark-complete` run. The log reports the refusal, and the container exits with the runner's code |
| The run completed and every step was skipped | No archive when `run_logs/complete_handover.json` contains a `-complete` archive packed after the last start that ran a step finished, whether or not the archive is still in `handover/`. The log names the archive. Otherwise the data root is packed. Without room for it, nothing is packed when the record contains a `-complete-without-sample` archive packed after that time |
| The pre-checks failed at the scheduled Start, and the entrypoint began the month's run at a later Start in the same month, as late as its last day | At the next scheduled Start, the entrypoint begins the next month's run, because its calendar month is later than the month of the download |
| DSM's Task Scheduler starts the container at 00:00 on the first of a month in a zone east of UTC, where it is still the month before in UTC | The entrypoint compares the calendar months in the NAS's time zone, which the zone file mounted at `/etc/host-localtime` holds, and begins the month's run. The log names the zone |
| The container has no time zone file at `/etc/host-localtime`, or one that cannot be read | The entrypoint compares the calendar months in UTC, and a WARNING names the file to mount |
| The container was created from a `compose.yaml` without `AGENTCONTEXT_COMPOSE_REVISION`, or with another value than the image requires, such as one of an earlier bundle | One ERROR line that names the files to copy from the bundle of the same build. Exit 1 before anything is removed, packed or written |
| `run_logs/data_root.json` contains an earlier data root revision that the image converts, such as revision 1 of the run that began on 2026-10-23 | The entrypoint converts the stored files before any step and logs which files it rewrote, and the runner resumes the run. A kill during the conversion leaves the original files or the record of the renames still to make, and the next Start finishes the conversion. A part of the cache of labels that does not match the checksum of the index, or a file that cannot be written, ends the start with exit 1 and one ERROR line, and the files that the conversion has not replaced stay as the earlier image wrote them |
| `run_logs/data_root.json` contains another data root revision than the image's that the image does not convert, or cannot be read, or the data root has `run_logs/state.json` and no such record, as the data root of the first run on the NAS has | One ERROR line that names the record, the revision and two remedies: an import that resumes the run, of the image in the record or of another image with a `BUILD_INFO.txt` that names that revision, and a clean run in an empty project folder. Exit 1 before anything is removed, packed or written |
| `TZ` names a zone with an offset other than zero, or `/etc/localtime` or the zone file of UTC gives such an offset, as after a mount at `/etc/localtime` | One ERROR line that names the cause. Exit 1 before anything is removed, packed or written |
| `command:` names an abbreviation of an argument for one Start, such as `--fro release` or `--step repository_cloning:--fresh` | The runner stops with a usage error, and the container exits 1 with no step run. This happens at every Start until you write the argument in full |
| `command:` still names an argument for one Start that the run of an earlier Start used | A WARNING names it and says to remove it from `command:`. The entrypoint leaves it out and decides as without it: the runner resumes the run, or the entrypoint begins the month that is due. A `--step-arg` value keeps its other words |
| The runner refuses a Start that passes an argument for one Start, on its lock, in its pre-checks or in its check for modified inputs, or a kill ends the runner before it writes its pipeline execution state | The entrypoint passes the argument again at the next Start |
| A reboot kills the container while the runner runs with an argument for one Start | The record lists the argument as passed, and at the next Start, the entrypoint counts it as used when the pipeline execution state shows its effect |
| The GHS download of a run that passes `--step-arg ghs_download:--accept-smaller` or an `--end-date` fails, is stopped or is killed, or falls back to the previous sampling frame and ends `ok`, such as when GHS does not respond | The download took no retrieval, and the entrypoint passes the argument again at the next Start |
| A run of a Start, a resumed run, a run over a completed one or a monthly run, completed, or failed in the analysis stage after its release step, and the next month became due during it | The entrypoint packs its handover, begins the next monthly run, packs the handover of that run after it, and decides again. It packs the data root of a run that failed as `-complete` before the next run. It begins no next run when no `-complete` archive contains the data root of the run before it, which an error states, or when a Stop arrived during the Start, which the log states. A record that cannot be written causes no second packing of the data root |
| A monthly run left `sampling/ghs_retrieval_report.json` as it was, and the next month is due when it ends | A WARNING names the file, and the entrypoint begins no other monthly run. It decides again at the next Start |
| A check of the runner stopped a monthly run before its first step, after a run that completed or failed in the analysis stage after its release step | A WARNING says that the monthly run ran no step, and the entrypoint begins no other monthly run. The runner's ERROR line names the check. The entrypoint decides again at the next Start |
| A run of the Start rewrote `sampling/ghs_retrieval_report.json` with the outcome `fallback` | The entrypoint ends the Start with a WARNING that names the retrieval, the reason and how many downloads in a row fell back, and after a refused smaller retrieval, `--step-arg ghs_download:--accept-smaller` |
| The last run failed in a step of the analysis stage after its release step, and the next month is due | A WARNING names the failed step, the data root is packed as `-complete` when the record contains no such archive of it, and the next monthly run begins without resuming the failed run |
| The pre-checks failed for the monthly run of a Start after a run that failed in the analysis stage | At the next Start, the entrypoint begins the monthly run again. The record contains the archive that the entrypoint packed at the refused Start, and the entrypoint therefore does not pack the data root again |
| The last run completed, and `sampling/ghs_retrieval_report.json` is missing or cannot be read | A WARNING names the file and the `--from` arguments that begin the month. The runner continues the completed run, and the entrypoint begins no next monthly run |
| The entrypoint begins the next monthly run at a Start, and `run_logs/complete_handover.json` contains no `-complete` archive of the previous run | The data root is packed before the runner starts and before the entrypoint writes the machine record and the copies of the heuristics files of the Start. Under the image that ran the run before it, the run rewrites only `analysis/` and `run_logs/`, which the handover of the run before it contains unless its packing failed. The entrypoint packs the handover of the run at its end, as after any other run. A step of the analysis stage after the one that failed is not listed and counts as a step before the analysis stage, as in the row above |
| The pipeline execution state has no `last_steps_finished_at`, as a runner that does not record it writes the state | The record of its handover has null in place of the time and matches the state until a start runs a step. | A Stop arrives after the runner's last step, or after the runner ended, while the entrypoint measures the data root or the handover directory | The Stop is recorded, and the handover of the run that just ended is packed. | A Stop arrives before the runner starts | No runner starts, and the container exits `128 + signal`. ## Recovery from handover and storage errors

The outcome of the pipeline and the delivery of the handover are separate results.
Keep the project folder and export the log before you replace images, clean a volume or reset
the collection. The directories below are relative to the project folder on the NAS. Start, stop
and build in the rows below refer to the actions in [Import, create, start](#import-create-start).

| Message or error | Consequence and recovery |
|---|---|
| `The handover could not be packed` | `7zz` or a filesystem operation failed after the processing ended. The project data and logs remain on the mounted volume, but the expected archive is missing. Correct the storage or permission error that the message names, and keep a complete copy of the project data. You do not need to start the collection again to retrieve existing results. After the failed packing, the entrypoint wrote no record. At the next Start that skips every step, it therefore packs again, and at the next Start that would begin a monthly run, it packs first and begins the run only when that packing succeeds |
| `The handover was not packed, because a Stop (signal N) ended 7zz` | A Stop arrived while 7zz packed, and the container exits with 128 plus the signal after a run that exited 0. Nothing needs to be corrected. The files remain in the project folder, and the entrypoint packs them at the next Start, as after a packing that failed |
| `No handover contains the data root of the previous run` | At this Start, the entrypoint would have begun the next monthly run, or a run with a `--from` of `command:` that names a stage or step before the analysis stage. Either run rewrites the data root of the previous run, and no `-complete` archive contains that data root. No runner started. The line names the cause. For `its packing failed`, correct the error of the packing that the line gives. For `the data root does not fit on the handover volume`, make room on the handover volume. Archives that you delete in File Station free no space while the Recycle Bin of the shared folder keeps them in its `#recycle` folder. Empty it in Control Panel, Shared Folder, the shared folder of the project folder, Edit, Empty Recycle Bin. A snapshot of the shared folder keeps the space until its retention ends. Then start the container again. Before a run with such a `--from` in `command:`, the entrypoint packs the data root first in the same way, and it begins no such run without an archive of the data root either |
| `The pipeline execution state /app/data/run_logs/state.json cannot be read` or `is not a JSON object` | No step ran, and nothing was changed. Keep a copy of `data/run_logs/state.json`. Put in its place the `data/run_logs/state.json` of the latest archive in `handover/`, which the runner wrote at the end of the last start that ran steps, and start the container again. A step that completed after that archive was packed is not in its state, and the runner runs it again at the next Start. Deleting the file instead discards the record of every completed step, as [runner recovery](runner.md#recovery) describes |
| `the record of its GHS download ... does not exist` or `cannot be read` | The last run completed, and no monthly run begins until the start of its GHS download is known. Restore `data/sampling/ghs_retrieval_report.json` from the latest `-complete` archive, or put `--from ghs_download --from repository_cloning` in `command:` for one Start and build the project to begin the month |
| `Could not remove ..., which a killed process left` | The named files or directories in `data/sampling/ghs_retrievals/` or `data/collection/_scratch/` take free space that the pre-checks measure. Correct the permission or storage error that the message names, or remove them while the container is stopped |
| `Could not pack the collected and validated trees` | The archive of the state and logs was already saved, but its `-trees` companion, which contains the collected and validated trees, was not. Retrieve `data/collection/data/collected/` and `data/collection/data/validated/` from the project folder as well. The container exits with the runner's exit code |
| `Did not pack the whole data root ... less than twice that` | The run completed. Instead of the data root, which would have filled the handover volume, the entrypoint packed the pipeline execution state, the logs and the lists, and the trees when they fit. Make room, emptying the Recycle Bin of the shared folder after you delete archives as the row above describes, and start the container again. At a Start that skips every step, the entrypoint packs the data root when `run_logs/complete_handover.json` contains no `-complete` archive of the run. You can also copy the data root from the project folder. At a Start that would begin the next monthly run, the entrypoint packs the data root first, and it begins no new month while the data root does not fit |
| `Did not pack the collected and validated trees ... less than twice ...` | The entrypoint skipped the packing on purpose, because the handover volume had less than twice the size of the collected and validated trees free. The skip does not mean that the collection lost the files. Retrieve them from the project folder |
| `Did not pack the collected and validated trees again, because ... contains them as they are` | The named `-trees` archive in `handover/` contains the trees as they are, and the entrypoint packed no copy of them. Keep that archive until you have downloaded it. To make the entrypoint pack the trees again at the next Start that packs them, delete `data/run_logs/trees_handover.json` |
| `Calendar months are counted in UTC, because there is no time zone file at /etc/host-localtime` or `because /etc/host-localtime cannot be read as a time zone file` | The container does not read the NAS's time zone, and a scheduled Start early on the first of a month can fall in the month before. Mount the NAS's `/etc/localtime` read-only at `/etc/host-localtime`, as the shipped `compose.yaml` does, build the project, and check the zone in the log of the Start after the Build. A mount at `/etc/localtime` would shift every commit time that the cloning step writes ([A run every month](#a-run-every-month)) |
| `The compose.yaml that created the container sets no AGENTCONTEXT_COMPOSE_REVISION` or `sets AGENTCONTEXT_COMPOSE_REVISION to ...`, with `this image requires revision N` | No step ran, and nothing was changed. The project's `compose.yaml` is not the one from the image's bundle, as after an import of a new image into a project created from an earlier bundle. Copy `compose.yaml` and `deploy.md` from the bundle of the same build as the image into the project folder, add again what you had added to `command:`, and build the project again |
| `The data root /app/data has a pipeline execution state (run_logs/state.json) and no record of its revision`, `is of data root revision ...` or `has a record of its revision ... that cannot be read`, with `This image reads only the stored formats of data root revision N` | No step ran, and nothing was changed. An image of a data root revision that this image does not convert, or an image that writes no record of the revision, began the data root. Since revision 2, an image converts a data root of revision 1 instead ([Restarting and updating](#restarting-and-updating)). To resume the run, import the image that the line names, or another image with a `BUILD_INFO.txt` that names the revision in its `data_root_revision` line. Copy `compose.yaml` and `deploy.md` from the bundle of its build, and build the project again. To run this image, download `handover/` and export the log, and follow [A clean run](#a-clean-run) with the image and its bundle |
| `Could not convert the data root /app/data to revision N (...)` | No step ran. The parentheses name the file, such as a part of the cache of labels that does not match the SHA-256 that its index records, or the error of a write, such as a full volume. Correct the cause, or replace the file with its copy in the latest archive in `handover/`, and Start again. The next Start finishes the conversion |
| `The environment of the container sets TZ=..., which gives the offset UTC+... on ...` or `... gives the offset UTC+... on ..., because compose.yaml mounts a file over the zone files of the image` | No step ran, and nothing was changed. The project's `compose.yaml` sets `TZ` to a zone other than UTC or mounts a file over `/etc/localtime` or the zone files of the image, and every commit time would be shifted. Copy `compose.yaml` from the bundle of the same build, which mounts the NAS's zone file at `/etc/host-localtime` only, and build the project again |
| `The next month is due, but the monthly run that just ended left the record of its GHS download ... unchanged` | The monthly run took no new retrieval, and the record still contains the download before it. Read `data/run_logs/ghs_download.log`. At the next Start, the entrypoint decides again and begins one monthly run when the month is due |
| `The monthly run that just ended ran no step` | A check of the runner stopped the monthly run before its first step, and the runner's ERROR line above names the check. Correct its cause. At the next Start, the entrypoint decides again and begins one monthly run when the month is due |
| `The GHS download fell back to the previous sampling frame` | The run completed over the sampling frame of the retrieval that the line names, and the window did not move. Read `data/run_logs/ghs_download.log`. A fallback after no response or after a stopped crawler needs nothing, because the download takes a retrieval again at the next monthly Start. When several downloads in a row fell back because GHS exported far fewer rows, and GHS has lost those rows for good, put `--step-arg ghs_download:"--accept-smaller"` in `command:` for one Start and build the project. Alone, the argument takes effect in the next monthly run. With `--from ghs_download --from repository_cloning`, the download takes a retrieval at the Start after the Build |
| ``The `command:` of compose.yaml still names ..., an argument for one Start that the run of an earlier Start used`` | A run of an earlier Start used the argument, and the entrypoint left it out at this Start. Remove it from `command:` and build the project. Until then, the entrypoint leaves it out at every Start with the same warning. To pass it for another Start, remove it and build the project, which makes a Start without it, then add it again and build the project once more |
| `Could not write the machine record` or `Could not create /app/data/collection/_scratch` | No step ran. Correct the named cause, such as a full volume or a file in the way, and start the container again |
| `7zz exited 1` | The packing treats the warning as a failure, logs the complete output and removes the incomplete temporary archive. Correct the reported cause. The project files remain on the volume |
| `7z warned while packing` from an earlier image | Earlier images accepted exit 1 and saved the archive. Review the omitted or unreadable files, test the archive's integrity with `7zz t <archive>`, and compare the expected contents with the source directories. An intact archive can still omit files |
| A `.7z.partial` file | Packing did not finish, and the file is not the completed handover. Keep the project data, and use an intact archive or copy the source directories before processing. At the next Start, the entrypoint removes the file before it measures free space |
| `7zz` failure while creating `release/repos_data.7z` | The failure is in the `collected_files_archive` step, which requires exit 0 and keeps the earlier archive on a failed attempt. Correct the cause, and run `collected_files_archive` and `release` again, on the NAS with `--from collected_files_archive` in `command:` for one Start and a Build. An existing archive alone does not establish that it belongs to the new release |

The archive of the state and logs of a stopped, failed or killed run is not a complete
collection on its own. Its `-trees` companion also omits `collect_commits/`,
`clone_logs/` and `data/file_lists/`. Retrieve those directories from
`data/collection/` on the NAS to validate the evidence. Keep the files of one collection
together, because the cloning step can resume a collection over several starts. Copy them while
the container is stopped, or use a consistent filesystem snapshot.
[Prepare a working copy of the handover](development.md#handover-working-copy) and follow
[the regeneration order](development.md#continuous-improvement-from-handovers).

`ERROR runner:` messages name a step failure or a problem with the state or an output.
[The stop rule](#the-stop-rule) and [runner recovery](runner.md#recovery) cover those cases. Errors about commit
logs or checksums require [evidence recovery](steps/commit_reclassification.md#recovery), not
only a successful extraction of the archive.
