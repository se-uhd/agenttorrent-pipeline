# Configuration collection

## Context

The cloning step collects the configuration artifacts of the six tools (i.e., Claude Code, Gemini CLI, OpenAI Codex CLI, GitHub Copilot, Cursor and OpenCode) from a list of GitHub repositories. It clones each repository, records its submodules without checking them out, and copies every matching configuration artifact or directory, and every planning document, into a directory of the repository in the collected tree. It then records a boolean flag per tool and for files such as `CLAUDE.md` and `.cursorrules` ([Output](#output) lists them), and deletes the clone.

The input is a CSV with a `repo_name` column in which every value is a whole `owner/repo` identifier (default `../classification/repos_annotated_included.csv`, which the `engineered_project_selection` step writes). The step also reads `repos_excluded.csv` beside it, when it is there, for the repositories that the labeling found gone. The output is the collected tree (`data/collected/`, `--collected-dir`), with one directory per repository and two lists at its root: the collected list (`data/collected/repos.csv`, `--collected-csv`) and the list of clone failures (`data/collected/clone_failed.csv`, `--fail-csv`). Each list is inside the tree that it lists rather than beside it, so that the tree keeps its own index wherever you move or extract it. `repos.split` expects those two names, and a run therefore does not log the file that a step wrote a moment earlier as a stray.

Repository cloning is the first step of the collection stage. The collected tree holds what the collection copied, and no later step changes `data/collected/` in place. `agentcontext/steps/collected_file_cleanup.py` (cleanup and validation) reads it, copies the repositories and derives the `data/validated/` tree with its `data/validated/repos.csv`. Every later step reads the validated tree, and the published dataset of configuration artifacts comes from it. After a failure in the cleanup or a later step, run the cleanup and the steps after it again with `python3 -m agentcontext run --from collected_file_cleanup`, without cloning the sample again. The detection heuristics specify which files and directories count as configuration for each tool ([Per-tool collection heuristics](#per-tool-collection-heuristics) below). The cloning step implements those heuristics, and `agentcontext/steps/collected_file_cleanup.py` applies them again, independently, after it.

## Key decisions

- **A clone that failed on the network or the machine is tried again by the next run that runs the step, and so is a repository that the step itself failed on.** `clone_failed` and `collector_error` are the transient outcomes, `TRANSIENT_OUTCOMES`. The list of finished repositories keeps their lines, and the lists that a stopped run writes are therefore complete. A resumed run treats such a repository as pending and appends a newer line that replaces the old one. A refusal by GitHub, `not_found_or_no_access`, `dmca_takedown` or `disabled_by_github` (`clone.PERMANENT_OUTCOMES`), concerns the repository itself, and the outcome stays for the collection. `file_name_too_long`, a name in the tree of the repository that the file system of the machine cannot write, stays for the collection too, and the next collection clones the repository again. `size_bound_exceeded` stays in force only under the size bound under which the step recorded it. The line records the size bound, and a run under a larger size bound clones the repository again, as it fetches a history again after the size bound stopped the fetch. A repository with a line from before the lines recorded the size bound is cloned once more. `time_bound_exceeded`, a clone that the time bound ended twice, stays in force for the rest of the collection that wrote the line, under the time bound that the line records (`resume.time_bound_holds`), whatever import heuristics the line records. A run under a larger time bound or the next collection clones the repository again. A transfer that the time bound stopped on one day can finish on another, and the step therefore does not keep this outcome across collections, as it keeps `size_bound_exceeded`. If the outcome held under every bound, no later collection would clone the repository, also after the size bound is raised. When a container can no longer start processes, the step records `clone_failed` for most of the sample within minutes, and a resumed run that kept those outcomes would publish a sample with most of its repositories missing.
- **A failure of the step after the clone is recorded under its own name, with its traceback.** An exception in `process_repo` after a successful clone, such as an output tree that cannot be written or a path that the reader cannot decode, is `collector_error`. Its traceback goes to stderr and to the clone log, and it counts toward the failure ceiling as a failed clone does. The step also counts `collector_error` outcomes separately: `--max-consecutive-failures` of them among the last `ERROR_WINDOW` finished repositories stop the step without the network probe. A git process that cannot be started, for example because `fork()` fails, is a failed attempt inside the retry loop, with the backoff. Outside the loop, the step would give up on a repository after one attempt in which `fork()` failed within a millisecond.
- **The workflow files are kept beside the collection.** A workflow that runs an agent contains the prompt that the agent runs with, and that prompt is configuration. The pipeline matches <!--s:heuristics.config_path_patterns.workflow_files:words-->six<!--/s--> workflow files by name, as a documented configuration path: Copilot's `copilot-setup-steps.yml` and `copilot-code-review.yml`, Claude Code's `claude.yml` and `claude-code-review.yml`, the Gemini CLI action's `gemini-dispatch.yml`, and OpenCode's `opencode.yml`. A workflow under any other name counts when it runs a documented agent action (`workflow_uses:`), is a GitHub Agentic Workflow with an engine of one of the six tools (`workflow_engine:`) or runs a documented headless invocation of a tool in its shell (`workflow_command:`). `paths.collect_agent_workflows` copies those workflows into the collected tree. It also copies the files that a GitHub Agentic Workflow imports, because its engine can come from one of them, and the prompt file that a step running the Codex action or the Claude Code Base Action names in its input `prompt-file` or `prompt_file` (`paths.action_prompt_files`). `collected_file_cleanup.is_agent_workflow` keeps them. The cleanup deletes every other workflow file, which is ordinary CI, from a collected `.github` as an irrelevant file. In the `deletion.csv` of the collection that the checkout tracks, <!--s:collection.github_deletions_workflow_yaml-->25,924<!--/s--> of the <!--s:collection.github_deletions-->50,308<!--/s--> files that the cleanup deleted from `.github` are workflow YAML. While the clone is still on disk, the cloning step therefore copies the `.github/workflows/*.yml` of each repository into `data/workflows/<owner§repo>/`, a tree that no step reads and no CSV records, and the copy changes no published value. The handover contains the tree, and from it you can decide, rather than guess, whether a workflow with a `prompt:` key is a configuration artifact. The copy takes at most <!--s:parameters.agentcontext.paths.MAX_WORKFLOW_FILES-->50<!--/s--> files of at most <!--s:parameters.agentcontext.paths.MAX_WORKFLOW_BYTES-->256<!--/s--> KiB each and skips a larger file, and a repository with a thousand generated workflows therefore adds at most <!--s:parameters.agentcontext.paths.MAX_WORKFLOW_FILES-->50<!--/s--> files to the tree. A failed copy is a warning, because the purpose of the run is the collection, and the workflow files are a supplementary record of it. `--no-workflows` turns the copy off.
- **Keep the file list of each successfully cloned repository.** `git -C <temporary-clone> ls-tree -r -z HEAD` lists every tracked file, symbolic link and gitlink at the collected HEAD commit. `clone.write_file_list` saves the mode and path of each entry, NUL-separated and xz-compressed, to `data/file_lists/<owner§repo>.ls-tree.xz`. The file lists also cover the repositories from which the collection copied no configuration, and `clone.read_file_list` reads them for an offline review of the heuristics. The file list omits object IDs, because it serves path analysis rather than content retrieval. `--no-file-lists` turns the file lists off. A failed clone creates no file list. If the replacement clone of a retry fails on the network or exceeds the time bound twice, the retry keeps the earlier successful collection and its file list under the conditions that [Key decisions](#key-decisions) gives for a retry of an ok line, also for a repository from which the earlier collection copied nothing. A repository that `clone.read_snapshot_metadata` found to be empty, with no HEAD and zero commits, gets an empty file list and `entries` of 0 without running `ls-tree`. A missing file list therefore always means a failure. If Git cannot list HEAD of a repository with commits, the step logs the repository, the clone path, the command, the exit code and Git's stderr, and appends that message under `FILE_LIST_ERROR` to the clone log of the repository. The step goes on copying the configuration, but the file list and the submodule rows are unavailable, and the step removes a stale file list so that it cannot describe the wrong revision. When the step cannot write the file list, its warning gives the destination and the operating-system error, and the step removes any stale file list too. Neither failure means that the repository contains no configuration.
- **Copy the files that the imports reach to a tree of their own.** After the passes that copy the configuration artifacts, `imports.collect_imports` reads every copied file that a row of `heuristics/import_patterns.csv` names as an importing file. It reads the file in the clone, where the tool reads it, and follows its imports as the row states: the syntax, what a path resolves against, the hops and the limits ([heuristics](../heuristics.md#imports)). Every file inside the repository that an import reaches is copied to `data/imported/<owner§repo>/<path>`, also where the collection copied it too, so that the tree holds what the tools read. A target counts where it is a regular file after its links, outside `.git` and outside the gitlinks that `submodules.csv` records, and where each name of its path is the entry of its directory in case. A chain of Claude Code or Gemini CLI from a root file in another case looks a name up ignoring case where no entry has it in its case ([heuristics](../heuristics.md#the-rows-of-each-tool)). A file that no chain reads because of its extension, its content, its size or a link on its path is a stub in the tree, without its bytes. The stub has the size of the file, or one byte more than 4 MiB, the largest limit of a row, where the file is larger than that. Its first byte is not UTF-8 where the text of the file is not valid UTF-8. The import detection step, which reads the imported tree, then gives the file `not_read` or `over_limit` as the chain did in the clone, and the bytes of such a file never reach the tree, whatever its size up to the bound of the clone. A list beside the directory of the repository, `data/imported/<owner§repo>.stubs.json`, contains every stub. The copy removes the list of an earlier collection, so that a stub of a kept earlier collection that other import heuristics read is `not_copied` rather than `found` ([import detection](import_detection.md)). The step does not copy a path that the archive step prunes, such as a session transcript of Claude Code or a log, and the import detection step marks it `pruned`. Nor does it copy a file with a path that is not valid UTF-8 after its links, because no CSV can hold the path. A file is copied to the path that its links lead to, and a path that leads there through a link becomes a relative link inside the tree. An importing file that is a link in the clone and contains an import becomes such a link too, and the import detection step reads its text there. The collected tree, the rows, the file list and the commit records are the same with or without the copy, which `tests/test_imports.py` checks over a real clone. A file that cannot be written ends the repository as a `collector_error`, as it does in a copy of the collection, because an imported tree written in part would be published. A failed clone or a collector error removes the imported files of the repository with the collection, and a retry that keeps the earlier collection keeps them too. `--imported-dir` sets the tree. The step creates the tree also where no import reaches a file, so that the import detection step can tell a collection without imported files from a collection that predates the tree.
- **The list of finished repositories keeps what each repository cost.** The line of a repository has `measures`: `seconds` for the whole repository, `clone_seconds` for the clone with its retries, `clone_bytes` for the clone on disk after it, `history_seconds` and `history_bytes` for the history fetch and the clone after it, `history_read_seconds` for reading the commit history, `entries` for the files, links and gitlinks at the collected commit, and `copied` for the files that the step copied. Each measure is present where its part of the work ran. The clone bounds of <!--s:parameters.agentcontext.git.bounds.DEFAULT_MAX_BYTES-->32<!--/s--> GiB and <!--s:parameters.agentcontext.git.history.GIT_TIMEOUT_SECONDS.hours:words-->one<!--/s--> hour were set from a probe of <!--s:clone_probe.repositories:words-->nine<!--/s--> repositories. The clone logs record only when each attempt starts, and they show how many repositories went over a bound but not how close the rest came. `read_finished` ignores `measures`, and the key therefore does not change how a resumed run behaves.

- **Stop repeated failures while preserving resumable progress.** After `--max-consecutive-failures` consecutive `clone_failed` or `time_bound_exceeded` outcomes (default <!--s:parameters.agentcontext.guards.MAX_CONSECUTIVE_FAILURES-->20<!--/s-->), the step probes `--probe-url` with the clone transport and authentication. After a failed probe, it starts no clone and probes again after each of <!--s:parameters.agentcontext.guards.PROBE_WAITS.length:words-->five<!--/s--> waits, from <!--s:parameters.agentcontext.guards.PROBE_WAITS.0.minutes-->5<!--/s--> minutes to <!--s:parameters.agentcontext.guards.PROBE_WAITS.4.hours:words-->four<!--/s--> hours (`guards.PROBE_WAITS`), with a `WARNING repository_cloning:` line for each wait. Without the waits, an outage of the network or of GitHub that passes would stop an unattended run until someone started the container again, with Action, Start in Container Manager ([deploy](../deploy.md#import-create-start)). When every probe fails, the step starts no new clone, lets the active workers finish, saves its progress and exits 4. A successful probe resets the count, and the collection continues. A stop during a wait ends the step as it does during a clone. A network that stalls transfers ends clones at the time bound rather than with an error, and `time_bound_exceeded` therefore counts as a failed clone here. The probe establishes only that the probe repository is reachable and shows nothing about the cause of the individual failures. Read the clone logs of the failed repositories, `clone_logs/<owner§repo>.log`, for those causes. `--max-consecutive-failures` `collector_error` outcomes among the last `ERROR_WINDOW` completed repositories stop the collection without a network probe, and their tracebacks identify the failing operations. After the retry rounds, the step also exits 4 when the transient outcomes exceed `--max-clone-failures`. The default ceiling is <!--s:parameters.agentcontext.guards.CLONE_FAILURE_SHARE.multiplier:words-->three<!--/s--> times the failure share observed in the March collection, rounded up and at least <!--s:parameters.agentcontext.guards.clone_failure_ceiling.minimum:words-->one<!--/s-->. A value of zero disables the ceiling.
- **The step takes the sample in a fixed pseudo-random order.** `processing_order` sorts the pending repositories by the SHA-256 of their names. The input lists the sample in alphabetical order, which would run hundreds of repositories of one owner back to back. Their large clones would run side by side, and the repositories of an organization that no longer exists would fail one after the other. A stopped run would also have covered the names from `0x` to wherever it stopped. The hash order spreads the repositories of one owner over the run, and a stopped run covers a part of the whole sample. The order is the same in every run, and a resumed run therefore takes the remaining repositories in the same order. The rows that the step writes stay in input order, because the step assembles them from the input list.
- **The step retries, before it ends, the work that a later run would redo.** GitHub can return HTTP 400 to fetches for minutes, and a repository with a failed fetch would otherwise keep a `redo` mark for a run that someone has to start by hand, count toward the failure ceiling and be left to the file history step for its git columns. `collect_with_retries` runs the pass, waits `--retry-pause` (<!--s:parameters.agentcontext.guards.RETRY_PAUSE_SECONDS-->300<!--/s--> s) and runs the pass again over the same list of finished repositories, as a resumed run does. The repeated pass redoes a failed clone, a failed fetch of the commit history or query of the file history, a commit history that a machine failure left unread and a tree that is gone. It stops after `--retry-rounds` (<!--s:parameters.agentcontext.guards.RETRY_ROUNDS-->2<!--/s-->) rounds, or earlier when nothing is left to redo, and only then counts the remaining repositories against the failure ceiling. The step logs a `Retry round N of M` line for each round. A configuration built in code has no retry rounds unless it sets them, as it has no disk minimum.
- **A worker that ends unexpectedly stops the collection with resumable progress.** When a result or a submission reports `BrokenProcessPool`, the step records the repositories in flight as `clone_failed`, writes the lists and exits 4. A retry that the pool refuses at submission never began. The step therefore writes again the line that the repository had before it was marked `retrying`, and the next run keeps its earlier collection after a failed clone. The warning names the list of clone failures and states that the cause is unknown. Check the memory and process limits of the container and the operating-system logs, and lower the number of workers with `-w` if a limit caused the exit. A resumed collection retries the affected repositories. With one worker, the serial loop installs the same shutdown handler and restores the previous handler afterward.
- **A git process that the worker starts ends with the worker, whatever ends the worker.** On Linux, `bounds.run_bounded` runs every command under `setpriv --pdeathsig KILL`, util-linux's wrapper for the parent-death signal. When the kernel kills a worker, its clone process therefore ends too, rather than writing into the scratch directory until the container ends. Each process checks once whether the wrapper is installed and supports the option, and on a machine without it the command runs unwrapped. Python's `preexec_fn` can set the same flag, but its documentation calls it unsafe in a process with threads, and the size watcher runs a thread in every worker.
- **A commit history that a machine failure left unread is read by the next run that runs the step, and git that could not be started anywhere after the clone is a collector error.** When reading the commit history raises an `OSError`, a failure of the machine, the worker sets `transient` in the per-repository commit record. The parent process reads that record when it records the repository and writes `redo` into the line of the repository in the list of finished repositories. A resumed run treats such a line as pending, as it treats `clone_failed`. A resumed run also reads the per-repository commit record, because a tree written before the list recorded `redo` has only that record. It recognizes a `history_read_failed` record written before the step set `transient` by the exception in the `detail` of the record. When git refuses to read the history, the failure recurs, and the history is not read again. When the timeout ends the reading, only a run under a larger timeout reads it again. A run that ends with lines marked `redo` counts them with the rows of the list of clone failures toward `--max-clone-failures` and names them in its log.

  Everywhere else after the clone, a git process that could not be started raises `history.MachineFailure`, which the worker records as `collector_error`. `MachineFailure` covers the history fetch, the shallowness check, the root commit query and the history query of a file. The snapshot query, `clone.read_snapshot_metadata`, raises when git cannot start or a query fails on a repository with commits, and the worker records that failure as `collector_error` too. The HEAD readers that the snapshot query replaced returned '' and left a repository recorded with no `head_sha`, the column that identifies the snapshot. A history that does not arrive within the timeout or the size bound is `history_unavailable`, and the per-repository commit record records the timeout and the size bound. Under the same bounds the failure recurs, and fetching again would cost a clone and <!--s:parameters.agentcontext.git.history.HISTORY_FETCH_TRIES:words-->two<!--/s--> attempts under the timeout per such repository in each run. A run with a larger `--clone-timeout` or `--max-clone-mb` fetches the history again, as the last log message of the run says. The file history step measures the git and AI columns of those repositories.
- **A resumed run reads the tree beside the list of finished repositories.** A repository that has a tool or file flag in its row, or a per-repository commit record, but no directory is pending again. An archive can restore the lists and the list of finished repositories without the collected and validated trees and without the per-repository commit records. A resumed run that read only the list of finished repositories would record every repository as collected with nothing on disk, and the collected file cleanup would refuse the tree in every later run. A repository that contributed only `.agents/` sets no flag, and a resumed run finds it through its per-repository commit record if the shards still exist.
- **A collector error leaves no tree, and a tree emptied of names that are not UTF-8 is no tree.** If the copied directory stayed after an exception, a run that ended under the failure ceiling would pass to the collected file cleanup a tree with a row of the collected list that records nothing copied, and the tree would be published with a blank branch and `head_sha`. For trees written before this decision, the collected file cleanup also leaves out a directory that is in the list of clone failures. A directory that the removal of undecodable names emptied would pass the check that decides whether to read the commit history, and the step would read the commit history of the depth-1 clone without having fetched that history.
- **The step checks in the clone whether the history fetch brought the history, and the fetch runs under the bounds of the clone.** A `--depth 1` clone stays at one commit when the timeout kills its `fetch --unshallow` during the transfer. If the step trusted a fetch that raised, it would measure every copied file against that one commit, cache the history as complete and never examine it again, with one WARNING line as the only record of the failure. The step checks the clone after the fetch with `rev-parse --is-shallow-repository`, because a fetch killed after git rewrote `.git/shallow` has left the history in place. The fetch runs under `--clone-timeout` and the size bound of the clone instead of the fixed timeout of the metadata module and no size bound. After a timeout, the step tries the fetch once more, and after a clone over the size bound, it does not.

  The fetch does not recurse into submodules (`--no-recurse-submodules`). By default, git fetches submodules on demand and parses the `.gitmodules` of the working tree before it fetches anything. A file that git cannot parse, such as a file with committed merge-conflict markers, would fail the fetch on every attempt with `exit`, and every run would collect the repository again without its history. The history of the repository needs no submodule. The step reads the date of the head commit with `git log -1` rather than `git show -s`. In a depth-1 clone, `git show -s` compares the tree of the commit with the tree of its parent, the empty tree, and reads the same file at a gitlink. The query would then fail, and the collection of the repository with it in every run, as a collector error. The queries over the history of each collected file run over an empty working tree for the same reason (`history.path_commits`, [git](../git.md)).

  Before the second attempt, the step deletes the lock files that the killed fetch left in `.git`. The timeout stops git with SIGKILL, the one signal after which git cannot clean up, and a `fetch --unshallow` holds `.git/shallow.lock` for its whole transfer. Without the deletion, the second attempt would fail at once on that lock, and the timeout would be recorded as a network failure, `exit`, which every later run fetches again. When the history is missing, the files get no history row, the file history step clones for them, and `ai_commits-repos.csv` records the repository as `history_unavailable` rather than `no_files`.

  `is_shallow_repo` returns None when its own git raised or exited non-zero. With False instead of None, a `fork()` refused at that one call would make a depth-1 clone count as having its history. A None from a git process that could not be started counts as a machine failure, and a None from a timeout as a failure of the repository. The step decides whether to read the commit history from the result of the fetch and does not check the clone a second time, because a second call under a refused `fork()` would return None and leave the history neither read nor recorded as not read.

  A history query that exits non-zero is also a failure, and the step does not read it as an empty history. On a blobless clone, such a failure is a network failure of the blob fetch that `--follow` needs, and read as a result it would give a row with two of its four git columns blank. This step and the measurement of the file history step therefore both leave the row out. The file history step then clones for it and writes both its git columns and its AI columns from the same <!--s:parameters.agentcontext.git.history.PATH_QUERIES:words-->three<!--/s--> queries in a clone at `head_sha`. The per-repository commit record also lists the file under `history_failed`, and the next run of this step collects the repository again, as it fetches a history again after a network failure.
- **A symlink target that is not UTF-8 becomes an escaped marker.** The step escapes the bytes that are not UTF-8 in the marker. Written with the strict default encoding, a link to such a name would be a `collector_error` in every run.
- **A name that is not UTF-8 is left out of the tree, and logged.** `.github/` is copied whole for every Copilot path, and a file name under it need not be UTF-8. `os.walk` and `rglob` yield such a name as lone surrogates, which the JSON of `finished_repositories.jsonl` escapes and on which the cache writer raises. After the copy, `remove_undecodable_names` deletes every such entry from the tree of the repository, and the worker logs what it left out through `paths.printable_name`, which escapes each byte that is not UTF-8 as `\xNN`. Escaping the decoded string instead would print the surrogate, `\udce9` for the byte `\xe9`. The test for this escaping runs only on a file system that accepts such a name, such as Linux's. No CSV of this pipeline can store the name. For the same reason, the submodule reader decodes the output of `git ls-tree` with a replacement character.
- **One reader of the shards.** `readable_shards` yields one entry for each per-repository commit record, with the csv beside it, or with None in two cases: the record does not parse, which is `shard_unreadable`, or the csv is missing. The assembler and the restriction of the detection step both read through `readable_shards`. Reading every csv on disk would put back the rows of a repository that the assembler had excluded, including the rows of a csv without a per-repository commit record, which a killed worker leaves. Every row is read into the current `COMMIT_COLUMNS` through `shard_rows`, blank where the shard lacks a column. The commit histories of successful repositories are never read again, and a column added later is therefore missing from the old shards. Read under the header of the first shard, a shard with another header would make both assemblers raise after the whole collection. The step logs a shard with another set of columns in its header once and identifies it by that header. Identified by a key of the per-repository commit record instead, a shard with the current header would be logged as foreign. A csv with a byte-order mark is read past the mark. A csv with an empty header or a header that is not UTF-8 is `shard_unreadable`. So is a per-repository commit record that parses but lacks the columns that the cloning step writes, or contains another value where a list belongs. The step reads the shards once per run. The assembler returns the repositories with histories that did not arrive, and the run logs them at its end from that list.
- **The shards are written under their names by a rename, and a per-repository commit record that does not parse is logged rather than fatal.** A worker killed between writing two files, at the end of the thirty-minute grace period of a Stop (`stop_grace_period` in `compose.yaml`) or by the kernel, can leave a torn per-repository commit record, which the assembler would read after the whole collection on every resumed run. The last line of `finished_repositories.jsonl` can be torn the same way. The next run would then append its first line to that line, and the reader would skip both lines.

  The step writes the per-repository commit records through `caches.replace_file`, and the shards and the commit log through a `.tmp` name and `os.replace`. Both ways sync the temporary file to disk before the rename and the directory after it, and the step syncs each line of the list of finished repositories before it goes on. Before it appends to the list of finished repositories, the step writes a newline when the last byte of the file is not one. A power loss of the NAS therefore leaves neither an empty per-repository commit record under its name nor an earlier line in force over files that the step has since replaced.

  Before the step writes the line that declares a repository finished, `process_repo` syncs every file that the line describes, that is, the collected tree, the workflow files, the file list and the imported tree with its list of stubs (`caches.sync_tree`), and the directories of the shards. The collection can remove what an earlier collection of the repository left, after a failed clone, after a collector error, or because the repository no longer has configuration. The step then syncs the directory that held each removed tree or file, so that a power loss does not bring the files back under a line that describes a collection without them. On ext4 and btrfs, the data of a file reaches the disk up to half a minute after a program writes it. After a power loss, a line synced before the data would describe a collection with empty files. In an earlier version, a resumed run took such a collection over as complete, and the cleanup then deleted the files as empty and dropped the repository.

  `caches.replace_file` removes only the leftover temporary files of the same name, so that two workers that write the records of `o/a` and `o/a.json`, `o§a.json` and `o§a.json.json`, at the same time cannot remove the temporary file of each other ([caches](../caches.md#storage-and-tests)). The assembler records a per-repository commit record that it cannot parse as `shard_unreadable`, with a warning. `main` writes `submodules.csv` before the assembly and turns an assembly that raises into an `ERROR repository_cloning:` line and exit 1, with every list already on disk.

  Before it closes the collection and exits 0, `main` syncs the directory of the commit CSVs with every file in it (`caches.sync_tree`). `commits.assemble_ai_commits` writes the CSVs by a rename without a sync, and `caches.replace_file` has already synced the lists and the caches. Without this sync, a power loss after the step exited could leave a collection that ended without its commit CSVs on disk, and the runner would record the step from its record of the exit (`record_exited_step`). `main` syncs these files and not the file system that holds them, because a sync of the file system waits for every write that is pending on the volume ([the runner](../runner.md)).
- **The GitHub access token reaches git through a credential helper, never through the URL.** In the clone URL, the GitHub access token would be in git's argv for the whole clone, in `.git/config` of the clone and in any message that echoed the command. `git.auth`, which the git metadata reader has used since 2.0.0, puts a placeholder user in the URL and supplies the password for git's prompt from an environment variable. `redact_token` remains in use for the logs.
- **Each clone log covers one collection, under `clone_logs/`.** A log appended across runs would grow with every run. `clone_with_retry` empties the log before the first attempt, and `--fresh` removes the directory. The attempts of an earlier run are in the handover of that run.
- **No LFS process filter.** With `filter.lfs.process=cat`, git would start `cat` as a long-running filter. `cat` does not implement the filter protocol, and for every LFS file git would write error lines into the clone log and kill `cat`. The step sets the option empty. Git then uses the two one-shot filters, which `cat` handles, and the checkout contains each LFS file as the pointer file that the repository stores.
- **The backoff is between attempts.** No wait follows the last attempt, because no attempt would follow the wait, and a wait there would only lengthen every `clone_failed`.
- **`--fresh` removes what a collection leaves.** If `--fresh` removed only the list of finished repositories, the shards, the clone logs and the collected repositories of the earlier collection would stay. The commit CSV would then contain commits of histories that the new run did not read again, and a repository dropped from the input would keep its tree for the collected file cleanup to read. `fresh_start` removes the list of finished repositories, `collect_commits/`, the clone log directory, the file lists, the workflow files, the imported files, the kept path heuristics under `collection_heuristics/` and every repository directory under the collected tree. It finds the repository directories through `repos.split`, and it therefore logs a symlink with the name of a repository as a stray and leaves it in place. Every directory goes through `paths.remove_tree`, which removes what Synology DSM writes into a directory while the directory is being removed. `fresh_start` leaves the two lists at the root of the tree, which the run rewrites and one of which is tracked. Pass the option only when you intend a new collection, on the NAS in a `--step-arg` of the `command:` in `compose.yaml` for one Start ([deploy](../deploy.md#deployment-options)). `remove_shards` also removes what a killed worker leaves beside the two shards of a repository: the `.tmp` csv, the unprocessed output of `git log` and the per-repository commit record under its temporary name.
- **The shard reader takes a commit message of any length.** It sets `csv.field_size_limit(sys.maxsize)` at import, as every other reader of the commit CSV does. The commit CSVs that the checkout tracks contain <!--s:collection.long_commit_messages-->210<!--/s--> commits with a message over the default limit of <!--s:parameters.python.csv.field_size_limit-->131,072<!--/s--> characters, the largest with <!--s:collection.longest_commit_message_chars-->1,283,283<!--/s-->, and a reader with the default limit raises on the first of them.
- **No git command that this step runs leaves a process behind.** Since 2.47, git ends every fetch with `maintenance run --auto --detach`. The detached child outlives the fetch, finds nothing to do on a clone deleted minutes later, exits and stays a zombie under a process 1 that does not reap it. A container runs out of processes that way. `bounds.run_bounded` runs every git command with `maintenance.auto=false`, `gc.auto=0` and `gc.autoDetach=false`, and the container therefore needs no reaper for anything that this step starts. The init process that `compose.yaml` sets up remains as a fallback.
- **The run logs its progress.** When a repository finishes, the step writes an `INFO repository_cloning:` progress line to stderr if `--progress-every` repositories have finished since the last line (<!--s:parameters.agentcontext.guards.PROGRESS_EVERY-->100<!--/s--> by default) or `--progress-seconds` have passed without one (<!--s:parameters.agentcontext.logs.PROGRESS_SECONDS.minutes:words-->ten<!--/s--> minutes by default). The line gives the repositories done and the total, the repositories ok and failed in this run, the repositories per minute over this run, the elapsed time and the time left at that rate. Where `/proc` exists, it also gives the number of processes in the container and how many of them are zombies. Without that count, zombies that grow by one per repository become visible only when `fork()` fails. A resumed run counts the repositories that the list of finished repositories records as done but leaves them out of the rate. Without the line, a container over the <!--s:collection.sample_repositories-->40,901<!--/s--> repositories in the sample would show nothing for hours, because the step logs the per-repository lines only under `--print-matches`.

- **The file history is measured here, from the clone that is already on disk.** A `--depth 1` clone has one commit and no history. After the step has copied the files that the path patterns match and before it deletes the clone, `ensure_full_history` therefore fetches the rest, and the `created_at`, `#commits`, `first_commit_sha` and `last_commit_sha` of every copied file go into `file_history.csv`. `file_history.csv` records nothing about the contents of a file. `is_empty` is not published at all, because `agentcontext/steps/collected_file_cleanup.py` deletes every empty file before detection runs, and the detection step reads `language` from `data/validated/`, the tree that every other column of the row describes.
- **Merging the file history into this step saves no wall-clock time.** Over a sample of repositories, `git fetch --unshallow` on the depth-1 clone took about as long as a fresh `--filter=blob:none` clone of the same repositories. The merged step reads the history at the collected commit, in the same clone as the commit history, and it does not resolve repository names, commits and default branches a second time.
- **`git log --follow` on a blobless clone reaches the network.** It fetches blobs lazily for rename detection, roughly one round trip per path. A path therefore costs a round trip on a cold clone and far less once the blobs are local. `agentcontext/steps/file_history.py` has the same cost. Merging the steps changed the number of paths from the published rows to every file that the collector copies.
- **`scanned_at` and `head_commit_date` are separate columns.** Until 2.0.0, one column named `timestamp` contained the committer date of the HEAD commit but was documented and published as the time of the scan. The row of a repository with a failed clone therefore recorded the moment of the failure as though a commit had been made then. The step reads the clock for `scanned_at` once per repository, before the clone, and the three paths out of `process_repo` all record the same value for it. `head_commit_date` is `git log -1 --format=%cI HEAD --`, read by `clone.read_snapshot_metadata`. It is blank only for an empty repository, as `head_sha` is, and a failed query on a repository with commits is a `collector_error`, as the snapshot identity decision below states.
- **`first_commit_sha` is the root commit of the repository,** read in the same pass from the full history, because a depth-1 clone has no root commit to read.
- **The commit history is read here, from the clone after its history is fetched.** The scan that this reading replaced, retired with step 3 of the restructuring, cloned every published repository a second time to read its commits for AI authorship. This step already has the clone and has fetched its history for the file-history rows. After `measure_collected_files` and before the clone is deleted, `read_commit_history` therefore resolves the refs and HEAD of the clone, passes their commit hashes to `git log --stdin` and classifies every commit with the heuristics in `heuristics/ai_commit_patterns.csv`, through the functions that `agentcontext/commits.py` exports. The reading follows these decisions:
  1. *Shards per repository.* Each worker writes one shard per repository under `collect_commits/` (`--commits-dir`): `<owner§repo>.csv` contains the matched commits, and `<owner§repo>.json` is the per-repository commit record, with the AI-authorship rows of the copied files. `main` assembles every shard into the output CSVs at the end of the run. The rows go neither through the result tuples of the pool nor into `finished_repositories.jsonl`, which the parent process parses in full on every resumed run, because a shard is written once and read once.
  2. *Resume.* The assembly reads the shards of the repositories in the input list and merges the commit CSV across runs, as the step merges `file_history.csv`. A repository collected in an earlier run of the same checkout keeps its rows until it is collected again, and the shards of a run that stopped are in the CSV of the next run. Before the step collects a repository, it removes the shards that an earlier run left for it. A repository that fails to clone this time, or that no longer contributes a file, does not keep the rows of the run that read its history. `ai_commits-repos.csv` covers the repositories of the list of finished repositories of this run that are in the input list. An assembly that read every shard on disk would keep the rows of a repository dropped from the input in a CSV that no step published.
  3. *Membership.* This step runs before detection determines which repositories are configured. It writes the commit CSV for every repository with a commit history that was read, and `agentcontext/steps/detection.py` restricts the CSV to the repositories that it publishes. The detection step applies the restriction, and this step does not correct the CSV itself.
  4. *Memory.* `git log` writes to a file under `collect_commits/`, which the step reads one record at a time. The worker keeps one commit and the list of copied files in memory rather than the whole history of a repository. The cloning step read <!--s:subsample.streamlit_commits-->11,238<!--/s--> commits of `streamlit/streamlit` in the collection that the checkout tracks, and the sample contains larger histories.

  Reading the commit history resolves every ref of the clone and includes HEAD explicitly. The
  clone is single-branch, but fetched tags can include additional history. The per-repository
  commit record therefore lists the refs that the step read, and no other branch of the remote
  counts as read.
- **The CSVs that measure recall are written once, here.** Beside the commit CSV, the assembly writes `all_ai_commits-unmatched.csv` and `ai_commits-repos.csv`. `all_ai_commits-unmatched.csv` contains every attribution in an unmatched commit that no heuristic explains, keyed `(kind, token)`, with up to `UNMATCHED_SAMPLE` (<!--s:parameters.agentcontext.commits.UNMATCHED_SAMPLE-->20<!--/s-->) shas and the whole lines that it came from, that is, the full trailer line rather than the value cut at `<`. `ai_commits-repos.csv` has one row per repository of the run with the clone outcome, `commits_read`, `commits_matched` and up to `NO_SIGNAL_SAMPLE` (<!--s:parameters.agentcontext.commits.NO_SIGNAL_SAMPLE-->5<!--/s-->) shas of commits that have no attribution at all. In the output of the scan that this step replaced, a failed clone and a repository without matched commits looked the same. With the no-signal sample, the ranking of unmatched attributions gives a bound on the miss rate. Every commit row has `matched_heuristics`, the ids of the heuristics that explain it. The commits that each heuristic matches can therefore be counted from the commit CSV without a reclassification, as the detection accuracy evaluation counts them. Both samples are drawn with a generator seeded on the repository name, and a rerun over the same clone draws the same shas.
- **A line naming one of the six tools in a commit that no heuristic matched is kept, grouped by its phrasing.** An attribution in prose, such as "Generated with Cursor", has no trailer and no identity. The unmatched attributions therefore never contain it, and without this record nobody would see a new phrasing until someone read the commits of the sample again. `commits.tool_mentions` searches every line of such a commit for the names of the six tools as `ai_commit_patterns.csv` spells them, as whole words in any case. It skips a name that is part of a path, such as `CLAUDE.md` or `.cursor/rules`, because such a name refers to the file. `mention_pattern` removes differences of case, links, hashes, numbers and runs of white space, so that the same phrasing forms one group across commits. The assembly writes `output/all_ai_commits-mentions.csv`, one row per tool and phrasing, ranked by repositories, with up to `MENTION_SAMPLE` (<!--s:parameters.agentcontext.commits.MENTION_SAMPLE-->5<!--/s-->) shas and one line as a commit wrote it. A repository keeps up to `MENTION_PATTERNS` (<!--s:parameters.agentcontext.commits.MENTION_PATTERNS-->50<!--/s-->) phrasings per tool and counts the commits beyond them in its per-repository commit record's `mentions_dropped`, because the commits of a repository about editors use the word cursor in hundreds of different lines. The step does not search for the names of the tools outside the six, because Continue, Factory, Warp, Amp and pi are ordinary words.
- **The step reads no commit history of a repository from which it copied nothing,** because the step fetches no history for it. Nor does it read the commit history of a repository with every copied file removed as a name that is not UTF-8, which leaves no tree and sets no flag. When the time bound stops the reading or git refuses it, the step records `history_read_failed` in the per-repository commit record, with no rows, and keeps the file-history rows that it has already measured.

- **Language:** Python 3.14 (the step's module `agentcontext/steps/repository_cloning.py` and the collector `agentcontext/collector.py`), with the standard library and PyYAML, which `agentcontext/requirements.txt` pins. The collector parses the front matter of an Antigravity rule with PyYAML (`paths.has_trigger`) where a registration file names the rule or where the rule starts an import chain, and `paths` imports PyYAML only then (`paths.load_yaml`). The other external dependencies are the `git` and `rsync` binaries on `PATH`.
- **Parallelism:** `ProcessPoolExecutor`, one task per repository, each cloning, collecting, writing its row and deleting end-to-end with no shared state. Workers return tuples, and the main process reorders results to input order before writing the CSVs. When `process_repo` raises in a worker, the worker records `collector_error` rather than aborting the run. With `--workers 1`, the work runs serially in-process, which the tests use.
- **A retry of an ok line is in the list of finished repositories before it starts.** A resumed run can retry a repository because of its per-repository commit record or its tree, rather than because of a row of the list of clone failures or a `redo` in `finished_repositories.jsonl`. If the old line stayed in force while the retry ran, a Stop after the clone and before the new line would leave the old line describing the new tree, with the per-repository commit record gone. That span lasts minutes for a large repository, and the next run would count the repository as done. Right before a retry of an ok line starts, `run_collection` therefore appends the old line again with `redo`, `retrying` and its `collected_under`, also for a line that already has `redo`. It does so in the serial loop, or when it hands the repository to the pool, which takes one repository per worker. The next run then repeats a stopped retry. A retry removes the earlier commit shards and tree before it writes its own, and a line still marked `retrying` means that the tree on disk may be neither the earlier tree nor the new one. A failed clone then keeps nothing of that tree, and the repository is a clone failure that a later run retries. A failed clone that kept the tree as the earlier snapshot would publish the tree of the stopped retry under the earlier row. The step writes each line right before its retry rather than for every pending retry before the first clone. Otherwise a stop before a retry started, such as for low free space, for failed clones in a row or for a lost worker, would leave `retrying` lines of retries that had not begun. For each such repository with a clone that failed or exceeded the time bound, the next run would then remove the tree, the shards, the file list and the workflow files.
- **A stop ends the workers and the git processes that they started.** Workers are separate processes, and a `SIGTERM` to the collector alone ends only the parent process. The workers would go on cloning into the scratch directory, and a run resumed while they were still running would share that directory with them. A worker of the stopped run could then delete the clone that a worker of the resumed run is reading, which leaves files without a history row. While the pool is up, the parent process handles `SIGTERM` and `SIGINT` by terminating every worker, waiting `WORKER_STOP_SECONDS` for them, killing the remaining workers and exiting with `128 + signal`. A worker handles the same signals by killing the process group of every git command that it has in flight, through `bounds.stop_running`, and exiting the same way. Nothing is recorded for the repository in flight, and a resumed run redoes it, under the rules of the list of finished repositories (below). For a retried repository, the resumed run reads the line that the step wrote before the retry started.
- **Snapshot identity:** every row records `head_sha`, the SHA that `git rev-parse HEAD` returns in the clone from which the configuration artifacts were copied. `branch` and `head_commit_date` do not identify a state. A branch advances with every push, and reconstructing a state from a date assumes that commit dates are truthful and the commits still reachable, which a rebase or force-push breaks. The SHA identifies the snapshot directly, and a later analysis can check out exactly what was collected. The row of a failed clone or of an empty repository has `""` as `head_sha`. A failed snapshot query on a repository with commits is `collector_error` and is retried, rather than treated as a successful collection with an unknown revision.

- **Vendored-directory pruning:** the directory names listed in `vendored_dirs.txt` (the canonical list shared with `agentcontext/steps/collected_file_cleanup.py`) are build output or vendored dependencies, and the step excludes them from collection, matched by exact name at any depth. Pruning applies to recursive searches and to directory copies. `.git/` is always excluded separately. [The vendored list](../heuristics.md#the-vendored-list) describes the list.
- **The local state of the tools is not copied:** `heuristics/local_state_paths.csv` lists the places where a tool keeps session logs, histories, caches, locks and logins inside a tool directory that the step copies whole, such as `.claude/projects/-<path>/` or `.codex/sessions/`. The step leaves these places out of every listing of the clone (`paths.is_pruned`) and out of each `rsync` copy (`paths.local_state_excludes`). The nested `.claude` of a checkout under `.claude/worktrees/` is therefore not found either. No tool reads these files as configuration, and they can contain a user's paths, prompts and credentials. [The local state of the tools](../heuristics.md#the-local-state-of-the-tools) describes them.
- **A tool directory that is a symlink is collected as the directory that it leads to:** a tool reads its directory through a link as its own, because the operating system resolves the link in every path that the tool opens below it. Claude Code reads the `.agents/skills` of a repository with `.claude -> .agents` as `.claude/skills`, and Cursor reads comet-ml/opik's `.agents/agents/*.md`, with `.cursor -> .agents`, as `.cursor/agents/*.md`. Antigravity CLI 1.4.2 listed the agents of `.agents/agents/` through an `.agents` that links to `config/agents` ([Configuration artifact detection](../heuristics.md#configuration-artifact-detection)). The tool directories are the `spec_dir` rows of the heuristics (`paths.TOOL_DIRECTORIES`): `.claude`, `.gemini`, `.cursor`, `.codex`, `.opencode` and the Antigravity customization roots `.agents`, `.agent`, `_agents` and `_agent`, which a per-tool pass or `collect_shared` copies whole wherever it is. The directory searches of these passes skip a symlink, and `collect_symlink_targets` writes the marker of a tool directory that is a link, at the root or below it and outside the vendored directories, and copies the directory that the link leads to at that directory's path, as it copies the target of a linked `.claude/skills` (the item Symlink targets below). The copy leaves out the places of the tool's local state both at their paths through the link and at their paths in the directory (`paths.copy_dir`), so that the session logs of the `config/claude` that `.claude` links to stay out as those of a `.claude` do. The tool writes its local state through the link, and where a pass has already copied the directory under its own name, as `collect_shared` copies the `.agents` that `.claude` links to, the step removes the places of the linking tool's local state from the copy (`paths.remove_local_state`), such as `.agents/shell-snapshots/`, because `rsync --delete` keeps a file at the receiver that an `--exclude` matches. A second copy into the directory, through another tool directory that links to it, as in comet-ml/opik, or through the link of a mechanism directory into it, would copy back the places that the first copy left out, because each copy names the places from its own link alone. Once every link is followed, the step therefore removes the places at their paths through every tool directory that links to the directory. The step follows the links in that directory as in the tool directory itself (`paths.linked_tool_directories`, `paths.link_parents`), and the detection step credits the tool of the link with what it reads there ([detection](detection.md)). A pass that reads a file of a tool directory by its path, such as `.claude/loop.md` or a Codex config that names an instructions file, reads it in the directory that the link leads to and copies it at its path there (`paths.at_its_own_path`), and the collected file cleanup and the detection step read it at the same path. Read through the link, the file would be copied below the link's path, where the marker could then not be written. A link that leads out of the repository, to the repository root or to a directory that contains it stays a marker, and the step copies nothing through it. `.github` is no such tool directory. The Copilot pass copies it only when it contains a Copilot path, and the collected file cleanup keeps only its Copilot paths and agent workflows. The Copilot pass reads a `.github` that is a link through the link and copies it at the link's path. The `SKILL.md` pass does not descend into a linked tool directory, because the copy of its target contains its `SKILL.md` files. File searches include a symlink that leads to a file or to nothing and leave out a symlink that leads to a directory, which `os.walk` lists among the directories (`paths.list_repo_files`). A copied symlink becomes a regular file containing the symlink's target string, a symlink to a directory included (the item Links omitted by rsync below). An Antigravity customization root that is a link, such as an `.agents` that links to `config/agents`, is also read for its registration files. Antigravity CLI 1.4.2 read them through the link and resolved them against the directory that contains the link. The step copies such a registration file at its path in the repository, with what it selects, and the link as its marker. The collected file cleanup keeps the marker as a file with the name of a spec directory, and the cleanup and detection follow it (`paths._linked_directory`). The marker names the directory that the link leads to, relative to the directory that contains the link, rather than the link's own target. For `.agents -> lnk -> config/agents`, the target of the link is `lnk`, another link, which the collected tree does not contain.
- **A declared plugin-root skill:** when a manifest's `skills` entry names its own root and that root contains `SKILL.md`, the step copies the skill and its `scripts/`, `references/` and `assets/`. It copies neither the whole plugin root nor a support folder that is the skill's folder or a folder above it, such as a `scripts` that links to `.` and would put the whole checkout into `scripts/` (`paths._support_dirs`). The root skill that a registration selects follows the same rule. The same paths pass through validation and detection, including when the plugin is the repository itself. `TestDeclaredRootSkillCollection` checks the collected files and the skill row after validation for both manifest formats.
- **Links omitted by rsync:** after copying a directory, the step keeps any symlink that `--safe-links` omitted as a regular file containing its target string, both directly under a tool directory and deeper inside it. That is every link that leads out of the copied directory, to a file or to a directory (`paths.directory_links`). The extra pass uses the same vendored-directory exclusions and does not read the target. A symlinked `.github/copilot-instructions.md` therefore survives collection and validation as a context file, and meshery/meshery's `.claude/hooks`, which links to `../.agents/hooks`, survives as its marker. The step writes the marker of a link to a directory once every pass has copied, and only where no pass has copied a file below the link's path (`paths.write_directory_link_markers`). A Codex config can name a context file through a `.codex/shared` that links to `../docs`, and the step copies that file below the link's path, where a marker would leave no directory for it. The step copies what such a link leads to only under the conditions that the next item, Symlink targets, states, and a link in a skill folder other than its `SKILL.md`, such as the `scripts` of tursodatabase/turso's `.claude/skills/debugging`, stays a marker. `TestCopiedFileSymlinkMarkers` also checks missing and outside targets.
- **Symlink targets:** after the per-tool passes, `collect_symlink_targets` checks every tool directory and every mechanism directory that the heuristics name, also in the directory that a linked tool directory leads to. Where such a directory is a symlink, the step writes the marker itself and, when the target resolves inside the repository, copies the target tree as well. The step needs both, because `rsync --safe-links` drops a symlink that points outside the directory being copied. A `.claude/skills` pointing at `../.agents/skills` would otherwise leave neither the link nor what it pointed at. The step follows a link directly in such a directory the same way, and a link directly in a folder of the parts of a plugin with items that are files, such as the `rules/` and `agents/` of an Antigravity plugin (`paths.link_parents`). It also follows a `SKILL.md` that is a link in a skill folder of a skills directory (`paths.skill_files`), as feast-dev/feast's `.claude/skills/feast-dev/SKILL.md` links to `../../../skills/feast-dev/SKILL.md`, because the tool reads the skill through the link. Another link in a skill folder stays a marker. These folders are each folder of items that a heuristic names, among them the rules and agents with a front matter test, and each plugin manifest folder. angular/angular's `.agent/rules/agents.md`, for example, links to `../../AGENTS.md`, and Antigravity reads the trigger of the rule in that file, as the detection step does in the copy. The step copies no target in the `.git` of the clone (`paths.in_git_directory`), because a file there, such as the log behind a link to `.git/logs/HEAD`, belongs to the clone and not to the repository. A target outside the repository is never copied, nor is a target that contains the link, which would put the surrounding tree into the collected configuration artifacts and leave a live symlink where the marker was. The marker still records that the directory existed and where it pointed. A link can have a target, read without following links, that differs from the path that it resolves to, because it leads to another link or through a linked directory. The marker of such a link names the path that it resolves to, which is the path that the step copies (`_mark_the_end_of_a_chain`). NVIDIA/Model-Optimizer links `.claude/skills/<name>` to `../../.agents/skills/<name>`, and `.agents/skills` to `../plugins/modelopt/skills`, and a marker of the first hop would name a path that the collected tree lacks. The same applies to the places that `paths.plugin_components` and `paths.declared_context_files` name. The step does not read a part of a plugin, a folder beside its root skill or a context file behind a symlinked folder that leads out of the repository, because the target of the symlink is on the collecting machine. A link or a target that cannot be read is a warning, and the step goes on with the repository. A target that rsync copies only in part (`paths.CopyFailed`) and a destination that cannot be written to (`ENOSPC`, `EDQUOT`, `EROFS`, `EIO`) end the repository as `collector_error`, because a tree copied in part would otherwise be recorded as collected.
- **A place that a plugin's manifest declares is read inside the repository only:** a declared place that is a link out of the repository, such as `skills -> ../..`, yields no part, and the step does not list its files (`paths._resolve_declared`). Listing it would read the collected trees and the clones beside the repository, or the whole file system, for a result that the step discards.
- **A file with content that decides what the step copies is read inside the repository only:** a registration file, a file that names a context file, a marketplace, a plugin manifest and a portable plugin document are read only where they resolve to a regular file inside the repository (`paths._repository_text`). Git stores a symlink as it was committed. A link to `/dev/zero` has no end, a link to a FIFO blocks the reader, and through a link to a file of the collecting machine, that file would decide what the step copies. `TestARepositoryFileThatLeadsOutIsNotRead` checks each reader.
- **Such a file behind a link inside the repository is stored with its content:** the step reads a file with content that decides what it copies through a symlink that stays inside the repository, as the tool does. For each such file that the step collected, a registered rule or agent with its front matter among them, `paths.store_declaring_files` writes the content that the step read in place of the marker of the link. The collected file cleanup and the detection step then read the same content. From the one line of the marker, they would select nothing of what the file declares, and the cleanup would delete what the step had copied for it, such as the context file that a linked `.gemini/settings.json` names or the skills of a plugin that a linked marketplace names. Only a file that the step read is stored. A link that leads out of the repository or into its `.git`, or to a file that is not UTF-8 where the reader requires UTF-8, stays a marker, because the step read nothing through it, and the cleanup and detection read nothing from the marker either. If the step stored such a file, a binary file would replace the marker, and a link to `.git/logs/HEAD` would put the log of the clone into the archive. `TestADeclaringFileBehindALink` checks each kind of such file through the three steps.
- **The portable plugin documents are copied by their content, not by their name:** `collect_agent_plugins` reads every `plugin.json` and `mcp.json` in the tree and copies it only where the document declares the Agent Plugins schema that the standard requires of it. Both names belong to many programs that have nothing to do with agents, and the standard puts its own documents in the plugin root rather than in a vendor directory. Only the document's content, not its path, therefore identifies such a file. The test is `heuristics.is_agent_plugins_document`, and the repository has one copy of it. `agentcontext/steps/collected_file_cleanup.py` and `agentcontext/steps/detection.py` call it too, because a file that this pass copies and the collected file cleanup then deletes would be a file that nobody can explain. As for `AGENTS.md`, the standard names no tool, and the pass sets no flag.
- **Shared directories:** `collect_shared` copies the shared and specification directories derived from the heuristics, including `.agents/`, `.agent/`, `_agents/`, `_agent/` and `.plugin/`. It copies a `_agents/` or `_agent/` only where the directory contains a place of Antigravity, such as `skills/` or `mcp_config.json`, with a file below it (`paths.is_spec_directory`), because a Python package can have the same name. It copies the root files that several tools read, which a row of tool `any` with the match mode `root_file` names, such as `REVIEW.md`. It sets no flag.
- **Copy semantics:** single files are copied with metadata preserved. Symlinks are written as a one-line file containing the readlink target, except a symlink to a file of the repository with content that decided what the step copies (above). Directory trees are copied by shelling out to `rsync -a --links --safe-links --delete`, excluding `.git/` and vendored names, to reproduce the rsync behavior of the bash script exactly.
- **Clone strategy:** shallow, single-branch, blobless (`--depth 1 --single-branch --filter=blob:none`) with Git LFS smudge disabled. If the server rejects the filter, the same attempt retries without it (no extra retry consumed). Permanent failures (i.e., a missing repository, a repository that GitHub closed or no access) abort the retry loop immediately. Other failures retry with exponential backoff up to `--max-tries`.
- **Submodules are recorded, not checked out:** a submodule is a pointer, and the files behind it belong to the repository that the gitlink names. None of them is therefore this repository's configuration. An earlier collector ran `git submodule update --init --recursive`, which checked them out and copied whatever they contained, so that published rows were another project's configuration, some of them of a repository that the sample contains under its own name. The collector reads the gitlinks out of the clone, with `git ls-tree` and the clone's `.gitmodules`, and writes them to `submodules.csv` for the collected file cleanup. Reading them costs no request, because the checkout already contains them. Leaving the submodules uninitialized also keeps the run from cloning them at full history from servers unrelated to the repository being measured.
- **Resumability (list of finished repositories):** cloning thousands of repositories takes hours. The step appends each finished repository to an append-only JSONL list of finished repositories (`--finished`, default `finished_repositories.jsonl` in the stage directory, beside `data/`), and a rerun takes over the repositories that the list already records, as the next decision describes. A crash costs only the repositories that were in flight, not the run. The list follows these rules:
  1. The list of finished repositories stores the finished CSV rows of each repository, not just its name. The clone is deleted once a repository is done, and a resumed run could not compute the rows again. Writing the CSVs is therefore a pure function of the list of finished repositories and can be repeated without a clone.
  2. Only the main process writes the list, because the workers already return their rows to it. No two processes compete for writes, and the list needs no locking.
  3. The step appends a line only after a worker returns, that is, after the tree of configuration artifacts of the repository is fully written. A torn or missing line costs at most a redo of that repository and never leaves a half-collected repository recorded as done. The line of a retry of an ok line is appended before the retry starts, and the line that a resumed run reads is then the line of the retry. The list is JSONL rather than SQLite, because there is one writer and no queries, and a crash tears at most the final line of an append-only file, which the reader skips.
  4. Rows are assembled in input order and include only repositories present in the current input. A changed input CSV therefore needs no fingerprinting or versioning: Lines of dropped repositories are ignored, and added repositories are pending. A run that finished every repository removes the tree, the shards, the file list, the workflow files, the imported files and the clone log of each repository that left the input (`reuse.remove_left`). Otherwise the cleanup step would log such a tree in every run as a directory without a row. For each such repository with an ok line, the run appends the line again once, with `redo` and without `collected_under`. An input list that names the repository again then collects it, and a failed clone of that retry keeps nothing, because `reuse.heuristics_reach` cannot test a line without `collected_under`. If the line stayed as it was, a repository that returned with the same head would be taken over with nothing on disk wherever its row has no flag and its per-repository commit record was removed with it, as for a repository with files under `.agents/` alone, which sets no flag. The step appends the line before it removes the files, and a stop in between leaves files that the next collection of the repository replaces. If the step appended the line after the removal, a stop in between would leave the ok line with `collected_under` in force over files that were gone. The removal goes through `paths.remove_tree`, which removes what Synology DSM writes into a directory while the directory is being removed ([architecture](../architecture.md#the-layout)). A directory that `paths.remove_tree` cannot remove stays, with a warning that names it, and the step goes on. The line is already marked to redo, and a later run of the step removes the directory or collects the repository again. Raising the error instead would end the step with exit 1 after the whole collection. The collected file cleanup does not copy a directory without a row in the collected list, and the snapshot does not count one ([snapshot](../checks/snapshot.md)). The log counts only the repositories from which this run removed files. A count of every repository outside the input list would include, in every later run, a repository that left in an earlier run, because the list of finished repositories keeps its line after its files are gone. A file that belongs to a repository in the input list under a name that differs only in case is kept, because GitHub can return a name in another case in a later retrieval. A file system that folds case, such as the default file system of macOS, stores both names as one, and removing the files of the old name would remove the collection of the new name.
  5. The list stays append-only within a collection. When a collection begins, `resume.reduce_finished` rewrites it in one step with the lines that its readers use: the last line that parses for each repository, and the last line with a count of copied files when every later line of the repository repeats its row, because the commit reclassification reads the count from there (`commit_reclassification.finished_copied`). Without the reduction, every monthly run would add a line for each repository in the sample, and every later run would read all of them. The handover of each run contains the list as that run left it, with the measurements of its own lines. A resumed collection leaves the list as it is.

  `--fresh` removes what a collection leaves and collects everything again.
- **A later run takes over a repository when collecting it again would give the same result, and collects every other repository again** (`agentcontext/reuse.py`). Without this decision, a monthly run over the same data root would find every repository of the earlier collection in the list of finished repositories and skip it, whatever had been pushed since. Each line records in `collected_under` what the repository was collected under: the fingerprint of the collector's code, the SHA-256 of the path heuristics and of the import heuristics, the records that the run kept beside the collection (i.e., the commit history, the file history, the file list, the workflow files and the imported files), and the version of git as `git --version` prints it. The git version is part of the key because `created_at`, `#commits` and `first_commit_sha` change with it. When git prints no version, the step exits 1 before it opens a collection or reads a line, and a retry round that meets such a git ends the step the same way, with the lines of the rounds before it kept ([git](../git.md#the-git-client) gives the reason).

  The fingerprint is `reuse.collector_fingerprint`: `fingerprints.code_fingerprint` over the module closure of `agentcontext.collector` (`reuse.collector_files`), taken from the syntax tree of each file without docstrings, without statements that only write a log message, and without the text of an exception that a `raise` statement constructs. An edit to a comment, a log message or an error message therefore does not make a run collect the sample again. A string without a space among the arguments of an exception stays, because it can be a value that a caller stores, such as the cause `exit` of `history.HistoryUnavailable`, which the per-repository commit record keeps. A text that the code assigns to a name before it raises or logs it stays as well. The collector, `agentcontext/collector.py`, contains what the step does with one repository: `process_repo`, `measure_collected_files` and `CollectionConfig`. The closure leaves out `guards.py`, `logs.py`, `resume.py`, `reuse.py`, `fingerprints.py` and `steps/repository_cloning.py` (`reuse.SCHEDULING_MODULES`), which decide which repositories a run collects, in which order and when it stops. A fix to a stop rule during a collection therefore keeps what the collection has collected. The closure also leaves out `__init__.py`, which names the data root and the directories of the stages, and `git/__init__.py`, which documents the git modules (`reuse.PACKAGE_FILES`). The collector receives every directory that it writes in `CollectionConfig`, and the heuristics directory that `heuristics.py` derives from the package is also the directory of the path heuristics that a line records.

  Every other module of the closure decides which files the collector copies or what the records of a collection contain, and stays: `paths.py`, `heuristics.py` and `planning.py` decide what is copied, and `jsonc.py` reads the settings files that decide it by their content. `caches.py` defines the file history rows that a line stores, `commits.py` reads the commit history into the per-repository commit record and the commit log, and `repos.py` names the directory of each repository. `git/clone.py` reads the head, the file list and the submodules of the clone, `git/history.py` the history of each copied file, and `git/bounds.py` runs these git commands and keeps what they print. `git/auth.py` stays as well, because it builds the URL that git clones and the environment of every git command that reads the clone.

  A change of the collector's code gives it a new fingerprint, and the record of the versions of the collector's code (`code_versions.COLLECTOR`) declares which repositories the change reaches: none, every repository, or the repositories that a predicate of `agentcontext/code_versions.py` accepts. `linked_skill_file`, a predicate over the file list, accepts the repositories with a SKILL.md that is a link in a skill folder. `path_added_again`, a `RecordReach`, reads the per-repository commit record and accepts the repositories with a path that a commit deleted and a later commit added again. `prompt_file_input`, a `WorkflowReach`, reads the kept workflow files and accepts the repositories with a workflow that gives an agent action a prompt file. A line of an earlier recorded version is taken over when no change from its version to the current one reaches the repository (`reuse.collector_reach`), and a line of a version that the record does not name is collected again. A predicate over the file list reads the definitions of the collector's own code, such as `paths._SKILL_PARENTS`, so that the predicate and the collector name the same places. It reads the file list, which the collection kept with the mode of each entry, so that a link is visible. [Recording a change of the collector](#recording-a-change-of-the-collector) gives the steps.

  The path heuristics are the five columns of `config_path_patterns.csv` that decide what is copied, `tool`, `mechanism`, `path`, `match_mode` and `content_format`, with the vendored directories, the heuristics of the planning documents and the places of the tools' local state, the `path` column of `local_state_paths.csv`. The documentation watch changes the other columns every week. The import heuristics are the columns of `import_patterns.csv` that decide what is copied to the imported tree (`imports.COLLECTION_COLUMNS`), with the fingerprint of the code that reads them: `imports.py`, and `prune.py`, which defines the paths that the archive step prunes and the copy leaves out (`reuse.import_files`). The fingerprint of the collector's code leaves that code out, so that a change to a parser makes the step collect again only the repositories with a file that can import, rather than the whole sample. The fingerprint of the code of the imports (`reuse.import_code_fingerprint`) leaves out docstrings, log statements and exception texts as the collector's does, and `code_versions.IMPORTS` records its versions with the reach of each change. The test of the pruned paths is a module of its own, so that neither the archive step nor the command line that it imports is code of the imports, and an edit to either makes the step collect nothing again. Each version of either set of heuristics is kept under `collection_heuristics/<sha256>.json` in the stage directory. A line is taken over when:
  1. it records what it was collected under, which a line written before this decision does not;
  2. the records and the version of git are this run's, and the collector's fingerprint is this run's, or that of an earlier recorded version, and no change since that version reaches the repository through its file list, its per-repository commit record or its kept workflow files (`reuse.collector_reach`);
  3. the path heuristics are this run's, or every row that changed misses the file list of the repository (`reuse.affected`). A changed row reaches the repository when a path of the list contains the path of the row anywhere, in any case, which is more than the collector copies. A row that names a file that declares other paths, such as a settings file, a registration file or a workflow, reaches the repository that contains the file. The parts of a plugin can be anywhere that its manifest names, and a row with a placeholder such as `<claude-plugin>`, or a file beside the root of a plugin, reaches every repository that the path of another row reaches. A row of the manifest that identifies a plugin, such as `<copilot-plugin>/plugin.json`, decides only whether a file of its name is a plugin, and it reaches a repository with a file of that name (`reuse._manifest_row`). A row of the parts of an Antigravity plugin, such as `<antigravity-plugin>/skills`, reaches a repository with a `plugin.json`, which every Antigravity plugin has. A vendored directory that changed reaches a repository with a directory of that name, and the same rows in another order reach every repository. A place of the tools' local state that changed, or that a kept version from before the places lacks, reaches a repository with a path in the place. A changed row, place or vendored directory that begins with a tool directory, such as `.claude/commands`, also reaches a repository with an entry of that name at any depth, because such an entry can be a link through which the collector reads the row (`reuse._links_reach`). A changed import row reaches the repository when a path of the list contains the importing file of the row anywhere, in any case (`reuse.imports_reach`), and a change to the code of the imports counts as a change of every import row unless the record of the versions of that code (`code_versions.IMPORTS`) declares that the change reaches no repository. A row of the rules of an Antigravity plugin, `<antigravity-plugin>/rules` or `<antigravity-plugin>/rules.json`, reaches a repository with such a path in a directory with a `plugin.json`, or above a `.antigravity-plugin` or `.gemini-plugin` folder with one, which every Antigravity plugin has, rather than every repository with a folder named `rules`. No import row reaches a repository from which the collection copied no file, because the importing files are among the copied files. The log lists the repositories that changed import heuristics reach separately from the repositories that changed path heuristics reach. A heuristic of the planning documents that changed, or that a kept version from before the planning documents lacks, reaches a repository with a path that its pattern matches, or with its marker or its settings file, whatever its anchor. A heuristic with a pattern, a marker or a settings file that begins with a tool directory, such as `.claude/settings.json`, also reaches a repository with an entry of that name, because the matching follows a link of that name into the directory that the link leads to (`planning.find`), and the file list does not record where a link leads. A run over such a collection therefore collects again every repository with a path of a documented layout, a `.specify/` or a `.claude/settings.json`. The test reads a file list once however many heuristics changed (`reuse._planning_reaches`). One search finds the markers and the settings files of all of them, and each path is matched only against the heuristics of the directories that it contains, where it contains the text that every match begins with. Reading the file list once for each changed heuristic would multiply the time of the test by the number of changed heuristics, and an edit of the heuristics of the planning documents, such as the edits of 2026-10-19, changes many of them at once. The step keeps each decision for the rest of the process under a digest of the line, the heuristics of this run and the bytes of the file list (`reuse.heuristics_reach`). Its retry rounds and its test of whether a failed retry keeps the earlier collection then take the kept decision rather than match the list again, and the step decides again for a line or a file list that changes during the run. Without a kept version or a file list, the repository is collected again;
  4. `git ls-remote --symref` still returns the branch and the commit that the row records (`clone.remote_head`), over the URL and the credential helper that a clone uses. The step queries <!--s:parameters.agentcontext.reuse.HEAD_CHECK_THREADS-->32<!--/s--> heads at a time and queries a head up to <!--s:parameters.agentcontext.reuse.HEAD_CHECK_TRIES:words-->two<!--/s--> times when git returns no head commit, the first time with the GitHub access token and the second time without it (below). A repository for which git still returns no head commit is taken over for the run, and its line is written again with `head_no_response`. The retry rounds query its head again, and at its end the run counts it with the repositories to retry toward `--max-clone-failures` and names it in the line `No head commit from git for N repositories`. The next run that runs the step queries it again. If the step collected such a repository again, a network outage of a few minutes would cost a clone of each such repository, and the line written before the clone would mark the repository for the next run to clone again whatever its head. A refusal by GitHub, which `clone.remote_head` reads from git's message as a clone does, makes the step collect the repository again, and the clone records the refusal. A query of a head takes a fraction of the time of a clone, which with its history fetch and the reading of its commit history takes minutes. The retry rounds of a run query again only the heads for which git returned no head commit.

  When git returns no head commit for more repositories than the ceiling of `--max-clone-failures` allows, the step waits and queries those heads again before it takes any of them over (`reuse.remote_heads`). GitHub can limit the rate of the queries, or the network can fail, while the step queries the heads of thousands of repositories within minutes. The step waits before each of <!--s:parameters.agentcontext.reuse.HEAD_WAITS.length:words-->six<!--/s--> rounds, <!--s:parameters.agentcontext.reuse.HEAD_WAITS.0.minutes:words-->one<!--/s--> minute before the first and twice as long before each further round, up to <!--s:parameters.agentcontext.reuse.HEAD_WAITS.5.minutes-->32<!--/s--> minutes. Each round has half the threads of the round before, at least <!--s:parameters.agentcontext.reuse.HEAD_WAIT_THREADS:words-->four<!--/s-->, so that it sends its queries at a lower rate. A round first queries as many heads as it has threads, spread over the heads without a head commit and shifted by one each round. Heads that fail every time, such as the heads of one owner, which sort together, are then not the only heads that it queries. When git returns no head commit for any of them, the round queries none of the others and the next wait begins, and a network that is down therefore costs a few queries per round rather than one per head. The waits end as soon as the heads without a head commit are within the ceiling. Each such repository counts toward the ceiling. Without the waits, the step would exit 4 after a burst unless its retry rounds, which query the heads with all threads again <!--s:parameters.agentcontext.guards.RETRY_PAUSE_SECONDS.minutes:words-->five<!--/s--> minutes apart, got a head commit for enough of them. The runner would then record the step as not complete, and a monthly run would stay unfinished until someone started the container again. At or within the ceiling, the step does not wait. A few heads that fail every time then cost no wait, and the retry rounds query them again. The retry rounds wait the same way. The first wait is the pause that `github_api` gives a rate limit for which GitHub gives no wait, and the waits together last many times as long as the burst of HTTP 400 responses that GitHub returned to history fetches during the run started on 2026-09-22.

  The first query of a head sends the GitHub access token with its first request. The second query, when the first returned no head commit, is anonymous and sends the GitHub access token only after GitHub responds with 401, as a clone does (`reuse._head`). git sends the credential of a URL only after the server responds with 401, which GitHub does for a repository that is not public. Without `auth.PROACTIVE_AUTH`, every request of the head check for a public repository would be anonymous, whether or not the run had a GitHub access token. The options set `http.proactiveAuth=basic`, with which git 2.46 and later, such as the 2.55.0 that `mise.toml` pins for the images and the development machines, runs the askpass helper for the password before the first request ([git-config 2.47.0](https://git-scm.com/docs/git-config/2.47.0#Documentation/git-config.txt-httpproactiveAuth): "Attempt authentication without first making an unauthenticated attempt and receiving a 401 response"). They also set an empty `credential.helper`, so that no credential helper of the machine supplies the password or keeps the GitHub access token that git approves after each request that succeeds. GitHub limits anonymous git requests over HTTPS more than authenticated ones. Its changelog of May 8, 2025 states that "These changes will apply to operations like cloning repositories over HTTPS, anonymously interacting with our REST APIs, and downloading files from raw.githubusercontent.com" and that "developers using authenticated requests will continue to enjoy higher rate limits with uninterrupted access to their workflows and tools" ([updated rate limits](https://github.blog/changelog/2025-05-08-updated-rate-limits-for-unauthenticated-requests/), read on 2026-10-21). Its changelog of October 19, 2026 states that "During periods of unusual traffic, GitHub may temporarily require authentication for some clones and fetches of public repositories over HTTPS" and names "Authenticated Git operations over HTTPS" among the operations that the requirement leaves unaffected ([authentication for Git over HTTPS](https://github.blog/changelog/2026-10-19-some-git-over-https-may-temporarily-require-authentication/), read on 2026-10-21). Neither page gives a number, and GitHub's documentation of the rate limits of the REST API states a separate limit only for Git LFS, which the step does not use. A head query sends `GET info/refs?service=git-upload-pack` and `POST git-upload-pack`, the requests to the service that a clone uses, and the step sends <!--s:parameters.agentcontext.reuse.HEAD_CHECK_THREADS-->32<!--/s--> queries at a time, for thousands of repositories within minutes from one address. git does not repeat with the GitHub access token an anonymous request that GitHub refuses with 429, and without the GitHub access token such a response would leave the head without a head commit.

  The second query is anonymous because GitHub refuses some authenticated requests for public repositories that it serves to anonymous ones. An organization's IP allow list restricts "Public resources, when a user is signed into GitHub (including non-interactive authentication methods such as: Personal access token" and not "Public resources, when accessed anonymously" ([allowed IP addresses](https://docs.github.com/en/enterprise-cloud@latest/organizations/keeping-your-organization-secure/managing-security-settings-for-your-organization/managing-allowed-ip-addresses-for-your-organization), read on 2026-10-21). A query with the GitHub access token from another address therefore gets 403 for a public repository of that organization. GitHub also refuses a GitHub access token that has expired or been revoked since the pre-checks verified it, with "Invalid username or token". `clone.remote_head` reads that refusal of the authenticated query as no response rather than as a repository that is gone, because GitHub returns "Repository not found" to a valid GitHub access token for a repository that is gone. Single sign-on and an organization's policy for personal access tokens refuse no such query: "IdP authentication is not required for accessing public repositories in certain ways", among them "Performing read operations via Git, such as cloning the repository" ([single sign-on](https://docs.github.com/en/enterprise-cloud@latest/authentication/authenticating-with-single-sign-on/about-authentication-with-single-sign-on)), and "Regardless of the chosen policy, Personal access tokens will have access to public resources within the organization" ([policy for personal access tokens](https://docs.github.com/en/organizations/managing-programmatic-access-to-your-organization/setting-a-personal-access-token-policy-for-your-organization)), both read on 2026-10-21. A fine-grained personal access token can read every public repository: "Tokens always include read-only access to all public repositories on GitHub" ([personal access tokens](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens), read on 2026-10-21).

  The clones, the history fetch, the blob fetches of `git log --follow` and the connectivity probe stay anonymous and send the GitHub access token only after GitHub responds with 401. The October 2–3 collection cloned <!--s:collection_2026_10_02.sample_repositories-->36,710<!--/s--> repositories anonymously in <!--s:collection_2026_10_02.duration_hours-->21<!--/s--> hours, at a far lower rate of requests than the head check sends. With the GitHub access token in every request, every git command in the clone of a public repository of an organization with an IP allow list would fail, and a GitHub access token that GitHub stops accepting during the collection would fail every clone with "Invalid username or token". An anonymous clone sends the GitHub access token only when GitHub requires a credential, for a repository that is not public, or for a public repository while GitHub requires authentication. A refused GitHub access token then fails the clone as `clone_failed`. The repository keeps its earlier collection, and the failure counts toward `--max-clone-failures` and toward the failures in a row that start the connectivity probe. The retry rounds and a resumed run clone the repository again, so that the first run after you replace the GitHub access token in `credentials.csv` collects it. If the step read the message as a refusal of the repository, `not_found_or_no_access`, it would record a repository that exists as gone for the rest of the collection, outside the ceiling, and remove its earlier collection. When GitHub responds to an anonymous request with 401, git sends the GitHub access token. Against a loopback server, git 2.47.3, 2.55.0 and 2.56.0 followed the request without a credential with a request that names the placeholder user with an empty password and then with a request that carries the GitHub access token. The changelog of October 19, 2026 does not give the status with which GitHub refuses an anonymous clone and states only that "it will fail with a message indicating that authentication is required".

  A repository with a refusal by GitHub is taken over while git returns no head commit for the repository, and collected again when git returns one. A clone that the size bound stopped stays under the rule of `resume.clone_needs_redo`. A change to the commit heuristics needs no clone. When a repository is taken over and its per-repository commit record has a `classified_by` of other commit heuristics, the step classifies its commits again from the kept log (`commits.reclassify`) in a pool of `--workers` processes. It collects the repository again where that log fails validation. A record of the current heuristics is not classified again. The step therefore also reads the result of the last commit reclassification, `commit-reclassification.json` beside `--ai-commits-csv`, and collects again every repository that the file lists as `failed` while the per-repository commit record of the repository has the SHA-256 that the file records for it (`resume.reclassification_failed`). Without this file, a truncated commit log of a repository classified under the current heuristics would stay `failed` in every later collection, although the log of the reclassification says that a later collection retries it. A repository taken over keeps the row of the run that collected it, its `scanned_at` included, because `head_sha` is the same commit.

  A repository collected again is a retry of an ok line. Its line is written before the clone, and after a clone that fails on the network, the repository keeps the earlier snapshot with `redo`, as after a history repair. After a clone that the time bound ends twice, the repository keeps the earlier snapshot too, that is, its tree, shards, file list and workflow files with its row, and the line records the time bound instead of `redo`. While that bound holds, for the rest of the collection under the same `--clone-timeout`, neither the retry rounds nor a resumed run clone the repository again or classify its commits again for its line, and the log at the end of the run names such repositories. The next collection clones the repository again. Removing the repository with all its files and recording it as `time_bound_exceeded` would cost a repository with an earlier collection its whole collection for one slow transfer. Path heuristics that change within the collection in a row that reaches the file list of the repository are the exception to the bound (`reuse.heuristics_reach`, tested before the bound). The step then collects the repository again, and a retry that the time bound stops keeps nothing of the earlier collection (condition 3 below). In an earlier version, which tested the bound first, a resumed run published the files of the earlier path heuristics.

  The earlier snapshot is kept only when it is complete and is what this run would collect at the same head (`preserved_on` in `run_collection`):
  1. The last line of the repository is an ok line that does not have `retrying`.
  2. The collection is on disk: a row with a flag, or a per-repository commit record, has its directory (`resume.tree_missing`). A repository from which the collector copied nothing has no directory, and its row and file list are kept.
  3. The path heuristics that the line records in `collected_under` are this run's, or every row that changed misses the file list of the repository (`reuse.heuristics_reach`, the test by which a line is taken over). ## `agentcontext/steps/repository_cloning.py`

### Architecture

#### Parallelism model

`run_collection` submits one `collector.process_repo` task per repository. With `workers <= 1`, it runs serially in-process. Otherwise it uses a `ProcessPoolExecutor` with a window of one task per worker, collects the results keyed by repository and writes both output lists in input order regardless of completion order. With that window, a worker takes each task as soon as the pool receives it, and the line marked `retrying` that `run_collection` writes when it hands the pool a retry therefore belongs to a retry that has begun. A pool that has detected a dead worker refuses the task at submission, and `run_collection` then writes the line from before the mark again (`not_started`). With a window of twice as many tasks as workers, a stop would leave the mark on the queued retries that no worker had begun. The next run would then not keep their earlier collections when their clones failed, and a lost worker would record them as `clone_failed`.

The step measures the free space on the volume that contains the clone directory before the first clone and after every `--disk-check-every` finished repositories. Below `--min-free-gb`, no further clone starts, and the clones in flight finish and reach the list of finished repositories. If a repository was left unstarted, the step then raises `LowDiskStop` with the rows assembled so far and the minimum as `minimum_free_bytes`. Once every repository has started, low space is only a warning, and the step finishes normally. After the last repository, the free space can fall below the <!--s:parameters.agentcontext.runner.MIN_FREE_DISK_GB-->190<!--/s--> GiB minimum, and a stop at that point would keep the run from the later steps, which clone nothing. The step lets the clones in flight finish rather than stop them, because a clone killed halfway is a repository to redo, while a line of the list of finished repositories, written after the worker returned, is never torn. `main` writes the lists that it reached and exits `3`. The list of finished repositories records every finished repository, and the next run therefore continues where this one stopped. The default of `--min-free-gb` is the runner's `MIN_FREE_DISK_GB`, and a test checks that the two values are equal. The step measures the space again because the pre-checks measure once and the step runs for days.

`process_repo` is a module-level function (picklable on all platforms) and never raises. An exception after the clone is recorded as `collector_error`, with the traceback on stderr and in the clone log and the copied tree removed. A repository that fails therefore cannot abort the pool, and the next run redoes it. A future that raises `BrokenProcessPool`, as after the kernel kills a worker, ends the loop with `WorkerLostStop`, which contains the rows so far, with the repositories in flight, one per worker, recorded as `clone_failed`. `main` writes the lists and exits `4`. After `config.max_consecutive_failures` `clone_failed` outcomes in a row, the loop calls `remote_responds` on `config.probe_url` and calls it again after each wait of `config.probe_waits`, which is empty in a configuration built in code and `guards.PROBE_WAITS` at the command line. It raises `ConsecutiveFailuresStop` only when every call fails. The loop records the results in the main thread of the parent process before it submits the next repository, and no clone starts during a wait. `config.max_consecutive_failures` `collector_error` outcomes among the last `ERROR_WINDOW` finished repositories raise the same exception without the probe, and the `kind` of the exception records which of the two conditions stopped the loop. The serial branch installs `guards.worker_stop` for the loop and restores the previous handlers after it.

#### Clone retry

`clone_with_retry` empties the clone log of the repository, builds the clone URL through `auth.clone_url` (i.e., SSH, HTTPS with the placeholder user when a GitHub access token is set, or plain HTTPS) and puts the GitHub access token into the environment for the credential helper to supply. It then tries up to `max_tries` times, with an exponential backoff that starts at <!--s:parameters.agentcontext.git.clone.clone_with_retry.base_delay:words-->five<!--/s--> seconds and waits between attempts, not after the last. Each attempt runs through `bounds.run_bounded`, with the destination as the directory under the size bound and `clone_timeout` as the wall clock. The clone had neither bound until 2.0.0, and <!--s:repo_sizes.over_4_gib-->42<!--/s--> measured repositories exceed 4 GiB packed. Each attempt first tries `--filter=blob:none`. If the log matches the filter-unsupported pattern, the same attempt retries without the filter.

After each attempt, the step checks the accumulated log against the permanent-failure patterns, including `Repository not found`, `permission denied (publickey)`, `not authorized`, `access denied`, `Access to this repository has been disabled`, `Repository unavailable due to` and `could not read Username`, which git prints when GitHub requests a credential and the run has no GitHub access token. A match aborts the loop and returns the reason that `clone.permanent_failure_reason` reads from git's message: `dmca_takedown` when the message names a DMCA takedown, `disabled_by_github` for `Access to this repository has been disabled` or another `Repository unavailable due to`, and `not_found_or_no_access` otherwise. GitHub's `Invalid username or token` and git's `Authentication failed for` are a refusal of the GitHub access token, not of the repository. Such a message ends the loop with `clone_failed`, because GitHub refuses the same GitHub access token on every attempt, and the step writes `CREDENTIAL_REFUSED` into the log. GitHub returns `Repository not found`, not these messages, to a valid GitHub access token for a repository that is gone or private, and it may require authentication for a public repository during unusual traffic ([Key decisions](#key-decisions)). A clone for which git prints `Clone succeeded, but checkout failed` because a name is too long for the file system, more than 255 bytes on ext4, btrfs and APFS, ends the loop with `file_name_too_long`, because the file system refuses the same name on every attempt.

A timeout is a failed attempt and is retried as a network failure is, and so is a git process that could not be started, that is, an `OSError` from `Popen`. After `clone.TIMEOUT_TRIES` attempts that the time bound ended, the loop removes the clone and returns `time_bound_exceeded`. Each further attempt under the same bound would hold a worker for the whole bound, in every retry round and in every run. An earlier version let a depth-1 clone of one repository over `--clone-timeout` hold a worker for all `--max-tries` attempts in the run, in each retry round and again in every later run. A clone over the size bound aborts the loop and returns `size_bound_exceeded`, because the bound is deterministic and a retry would download the same bytes again. A clone that finished within the sampling interval of the watcher but ended over the size bound counts as over the size bound too, because the bound applies to the working tree that the clone produced, and the tree is removed either way. Exhausting the attempts returns `clone_failed`, and success returns `ok`. Every attempt appends to the clone log of the repository, with the clone URL redacted and each bound named when it stops an attempt.

For a repository stopped by the size bound, the step records an all-`FALSE` row of the collected list with the scan time, a `clone_failed.csv` row under `size_bound_exceeded`, and a line in the list of finished repositories, as for any finished repository, and a resumed run under the same size bound therefore keeps the result. A run with a larger `--max-clone-mb` clones again the repositories recorded under a smaller bound. A repository stopped by the time bound is recorded the same way under `time_bound_exceeded`, with `time_bound` in its line, and a run with a larger `--clone-timeout` clones it again, as does the next collection. A repository with an earlier collection keeps that collection when the time bound stops its retry, under the conditions of [Key decisions](#key-decisions). At its end, the run logs how many repositories the time bound stopped, in each of the two cases. Neither outcome counts toward `--max-clone-failures`, including the `time_bound_exceeded` of a retry that was to read a commit history again, which has no `redo`. The commit reclassification records such a repository as `unavailable`, as it records every clone failure of `clone_failed.csv`, and the population stays incomplete until a later run clones it. Pass `--fresh` only to clear the whole collection and collect every repository again.

#### Vendored pruning

`list_repo_files` and `find_dirs_by_name` call `os.walk` and prune `dirnames` in place, removing any directory with a name in the vendored set or named `.git`. `copy_dir` passes one `--exclude` per vendored name to `rsync`. Pruning matches the exact name at any depth, and a directory with a name that only shares a prefix with a vendored name is not pruned. `find_dirs_by_name` also skips an empty directory. Git tracks no empty directory, and in a checkout an empty directory is therefore a submodule that the clone did not check out. `submodules.csv` lists a submodule named `.claude` in <!--s:collection.claude_submodule_repositories:words-->two<!--/s--> of the repositories of the collection, and the step copies nothing from that directory.

#### Copy semantics

`copy_file` writes the target string of a symlink as a one-line regular file, or copies a regular file with `shutil.copy2`, and neither writes through a link at the destination. `rsync` keeps a link inside a directory that a pass copies whole as a link, and a later copy of the same path by name finds the link there. A link to a file of the collected tree stays, because writing through it would replace that file, such as the `CLAUDE.md` that a `.claude/AGENTS.md` beside it links to. A link that leads nowhere is replaced by the marker, because writing through it would create its target. After the passes, `store_declaring_files` replaces with its content the marker of each file that the passes read through a link inside the repository. `copy_dir` shells out to `rsync` with `--links --safe-links --delete` and the excludes of the vendored directories, of `.git` and of the places of the tools' local state. After rsync, `copy_dir` writes the marker of each link that `--safe-links` left out, and while `collect_repo` runs, the step writes the marker of a link to a directory only after every pass has copied (`write_directory_link_markers`). The path of a copy is the path of the configuration artifact relative to the root of the repository.

at any depth, makes a Codex plugin of its folder where Codex loads the folder, and a source of a
Copilot CLI marketplace makes a Copilot plugin of a folder with a manifest that the CLI reads
([The parts of a plugin](../heuristics.md#the-parts-of-a-plugin-wherever-the-repository-puts-it)).
The step copies the parts that the tool reads there, such as the `.app.json` of a Claude Code
plugin that a Codex marketplace lists, and flags the tool for the portable `skills/` and
`mcp.json` of a portable plugin that the tool reads. It copies the Copilot CLI marketplace with
the plugin manifests (`paths.plugin_manifests`), also from a `.github` below the root, such as
dotnet/dotnet's `src/msbuild/.github/plugin/marketplace.json`, so that the collected file cleanup
and the detection step find the plugins that it lists. An Antigravity plugin can keep its
manifest in a `.antigravity-plugin/` or `.gemini-plugin/` folder, and the plugin is the directory
above the folder. A Claude plugin with an invalid declared component path contributes no plugin
components, defaults included, and its manifest stays collected. A missing path, a path without the required `./` prefix and a path
outside the plugin fail this check.

The collector and the collected file cleanup recognize both recursive and immediate-child skill
container modes, including their linked targets. Detection applies the selected
depth, and copying a directory therefore does not classify every nested skill marker.

A declared Copilot skills path that contains its own `SKILL.md` identifies that
skill, and discovery stops beneath that declaration, although a separate manifest
entry can name a child skill explicitly. Hook and LSP alternatives must satisfy their
component schemas. Invalid inline hooks retain default files, while valid empty
component objects stop the fallback.

Collected configuration artifacts are under `<collected-dir>/<owner§repo>/`, at their paths within the repository. The clone logs of the repositories are under `<log-dir>/<owner§repo>.log`, `clone_logs/` by default, each with the attempts of the latest collection of its repository.

## Recording a change of the collector

`tests/test_code_versions.py` fails while the fingerprint of the collector's code
(`reuse.collector_fingerprint`) is not the last version of `code_versions.COLLECTOR`, or the
fingerprint of the code of the imports (`reuse.import_code_fingerprint`) is not the last version
of `code_versions.IMPORTS`. When you change the code of either, record the change in the
same commit:

1. Run `python3 -m unittest tests.test_code_versions` from the root. The failure names the
   fingerprint of the changed code.
2. Read the diff and decide what the change alters in a collection: the files that the collector
   copies, the rows that a line of the list of finished repositories stores, the file list, the
   per-repository commit record and the commit log, the workflow files or the imported tree.
3. Append a `Version` to the record with that fingerprint, the commits that made the change, a
   sentence that states what changed, and the reach of the change:
   - `NO_REPOSITORY` for a change that alters no collection, such as a refactoring, a reworded
     text, or a change of the commit heuristics, which a run applies to the kept commit logs of
     the repositories that it takes over (`commits.reclassify`).
   - A predicate over the file list, `(mode, path)` pairs, that is true for every repository with
     a collection that the change can alter. Write it in `agentcontext/code_versions.py` from the
     definitions of the collector's code, as `linked_skill_file` reads `paths._SKILL_PARENTS`,
     and add a test to `tests/test_code_versions.py` that collects layouts with the changed and
     the earlier code and requires the predicate wherever the two collections differ, as
     `TestALinkedSkillFile` does. A predicate that accepts more repositories than the change
     alters costs only their clones. A predicate that accepts fewer keeps a collection of the
     earlier code in the published dataset.
   - A `RecordReach`, a predicate over the commits of each copied path that the per-repository
     commit record keeps (`path_commits`), for a change with a reach that only the history of the
     copied paths decides, such as a change of how the history of a path is read.
     `path_added_again` accepts the repositories with a path that has a commit older than its
     recorded creation commit. `reuse.recorded_path_commits` reads the record, not the commit log,
     and only for a line of an earlier version. A repository from which the collection copied no
     file keeps no record and has no path, and the predicate does not reach it. A repository from
     which the collection copied a file is collected again when it has no record or no commit log,
     when its record cannot be read or names a commit other than the collected commit of its line,
     or when its record does not show a commit history that was read completely. Add a test to
     `tests/test_code_versions.py` that gives the predicate the commits of paths that the change
     alters and of paths that it does not, as `TestAReachOverTheRecord` does.
   - A `WorkflowReach`, a predicate over the text of each workflow file that the collection kept in
     `data/workflows/<owner§repo>/`, keyed by file name, for a change with a reach that only the
     steps of the workflows decide, such as a change of the inputs from which
     `paths.action_prompt_files` reads a prompt file. `prompt_file_input` accepts the repositories
     with a kept workflow that runs an action of `paths._PROMPT_FILE_INPUTS` and has a line that
     starts with the input of that action, such as `prompt_file:`. `reuse.kept_workflows` reads the
     kept workflows, and only for a line of an earlier version. A repository with no workflow file
     in its file list has none, and the predicate does not reach it. A repository is collected again
     when the run keeps no workflow files, when the repository has no file list, and when its file
     list names a workflow file that is not a link and that the collection did not keep. The cloning
     step leaves out each workflow file after the first
     <!--s:parameters.agentcontext.paths.MAX_WORKFLOW_FILES-->50<!--/s-->, which
     `paths.action_prompt_files` still reads, and each one larger than
     <!--s:parameters.agentcontext.paths.MAX_WORKFLOW_BYTES-->256<!--/s--> KiB, which it does not
     read. The file list does not show which of the two limits left a workflow file out, and the
     repository is therefore collected again in either case. Add a test to
     `tests/test_code_versions.py` that collects layouts with the changed and the earlier code and
     requires the predicate over their kept workflows wherever the two collections differ, as
     `TestThePromptFileOfTheClaudeCodeBaseAction` does.
   - `EVERY_REPOSITORY` where no predicate can find the repositories, such as a change of the
     format of a record.
4. Run the suite again, and commit the change with its version.

A line records the fingerprint of the code that collected the repository, and on the NAS that code
comes from an image. Commits between two images can therefore share one version, with a reach that
covers each of their changes, and a working copy or a subsample run with lines of a fingerprint
between two versions collects those repositories again. A change to other code, such as
`agentcontext/steps/collected_file_cleanup.py` or `agentcontext/steps/detection.py`, keeps both
fingerprints and needs no version. A run applies such a change to every repository in the steps
after the cloning step.

`changes` gives a line only the changes of the versions after its own, and the code of each
version therefore has to contain every change that the versions before it record. A branch that
records versions of its own can keep them in its merge only where `main` recorded no version after
the branch began. Where `main` did, the code under a version of the branch lacks those changes, and
a line under it would be taken over without them. The merge then replaces the versions of the
branch with one version of the merge's fingerprint, with the sentences of their changes and a reach
that covers each of them, as `agent_role_file_or_opencode_agent_configuration` combines the reaches
of a Codex role and of an OpenCode configuration. A line under a fingerprint of the branch is then
collected again, because the record does not name it. No test checks the rule, because a test
would need the code at each recorded fingerprint, which only the history of the private repository
holds.

## Error handling & edge cases

| Scenario | Behavior |
|----------|-----------|
| Input CSV missing the repository column | `parse_repo_csv` exits non-zero with a message to stderr |
| A value that is not a whole `owner/repo`, such as a URL or a path below a repository | Skipped. A `WARNING repository_cloning:` line names how many and the first. A blank value is skipped silently |
| Duplicate repository in input | First occurrence kept, later ones dropped |
| `git` or `rsync` not on `PATH` | `main` returns 1 with an error to stderr |
| Snapshot query fails on a repository with commits | `collector_error`, with the Git command, exit code and error in its traceback. No configuration is copied or history cached, and a resumed run retries it |
| Snapshot metadata is absent and Git confirms zero commits | An empty repository has blank snapshot fields and no history measurements. A failed commit-count query does not establish emptiness |
| Clone fails after all retries | A first collection writes `clone_failed` and an all-`FALSE` row of the collected list. A retry of a successful collection keeps its previous rows, tree, file list and commit shards, with `redo` set for another attempt. It keeps nothing when the last line of the repository is a retry that never recorded its end (`retrying`), because the tree may already be the tree of the retry. It also keeps nothing when the collection is not on disk, when its commit log is missing, or when its path heuristics differ from this run's in a row that reaches its file list. The failed attempt still counts toward the failure guards |
| `git` cannot be started, such as when `fork()` fails | A failed attempt, `NOT STARTED` in the log, retried with the backoff as a timeout is |
| A repository that GitHub closed, `Access to this repository has been disabled` or `Repository unavailable due to` | Permanent after one attempt. Recorded as `dmca_takedown` when the message names a DMCA takedown and as `disabled_by_github` otherwise, the reason that git's message gives. |
| The history fetch times out twice, breaches the size bound, or exits non-zero twice | The files get no history row, and a WARNING names their count. The per-repository commit record and `ai_commits-repos.csv` record `history_unavailable`, and the per-repository commit record also records the cause and the bounds. The file history step clones for the rows that are missing from the cache. A run under larger bounds fetches again a history that the timeout or the size bound stopped, and the next collection fetches again a history with a fetch that exited non-zero. The Git error identifies the failed operation and its cause |
| A file or directory name in the tree is not UTF-8 | Removed from the collected tree after the copy. A `WARNING repository_cloning:` line and an `UNDECODABLE_NAMES` line in the clone log name what was removed |
| A gitlink path is not UTF-8 | Decoded with a replacement character, and the row is recorded |
| Repository missing or no access | A permanent-failure pattern ends the retries early, and the repository is recorded as `not_found_or_no_access`. GitHub returns `Repository not found` for a deleted repository and a private repository alike, and so does its API, and the two cases therefore stay one reason |
| GitHub refuses the GitHub access token, with `Invalid username or token` or `Authentication failed for` | `clone_failed` after that attempt, with `CREDENTIAL_REFUSED` in the clone log. The earlier collection stays, the failure counts toward `--max-clone-failures` and the failures in a row, and the retry rounds and a resumed run clone the repository again |
| A name of the tree is longer than the file system allows, `Clone succeeded, but checkout failed` with `File name too long` | `file_name_too_long` after that attempt, outside `--max-clone-failures`. The rest of the collection keeps the outcome, a retry of an ok line removes the earlier collection as a refusal by GitHub does, and the next collection clones the repository again |
| Clone grows past `--max-clone-mb`, while running or once finished | Stopped, with the tree removed and no retry. Recorded as `size_bound_exceeded` with the size bound, in the list of finished repositories as any finished repository is. Cloned again by a run under a larger `--max-clone-mb`, and not under the same |
| One clone attempt exceeds `--clone-timeout` | The process group is killed, and the attempt counts as failed. It is retried with backoff as a network failure is |
| A second clone attempt exceeds `--clone-timeout` | The clone is removed and recorded as `time_bound_exceeded` with the time bound, without further attempts. Neither the retry rounds nor a resumed run of the same collection under the same `--clone-timeout` clone it again, and a run under a larger one and the next collection do. The outcome counts toward `--max-consecutive-failures` |
| A second clone attempt of a retry of an ok line exceeds `--clone-timeout` | The earlier collection stays, with its tree, shards, file list, workflow files and row, and the line records the time bound without `redo`. The rest of the collection keeps it as it is under the same `--clone-timeout`, and a run under a larger one and the next collection clone it again. The earlier collection is removed and the repository recorded as `time_bound_exceeded` where a failed clone would not keep it either, and where the commit history has to be read again. That line records the time bound without `redo`, as every `time_bound_exceeded` line does |
| Free space on the clone directory's volume drops under `--min-free-gb` | No further clone starts. The clones in flight finish and are recorded, the lists that the step reached are written, and the step exits `3` if work remains unstarted. Otherwise it warns and lets the running repositories finish |
| `SIGTERM` or `SIGINT` while the pool is up | Every worker is ended, and every git command that the workers started is killed by process group. The step exits `128 + signal`, with the list of finished repositories recording what finished and the retries written before they started, and nothing else for the repository in flight |
| Server rejects `--filter=blob:none` | The same attempt retries without the filter, and no extra retry is consumed |
| Repository declaring a submodule | Its gitlinks are recorded in `submodules.csv`, and nothing below a gitlink is copied. The files behind a gitlink belong to the repository that it names. No submodule is fetched, and an unreachable submodule therefore costs the run nothing |
| A tool directory, such as `.claude`, `.cursor` or `.agents`, is a symlink to a directory of the repository, at the root or below it | Its marker and the directory that the link leads to are collected, at that directory's path and without the places of the tool's local state, both at their paths in the directory and at their paths through the link. A place of the tool's local state that another pass or a second link copied with the directory, such as `.agents/shell-snapshots/` with `.claude -> .agents`, is removed once every link is followed. A planning document there is matched through the link and copied at its own path. The links in that directory are followed as in the tool directory. The detection step credits the tool of the link with what it reads there, and comet-ml/opik's `.agents/agents/*.md`, with `.cursor -> .agents`, are Cursor's subagents as well as Antigravity's |
| A tool directory is a symlink out of the repository, to the repository root or to a directory that contains it | Its marker alone is collected, which the detection step reports as an `other` row of the tool |
| `.agents` is a symlink to a directory of the repository | Its registration files, at their paths in the repository, what they select and a marker are collected. The marker names the directory that the link leads to, also through a chain of links such as `.agents -> lnk -> config/agents`. The directory is collected as that of any tool directory that is a link |
| A rule or an agent in a rules or agents folder, an Antigravity plugin's among them, is a symlink to a file of the repository, such as angular/angular's `.agent/rules/agents.md` that links to `../../AGENTS.md` | The marker of the link and the file that it leads to are collected. A file in the `.git` of the clone, such as its log, is not |
| The `SKILL.md` of a skill folder is a symlink to a file of the repository, such as feast-dev/feast's `.claude/skills/feast-dev/SKILL.md` that links to `../../../skills/feast-dev/SKILL.md` | The marker of the link and the file that it leads to are collected |
| A registration file, a settings file, a Codex config, a plugin manifest or a marketplace is a symlink to a file of the repository | Stored with the content that the step read through the link. A link that leads out of the repository or into its `.git`, or to a file that is not UTF-8, stays a marker, and nothing is read through it |
| A place below the root that Copilot CLI reads, such as dotnet/dotnet's `src/msbuild/.github/copilot-instructions.md`, is a symlink to a file or a folder of the repository | Its marker is collected. Where the link is at the place of a folder, such as `agents/`, the folder that the link leads to is collected too, at that folder's path. A link out of the repository, to its root, into `.git` or to a folder that contains it is no place, and nothing is collected for it |
| A symlink to a directory inside a directory that the step copies whole leads out of that directory, such as meshery/meshery's `.claude/hooks` that links to `../.agents/hooks` | Its marker is collected, unless a pass copied a file below the link's path. A link to a directory inside the copied directory stays a link, as rsync copies it |
| Nothing collected for a repository, or a first collection failed | The repository's output directory is absent |
| `GITHUB_TOKEN` set | Used for cloning, redacted from logs, and never written to `clone_failed.csv` |
| Worker raises an unexpected exception after the clone | Recorded as `collector_error`, with the traceback on stderr and in the clone log and the copied tree removed. The run continues, and the next run redoes the repository, unless the run ended within `--max-clone-failures`. The runner then records the step as complete, with the row as a failure |
| Git cannot enumerate HEAD with `ls-tree` | A warning and `FILE_LIST_ERROR` in the clone log name the repository, clone, command and retained Git error. Configuration copying continues. No file list or submodule rows are saved, and an earlier file list is removed. An established empty repository is not queried and gets an empty file list |
| `rsync` cannot copy a configuration directory | `paths.CopyFailed` names the source and destination, the exit status and the end of rsync's stderr. The worker records `collector_error` with that traceback in the clone log and removes the partial tree, and a resumed run retries the repository |
| A file list cannot be written | A warning names the destination and the OS error. Any stale file list is removed, and configuration copying continues |
| A worker dies, whether a result or `submit` reports it | `WorkerLostStop`: the repositories in flight, one per worker, are recorded as `clone_failed`, a repository that the pool was not handed keeps its line, the lists are written, a `WARNING repository_cloning:` line states that the cause is unknown and names the memory and process limits to check, and the step exits `4`. The next run retries them, and a tree that a worker was copying when it died stays until that retry removes it first |
| `--max-consecutive-failures` `clone_failed` or `time_bound_exceeded` in a row while the probe of `--probe-url` succeeds | A `WARNING repository_cloning:` line names the count and the log directory, the count starts over, and the run continues |
| Reading the commit history raised an `OSError` | The per-repository commit record records `history_read_failed` with `transient`, and the repository's line in the list of finished repositories has `redo`. The step redoes the repository in its rounds before it ends, and the next run that runs the step redoes it when those fail too, with each retry written into the list of finished repositories before it starts |
| Reading the commit history was refused by git | `history_read_failed` without `transient`, recorded and not redone |
| The history fetch did not bring the history under `--clone-timeout` or the size bound | `history_unavailable` with `cause` `time_bound` or `size_bound` and the bounds recorded. A run under larger bounds redoes it, and a run under the same bounds does not. The file history step measures the git and AI columns, and the last log messages of the run give how many |
| The history fetch exited non-zero on either attempt | `history_unavailable` with `cause` `exit` and `transient`, and the repository's line in the list of finished repositories has `redo`. The step fetches the history again in its rounds before it ends, and the next run that runs the step fetches it when those fail too. The exit code alone does not establish a network cause |
| Reading the commit history was ended by `--clone-timeout` | `history_read_failed` with `cause` `time_bound` and the timeout recorded. A run of the step under a larger timeout reads it again, and the log at the end of the run names it in the line `Reading the commit history timed out for N repositories` |
| A run ends with lines marked `redo`, after its rounds | Counted with the rows of the list of clone failures toward `--max-clone-failures`, and named in the line `N repositories remain to collect again`: a commit history that git could not start reading, a failed fetch of the commit history or query of the file history, missing copied files or a missing commit log, and a retry written before it started |
| A repository in the current format with a commit history that was read has no commit log after the retry rounds | Collection exits `4` regardless of `--max-clone-failures`, names the missing log and remains incomplete. Correct the storage failure, then resume the collection with the next run of the step, on the NAS with a Start of the container ([deploy](../deploy.md#import-create-start)). The repository is collected again with its actual revision and retrieval date, also when its line records a time bound that holds. A retry that fails keeps nothing of the earlier collection, and no record without its commit log remains |
| The last commit reclassification lists a repository as `failed`, and the per-repository commit record of the repository has the SHA-256 that `commit-reclassification.json` records for it | Collected again by the next run of the step, whatever its line and its head, with its line written before the clone |
| Every file of a repository's tree is one that `remove_undecodable_names` removes, whatever directories are left | The tree is removed and the flags of the row cleared, and the row and the tree agree in every run. No history is read, and the outcome is `no_files` |
| git could not be started for the history fetch, the shallowness check, the root commit or a file's history, or the snapshot query failed on a repository with commits | Recorded as `collector_error` with the traceback, through `MachineFailure` for the first four. The next run redoes the repository |
| A history query exits non-zero | The row is left out of both caches, and a `WARNING repository_cloning:` line names the file. The per-repository commit record lists it under `history_failed`, the repository's line in the list of finished repositories has `redo`, and the step collects the repository again in its rounds before it ends. When those fail too, the file history step clones for its git and AI columns, and the next run that runs the step collects it again |
| The first history fetch is killed at `--clone-timeout` | The lock files that it left in `.git` are deleted, and the fetch is tried once more under the same timeout |
| A repository's row has a flag, or its per-repository commit record is there, and its collected directory is not | Pending again on the next run that runs the step, with the retry written into the list of finished repositories before it starts, and the `Collecting N repositories again` line counts it |
| A clone, a history fetch or a file's history query fails on the network during the pass | Tried again after `--retry-pause`, <!--s:parameters.agentcontext.guards.RETRY_PAUSE_SECONDS-->300<!--/s--> s, in up to `--retry-rounds`, <!--s:parameters.agentcontext.guards.RETRY_ROUNDS-->2<!--/s-->, rounds before the step ends, each a resumed run in-process that logs a `Collecting N repositories again` line. A stop raised in a round ends the step as it would end the pass |
| `--max-consecutive-failures` `collector_error` among the last <!--s:parameters.agentcontext.guards.ERROR_WINDOW-->200<!--/s--> finished | No further clone starts, the clones in flight finish and are recorded, a `WARNING repository_cloning:` line names the defect and the tracebacks, and the step exits `4`. The probe does not run |
| A symlink's target is not UTF-8 | The marker contains the target with its bytes escaped |
| A shard with another set of columns in its header | Read into the current columns, blank where a column is new. A warning names the repository as one with a history that the step read under another set of columns |
| A csv under `collect_commits/` with no per-repository commit record | What a killed worker left rather than a shard. Nothing reads it |
| The same failed clones in a row while the probe of `--probe-url` fails | No further clone starts, and the step probes again after each wait of `guards.PROBE_WAITS`, with a `WARNING repository_cloning:` line per wait. When a probe succeeds, the count starts over and the run continues. When every probe fails, the clones in flight finish and are recorded, the lists that the step reached are written, a `WARNING repository_cloning:` line names the probe, and the step exits `4` |
| `SIGTERM` or `SIGINT` with `--workers 1` | The git process in flight is killed by process group, and the collector exits `128 + signal`, as a pool worker does, and the handlers are restored after the loop |
| A per-repository commit record under `collect_commits/` does not parse, such as a record that a power loss left empty | A WARNING names the file. The repository is recorded as `shard_unreadable` in `ai_commits-repos.csv`, and none of its rows reach the commit CSV. A record that does not parse comes from a disk that failed or a copy that was cut short, because `caches.replace_file` syncs the record before its rename. No later step can read such a record, and the next run of the step therefore collects the repository again (`resume.history_needs_reread`), with its line written before the clone. Without this rule, such a record would stay in every later collection of a repository that was taken over |
| The assembly of the commit CSV raises | An `ERROR repository_cloning:` line with the traceback, and exit `1`. Both lists, the caches and `submodules.csv` are already written |
| `--fresh` | The list of finished repositories, the records of the collection in progress and of the last collection that ended, `collect_commits/`, the clone log directory, the file lists, the workflow files, the imported files, `collection_heuristics/` and every repository directory under the collected tree are removed and named. The two lists at the tree's root stay |
| Directory name shares a prefix with a vendored name | Not pruned (exact-name match only) |
| Run killed mid-flight | Repositories already in the list of finished repositories are taken over by the next run, which resumes the collection and queries the heads only of repositories that the collection has neither collected nor confirmed. The clones in flight are redone, a retried repository through the line that the step wrote before the retry started. The final CSVs match the CSVs of an uninterrupted run apart from `scanned_at`, the wall clock of each repository, and the shards of what finished are read into the next assembly |
| Reading the commit history is stopped by `--clone-timeout`, or git refuses it | `history_read_failed` in the per-repository commit record and in `ai_commits-repos.csv`, with no commit rows. The file-history rows measured before it are kept |
| A commit message or identity is not UTF-8 | Decoded with a replacement character, and the commit is read and classified as any other is |
| The head commit, a copied file's creation commit or an AI commit has a date that does not parse, such as a commit of the year 10000, which git prints as `9999-12-31T23:30:00-01:00` in the offset `-0100` and as `10000-01-01T00:30:00Z` in UTC | The repository is collected as any other. The collected list keeps git's `head_commit_date`, `file_history.csv` keeps git's `created_at` with a `WARNING repos:` line that names the value, and the shard keeps git's `commit_timestamp`. The detection step publishes each such value blank, as the file history step does with the two dates ([detection](detection.md)) |
| Nothing was copied, or the copy failed, or every copied file was removed as a name that is not UTF-8 | No history is read, and `ai_commits-repos.csv` records `no_files` or the failure's reason |
| `--no-file-history` or `--no-ai-commits` | No shard is written and no CSV assembled. The output CSVs on disk are left as they are |
| The final line of `finished_repositories.jsonl` torn by a crash mid-write | Skipped on read, and that repository is treated as not done and collected again. The next append writes a newline first, and the line after the torn line is therefore read |
| Repository redone after an interrupted attempt | Its output directory is removed before collecting, and a redo therefore never merges onto a half-written tree |
| `finished_repositories.jsonl` already records every input repository | A new collection queries the heads with `git ls-remote`, and a resumed collection queries only the heads that it has not collected or confirmed. No repository with a head that has not moved is cloned, and the CSVs are rebuilt from the list of finished repositories |
| A repository's name changes only in case between two input lists | Collected under the new name. The files of the old name are removed, unless the file system folds case and they are the new name's |
| Input CSV changed between runs | No versioning needed: lines of the list of finished repositories and shards for repositories no longer in the input are ignored during assembly, and a run that finished every repository removes their files and marks the ok line of each such repository to redo, once. Newly added repositories are pending, and so is a repository that returns after its files were removed |
| git returns no head commit for a repository, twice | Taken over, with its line written again with `head_no_response`. The retry rounds and the next run that runs the step query its head again, even when `taken_over` of the collection contains the repository. At its end, the run counts it toward `--max-clone-failures` and names it in the line `No head commit from git for N repositories` |
| git returns no head commit for more repositories than the ceiling of `--max-clone-failures` allows | The step waits and queries those heads again in up to <!--s:parameters.agentcontext.reuse.HEAD_WAITS.length:words-->six<!--/s--> rounds with growing waits and fewer threads, until they are within the ceiling, and takes over with `head_no_response` the repositories for which git still returns none. A round queries no other head when the heads that it queries first, spread over the others, return none |
| A repository's default branch moved since its line, or GitHub refuses it | Collected again, with its line written before the clone. After a clone that fails on the network, the repository keeps the earlier snapshot with `redo`, and after a clone that the time bound ends twice, it keeps the snapshot with the time bound, under the conditions of [Key decisions](#key-decisions) |
| The run stops before a retry of an ok line starts, such as for low free space | The repository's line is the line of its earlier collection, because the line marked `retrying` is written right before the retry starts, and the next run keeps that collection when its retry fails |
| A line without `collected_under`, or a line collected by code of a version that `code_versions.COLLECTOR` does not name, under another version of git or with other records | Collected again |
| A line collected by an earlier version of the collector's code that `code_versions.COLLECTOR` names | Taken over when no change from that version to the current one reaches the repository, and otherwise collected again. A repository without a file list is collected again after a change with a predicate over the file list |
| `git --version` prints no version, such as when a fork fails on the NAS | Run again, up to the tries of `clone.git_version`. Then the step exits 1 before it opens a collection, and the list of finished repositories, the collected tree and the lists stay as they are |
| A JSON or TOML file of a clone nested too deeply for the parser, which raises RecursionError | Read as a file that does not parse, as the cleanup and detection read it: a `plugin.json` or `mcp.json` is no Agent Plugins document and is not copied, and a settings file or a manifest declares nothing. The repository is collected with the rest of its files |
| The path heuristics or the import heuristics changed since a repository's line | Taken over when no changed row reaches its file list, and otherwise collected again, also when the line kept its earlier collection under a time bound that holds. Collected again without a kept version or a file list |
| The commit heuristics changed since a repository's commit history was read | Taken over, with its commits classified again from the kept log. Collected again when that log fails validation |
| A refusal by GitHub, and git now returns a head commit | Collected again |

## Collection state and regression coverage

When reading the commit history succeeds, the step records the source URL, the UTC retrieval
date, the collected revision, the resolved refs and the Git version under `commit_evidence`.
Reading the commit history fails on a shallow clone and on a clone with a HEAD other than the
collected revision. Matched and unmatched commits remain in the compressed log, with complete
messages and NUL-delimited fields, and the per-repository commit record stores the checksum and
the commit count of the log, plus checksums for the classified CSVs. The step adds
`collected_artifacts` whether or not the path queries succeed, so that the reclassification can
detect missing path histories. `collected_artifacts`, the files for which the step reads the
history and every later comparison of the tree with the record come from the listing of the
directory by `paths.tree_files`. That listing leaves out a `.DS_Store` and every file below an
`@eaDir` (`paths.DISCARDED_DIRECTORIES`), the directory that Synology DSM writes into a
directory that File Station visits on the NAS. Counting such a file would make a valid record
`no_path_history` in the reclassification and make the cloning step clone its taken-over
repositories again. [The reclassification specification](commit_reclassification.md) defines
validation and coverage outcomes. When a commit log cannot be written, the reclassification is
not complete, even when its classifications are current. The `measures.copied` count of the line
of the repository in the list of finished repositories distinguishes a repository without copied
files from a repository with a required commit history and a missing per-repository commit
record.

`data/collected/` preserves the collected files and the `head_sha` of each repository. The
collected file cleanup derives the validated tree, and you can therefore run the later steps
again without changing the collected files. `finished_repositories.jsonl` records completion and
retry information. A resumed run uses the latest line of each repository and retries the
recoverable failures described above.

The list of excluded vendored directories is stored in `heuristics/vendored_dirs.txt` at the repository root (one name per line, and [The vendored list](../heuristics.md#the-vendored-list) gives the rationale). The collector, the collected file cleanup and the detection step read it through `agentcontext/heuristics.py` and therefore use the same list. The places of the tools' local state are in `heuristics/local_state_paths.csv`, which the collector and the collected file cleanup read through `agentcontext/heuristics.py` in the same way.

The collection regression suite runs a real local repository through `process_repo`, then reclassifies its commit log. It checks that the per-repository commit record lists the commits for each configuration artifact and that reclassification updates the AI-authorship row from that record. Leaving `path_commits` out of the per-repository commit record makes this integration test fail.

The regression tests of the retries cover a transient failure to clone a previously collected
repository and a failed file-history query that succeeds in the next retry round. They check
preserved data, repaired metadata and the pending retry status.

The regression tests of the collection use local remotes for transient and permanent clone
failures. They simulate a timeout while the commit history is read and check the processing
order against literal expected values under separate Python hash seeds. The tests of the
process cleanup wait for execution to end. On Linux, a zombie has exited even if its parent has
not reaped it. A fixture of the collection stage also checks that vendored plugins and context
files produce no copied tree or history rows.

The regression tests of the head check run the step with a stand-in `clone.remote_head` and a
clock that each wait advances instead of sleeping. Five of six heads without a head commit for
three minutes are waited out, and the step exits 0 without a clone. Two heads that never get a
head commit, within the ceiling, cost no wait and keep their earlier collection. Three heads
above the ceiling that never get one are waited through every round before the step exits 4.
Without the waits, the first case exits 4. The cases of `reuse.remote_heads` alone add a network
that is down, which costs a few queries per round, and heads that fail every time and sort
first, which do not keep a round from querying the others.

The tests of the head query run `git ls-remote` against a loopback server of `git http-backend`
in place of github.com, which records the credential of each request
(`tests/_fixtures.github_on_loopback`). With a GitHub access token, the first request carries it,
and without one, no request carries a credential. A refused GitHub access token is no response
rather than `not_found_or_no_access`. When GitHub refuses the authenticated query, as it does for
an address outside an organization's IP allow list or for a GitHub access token that has expired,
`reuse._head` takes the head from the anonymous query. No credential helper of the machine keeps
the GitHub access token.

A new collection of a repository replaces its workflow copies under `data/workflows/` and its
imported files under `data/imported/`, with the list of the stubs beside them. A failed clone or
a collector error removes them with the incomplete collection. The list of the stubs stays,
beside no directory, until the next collection of the repository removes it. No step reads it,
because the collected file cleanup derives no directory of the repository in the validated tree.
When the clone for a history repair fails, the previous collection, its workflow copies and its
imported files stay.

The regression tests of the file list cover a real empty repository with no HEAD, which
receives an empty file list, a failed query with retained credential-redacted stderr and
copied configuration, and a failure to write the file list that removes a stale file list.
Reintroducing the discarding of Git's stderr makes these checks fail.

A `history_read` record in the current format with scope provenance but no commit log is
pending on a resumed run, because a successful classification does not make lost evidence
complete. [Error handling & edge cases](#error-handling--edge-cases) gives the exit and the recovery. A storage error while
checking the log is not treated as confirmed absence.
