# Validate and clean collected configuration artifacts

## Context

This script builds the validated tree, which every later step reads, from the collected tree that `agentcontext/steps/repository_cloning.py` writes. The cloning step copies more than the dataset needs, such as whole spec directories and every candidate standalone file. The collected tree therefore includes files that are not configuration artifacts, such as operating system `.DS_Store` files, context files with the wrong letter case, vendored subtrees under a kept ancestor, and `.github` directories without Copilot configuration. This script applies the validity rules to a copy of that tree and deletes every file that fails them.

The input is the collected tree `data/collected/`, with its list at `data/collected/repos.csv`. The script copies the repositories to `data/validated/` and the list to `data/validated/repos.csv`, and it cleans the copy in place. It drops the repositories that are left with no file or with no named mechanism that the detectors find. It writes the deletion log, `deletion.csv`, with one row per removed file, directory and repository. The step only reads the collected tree, and running this script again therefore recovers from a failure here or in any later step without cloning again.

The collected list and the list of clone failures are at the root of the collected tree, beside the repository directories. The step therefore copies each repository directory on its own. A copy of the whole directory would copy `repos.csv` and `clone_failed.csv` into the validated tree and publish the list of clone failures as part of a sample that it does not belong to. Every step that lists the validated tree names the list that this step writes there, `data/validated/repos.csv`, in the `expected` argument of `repos.split`. Otherwise every run would log the file that it wrote a moment earlier as a stray entry.

## Key decisions

- **The source list has to name its metadata columns.** The step reads the header before it writes the validated tree, and it exits `1` for a header that lacks `repo_name` or names none of `scanned_at`, `branch`, `head_sha` and `head_commit_date`. The check does not require every column, because a list from a run before a column existed still has to validate. The filter that derives the validated header keeps the columns that it recognizes. If the filter fell back to the full set for a header that names none of them, it would validate a list of names that a killed cloning run truncated, with every other column blank. The detection step would then publish that list without a branch, a `head_sha` or a `github_link`
- **The header of the list of clone failures is checked.** Reading its rows with `.get` would return an empty set for a list with another header and for the zero-byte list that a killed cloning run leaves. The check in the next item would then exclude nothing, without a warning. When the list has no `repo_name`, the step logs a warning that names the file
- **A directory that the list of clone failures names is not copied.** A cloning error after the copy can leave a directory behind, while the row of the repository in the collected list records nothing as collected, with a blank branch and `head_sha`. A copy of such a directory would publish the repository with both blank. The cloning step removes such a directory, but an older collected tree can still contain one. This step leaves the directory out and logs a line that names it
- **A directory that the collected list does not name is not copied.** The cloning step rewrites its list from the input list, and a repository that is no longer in the input keeps the directory that an earlier run wrote. A copy of such a directory would be validated with every metadata column blank and published without a `head_sha`. This step leaves such directories out, one warning gives their count and names the first of them, and the `deletions` check accounts for them as `repository_not_listed`

- **A submodule's files are not this repository's:** a submodule is a gitlink in the tree, and the files below it belong to the repository that the link names. `submodules.csv`, which the cloning step writes on every run, records which collected directories are gitlinks. The step deletes every file below a gitlink with the reason `inside submodule (<path>)`. This test comes before every other rule except `.DS_Store`, because a submodule can contain a spec directory, a plugin manifest or a context file, each of which another rule would otherwise keep
- **The list of kept `.github` paths distinguishes directories from files:** a directory entry keeps everything below it, and a file entry keeps only that exact path. <!--s:heuristics.config_path_patterns.workflow_files:Words-->Six<!--/s--> workflows are kept by name: Copilot's `copilot-setup-steps.yml` and `copilot-code-review.yml`, Claude Code's `claude.yml` and `claude-code-review.yml`, the Gemini CLI action's `gemini-dispatch.yml`, and OpenCode's `opencode.yml`. Any other workflow is kept when it runs an agent (`paths.workflow_tool`). Keeping `workflows` as a directory would publish the CI workflows of every repository
- **The plugin rules apply to all four manifest directories:** Cursor and Codex copied Claude's plugin layout, and Copilot CLI keeps its manifest in `.plugin/`. `.cursor-plugin/`, `.codex-plugin/` and `.plugin/` therefore go through the same rules as `.claude-plugin/`, which keep everything inside the directory and the allowed siblings beside it
- **Some paths are kept by their exact path in the repository:** `ROOT_ONLY_PATHS` contains the exact paths, because `ROOT_ONLY_FILES` matches a basename at depth 1 and cannot express `.vscode/mcp.json`

- **Language:** Python 3.14 (single script `agentcontext/steps/collected_file_cleanup.py`), with the standard library and PyYAML, which `agentcontext/requirements.txt` pins. The step parses with PyYAML the front matter of an Antigravity rule that a registration file names (`paths.has_trigger`), and `paths` imports PyYAML only then (`paths.load_yaml`)
- **The collected tree is never changed:** the step only reads `data/collected/` and the list in it. Every run deletes `data/validated/` and copies the repositories of the collected tree again. A run is therefore idempotent and never builds on a half-cleaned validated tree that a killed run left
- **The imported tree is not cleaned:** the step neither reads nor changes `data/imported/`, which holds the files that the imports of the configuration artifacts reach and which the cloning step wrote. A file there is what a tool reads, whatever its name or content, and no rule of this step applies to it. A file that this step deletes from the validated tree, such as a misspelled context file below the root, stays in the imported tree where an import reaches it ([import detection](import_detection.md))
- **Symlinks preserved on copy, at any depth:** the step copies each repository with `paths.copy_tree`. A symlink that the cloning step stored as a one-line file stays a file, and a real symlink stays a symlink instead of being followed into a loop. `shutil.copytree` calls itself once per level of the tree, and rsync copies a configuration directory of a clone whatever its depth. Over a directory nested deeper than the recursion limit, `copytree` would raise RecursionError, and the step would exit 1 in every run over that tree. `copy_tree` lists the tree with `os.walk`, which keeps a stack of its own. As `copytree` does, it creates each directory before its contents and sets the mode and times of the directory after them
- **A symlink that leads outside the repository is removed first:** before every other pass, the step deletes every link that resolves to a target outside the repository directory, with the reason `symlink leading outside the repository`. Judged by its own path, a link inside a spec directory would be kept whatever its target, and the detection step would read through it. Through a `.claude/skills` link to a directory elsewhere, the detection step would count the SKILL.md files there as this repository's. The pass comes first because the `.github/hooks` pass lists the directory that it is given, and listing through a link would delete files in the target of the link. A link that resolves inside the repository is judged by its own path
- **A Synology directory is not copied, and the step removes every one that DSM writes into the copy:** Synology DSM writes an `@eaDir` directory into the directories that its File Station and indexing services visit, and on the NAS these include the collected tree and the validated tree. The copy leaves out every directory named `@eaDir` (`paths.file_manager_directories`). Copying such a directory would end the copy in `shutil.Error`, and the step with exit 1, when DSM removes one of its files between the listing and the copy. The same failure occurs when DSM has written an `@eaDir` into a directory of the copy before the copy reaches the `@eaDir` of the collected directory.
  DSM can write such a directory into the validated tree at any time after the copy. After the pass over the links, the step therefore deletes every directory named `@eaDir` at any depth with the reason `Synology DSM directory`, before any other pass reads the tree. No coding agent reads such a directory, but below a directory that a keep rule keeps whole, such as a plugin manifest directory, the validity pass would keep its files and publish them. A link with the name is judged as any other entry.
  `deletion.csv` has a `Synology DSM directory` row only for a directory that DSM wrote into the validated tree during the run, and none for the `@eaDir` directories of the collected tree. The log of an older collection, from a copy that took these directories along, lists them with the reason. `paths.DISCARDED_DIRECTORIES` names the directories, and every comparison of a tree with a per-repository commit record leaves out their files too (`paths.tree_files`). The runner leaves the same directories out of the manifest of the collected tree (`runner.DISCARDED_DIRECTORIES`, [the runner](../runner.md#resume-model)), so that opening the collected tree in File Station does not make the runner count the cloning step as unfinished
- **Every removal of a directory handles what DSM writes:** the step removes with `paths.remove_tree` the validated tree of an earlier run, each `@eaDir`, each repository without a detected mechanism and each directory that the passes empty. DSM can write an `@eaDir` into a directory while the step removes it. A removal with `shutil.rmtree` would then fail with ENOTEMPTY and end the step with exit 1 after the collection. `remove_tree` removes what DSM wrote and raises only when another entry is left
- **The repositories are copied, not the directory:** `repos.split(collected_dir, expected=COLLECTED_TREE_FILES)` returns the repository directories to copy, and the step leaves out the repositories that the list of clone failures names and the directories that the collected list does not name. The two lists that the cloning step writes at the root of its tree therefore stay out of the validated tree. The step then writes the validated list as `data/validated/repos.csv`
- **A vendored path is rejected before every keep rule:** the step rejects a path with a vendored component before it applies the spec-directory, `.claude-plugin` and `.github` rules, and a `node_modules/` inside `.claude/` is therefore deleted too ([The vendored list](../heuristics.md#the-vendored-list))
- **The local state of the tools is rejected before every keep rule:** `heuristics/local_state_paths.csv` lists the places where a tool keeps session logs, histories, caches, locks and logins, such as `.claude/projects/-<path>/` or `.codex/sessions/`. The step deletes a file at or below such a place with the reason `local state of a tool (<place>)`, whatever rule below would keep it, such as the rule for a spec directory, a plugin's parts or a planning document (`paths.local_state`). When a tool directory was a link, the step also checks, for each path below the directory that its marker names, the corresponding path through the link (`local_state_of`), because the tool writes its local state through the link. For example, with `.claude -> .agents`, `.agents/shell-snapshots/` is Claude Code's `.claude/shell-snapshots/`. The current cloning step copies none of these files ([The local state of the tools](../heuristics.md#the-local-state-of-the-tools)), but a tree collected under an earlier collector can contain them
- **One list for both steps:** `VENDORED_DIRS` is loaded at import from `heuristics/vendored_dirs.txt`, the same file that `agentcontext/steps/repository_cloning.py` reads, and the two steps therefore cannot prune different names
- **Case-sensitive spec filenames below the root:** `CLAUDE.md` is kept, and a `docs/claude.md` is deleted with the reason `wrong letter case of claude.md (instead of CLAUDE.md)`. At the repository root, `claude.md`, `agents.md` and `gemini.md` are kept in any case, as the `root_any_case` rows state, because Codex and Gemini CLI find them for the upper-case name on a case-insensitive file system. `compute_columns` sets their flags. The other exception is `.github/copilot-instructions.md`, which the step matches without regard to case because repositories spell it in varied cases
- **A context file that the configuration names is kept whatever it is called.** Before the validity pass, `paths.declared_context_files` reads what a Codex config, a Gemini CLI settings file or an extension manifest names, and what the `instructions` of an OpenCode configuration list, and `paths.declared_subagent_files` reads the role file that `config_file` of `.codex/config.toml` names and the files that a Codex agent role names, such as its `model_instructions_file`. `is_valid_file` keeps those paths after the submodule, vendored and local state checks and before every name rule. The collector copies these files, and without this rule the name rules of this step would delete them again, such as a root `CONTEXT.md` as not a spec file and the lowercase `gemini.md` that `google/clasp`'s extension manifest names as a misspelled `GEMINI.md`.
  The step keeps in the same way a component that an Antigravity registration file under `.agents/`, `.agent/`, `_agents/` or `_agent/` names, and every registration file of its inheritance chain that Antigravity reads (`paths.registered_configuration_files`), because such a file can be in a directory that no spec rule names. It does not keep an inherited file that sets none of `entries`, `inherits` and `exclude`, such as a package.json. The step keeps the whole folder of a registered skill, with its support files (`paths.registered_skill_folders`). Of a root skill, with the registration file that selects it in its own folder, the step keeps only the `SKILL.md` with `scripts/`, `references/` and `assets/`, so that the validated tree holds neither the source code nor the `.env` of a package that registers itself. An entry that names a skill's folder, or an agent file itself, selects that skill or agent as the collector reads it, and a plugin registration supplies a root to `paths.plugin_parts`. When a registration reaches a rule without a trigger, or an agent without a name and a description in its front matter, the step does not keep the file, because Antigravity CLI 1.4.2 read none of them. The step therefore keeps no README.md that a `.` entry at the workspace root reaches (`paths.has_trigger`, `paths.has_name_and_description`). A support folder that is the root skill's folder or a folder above it, such as `scripts -> .`, is no part of the skill.
  The step reads a registration file under a linked customization root, such as an `.agents` that links to `config/agents`, through the marker of the root, which it keeps as a file with the name of a spec directory. A declaring file that the collector read through a link is stored with the content that the collector read (`paths.store_declaring_files`), so that this step selects what the collector selected. The step keeps a file that the top-level `exclude` of a registration file leaves out of a default place, because it keeps a customization root and a plugin's parts whole. The detection step lists such a file under no mechanism of Antigravity (`paths.antigravity_left_out`)
- **A file that a GitHub Agentic Workflow imports is kept wherever it is.** Before the pass that removes empty files, `paths.agentic_workflow_imports` reads the imports of every GitHub Agentic Workflow in `.github/workflows/` with an engine that a `workflow_engine:` row names, and `is_valid_file` keeps those paths after the context files that the configuration names. The imports are the files that the front matter imports and the files that a runtime import in the body loads into the prompt, such as shopware/shopware's `.github/aw/sw-triage-policy.md` ([A workflow that runs an agent](../heuristics.md#a-workflow-that-runs-an-agent)). The rule for `.github` below would otherwise delete `.github/workflows/shared/engine.md` as CI, although the workflow's engine can come from that file, and the policy as a file outside the Copilot paths, although a runtime import loads it into the prompt. `is_valid_file` also keeps the prompt file that a step of a workflow passes to the Codex action in its `prompt-file` input (`paths.action_prompt_files`), such as a `.github/codex/prompts/review.md`, which is a part of that workflow. The rule for `.github` would delete it as a file that no Copilot row names. The step keeps an empty imported file as well, because gh-aw does not compile a workflow without a required import, and the pass that removes empty files skips it, as it skips an empty prompt file. `kept_when_empty` returns these files with the planning documents, their anchors and the CLAUDE files that determine whether Claude Code reads an AGENTS.md. The analysis of the content quality reads the same set in the validated tree and counts a listed empty file of the set with 0 lines
- **A plugin's manifest and parts are kept wherever the plugin is.** Before the validity pass, the step reads `paths.plugin_manifests` and `paths.plugin_parts`, which include what a Claude Code or Copilot CLI manifest names and a root `SKILL.md` (`paths.plugin_components`). `is_valid_file` keeps a file at or below one of those paths, after the submodule and vendored checks. Without this rule, the step would delete a plugin's skills and agents under `plugins/<name>/` as files outside every spec directory, and the Copilot CLI manifest under `.github/plugin/` as an irrelevant file in `.github`. `TestAPluginReachesTheDetector` runs this step and the detection step in order over such a plugin
- **`.github` is kept for Copilot configuration only:** the whole directory is dropped unless it contains a Copilot trigger or a context file. The triggers are `COPILOT_TRIGGERS`, every path that the heuristics name under `.github`, such as `copilot-instructions.md`, `instructions/`, `prompts/` and the <!--s:heuristics.config_path_patterns.workflow_files:words-->six<!--/s--> workflows kept by name. When the directory is kept, only the paths that `agentcontext/steps/detection.py` inspects remain, among them the app settings `.github/github-app.yml` and `.github/copilot-desktop.yml`.
  Agent workflows are kept whatever else `.github` contains. An agent workflow is a workflow directly under `.github/workflows/` with a `uses:` line that runs a documented agent action that a `workflow_uses:` row names, a GitHub Agentic Workflow there (Markdown with front matter that has `on:`) with an engine that a `workflow_engine:` row names, or a workflow with a shell step that runs a tool's documented headless invocation, such as `claude -p` or `codex exec`. `paths.workflow_tool` returns the tool of such a workflow, and the collector and the detector call it too when they copy and count the file. If this step deleted such a workflow as an irrelevant file in `.github` before the detector runs, none of the <!--s:heuristics.config_path_patterns.workflow_uses_rows:words-->six<!--/s--> `workflow_uses:` rows would reach a CSV in a real run, and a repository with that workflow as its only configuration would drop out of the configured repositories. A test that gives the detector a tree that this step has not cleaned cannot find that deletion, and `TestAnAgentWorkflowReachesTheDetector` therefore runs both steps in order. The rest of `.github`, such as its other workflows and issue templates, is not configuration.
  The step treats a `.github` below the root the same way, except for the places in it that Copilot CLI reads in the directory that it works in: `copilot-instructions.md`, `instructions/`, `agents/`, `skills/`, `lsp.json` and `mcp.json`. The rows with the match mode `nested:` name these places, and `paths.nested_places` finds them. The step keeps each of them, a folder whole, whatever the root's `.github` contains, as it keeps the `.mcp.json` of a directory below the root ([Copilot CLI's places below the root](../heuristics.md#copilot-clis-places-below-the-root))
- **`.claude-plugin` siblings, not descendants:** the contents of a `.claude-plugin` directory are always valid, but in its parent the step keeps only `README`/`LICENSE`/`package.json` and standalone spec files, and only as immediate siblings. Keeping the whole subtree of the parent would keep tens of thousands of unrelated files of repositories that nest a plugin above vendored submodules
- **`PLANS.md` requires Codex evidence, and this step accepts fewer kinds of evidence than the collector does:** a `PLANS.md` is kept only in a repository with a `.codex` directory at the repository root, an `AGENTS.md` or `AGENTS.override.md` that this step kept, or an `agents.md` in any case at the root. The collector copies a `plans.md` in any case when a `.codex` directory is at any depth or an `agents.md` or `agents.override.md` in any case is anywhere (`paths.collect_codex`). This step therefore deletes some of what the collector copied: a `PLANS.md` beside a `.codex` directory below the root as `PLANS.md without Codex configuration or AGENTS.md`, and a `plans.md` in another case as a wrong case. `PLANS.md` is a common filename for project plans and has no relation to Codex on its own
- **Metadata is copied, never recomputed:** the step copies `scanned_at`, `branch`, `head_sha` and `head_commit_date` unchanged from the collected list. This step clones nothing and reads no commit history, and it can only copy these values. It only deletes files, and the SHA that identified the collected snapshot therefore still identifies where the remaining files came from. A date derived again here would describe the validated tree instead of the collection. The list is `heuristics.META_COLUMNS`, the same <!--s:parameters.agentcontext.heuristics.META_COLUMNS:words-->five<!--/s--> columns that every published CSV has. The column order follows the collected list, and a list produced before `head_sha` existed validates without gaining a blank column
- **The step stops on a collected list that still names the head commit date `timestamp`.** The filter that derives the validated list keeps only the columns that it recognizes and drops the rest without a warning. Such a list would validate into a list with no dates, and the detection step would publish a blank column for every repository. The step reads the header before the copy that replaces the validated tree, and the error names the cloning step as the way to produce a list with the current columns

- **Flags computed, not written:** `data/validated/repos.csv` receives only the <!--s:parameters.agentcontext.heuristics.META_COLUMNS:words-->five<!--/s--> metadata columns. `agentcontext/steps/detection.py` computes the boolean columns from the same cleaned tree and is their single writer, because flags written by two steps could disagree. The flags do not determine which repositories stay either, because the keep check is `agentcontext.steps.detection.has_detected_mechanism`. `compute_columns` still runs, and the `PLANS.md` check is the only reader of what it computes
- **Fail on a missing or empty collected tree:** when `data/collected/` is absent or contains no repository directory, the step returns exit code `1` instead of writing an empty list and exiting `0`, which the runner would read as success. The step checks for repository directories and not for an empty directory, because the collected list is stored in the tree. A collection that produced nothing but its own list leaves a directory that is not empty, and a test for emptiness would never fail
- **Every deletion is logged:** `deletion.csv` records one row per removed file, per removed empty directory and per removed repository, each with a reason string. The `deletions` check compares it with the two trees and the output CSVs (`docs/checks/deletions.md`)
- **The checks find a reason by its wording:** the `deletions` check, `unmatched paths` and the `deleted:` entries of the subsample's `coverage` find rows of `deletion.csv` by the reason text. When you change the wording of a reason, change these matchers and the reason table below in the same commit, and regenerate the tracked log `deletion.csv.7z` and `dev_subsample.csv` as [development](../development.md#continuous-improvement-from-handovers) describes. A new kind of deletion gets a new string and a row of the reason table below

## `agentcontext/steps/collected_file_cleanup.py`

### Architecture

#### Collected tree and validated tree

`main` first checks the collected tree: the list must be a file, and the tree must exist and contain at least one repository directory. It then removes `validated_dir` if present and creates it again. With `paths.copy_tree`, it copies into it each repository that the collected list names and the list of clone failures does not, with symlinks kept as symlinks and without the `@eaDir` directories that DSM writes. `shutil.copy2` copies the collected list to `data/validated/repos.csv`. Everything after this point works only on the copy. The step reads the header of the collected list before it rewrites the validated tree, and the output header keeps the column order of the source.

#### Validity precedence

`is_valid_file` returns whether to keep a file. It tests the rules below in order, and the first rule that matches gives the result:

1. `.DS_Store`: delete, at any depth
2. Inside a submodule that `submodules.csv` records as a gitlink: delete
3. Inside a vendored directory: delete, overriding every rule below. Inside the target of a link at a mechanism path, only a vendored directory below the target counts (`vendored_dir_of`)
4. At or below a place of a tool's local state (`paths.local_state`), also where the path reaches the place through the marker of a tool directory that was a link: delete, overriding every rule below
5. Inside a plugin manifest directory (`.claude-plugin`, `.cursor-plugin`, `.codex-plugin`, `.plugin`): keep
6. A context file that a configuration names, or a component or registration file that an Antigravity registration names: keep
7. A file of `kept_when_empty`: keep. The set contains a file that a GitHub Agentic Workflow imports in its front matter or loads with a runtime import of its body (`paths.agentic_workflow_imports`), the prompt file that an agent action of a workflow reads (`paths.action_prompt_files`), the prompt file that an agent of an OpenCode configuration names (`paths.opencode_prompt_files`), a planning document or one of its anchors (`planning.find`, [Planning documents](../heuristics.md#planning-documents)), and a CLAUDE file that determines whether Claude Code reads an AGENTS.md (`imports.deciding_claude_files`). Planning documents and anchors include a `specs/001-name/spec.md` beside `.specify/`, a file of `.github/upgrades/` and the `.bmad-core/` file that the cloning step copied beside BMAD's `docs/prd.md`. Such a CLAUDE file is a CLAUDE file at the root where an AGENTS.md is, or in the directory of an AGENTS.md, because Claude Code reads no AGENTS.md beside a CLAUDE file, empty or not. For a root AGENTS.md in another case, which Claude Code reads only on a file system that ignores case, a root CLAUDE file in any case counts, such as an empty `claude.md`, which that file system opens as CLAUDE.md. The step computes the set before the passes. A pass can delete what put a file into the set, such as the AGENTS.md that made an empty CLAUDE file part of the set, when that AGENTS.md is empty itself or in a vendored directory. The analysis of the content quality computes the set in the validated tree. After the passes, the step therefore computes the set again over the cleaned tree, until the set holds every empty file that is left (`remove_empty_files`). A link that the deletion of an empty file left leading nowhere, such as a `.agents/CLAUDE.md` that links to the empty `AGENTS.md` beside it, counts as empty in the passes that follow, and the step deletes it when the set no longer names it
8. A plugin's manifest, or a file at or below one of its parts or of a registered skill (its folder, or a root skill's SKILL.md and support directories): keep
9. Immediate sibling of a plugin manifest directory and on the list of allowed siblings: keep
10. Inside a spec directory (the `SPEC_DIRS` derived from the heuristics) at any depth, or a file with the name of one, the marker of a tool directory that was a link: keep. A `_agents` or `_agent` is a spec directory only where it contains a place of Antigravity with a file below it (`paths.is_spec_directory`). The rules below judge the files of a Python package or a documentation partial with such a name, such as NVIDIA-NeMo/Curator's `nemo_curator/stages/audio/_agent/`.
11. A target of a symlink marker or a link (`find_marker_targets`, `find_marker_files`, `reads_through_marker`): keep. The targets are:
    - a path at or below a directory that a symlink marker of the collected tree names, at the root or at a place below it that the detection step reads (`detection._nested_anchors`), such as the `.cursor/rules` of a package
    - a path at or below the directory that the marker of a tool directory names, such as the `config/claude` of a `.claude` that links to it, at the same places (`_linked_tool_directories`), and a path at or below a directory that a marker in that directory names, such as `config/claude/skills`. The cloning step collects a tool directory that is a link as its marker and the directory that the marker names, and the tool reads the directory through the link ([repository cloning](repository_cloning.md)). A marker that names the repository root or a directory that contains the marker keeps nothing, because the cloning step copies no such target. A directory at or below `.github` that such a marker names is not kept whole, and rule 12 decides on its files
    - a path at or below the directory that a link leads to, where the link is at a mechanism path and rsync kept it, such as the `copilot-agents` of `.github/agents -> copilot-agents` in a `.github` that the collector copies whole
    - a path at or below the directory that a marker names, where the marker is at a place below the root that a `nested:` row reads (`paths.linked_nested_directory`), such as the `agents` that a package's `.github/agents` names as `../agents`
    - a file that a marker names, where the marker is directly in a folder of items that are files, such as rules and agents, a row of the folder reads the marker as a skill, an agent, a command, a rule or a hook file, and a rule of this list keeps the marker
    - a file that the `SKILL.md` of a skill folder in a skills directory names, where that `SKILL.md` is a marker and a rule of this list keeps it (`paths.skill_files`)
    - an entry that a link leads to where a rule of this list keeps the link, with each link of a chain
12. In a `.github` that the marker of a tool directory names, such as plesk/centos2alma's `.claude -> .github/`: keep a file that a row of the linking tool's mechanisms reads at its path through the link (`read_through_link`), such as `.github/settings.json` as `.claude/settings.json`, and leave every other file to rule 14, which deletes a CI workflow or an issue template as it would without the link
13. At or below a place below the root that a `nested:` row reads (`paths.nested_places`), such as a package's `.github/copilot-instructions.md`, `.github/agents/` or `.mcp.json`: keep
14. Inside `.github`: keep a workflow directly under `.github/workflows/` that runs an agent (`paths.workflow_tool`), and any other file only if the directory contains detected Copilot configuration or context files *and* the path is one that `agentcontext/steps/detection.py` inspects, and delete everything else
15. A `SKILL.md` that reached this point: delete, because it is outside every valid parent directory
16. A root-only file (`.mcp.json`, `REVIEW.md`, `.worktreeinclude`, or OpenCode's `opencode.json`, `opencode.jsonc`, `tui.json` and `tui.jsonc`) at the repository root, or an exact path of `ROOT_ONLY_PATHS` (`.vscode/mcp.json` and `marketplace.json`): keep
17. `claude.md`, `agents.md` or `gemini.md` in any case at the repository root: keep
18. A standalone spec file at any depth: keep
19. A `plugin.json` or `mcp.json` that declares the Agent Plugins schema: keep
20. Anything else: delete

The order is part of the specification. With the vendored check below the spec-directory check, the step would keep vendored trees. With the `.github` check above the spec-directory check, it would delete `.claude/` content that is under a `.github` ancestor. The planning documents come before the `.github` check, which would delete the files of `.github/upgrades/` as files that detection does not inspect.

#### Empty-file and empty-directory removal

The step removes empty files before the validity pass, and it logs an empty file as `empty file` instead of under whatever validity reason would otherwise apply. Every empty file outside `kept_when_empty` is gone before the detection step runs. An `is_empty` column would therefore be `TRUE` only for the files of that set, which the analysis of the content quality counts with 0 lines, and no published CSV has one. `is_empty_file` treats a file with only whitespace and a JSON file that parses to `{}` or `[]` as empty. An unreadable file counts as non-empty and is left for the validity pass. The pass skips the files of `kept_when_empty`, the set that item 7 of [Validity precedence](#validity-precedence) describes, which the step computes before the pass. An anchor can be empty, such as a `backlog/config.yml` of whitespace or cursor-memory-bank's `.cursor/commands/van.md`, and deleting it would also lose the documents that need it. After the validity pass, `clean_empty_dirs` removes directories from the bottom up, and the step logs only the topmost directory of each removed subtree. A pruned tree ten levels deep is one row instead of ten.

#### Flag computation and repo removal

`compute_columns` derives the boolean flags from the files that remain after cleaning. Spec directories at the top level of the repository set their tool flag, `.github` with a Copilot trigger sets `copilot`, and a check of every remaining file sets the context-file flags. The `PLANS.md` check reads `plans.md`, `codex` and `agents.md` of these flags, and nothing writes or reads the other flags.

A `plugin.json` or an `mcp.json` is kept only where the document declares the Agent Plugins schema, the same test by which `agentcontext/paths.py` copies it. Over a tree that the current cloning step produced, the test always passes, because nothing else was copied. The step applies the test again because it also runs over trees collected under older heuristics, where a `plugin.json` of an unrelated program can be beside a plugin manifest directory.

The step drops a repository that has no file left after cleaning, or no named mechanism detected in what is left. `agentcontext.steps.detection.has_detected_mechanism` tests for a named mechanism. It runs the detectors that build the mechanism CSVs, and the configured repositories therefore have one definition instead of two. The `other` detector is not among them, and a repository with only files that no heuristic explains is dropped. Because a planning document is no configuration artifact, a repository with planning documents alone is dropped too, with its planning documents. The step removes the dropped directories from `data/validated/` and logs them.

The keep check does not test whether every flag is `FALSE`. Under that test, an empty `.claude/` directory, which sets the `claude` flag, would keep its repository, while the repository of a root `.mcp.json`, which sets no flag, would be dropped. The `PLANS.md` check for Codex evidence still deletes a `PLANS.md` without that evidence. It can leave a repository with no flag set, and the repository stays when the files that are left contain a named mechanism, such as a root `.mcp.json`.

### Output

`data/validated/repos.csv` contains only the metadata columns, sorted by `repo_name`:

| Group | Columns |
|-------|---------|
| Metadata | `repo_name`, `scanned_at`, `branch`, `head_sha`, `head_commit_date` |

Each run of the step rewrites `deletion.csv`, which git ignores. The tracked `deletion.csv.7z` holds the log of the current collection. The log has the columns `path` and `reason`. Paths are relative to the working directory that the script ran in, not to the repository, and each path therefore starts with `data/validated/` (a log of an older collection starts with `repos/`). The reason vocabulary is closed:

| Reason | Emitted for |
|--------|-------------|
| `symlink leading outside the repository` | A symbolic link that resolves to a target outside the repository directory, removed before every other pass |
| `empty file` | A file with only whitespace, or JSON that parses to `{}` / `[]` |
| `non-JSON file in .github/hooks` | Any non-`.json` file directly in `.github/hooks/`, unless `.github/hooks` is a link, in which case the files of the folder that it leads to are judged by their own paths |
| `macOS Finder file` | `.DS_Store` at any depth |
| `Synology DSM directory` | A directory named `@eaDir` at any depth that DSM wrote into the validated tree after the copy, removed whole after the links that lead outside the repository and before every other pass. The copy leaves out the `@eaDir` directories of the collected tree, and the log has no row for them |
| `inside submodule (<path>)` | A path under a submodule that the tree records as a gitlink. `<path>` is the submodule's own path |
| `inside vendored directory (<name>)` | A path with a vendored component, except a skill folder with a vendored name. Inside the target of a link at a mechanism path, only a component below the target counts. `<name>` is the first vendored name matched |
| `local state of a tool (<place>)` | A path at or below a place of `heuristics/local_state_paths.csv`, such as a transcript under `.claude/projects/-<path>/`. `<place>` is the place as the file names it, such as `.claude/projects/-*/` |
| `wrong letter case of <file> (instead of <FILE>)` | A case variant of `CLAUDE.md`, `AGENTS.md`, `GEMINI.md`, or `PLANS.md` |
| `SKILL.md outside valid directory` | A file named exactly `SKILL.md` that no keep condition kept, inside `.github` as well as outside every spec directory |
| `file in .github without Copilot configuration or a context file` | Any file under a `.github` directory without detected Copilot configuration or context files |
| `file in .github outside the Copilot paths` | A file under a kept `.github` that no detector inspects |
| `not a spec file` | Everything else that matched no keep rule |
| `PLANS.md without Codex configuration or AGENTS.md` | A `PLANS.md` that fails the Codex check |
| `empty directory after cleanup` | The topmost directory of each removed empty subtree |
| `no detected mechanism, repository directory removed` | A repository left with no files, or with no named mechanism detected in it |
| `other-only repo moved to repos_excluded` | Removed. The step that wrote this reason no longer exists ([Error handling & edge cases](#error-handling--edge-cases)). The reason string keeps the old directory name, because the published `deletion.csv` recorded that name |

`data/validated/` contains the validated tree, one `<owner§repo>/` per remaining repository, with `repos.csv` at its root. Every run creates `data/excluded/`.

## Error handling & edge cases

| Scenario | Behavior |
|----------|-----------|
| `data/collected/repos.csv` missing | Logs `ERROR collected_file_cleanup: Could not find the collected list` and returns exit code `1` |
| `data/collected/repos.csv` with a `timestamp` column | Logs `ERROR` naming the rename and the cloning step as the way to produce a current list, and returns exit code `1` before the validated tree is derived |
| `data/collected/` missing, or containing no repository directory | Logs `ERROR` and returns exit code `1`, because a collected tree with no repositories is an incomplete collection and not a clean run |
| `data/validated/` or its list damaged by a killed run | Every run rebuilds both from the collected tree at its start, and no recovery step is needed |
| Repository directory present but absent from the list | Not copied. One `WARNING` gives the count and names the first <!--s:parameters.agentcontext.steps.collected_file_cleanup.unlisted_named:words-->ten<!--/s-->. The `deletions` check accounts for it as `repository_not_listed` |
| CSV row with no matching directory | Absent from the output without a warning, because the step processes directories, not rows |
| A repository's directory in the validated tree contains directories but no files | The repository is dropped as empty and logged as `no detected mechanism, repository directory removed` |
| Vendored subtree under a spec directory | Deleted, because the vendored check precedes every keep rule |
| A place of a tool's local state under a spec directory, such as `.claude/scheduled_tasks.lock` or a worktree's `.claude/worktrees/<name>/CLAUDE.md` | Deleted with `local state of a tool (<place>)`, because the check precedes every keep rule. A folder of a repository's own under `.claude/projects/` with a name that is no encoded path, such as apache/superset's `js-to-ts`, is kept |
| Directory name shares a prefix with a vendored name | Kept, because only an exact path component matches |
| A skill folder named like a vendored directory, such as unoplatform/uno's `.claude/skills/docs-build` | Kept, because it contains a `SKILL.md` of its own (`paths.is_vendored`). A vendored tree inside it and a folder that contains only skills, such as `skills/vendor`, are deleted |
| A skill that a link at a mechanism path leads to inside a vendored directory, such as open-metadata/openmetadata's `.claude/skills/composition-patterns`, which links to `../../skills/vendor/composition-patterns` | Kept, because the tool reads the skill through the link and the collector copies the target (`find_marker_targets`). A vendored directory below the target, such as a `node_modules/`, and a skill in the same vendored directory that no link names are deleted |
| `.github` with workflows but no Copilot trigger or context file | Every file under it is deleted with `file in .github without Copilot configuration or a context file`, except a workflow that runs a documented agent action, a GitHub Agentic Workflow with an engine that a `workflow_engine:` row names, and a workflow with a shell step that runs a tool's documented headless invocation |
| A workflow under any name with a `uses:` that runs an action that a `workflow_uses:` row names, such as `anthropics/claude-code-action` or `openai/codex-action` | Kept and counted by the keep check, and a repository with that workflow as its only configuration stays among the configured repositories |
| `.github` kept, but containing release workflows | The release workflows are deleted with `file in .github outside the Copilot paths` |
| Copilot trigger with unexpected casing (`.github/Copilot-Instructions.md`) | The cloning step, this step and the detection step match the Copilot path names without regard to case on macOS and Linux, and copied paths keep their original names |
| Trigger name present as the wrong type (a file named `skills`) | Counts as a trigger, because the step tests existence, not type |
| `.github/hooks` with git hook scripts and no `.json` file at any depth | No trigger, because Copilot reads only the JSON files there, also in subfolders, and this step deletes the scripts (`holds_hook_file`). If the scripts counted as a trigger, the step would keep `.github`, and the context files below a nested `.github`, in the pass that deletes the scripts, and a second pass over the same tree would delete those files |
| A `.mcp.json` below the repository root | Kept where `paths.nested_places` finds it, outside the vendored directories and the directories that their own rows read whole, because Copilot CLI reads the `.mcp.json` of the directory that it works in and of each directory between that directory and the root. The rule for root-only files keeps the root's `.mcp.json` |
| `.github` nested below the repository root | Its places that Copilot CLI reads where it works (i.e., `copilot-instructions.md`, `instructions/`, `agents/`, `skills/`, `lsp.json` and `mcp.json`) are kept whatever the root's `.github` contains (`paths.nested_places`). A place that was a link is kept as its marker, and the marker of a folder keeps the folder that it names. The step judges the rest of it by the decision for the root `.github`, which it makes once per repository. The rest is dropped when the root `.github` is absent or contains no detected Copilot configuration or context files. Otherwise only the context files inside it remain, because `is_relevant_github_file` inspects the path component after the repository root, not the component after the nested `.github` |
| Deep descendant under a `.claude-plugin` parent | Deleted unless it is a spec file in its own right. Only immediate siblings are kept |
| Unreadable or non-UTF-8 file | `is_empty_file` returns `False`, and the validity rules alone determine whether the step keeps the file |
| A JSON or TOML file nested too deeply for the parser, which raises RecursionError | Read as a file that does not parse: `is_empty_file` returns `False`, a `plugin.json` or `mcp.json` is no Agent Plugins document, and a manifest or settings file declares nothing. The step goes on with the other files and repositories |
| A JSON or TOML file with an integer literal of more than <!--s:parameters.python.int_max_str_digits-->4,300<!--/s--> digits, which Python does not convert. The parser then raises a ValueError that is neither a JSONDecodeError nor a TOMLDecodeError | Read as a file that does not parse, as a file nested too deeply is. Every reader of a collected file catches ValueError, not the decode error alone |
| DSM writes an `@eaDir` into a directory while the step removes it | Removed with the directory (`paths.remove_tree`), and the step goes on. When another entry appears there, the step exits 1 and names the directory |
| DSM removes a file of an `@eaDir` of the collected tree during the copy, or writes an `@eaDir` into a directory of the copy | The copy leaves every `@eaDir` of the collected tree out, and the Synology pass removes what DSM wrote into the copy. The step goes on |
| A directory nested deeper than the recursion limit, which rsync copies whatever its depth | Copied (`paths.copy_tree`) and validated as any other directory |
| `PLANS.md` alone in a repository | The check fails, the file is deleted, no named mechanism is left, and the repository is dropped |
| `PLANS.md` beside a `.codex` directory below the root, with no other Codex evidence | Deleted as `PLANS.md without Codex configuration or AGENTS.md`, although the collector copied it |
| Repository with remaining files that set no flag | Kept if a named mechanism is detected, as a lone `.mcp.json` is. The step moves no repository to the excluded directory, because under the keep check such a move would remove configured repositories. This step still creates `data/excluded/` and is its only writer. The directory stays empty, and neither the runner nor the archive step names it. |
| Symlink in the collected tree | Copied as a symlink and judged by its own path, and never followed while the tree is read |
| A link that rsync kept inside a directory that the collector copies whole, such as `.github/copilot-instructions.md -> docs/copilot.md` or `.github/agents/reviewer.agent.md -> ../agent-defs/reviewer.md` | Where a rule keeps the link, the entry that it leads to is kept, and so is each link of a chain, because the detection step reads the file through the link. Judged by its own path, the target in `.github` would be deleted as an irrelevant file, and the link would lead nowhere. A kept directory can contain links that a rule then keeps, and the search therefore repeats until it reaches no new entry. The target of a link that the step deletes is judged by its own path |
| The marker of an `.agents` that links to `config/agents` with a registration file | Kept as a file with the name of a spec directory. The registration file in `config/agents` and what it selects are kept, with its paths resolved against the directory that contains the marker |
| The marker of a tool directory that was a link, such as a `.claude` that names `config/claude` or a `.cursor` that names `.agents`, at the root or below it | Kept as a file with the name of a spec directory, and the directory that it names is kept whole, as the tool directory would be, with the targets of the markers in its mechanism directories, except the places of the linking tool's local state, such as `.agents/shell-snapshots/` behind `.claude`. A marker that names a directory outside the repository, the repository root or a directory that contains the marker keeps nothing else |
| The marker of a tool directory that names `.github`, such as plesk/centos2alma's `.claude -> .github/` | Kept as a file with the name of a spec directory. The files of `.github` that the linking tool reads through the link are kept, such as `.github/settings.json` as Claude Code's settings, and the `.github` rule decides on the others, such as a CI workflow, which it deletes as it would without the link |
| A README.md that `.` in an `.agents/agents.json` or `.agents/rules.json` reaches | Deleted, because it has no name and description and no trigger in its front matter, unless another rule keeps it |
| A rule or an agent linked on its own: a one-line marker that names a file in the repository, directly in a folder of items that are files, a plugin's folder among them, such as angular/angular's `.agent/rules/agents.md` for `../../AGENTS.md` | The file is kept wherever it is, and so is each file of a chain of such markers. The detection step reads the rule's or the agent's front matter in that file, and the `language` of every skill, agent, command and rule that is a link (`detection.measured_artifact`). Deleting the file behind a linked Claude agent would make the agent an `other` row. A file in a `.git` directory is not kept, and neither is a file that a marker in a skills directory names, which is no skill |
| A marker in a folder of items that are files that no row of the folder reads as a skill, an agent, a command, a rule or a hook file, such as `.cursor/rules/notes.txt`, a link without `.json` in `.github/hooks` or in `.codex/environments`, or a linked `.github/instructions/*.instructions.md` | The marker does not keep the file that it names, because no row reads that file. The detection step publishes no column read from the text of a settings file, and it publishes a context file that is a link as a reference to its target. This step deletes a file of `.github/hooks` that is no `.json` file. A `.json` link in `.github/hooks` keeps the file that it names, which the detection step tests for hooks |
| A file of one line with a NUL, such as a file of NUL bytes in a commands folder | No marker (`paths.marker_target`), and judged as the file that it is. A symlink's target cannot contain a NUL, and the path functions raise `ValueError` for a path with a NUL. Read as a marker, such a file would stop the step in every run |
| A marker with a target that has a space, such as `../../Shared Skills/pdf`, also at its start or end, such as `../../shared/pdf ` | A marker where the text names a path beside the marker (`paths.marker_target` with the marker's folder), and the step keeps what it names, as the collector copied it. Spaces at the start or end of the text belong to the target where the text with these spaces, without the line end that the collector writes, names a path there, because the collector copies the target as git stored it. A text of one line with a space that names no path is prose, such as a rule of one sentence, and is judged as the file that it is |
| A folder linked on its own into a Claude Code commands or rules directory, such as GovTechSG/sgds-web-component's `.claude/commands/sgds-forms`, which names `skills/sgds-forms`, or opendatahub-io/opendatahub-operator's `.claude/rules/.rules`, which names `.rules` | The directory is kept wherever it is when it contains a `.md` file at any depth, because Claude Code reads every `.md` below the link as a command or a rule (`find_marker_targets`). A directory without one is deleted, and the marker remains an `other` row |
| A skill linked on its own, a one-line marker in a skills directory at any depth that names a directory in the repository | The directory is kept wherever it is when it contains a `SKILL.md`, as the target of a linked mechanism directory is. Without this exception, the rule for a skill outside a skills directory would delete such a `SKILL.md` |
| A marker in place of the `SKILL.md` of a skill folder, naming a file in the repository, such as feast-dev/feast's `.claude/skills/feast-dev/SKILL.md`, which names `skills/feast-dev/SKILL.md` | The file is kept wherever it is (`find_marker_files`), where a rule keeps the marker, and the detection step reads the skill in it. Judged by its own path, the file would be deleted, and the row of the skill would have a blank `language` |
| A directory named `@eaDir` in a repository directory, such as a directory that Synology DSM writes | Not copied, and the log has no row for it. A directory that DSM writes into the validated tree after the copy is deleted whole with `Synology DSM directory`, one row for the directory. A file or a link with the name is judged as any other entry. An `@eaDir` beside the repository directories is a stray, which the step names and does not copy |
| Symlink with a target outside the repository, including a target in a sibling repository | Deleted with `symlink leading outside the repository` before any other pass, wherever it is, and no pass reads or deletes through it. Its target is left alone |
| An entry with the name of a repository directory that is a symlink | Named as a stray entry and not copied into the validated tree. `os.path.isdir` follows a link, and a test with it would scan through the link. The cleanup would then delete the invalid files in the link's target, outside the validated tree, and inside the collected tree when the link points there. The link's own name would reach `data/validated/repos.csv` as a repository that nobody collected, and `shutil.rmtree` would then stop the run, because it raises an error for a symbolic link |
| Another run on an already-cleaned validated tree | Identical result, because the validated tree is discarded and derived again first |

A repository with only a Cursor worktree setup in `.cursor/worktrees.json` has a named settings mechanism, and the step keeps it.

The regression tests of this step name Copilot LSP files and marketplaces, the portable plugin directory and Antigravity paths explicitly, and each of these files must remain after cleaning when it is the repository's only configuration.

The reason `inside submodule (<path>)` gives the path of the submodule that contains the file, matched by complete path components. A sibling with a name that shares a prefix with the submodule therefore does not match.

The spec directories include `.gemini`, which contains Antigravity's `.gemini/config.json`, and all four Antigravity customization roots: `.agents`, `.agent`, `_agents` and `_agent`. `_agents` and `_agent` count only with one of the places that Antigravity reads in a customization root, such as `skills/` or `mcp_config.json` ([heuristics](../heuristics.md)).
