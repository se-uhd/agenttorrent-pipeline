# Detect configuration mechanisms

## Context

This script writes the output CSVs of the dataset from the validated tree. The cloning step and the collected file cleanup determine which repositories have configuration and which files belong to it. This step sorts the remaining files of each repository into the ten configuration mechanisms (i.e., context files, settings, skills, subagents, commands, hooks, rules, MCP, plugins and LSP servers), and into an `other` CSV for the files that no mechanism covers. It writes one CSV per mechanism, with one row containing all published metadata for each configuration artifact.

The input is the validated tree `data/validated/` and its list `data/validated/repos.csv`, both produced by `agentcontext/steps/collected_file_cleanup.py`, and the two fact CSVs that this step joins. `file_history.csv` is the cache of the Git columns that the cloning step fills. `ai_authorship.csv` contains the AI columns of every copied file, and this step joins the rows of the context files. For each repository directory, the script runs over the tree a detector for each mechanism, one for the agent workflows and one for the files that no mechanism covers, and records every configuration artifact that they find. It reads the file of each configuration artifact of a mechanism with a `language` column or reference columns, joins the facts for each row, and derives the boolean tool and file flags from what the detectors returned. It then writes these files into `output/`: `output/repos.csv` with one row per repository, the mechanism CSVs, `planning-documents.csv` with the planning documents of these repositories, `excluded.csv` for list rows that no longer have a directory, and `provenance.json`. Three files of the collection are named `repos.csv`, and this document always gives the whole path: `data/collected/repos.csv` comes from the cloning step, `data/validated/repos.csv` is the input of this step, and `output/repos.csv` is its output.

Each mechanism has one CSV, which has every published column, and `agentcontext/steps/file_history.py` fills in the git columns of a row for which `file_history.csv` had no row. [The mechanism CSVs](#the-mechanism-csvs) describes the two files per mechanism that existed until 2.0.0.

This step computes every boolean column of `output/repos.csv` from the detected configuration artifacts and copies none of them from the validated list. The collected file cleanup computes flags too, for its `PLANS.md` check, and it selects the repositories that stay with the detectors of this step (`has_detected_mechanism`), but it writes no flag. This step is the only writer of the flags, and a flag therefore cannot disagree with the mechanism CSV that produced it. After it removes the rows of the repositories that git reports as gone, `agentcontext/steps/file_history.py` derives the same columns again from the mechanism CSVs, and the tool flags from their `tool` column.

## Key decisions

- **Language:** Python 3.14 (single script `agentcontext/steps/detection.py`). The script uses the modules `heuristics` (the heuristics and the published headers), `caches` (the caches), `repos` (the naming, the links and the UTC conversion), `paths`, `imports` (the import heuristics and their chains, for `.claude/AGENTS.md`), `jsonc`, `commits` and `logs` of the package. Its third-party packages are `lingua-language-detector`, for the `language` column, and PyYAML, with which the front matter tests of an Antigravity rule (`paths.has_trigger`) and of a Cursor skill (`_cursor_skill_loads`) parse YAML (`paths.load_yaml`). The script imports `lingua` inside a `try`, because its language models are large. A run without it records `n/a` for every language and logs the fallback instead of failing, so that everything else can still be regenerated offline
- **CLI:** `python -m agentcontext detection` takes no path options, and `--help` describes the command. The paths are the module-level constants `VALIDATED_DIR`, `VALIDATED_CSV`, `FILE_HISTORY_CSV`, `AI_AUTHORSHIP_CSV` and `OUTPUT_DIR`, all relative to the working directory. Run the command from `data/collection/`. `VALIDATED_TREE_FILES` names the one file that the collected file cleanup writes at the root of the validated tree, so that the directory listing below does not log it as a stray entry. The tests reassign the module globals instead of passing arguments
- **Detection reads only the file system:** it clones nothing and uses neither the network nor git. The presence, location and content of the files on disk determine every row, and the step joins the facts that earlier steps recorded in the two fact CSVs
- **The metadata block is one list:** `heuristics.META_COLUMNS`, the <!--s:parameters.agentcontext.heuristics.META_COLUMNS:words-->five<!--/s--> columns `repo_name`, `scanned_at`, `branch`, `head_sha` and `head_commit_date`, which every mechanism CSV uses. `output/repos.csv` takes the same columns through `fieldnames`, in the order of the validated list. The step exits 1 on a validated list that lacks one of these columns, because a `DictWriter` fills a name that the row does not have with a blank. An input list that lost a column would otherwise publish an empty column in every output CSV without failing, and `head_sha` is also part of the key that joins `file_history.csv`
- **Collection time and commit time describe different events.** The step converts `head_commit_date` to UTC, and `scanned_at` keeps the input value and its precision. A value with only a date must not become an invented timestamp at midnight.
- **A commit date that does not parse is published blank, and the step goes on.** git prints a commit of the year 10000 in a form that does not parse, `9999-12-31T23:30:00-01:00` in the offset `-0100`, and an instant before the year 10000 in UTC can still print with the year 10000, such as `10000-01-01T00:30:00+01:00`. A damaged repository can carry other such dates. The step leaves `head_commit_date`, `created_at` and `commit_timestamp` blank where the value does not parse (`repos.to_utc_or_blank`), and a WARNING for each of the three columns gives the count, one of the values and every repository. If the step stopped on such a value, it would stop at the same repository in every run, and the run would never reach the release. Published as git printed it, the value would be the only value in another format in a column of UTC values. `snapshot write` counts the rows of the published mechanism CSVs with a blank `created_at` or `head_commit_date` among the rows with missing commit metadata, which the release states among its evidence limits

- **Flags are derived from the detector output:** the six tool flags and the file flags come from the detector output alone. The columns of `data/validated/repos.csv` are only the <!--s:parameters.agentcontext.heuristics.META_COLUMNS:words-->five<!--/s--> metadata columns
- **Each configuration artifact names its tool:** every mechanism CSV has a `tool` column, which `artifact_tools` and `heuristics.tool_value` fill. Its value is one of the six tools, several tools joined with `|` in the order of the tool columns when another tool reads the file through a symlink marker, or `any` for a file that no specific tool owns. `tool_flags_of` sets a repository's tool flags to the union of the tools of its rows of the named mechanisms, and a flag without a row or a row without its flag therefore cannot occur. A row of `other.csv` keeps the tool that owns the directory that contains its file, and it sets no flag. The file of such a row is one that no detector of the tool reads, such as a file that `not_configuration.csv` records as unread by the tool. `other.csv` is not published either, and no published row would explain a flag that such a row set. `output_cross_check` checks the union on the published CSVs. After the file history step removes rows, `file_history.reconcile_repos_csv` rebuilds the tool flags from the same column and not from the paths, because flags derived from the paths would give every workflow the tool of whichever `workflow_uses:` row was read last
- **Shared files name no tool:** `AGENTS.md` sets the `agents.md` file flag and is attributed to `any`, as are `.agents/skills`, a root `REVIEW.md`, the Agent Plugins manifests and the root `.mcp.json` with its servers under `mcpServers` or in the bare form, in which each top-level key names a server, because several tools read each of these files and none owns them. A `SKILL.md` in `.agents/skills` that links to a file keeps `any`, because several of the directory's readers still read the link, although Codex skips it ([Detection heuristics](#detection-heuristics-per-mechanism)). A repository with a detected mechanism and no tool flag, in which every configuration artifact is such a file, gets `no_specific_tool=TRUE`. A repository with a tool's own files next to shared files counts for that tool. `agents_md_only`, the flag that `no_specific_tool` replaced, required an `AGENTS.md`, and it would leave out the <!--s:collection.no_specific_tool_without_agents_md-->100<!--/s--> repositories of the collection with other shared files and no `AGENTS.md`
- **Tool ownership comes from the heuristics of the row's mechanism:** each configuration artifact is matched against the rows of `config_path_patterns.csv` for its own mechanism, each read by its match mode, and takes the `tool` of the longest path among the rows that read it. Only the heuristics of the rules mechanism attribute a rule. A `.md` file under `.cursor/rules` is therefore not Cursor's, because Cursor's row reads `.mdc` there. A row marked `any` owns nothing. `AGENTS.md` and the root `.mcp.json` with its servers under `mcpServers` or in the bare form are evidence of a mechanism but not of a particular tool. A `.mcp.json` below the root is Copilot's, and also Claude Code's when it names its servers under `mcpServers`. A `CLAUDE.md` under `.github/` is a Claude context file rather than a Copilot context file. The `workflow_uses:`, `workflow_engine:` and `workflow_command:` rows own no path. They share `.github/workflows`, and the tool of an agent workflow is the tool of the action, engine or command that it runs, which `detect_agent_workflows` reads and `artifact_tools` prefers to the path. Matched by path, every workflow under that directory would get the tool of one of these rows
- **Paths are matched case-insensitively where the marker name is fixed:** `SKILL.md`, the `agent.md` of an Antigravity agent folder (`heuristics.is_folder_agent_file`), `.github/copilot-instructions.md` and the fixed settings, hook and MCP file names are found whatever their casing, and recorded under the file name on disk, while the directory part keeps the spelling of the heuristics. A case-sensitive lookup would make the result depend on the host file system, and the same repository would yield different rows on macOS and on Linux. That reason holds for a tool that tests the joined path, such as VS Code with `joinPath(child.resource, SKILL_FILENAME)` for each folder of a skills directory, or that compares the names without case, such as Antigravity with `strings.EqualFold`. Codex compares the name that the directory listing returns with `SKILL.md` exactly, `entry.path.basename().as_deref() == Some(SKILLS_FILENAME)` (`codex-rs/ext/skills/src/loader/discovery.rs` at f9c10053fb3d9b960e78cfeae1f3ffa21e0dc00a), and so do Cursor CLI 2026.09.28-64d2043, `"SKILL.md"!==e.name`, and OpenCode, `child.name === "SKILL.md"`, on every host. A marker in another case is therefore no skill of Codex and of no tool that reads another tool's skills directory for compatibility (`_skill_skippers`), and below the folder of another skill it belongs to that skill (`_find_skill_files`), as gohypergiant/standard-toolkit's `.agents/skills/accelint-skill-manager/references/skill.md` does. Cursor keeps such a marker in its own `.cursor/skills`, because the loader of the Cursor IDE was not read. Where a volume allows both spellings at once, the spelling that the heuristics name takes precedence, and a variant beside it therefore cannot shadow the file that a content test would have accepted. The names that a `basename` row reads at any depth, such as `gemini-extension.json` and the portable `plugin.json` and `mcp.json`, are compared in their case on every volume, as a case-sensitive volume such as the container's compares them (`_named`). So are the paths of the `root_file` rows of context files and of `other`, such as `REVIEW.md` and `.gemini/styleguide.md` (`_file_in_its_case`). The `root_file` rows of settings and MCP, such as `opencode.json` and `.mcp.json`, name fixed settings and MCP files and are found in any case (`_find_case_insensitive`), as `SKILL.md` is. The detector compares the names that a directory listing returns, because a glob with a fixed last segment, such as `rglob(name)`, and `Path.is_file` test the path with a stat. On a case-insensitive volume, such as macOS's, that stat succeeds for any spelling, and the row would name a path that exists in no tree
- **A symlinked mechanism directory is followed:** the cloning step stores a symlink as a one-line file that contains its target, and a symlinked `.claude/skills` is therefore a text file in the tree. When the target resolves to a directory inside the collected tree, the step reads that directory and reports its configuration artifacts at their real path, because a link path exists in no tree and its `github_link` would lead nowhere.
  `artifact_tools` credits a configuration artifact at or below the directory that the marker names, found through `marker_directories`, to each tool with a heuristic for its mechanism that reads it at the path through the link. A marker with no configuration artifact behind it adds no tool. A `.md` rule that both `.claude/rules` and a `.cursor/rules` link reach is therefore Claude's alone. A skill linked on its own, a marker in a skills directory that names a directory with a `SKILL.md`, is reported the same way. A target that the collector never copied cannot be resolved, and its marker is an `other` row.
  A tool directory that was a link (`paths.TOOL_DIRECTORIES`), such as a `.claude` that leads to `config/claude`, is a marker too, at the root or below it, and the collector copied the directory that it names at its own path ([repository cloning](repository_cloning.md)). In the directory that the marker names, the detectors read every mechanism directory and every fixed file of the tool directory, such as `config/claude/settings.json` for `.claude/settings.json` (`_below_a_marker`, through `_resolve_dir` and `_find_case_insensitive`), report what they find at its own path, and `artifact_tools` credits it to the tools that read it through the link. comet-ml/opik links `.cursor` and `.codex` to `.agents`, and its `.agents/agents/*.md` are Antigravity's and Cursor's subagents, because Cursor reads the Markdown agents of `.cursor/agents` and of `.codex/agents`. Its skills in `.agents/skills`, a place that names no tool because several tools read it, are Codex's and Cursor's through `.codex/skills` and `.cursor/skills`. A marker in the directory that a tool directory leads to, such as a `config/claude/skills/lint`, is also read at the path through the link, `.claude/skills/lint` (`marker_directories`). A file there that no detector returns is an `other` row of the tool. Its `link_path` is the path through the link (`linked_spec_files`) where the directory that the marker names is no spec directory, such as `config/claude`. Where it is one, such as the `.agents` that `.claude` links to in most repositories with such a link, the file is a file of that spec directory, at its own path, and `link_path` is blank. A context file there, such as the instructions file that the Codex config of a linked `.codex` names, is in the known set, as a context file in a spec directory is. A planning document there is matched at its path through the link as well (`planning.find`) and reported at its own path, and it is no `other` row. For example, samanhappy/mcphub's `.agents/plans/cleartext-logging-fix.md` is a plan of Claude Code through `.claude -> .agents`, and input-output-hk/daedalus's `.agent/plans/readme.md` is one through `.claude -> .agent`. A marker that resolves to no directory of the tree, such as a link out of the repository, or that names a directory that contains it, is an `other` row of the tool.
  A rule or an agent that is a link to a file is reported at the link's path, the file in the tool's folder. Every front matter test reads the file that its marker names inside the tree (`_file_text`), as the tool reads the item through the link. angular/angular's `.agent/rules/agents.md` links to `../../AGENTS.md`, which sets `trigger: always_on`. Tested on the marker's one line, the rule would be an `other` row. The test of Antigravity's named hooks reads a linked `hooks.json` the same way (`_loads_as_named_hooks`).
  A marker is a text of one line without a NUL, and without a space unless the text names a path beside the marker (`paths.marker_target`). A symlink's target cannot contain a NUL, and the path functions raise `ValueError` for a path with a NUL. Read as a marker, a file of NUL bytes in a rules folder would stop the step
- **Mechanism directories are read at any depth:** the tools read the directory that they are working in, not only the repository root. Claude Code loads a `.claude/skills` below the root for a session started in or under it, and Codex scans `.agents/skills` from the working directory up to the root. A monorepo that configures its packages one by one therefore describes real configuration.
  `_nested_anchors` lists the directories of each repository once and returns, sorted, every directory below the root that contains a mechanism directory, and a rerun writes the same rows in the same order.
  `.github` stays at the root, because GitHub reads a repository's `.github` there and nowhere else. The exception is the places that Copilot CLI reads in the `.github` of the directory that it works in and of each directory between that directory and the root (i.e., `copilot-instructions.md`, `instructions/`, `agents/`, `skills/`, `lsp.json` and `mcp.json`), and the `.mcp.json` of those directories. The rows with the match mode `nested:` read them below the root, where `paths.nested_places` finds them, and the detectors read them with the mode after the prefix (`_nested`, [Copilot CLI's places below the root](../heuristics.md#copilot-clis-places-below-the-root)). A place that was a link is a marker. The detectors read a folder through its marker, as they read a `.github/agents` at the root that is a link. They credit the tool of the place with what the marker leads to (`resolved_markers`). The `root_file` rows stay at the root too, including the `.mcp.json` that several tools read, `.worktreeinclude` and the `.gemini/config.yaml` and `.gemini/styleguide.md` of Gemini Code Assist.
  Vendored subtrees are never searched for nested mechanism directories, because configuration inside `node_modules` or a checked-in dependency belongs to the project that was vendored. `agentcontext/heuristics.py` provides the list of vendored names that the cloning step, the collected file cleanup and this step read. Nothing below a mechanism directory is searched either, because the heuristics of that directory already cover it, and a `.claude` inside a plugin bundle would otherwise be counted twice. The root's `.github` is the exception. Its heuristics name the places of Copilot and of the workflows, the collected file cleanup prunes the rest, and a tool directory below it is read as in any other directory, such as ydb-platform/ydb's `.github/scripts/utils/analytics/datalens/.agents/skills`, beside an `AGENTS.md` and a `CLAUDE.md`. A `.github` below the root stops the search.
  Every detector that reads a fixed path also reads it below the root, including the detectors of the <!--s:heuristics.config_path_patterns.fixed_context_files:words-->three<!--/s--> context files with fixed paths and of `.codex/config.toml` for hooks. Read at the root alone, a nested `.codex/config.toml` would get a settings row and an MCP row and no hooks row, and the file would then appear in `other.csv`. The basenames of ignore files are the opposite exception, because they match at any depth outside vendored directories.
- **Recursion is set per mechanism:** each heuristic states the depth that its tool loads. The heuristics for Claude skill containers, the skills folders that only Antigravity reads, Gemini agents, Copilot prompts and chat modes, and Codex rules read immediate children. Gemini commands, Copilot hooks and the `.claude/skills` that Cursor and OpenCode read are read recursively. Antigravity agents accept a direct Markdown file or `<name>/agent.md`, the name in any letter case
- **`other` contains what is left:** it is every file inside a spec directory that no other detector returned. It exists so that the dataset records every file in a spec directory, and the analyses exclude it from the ten named mechanisms
- **A file that a file manager wrote is no configuration:** the step leaves out of every listing of a repository's directory the paths that `paths.is_discarded_path` names, that is, the files below an `@eaDir` directory that Synology DSM writes and `.DS_Store`. It leaves them out through `_listed` or by pruning the directory in `os.walk`, and `_plugin_components` leaves them out of the places of a plugin. The collected file cleanup removes them from the validated tree, but File Station writes an `@eaDir` into every directory that it shows. When File Station showed the tree between the cleanup and a resumed detection, `.claude/@eaDir/settings.json@SynoEAStream` reached `other.csv` and `unmatched-paths.csv`
- **Detection can depend on file content as well as path.** The match modes in `config_path_patterns.csv` name the predicates, such as hooks and MCP objects, workflow actions and commands, Agent Plugins schemas and required descriptions. Manifest fields and declarations select additional paths. The heuristics determine which predicates apply, and a JSON filename alone does not imply a content test. After detection, the step reads from each configuration artifact the value of the `language` column, the line count and the columns that mark a context file as a pointer to another file.
- **The file is read here, over `data/validated/`, rather than by two later passes.** An earlier file history step read the language out of a fresh clone, which described a different version of the configuration artifact than every other column of the row, and `detect_references.py` then read the line count and the classification out of the validated tree. Both values are now read from the tree that the collected file cleanup produced, which every other column describes.
- **The files are read in `main` rather than inside the detectors.** `has_detected_mechanism`, the keep check of the cleanup, calls the same detectors once per repository over an input list of <!--s:collection.sample_repositories-->40,901<!--/s--> rows and discards everything but a boolean. `detect_agent_workflows` is among them, because a workflow that runs an agent action is a settings row that no path names. A detector that opened every configuration artifact that it found would read all of those files twice
- **Language detection reads a sample with a minimum length and filters no extension.** `detect_language` reads the file as UTF-8, then UTF-16, then latin-1, and takes the first encoding that decodes. It passes the detector the first <!--s:parameters.agentcontext.steps.detection._LANGUAGE_SAMPLE-->10,240<!--/s--> characters, and it returns `n/a` below <!--s:parameters.agentcontext.steps.detection._LANGUAGE_MIN_CHARS-->50<!--/s--> characters once leading and trailing whitespace is stripped, or where the detector returns no language. A filter that accepts only Markdown would return `n/a` for every other row, such as a `.cursorrules`, a `.toml` or a `.rules` file. The minimum keeps a symlink marker, which the collector stores as a one-line file that contains its target, from getting a language. In release 1.0.0, the column came from a filter that accepted only `.md`, `.mdc` and `.mdx`, mixed with the values of an older script. A symlink marker could get a language there, so a published value could describe a file that the row does not name
- **A reference is a short file that points at another file.** Length is the first check. A file over `MAX_REFERENCE_LINES`, which is <!--s:parameters.agentcontext.steps.detection.MAX_REFERENCE_LINES-->10<!--/s-->, has content of its own whatever it links to. Then one of the <!--s:parameters.agentcontext.steps.detection.REF_PATTERNS:words-->five<!--/s--> `REF_PATTERNS` has to capture a `.md` target, and then one of two conditions has to hold: <!--s:parameters.agentcontext.steps.detection.classify.meaningful_lines:words-->three<!--/s--> or fewer meaningful lines, or a `POINTER_PHRASES` match anywhere in the file. The phrase alone extracts nothing. A bare filename mentioned inline in prose is therefore not a reference, and the file has to contain a structural marker. `classify` returns `(line_count, is_reference, referenced_file)`
- **`is_empty` is not published.** `classify` returned it as a fourth element until 2.0.0, and every `-extended` CSV had it as a column. It was `FALSE` or blank on every published row, never `TRUE`, because `agentcontext/steps/collected_file_cleanup.py` deletes every empty file before this step runs. The column no longer exists in the output CSVs, in `file_history.csv` or in `caches.FileHistory`
- **The <!--s:parameters.agentcontext.heuristics.HISTORY_COLUMNS:words-->four<!--/s--> git columns are joined from the cache.** This step clones nothing, and `created_at`, `#commits`, `first_commit_sha` and `last_commit_sha` therefore come from `file_history.csv` through `preferred_facts` and `for_artifact`. `preferred_facts` takes the row that the cloning step wrote for the path at the commit where that row is complete. That row records no mechanism, because the cloning step reads the history of a file before any step assigns the file to a CSV. Otherwise `preferred_facts` takes the row with the exact `(repo_name, head_sha, mechanism, artifact)` key, which the file history step measured. The cloning step writes only complete rows, and the file history step measures a row only where the cache has none for the commit. Where both rows exist, the cloning step's row is the later measurement. `for_artifact` then finds a row of any mechanism, such as a row with a mechanism that a heuristic has since changed. `file_history.csv` keeps git's text for a creation date that does not parse, so that its row records a history that was read, and the step publishes that `created_at` blank. When neither lookup finds a row, the step publishes the row with blank git columns and logs it. `agentcontext/steps/file_history.py` measures those rows in the output CSVs that this step writes, and if this step stopped here, the file history step would have no output CSVs to fill in
- **The <!--s:parameters.agentcontext.heuristics.AI_COLUMNS:words-->four<!--/s--> AI columns are joined from `ai_authorship.csv`,** keyed on `(repo_name, head_sha, artifact)`, the key of the file history without the mechanism, through `caches.py`. A row applies to the commit that it names and to no other commit. A context file without a cache row at this commit gets blanks and not `FALSE`, because a blank records that the history of the file was not read, and `FALSE` would record that the file has no AI commit
- **The commit CSV is restricted here, to the repositories that this step publishes.** The cloning step reads the commit history of every repository that contributed a file, and it writes `output/all_ai_commits.csv` for all of them before the detection step determines the configured repositories. `restrict_ai_commits` rebuilds the CSV from the cloning step's shards under `collect_commits/`, read through the collector's own `readable_shards` and `shard_rows`. A repository with a per-repository commit record that does not parse therefore stays out here as it does in the assembled CSV, and every row is read into the current set of columns. The shards that the commit reclassification left out stay out too. `reclassification_left_out` reads `output/commit-reclassification.json` beside the CSV and leaves out each repository with `left_out` while its per-repository commit record still has the `record_sha256` that the file records. Rebuilt from every shard, the CSV would regain the rows that other commit heuristics classified, and the commit attribution validation after this step would stop the run on them. The step includes a repository again when its record changed since, such as after a new collection of the repository. When `output/commit-reclassification.json` exists and cannot be read, the step logs a warning and leaves out no repository.

  The step restricts the rebuilt CSV to the rows of the published repositories and leaves blank a `commit_timestamp` that does not parse, such as the `10000-01-01T00:30:00Z` that git prints in UTC for a commit of the year 10000. It writes the CSV after the mechanism CSVs, so that the CSV beside them describes the same repositories that they describe. If the step wrote it before them, a failure to read the shards would abort the step with `repos.csv` already rewritten from the new heuristics and the output CSVs beside it still from the old heuristics. Every CSV that this step writes is replaced in one operation, through the writer that the caches use. A process killed while the step writes a CSV therefore leaves the previous CSV, not a file that the next step reads as a CSV without rows. Where there are no shards, `restrict_ai_commits` rewrites the CSV in place. The function rebuilds from the shards because a CSV restricted in place cannot regain a row. A second run of this step over heuristics that newly publish a repository would find its rows gone. The rebuild happens on every run rather than as a one-time correction. When the CSV is absent, as in every regeneration over an earlier collection without the archive extracted, the step leaves it absent and logs that it is missing
- **No detector's row order depends on the file system.** A detector that reads the paths of the heuristics follows their order, which `docs/heuristics.md` explains and which sets the row order of the settings CSV, and a detector that lists directories sorts what it lists. The context-file detector, which lists the whole tree, sorts too. The order that the file system returns changes whenever `collected_file_cleanup` rebuilds `data/validated/`. Without sorting, two runs over the same sample would write the same rows in different orders, and `regressions check` would find a CSV with different bytes in which every row and column matches.
- **Malformed content is not a detection, and malformed means malformed for the tool that owns the file:** the step ignores a parse failure and does not record the configuration artifact. A repository with broken JSON is a repository without that mechanism, and the run goes on. A JSON or TOML file nested too deeply for the parser, which raises RecursionError rather than a parse error, is a parse failure too, at every place that reads a file. So is a file with an integer literal of more than <!--s:parameters.python.int_max_str_digits-->4,300<!--/s--> digits, which Python does not convert. The parser then raises a ValueError that is neither a JSONDecodeError nor a TOMLDecodeError, and every reader therefore catches ValueError rather than the decode error alone. A Claude Code plugin manifest with component paths nested too deeply to check declares paths that cannot load. Uncaught, the error of one repository's file would stop the detection over the whole sample.
  The parser of the tool that owns the file defines which bytes count as broken, and `content_format` in the heuristics records that format for each row. Gemini CLI reads its `.gemini/settings.json` with `JSON.parse(stripJsonComments(content))`. A comment there is part of the format, and the step reads the file with the comments stripped. Claude Code documents its settings file as strict JSON, where "a `//` comment or a trailing comma is a syntax error", and a comment there still means that the file is broken. Reading a file more permissively than its own tool does would record a configuration that the tool never applies.
  Trailing commas are accepted only where `content_format` is `jsonc_trailing`, including Antigravity MCP files. Gemini CLI parses its extension manifest, `gemini-extension.json`, with a plain `JSON.parse`, which makes that file strict JSON. `agentcontext/jsonc.py` finds comments by a scan rather than a regular expression, because a URL also contains `//`. It replaces each comment with spaces rather than removing it, as `strip-json-comments`, the package that Gemini CLI calls, does
- **A value that UTF-8 cannot encode does not stop the step.** The only code points that UTF-8 cannot encode are the lone surrogates, which JSON can escape, as in the key `"de\ud800ploy"`, and which `json.loads` returns in the string. `caches.replace_file` writes UTF-8 strictly. Such a key, published as the `name` of a skills row, would raise an error after the step had replaced `repos.csv` and the CSVs written before `skills.csv`. Because the tree does not change, every later run would fail at the same row. Where a value that the step reads from a file's content reaches a published CSV, the handling depends on the value:
  - A key of the `commands` object of a Claude Code plugin manifest or marketplace entry names a skills row. `paths.plugin_command_names` ignores a key that does not encode, with a warning that names the repository, the plugin and the file, and the row keeps the file stem, the name that it has where no key names the file. A name with U+FFFD in place of the surrogate would be a name that no manifest declares
  - A path that a manifest, a marketplace, a registration file or a settings file names reaches a CSV only as the path of a file that a detector found in the tree, and the cloning step deletes every name that is not UTF-8 (`paths.remove_undecodable_names`)
  - `referenced_file` and the other columns read from the configuration artifact come from the text that `read_artifact` decodes as UTF-8, UTF-16 or latin-1, and none of these decoders returns a lone surrogate. The marker that `artifact_text` reads for a context file that is a real symlink escapes each byte of the target that is not UTF-8, as `paths.write_marker` does. `language` is one of lingua's names, the `tool` of an agent workflow is the name of one of the six tools, and the metadata, the git columns and the AI columns come from CSVs read as strict UTF-8
  - Every CSV of this step but the commit CSVs goes through `_encodable_row`, which replaces each lone surrogate that a value still contains with U+FFFD and logs a warning that names the CSV, the columns, the configuration artifact and the repository. The replacement keeps the row and its other columns. A blank value would state that the file was not read, and a dropped row would remove a configuration artifact and change the flags of its repository. The commit CSVs are written from the shards or from their own rows, both read as strict UTF-8, and none of their values therefore contains a lone surrogate
- **Fail on missing or empty inputs:** for an absent `data/validated/repos.csv`, an absent `data/validated/`, or a validated tree with no repository directories, the step returns exit code `1` instead of writing empty output CSVs and exiting `0`

A symlinked context file, such as `.github/copilot-instructions.md` pointing to `AGENTS.md`, is
reported at its own path. The cloning step stores the link as a marker even where rsync would omit
the link, and the collected file cleanup keeps the recognized context path. The stored file is the
marker, not a copy of the target's contents. Some files determine by their content what the
cloning step copies, such as a registration file, a settings file that names a context file, a
plugin manifest, a marketplace or a registered agent. Such a file is stored with the content that
the cloning step read through a link inside the repository (`paths.store_declaring_files`), and
this step therefore reads what the tool reads there. A rule or an agent that is a link stays a
marker at its own path, and the front matter tests read the file that the marker names.

## `agentcontext/steps/detection.py`

### Architecture

#### Detection pass

`main` processes the repository directories that `repos.split(VALIDATED_DIR, expected=VALIDATED_TREE_FILES)` returns, in the order of their directory names, and every mechanism CSV has its rows in that order. A top-level entry that is neither a repository directory nor the list that the collected file cleanup wrote is named in a `WARNING detection:` line and skipped, because processing it would add rows for a repository that nobody collected to every mechanism CSV. `repos.dir_name_to_repo` converts each directory name back to `owner/repo`. For each repository, the mechanism detectors run in a fixed order: settings, context files, skills, subagents, commands, hooks, rules, MCP, plugins, LSP servers, then `other`, which needs the results of the other detectors to compute what is left. Each detector returns a list of configuration artifacts, and a mechanism's boolean flag is whether that list is non-empty. Every configuration artifact that a detector returns goes through `build_detail_row`, which assembles the published row: the metadata block, what the detector returned, the `github_link`, the dataset release, the joined file history, the columns read out of the file, and for a context file the joined AI facts.

#### Per-mechanism scope

Whether a detector recurses depends on the mechanism:

#### Flag derivation

`artifact_tools` takes the mechanism and the path of every row. An agent workflow takes the tool that it runs, and a file that a configuration declares takes the declaring tool in the rows of the declaration's mechanism (`declared_file_tools`), without the tool of a plugin that contains it. Any other row takes the tools of the heuristics for its mechanism that read its path (`tools_reading`). Each heuristic reads by its match mode through `heuristics.heuristic_matches`. A mode with a front matter test, such as a `description` or a `trigger`, also reads the file that the path leads to, through a linked directory or the marker of a linked file. A rule without a trigger that a `.claude/rules` link to `.agents/rules` reaches is therefore Claude's alone. A link to a shared skills directory adds no reader outside that reader's own directory (`_readers_without_their_own_link`), and a skills directory that the heuristics of one tool alone read, such as Antigravity's `.agent/skills`, `_agents/skills` and `_agent/skills`, is that tool's own. A file of `.claude/agents` that Claude Code loads (`_claude_agent_loads`) is Claude's, at its path and through a link, although Cursor reads that directory too (`_without_the_compatibility_reader`), and a file that Claude Code does not load and that has the front matter of a subagent of Cursor (`_cursor_agent_has_front_matter`) is Cursor's. The heuristic of `.claude/AGENTS.md` reads the file only where Claude Code reads it (`_claude_reads_agents_md`): where no `CLAUDE.md`, `.claude/CLAUDE.md` or `CLAUDE.local.md` is at the root or in the directory above the `.claude`, or where a chain of Claude Code's imports from its memory files reaches the file, by the rows and the condition `no_claude_md` of `import_patterns.csv` (`imports.importing_files`, `imports.chain`). The chain reads the validated tree and follows a symlink marker to the file that it names there. ng-alain/delon's `.claude/AGENTS.md`, beside a `.claude/CLAUDE.md` that imports nothing, therefore names no tool. A heuristic rooted at a nestable root reads at any depth, and a `nested:` heuristic reads below the root. The longest path among the heuristics that read the path takes precedence, and a row with the `tool` `any` yields no owner. A heuristic of a skills directory reads a skill's marker and no other file of the skill, because VS Code reads `joinPath(child.resource, SKILL_FILENAME)` of each folder and the other files are the skill's scripts, references and assets. GovTechSG/sgds-web-component's `.github/skills/storybook-stories/reference/examples.md`, which Claude Code reads as a command through the link `.claude/commands/storybook-stories`, is therefore Claude Code's alone. Of the tools that read a `SKILL.md`, `_tools_reading_a_skill` leaves out each tool that skips it (`_skill_skippers`): a tool that skips a link to a file, Codex where its parser does not accept the file (`_codex_skill_loads`), and for a marker in another case than `SKILL.md`, every tool but the tool of the tool directory. The tool of the tool directory that contains the skills directory then takes precedence over a tool that reads that directory for compatibility, and `.claude/skills/<name>/SKILL.md` is Claude Code's, `.claude/skills/<category>/<name>/SKILL.md` Cursor's and OpenCode's, `.codex/skills/<name>/SKILL.md` Codex's, and a `SKILL.md` there that Codex does not load Cursor's. A tool that reads a directory for compatibility gets no credit for a `SKILL.md` in the folder of a skill that the directory's own tool reads, also through a link, such as a `.claude/skills` that links to an `.agents/skills` with a skill in a subfolder of another skill. A path at or below a plugin part or a manifest of `plugin_part_tools` adds the plugin's tool. A part adds it only to rows of its own mechanism. A part with a row that reads only certain extensions, such as a Cursor plugin's `commands` with `.md`, `.mdc`, `.markdown` and `.txt`, adds it only to the files that its row reads (`_part_reads`). xberg-io/xberg's `plugin/commands/*.md` are therefore skills of its Claude Code plugin and commands of its Cursor plugin, and the Gemini CLI `.toml` commands that mondaycom/mcp keeps in the `commands` folder of its Cursor plugin are Gemini's alone. A hooks file adds the tool of its part only where that tool loads a hook from it, and an MCP file only where that tool loads a server of it (`_part_loads`), so that the `.mcp.json` of a folder with the manifests of a Claude Code and a Codex plugin, with a server that has a `url` and no `type`, is Codex's and not Claude Code's. An `other` row below a part keeps the plugin's tool. A plugins row that is a manifest of `plugin_part_tools` adds the tool of that plugin alone, and a part of another plugin that contains the manifest adds none, because the other plugin's tool reads the manifest as no plugin. The `plugin.json` of a legacy Copilot CLI plugin in a skill folder of a Claude Code and Cursor plugin is therefore Copilot's, and the folder's `SKILL.md` is a skill of the three plugins. A file at the root that a repository-level row matches gets the tool of a plugin at the root beside the tools of that row, unless a `root_file` row with the tool `any` matches it (`_shared_root_file`). Every tool that reads the repository's MCP configuration reads the root `.mcp.json` under `mcpServers` or in the bare form, and the file therefore stays `any` in wonderwhy-er/DesktopCommanderMCP, a legacy Copilot CLI plugin at the root, and in a Claude Code plugin at the root. A root `.mcp.json` with its servers under `servers` alone, as OrchardCMS/OrchardCore's, is Copilot's, because only Visual Studio reads that key there (`_servers_key_alone`). A path that another row with the tool `any` matches still takes the plugin's tool. The `SKILL.md` row, for example, reads the file at any depth, and a skill in the `skills/` of a plugin at the root is the plugin's. A path at or below the directory of a symlink marker adds the tools that read it at the path through the link, by the same logic, and the plugin's tool where the marker is a plugin part.

A row that no heuristic for its mechanism reads and that no link or plugin reaches takes the owner of its directory (`tool_for_path`). So does every `other` row, a file in a configuration directory that no mechanism covers. `tool_for_path` reads `config_path_patterns.csv`. A basename row matches by filename at any depth. Otherwise, the tool of the longest path in the heuristics that contains the configuration artifact applies, including a path that a `nested:` row reads below the root at any depth outside the spec directories. A file in a package's `.github/agents` that no row reads is therefore Copilot's. Attributing every row through `tool_for_path` and the tool of every marker would credit Antigravity with a nested `.agents/agents/<group>/<name>.md` that it does not read and Cursor with `.md` rules that a `.cursor/rules` link reaches. `.github/skills/x/SKILL.md` is attributed through `.github/skills` rather than through the bare `.github` row, and a new mechanism is attributed without an edit to this function. `file_flags_of` reads the file flags directly off the list of context files by basename, and `copilot-instructions` off a `.github/copilot-instructions.md` or a file under `.github/instructions/` at the root or below it. `no_specific_tool` is then set when a mechanism flag is set and no tool flag is.

#### The `other` CSV

`detect_other` subtracts the known set from every file inside the spec directories of `SPEC_DIRS` (recursively), without a `_agents` or `_agent` that contains no place of Antigravity (`_spec_directories`), plus ignore files matched by basename and root-only `other` paths. The known set is what the other detectors returned, widened for skills and subagents. An entire skill directory counts as known once its `SKILL.md` was detected, and a skill's `scripts/`, `references/` and `assets/` do not become `other`. This widening applies only to rows of a file named `SKILL.md`. A merged `.claude/commands` file adds only itself to the known set, and its neighbors still become `other`. A subagent's `MEMORY.md` counts as known when its `memory` column is `TRUE`. Context files count as known only when they are inside a spec directory. A root `CLAUDE.md` is never a candidate, because it is outside every spec directory. `.github`, `.claude-plugin`, `.cursor-plugin`, `.codex-plugin` and `.plugin` are `unclassified_dir` directories. The collected file cleanup prunes them first, and every file left there that no detector returned becomes an `other` row, such as a plugin's `toolkit.json`, its README, and the scripts of a skills directory below a manifest directory. The places that a `nested:` row reads below the root, such as a package's `.github/agents/`, are candidates as well, because the collected file cleanup keeps them whole, and an agent without a description there becomes `other`. A file that a GitHub Agentic Workflow imports and the prompt file that an agent action of a workflow reads (`paths.action_prompt_files`) are parts of their workflows and count as known, and so do the prompt file that an agent of an OpenCode configuration names with `{file:...}` (`paths.opencode_prompt_files`), a part of the agent, and the instructions file that a Codex role names in `model_instructions_file` (`_declared_subagents`), a part of the role. A followed symlink marker is part of the known set, because it stands for the directory that a detector read and is no stray file. A marker with a target that was never collected is not part of the known set, and such `.agents` links therefore appear as `other` rows.

A planning document that `detect_other` would return is in `planning-documents.csv` instead ([The planning documents](#the-planning-documents)).

#### Columns read from the configuration artifact

<!--s:parameters.agentcontext.heuristics.LANGUAGE_MECHANISMS:Words-->Five<!--/s--> of the output CSVs have a `language` column, and the context files CSV has <!--s:parameters.agentcontext.heuristics.REFERENCE_COLUMNS:words-->three<!--/s--> more columns that describe the file rather than its path. `build_detail_row` reads the file once, for the language, the reference columns or both, as the mechanism requires. For every mechanism but context files, it reads the file that a collected symlink marker at the row's path names inside the repository (`measured_artifact`, through `_followed_file`), the file that the tool reads through the link and that the front matter tests read. The row keeps the link's path. Read at the link's path, the language would describe the marker's one line, a path. NVIDIA/Model-Optimizer's `.claude/agents/modelopt-model-downloader.md`, a link to an English agent of its plugin, was published as German. Where the link's target is not a file of the tree, `measured_artifact` returns None, and the row's `language` is blank, as for a file that cannot be opened, with an `INFO detection:` line that names the row. A language measured on the marker's one line would describe no file. mathlab/pina links its skills to `.opencode/skills`, which the collector does not copy, and its `.claude/skills/condition-setup/SKILL.md` was published as English. Such a marker is a text that `paths.marker_target` accepts, with a `/` and without a leading `@` (`_unfollowed_marker`). A line that begins with `@` is a file reference, such as each of lge-ros2/cloisim's `.claude/commands/*.md`, `@../../.github/skills/<name>/SKILL.md`. A text without a `/` would name a file in the marker's own folder, which the collector copies with the marker. Both kinds of text are the file's own text, and the step measures their language.

A context file that is a link is a pointer to another context file by design. Its columns describe the marker at its own path, of one line and `n/a`, and `classify` publishes it as a reference with the target in `referenced_file`. `build_detail_row` takes the text from `artifact_text`. Where the validated tree holds such a link as a real symlink, with or without a target in the tree, `artifact_text` reads it as the marker that `paths.write_marker` writes for it, the link's target and a newline. rsync keeps a link inside a directory that the collector copies whole, and `paths.write_marker` leaves a link that leads to a file of the tree in place. gomlx/gomlx's `.agents/CLAUDE.md` and `.agents/GEMINI.md` are such links to the `AGENTS.md` beside them, and read through the link, both were published with the line count and the language of that AGENTS.md. A real symlink of another mechanism is read through, as the file that a marker names is. Any other file is read by `read_artifact`, which returns the whole text and tries UTF-8, then UTF-16, then latin-1, which decodes any bytes. For a file that cannot be opened, such as a file that the step may not read, `read_artifact` returns `None` and logs a warning that names the file. The row then has blank `language`, `line_count`, `is_reference` and `referenced_file`, and the run goes on. Those blanks mean that the file was not read, while `n/a` and a line count of `0` remain measurements of a text that was read.

`detect_language` runs for the <!--s:parameters.agentcontext.heuristics.LANGUAGE_MECHANISMS:words-->five<!--/s--> mechanisms in `heuristics.LANGUAGE_MECHANISMS`: context files, skills, subagents, commands and rules. The other mechanisms contain JSON, TOML or whatever other format a tool's directory contains, and a language detector returns no meaningful result for such files. The step builds the detector once, on first use, because building it is slow. The step logs an exception from the detector and records `n/a`, and one configuration artifact therefore cannot end the run.

`classify` runs for context files and returns `(line_count, is_reference, referenced_file)`. `line_count` counts the whole file, not the sample that the language detector is shown, because the column is the file's line count. A line ends at LF, CRLF or CR (`split_lines`). `str.splitlines` also ends a line at a vertical tab, a form feed, the separators U+001C to U+001E, NEL (U+0085), U+2028 and U+2029. A file can contain such a character inside a line, such as the U+2028 in a code span of a design spec of apache/struts, and `str.splitlines` would count a line there that the file does not have. Under the latin-1 decoding of `read_artifact`, the byte 0x85, an ellipsis in Windows-1252, is NEL. `meaningful_lines` splits the file at the same line breaks, and every line count that the dataset and its analysis publish is the length of `split_lines`: `line_count` of a context file and of a planning document, `target_line_count` of an import and the line counts of the content quality analysis. The <!--s:parameters.agentcontext.steps.detection.REF_PATTERNS:words-->five<!--/s--> `REF_PATTERNS` run in order, and each captured `.md` target is kept once, in the order first seen. `referenced_file` is the list joined with `;`.

#### The two fact CSVs

`file_history.csv` is the cloning step's record of what `git log` returned for each copied file, and `ai_authorship.csv` contains the AI columns of the copied files. This step cannot compute either fact CSV, and it therefore logs each row without a match in them. `git_columns_for` does the two-step lookup. `load_ai_authorship` loads the AI cache through `caches.AiAuthorshipCache`, keyed `(repo_name, head_sha, artifact)`. The cache is empty when the file is missing. A tree without `ai_authorship.csv` therefore gets blank AI columns, and the step goes on. A run logs how many rows each CSV contains, the number of rows without a file history row, with the first <!--s:parameters.agentcontext.steps.detection.without_history_named:words-->ten<!--/s--> of them named, and the number of context files without an AI row.

### Detection heuristics (per mechanism)

- **Settings**: each `SETTINGS_PATHS` entry that is a file, a workflow of a name row, such as `.github/workflows/claude.yml`, only with a line that is neither blank nor a comment (`_workflow_has_content`), `.github/workflows/gemini-dispatch.yml` only where a job calls a workflow of the repository that runs Gemini and declares `workflow_call` (`GEMINI_DISPATCHER`, `_dispatches_a_gemini_workflow`), `<claude-plugin>/settings.json` read under every Claude Code plugin root; every `*.toml` under each `SETTINGS_DIRS_TOML` directory, which is `.codex/environments`; every `*.json` directly in each `SETTINGS_DIRS_JSON` directory, which is OpenCode's `.opencode/themes`; and every file with a basename in `SETTINGS_BASENAMES`, which is `gemini-extension.json`, anywhere in the repository. `detect_agent_workflows` adds each workflow directly in `.github/workflows` that runs an agent, with the tool that it runs, and `paths.workflow_tool` returns the tool for each kind of workflow:
  - a YAML workflow with a `uses:` that names a documented action
  - a GitHub Agentic Workflow, Markdown with front matter that has `on:` and an `engine:` that names one of the six tools, or else the engine that its imports select, or else Copilot, with Cursor through gh-aw's sample engine
  - a workflow with a shell step that runs a tool's documented headless invocation (the `workflow_command:` rows), where it runs no documented action
- **Context files**: every file with a basename in `CONTEXT_FILENAMES`, anywhere in the repository. At the repository root, the detector also finds the <!--s:heuristics.config_path_patterns.root_any_case_rows:words-->three<!--/s--> names of `ROOT_ANY_CASE` in any other case, such as `claude.md` or `Agents.md`, records each under the name on disk, and sets the file flag that the lowercase name gives. It adds `.github/copilot-instructions.md` at the `.github` root and every `*.instructions.md` under `.github/instructions/` recursively, both of them in the `.github` of a directory below the root as well (`NESTED_CONTEXT_FILES` and `NESTED_CONTEXT_DIRS_SUFFIX`). It also adds every file that a Codex config, a Gemini CLI settings file or an extension manifest names as its context file, and every file that OpenCode's `instructions` match (`paths.declared_context_files` over the rows in `CONTEXT_DECLARATION_HEURISTICS`), listed once where a path pattern also found it. `docs/heuristics.md` states what each of the <!--s:heuristics.config_path_patterns.context_declaration_rows:words-->five<!--/s--> keys names. A `.cursorrules` inside a `.cursor` directory is not a context file, because Cursor reads "the .cursorrules file in the root of your project" ([rules, archived 2025-06-03](https://web.archive.org/web/20250603080456/https://docs.cursor.com/context/rules)), and a project is a folder opened in Cursor, which `.cursor` never is. The detection accuracy evaluation of 2026-10-13 found `.cursor/.cursorrules` and `.cursor/rules/.cursorrules`.
- **Skills**: for each skills directory, the `SKILL.md` markers at the depth that its heuristic specifies. Claude project and plugin skill containers accept immediate child skills, and so do Gemini CLI's `.gemini/skills` and the `skills/` of an extension, which Gemini CLI globs as `['SKILL.md', '*/SKILL.md']`. In a skills folder that only Gemini CLI reads, a `SKILL.md` counts only when its front matter has a `name` and a `description`, as Gemini CLI's `loadSkillFromFile` requires. OpenCode's configuration counts when its `mcp` key is an object with at least one server (`json_servers:mcp`). A Codex plugin's `.app.json`, or the file that its manifest's `apps` names, counts when its `apps` key is an object with at least one app (`json_servers:apps`). A Claude Code or Cursor manifest or a marketplace entry that configures a server inline counts under the file that holds it (`paths.plugin_components`), and a Claude Code manifest only where Claude Code accepts every server of its maps and loads one of them (`paths._claude_loads_inline_servers`). Plugin MCP files and the paths that a manifest selects use the content predicate of their own heuristic, and `content_format` selects JSON or JSONC parsing.
- **Plugins**: each `PLUGIN_FILES` path wherever its own directory is, matched at the repository root, under every nestable root, and at any depth below either, plus every file with a basename in `PLUGIN_BASENAMES`, which is `gemini-extension.json`, anywhere in the repository. Codex's marketplace among these paths, `CODEX_MARKETPLACE`, counts only where Codex can install a plugin from one of its entries (`_codex_marketplace`, `paths.codex_marketplace_installs`). A marketplace without such an entry, such as UMEP-dev/SUEWS's, with its only entry set to `NOT_AVAILABLE`, is an `other` row. OpenCode's plugins and custom tools are modules rather than manifests. `PLUGIN_MODULE_DIRS` lists the `*.ts` and `*.js` files directly in `.opencode/plugins`, `.opencode/plugin`, `.opencode/tools` and `.opencode/tool`, with the case of the extension as OpenCode's pattern `{plugin,plugins}/*.{ts,js}` reads it. A module counts when OpenCode loads something from it (`_opencode_module_loads`): a plugin module needs an export, because OpenCode takes each export as a plugin, and a tool module an export with `args`, `description` and `execute`. event-driven-io/Pongo's vitest file in `.opencode/plugins` and cloudflare/workerd's helper in `.opencode/tools` therefore do not count. The test reads the text of a module, not its values. OpenCode 1.19.3 loads nothing from a plugin module with an export that is neither a function nor an object with a function `server`, and nothing from a module with type exports alone, and detection counts both. OpenCode 2.1.1 loads a plugin module with a default export of an `id` and a `setup` or `effect` function, which OpenCode 1.19.3 refuses, such as forcedotcom/salesforcedx-vscode's `.opencode/plugins/safeguards.ts`. A tool module that re-exports a tool from another module lacks `args`, `description` and `execute` in its text, and a CommonJS `exports.X =` or an export that does not start a line is no export to the test. In the collection of the first complete run, every module that the test counts loads in one of the two versions, and no module has one of these forms. OpenCode 2 also loads a folder of `.opencode/plugins` or `.opencode/plugin` as a plugin package when the folder has an entry module. `_plugin_packages` reads the folders of each `PLUGIN_PACKAGE_DIRS` directory with the entry modules and the extensions of its `package_entry:` mode. A folder is one row, at its first entry module in the order of the names and then of the extensions, with the names compared in their case, as OpenCode resolves them on Linux. The other files of the folder belong to the package, and `_collect_known_files` adds them to the known set, so that none of them is an `other` row. The files of a folder without an entry module stay in `other`. A folder that is a link is read where the link leads inside the repository, and the row names the file there. A link that the collector stored as a marker is not followed.

  Claude Code describes a plugin as its own directory that contains a `.claude-plugin/plugin.json` manifest ([plugins](https://code.claude.com/docs/en/plugins)), and the sample puts those directories under `.claude/plugins/<name>/`, under `.claude-plugin/plugins/<name>/` and beside a package. Of the <!--s:collection.plugin_manifests-->234<!--/s--> such manifests in the `plugins.csv` of the collection that the checkout tracks, <!--s:collection.plugin_manifests_in_other-->191<!--/s--> are below the root, where a match at the root alone would leave them in `other`. A marketplace catalog counts beside a manifest. The page defines it as the list of plugins and where each is fetched from, and <!--s:collection.marketplace_catalogs_local_sources-->271<!--/s--> of the <!--s:collection.marketplace_catalogs-->288<!--/s--> catalogs that the plugins CSV lists name a source inside the repository that contains the catalog. Gemini CLI calls the same bundle an extension and declares it in `gemini-extension.json`, which is also a settings row and an MCP row, as `.claude/settings.local.json` is a settings row and a hooks row.

  A legacy Copilot CLI plugin can keep its manifest at its root as `plugin.json` too. The row `<copilot-plugin>/plugin.json` lists that file under every Copilot plugin that `paths.plugin_roots` finds, where the content of a legacy manifest identifies it (`paths.copilot_legacy_manifest`, [heuristics](../heuristics.md#the-parts-of-a-plugin-wherever-the-repository-puts-it)), and `plugin_part_tools` gives it Copilot. A `plugin.json` in a directory named `.<name>-plugin`, such as saadeghi/daisyui's `skills/.grok-plugin/plugin.json`, is the manifest of that vendor's plugin and no row, whether or not the dataset covers the vendor.

  The portable Agent Plugins manifest is identified by its content as well. The standard puts `plugin.json` in the plugin root, and many programs that have nothing to do with agents use that name. The heuristic is therefore the requirement that the standard itself states, "plugin.json MUST be a JSON object containing the required `$schema` and `name` fields", with `$schema` the canonical identifier `https://agent-plugins.org/schemas/1.0.0/plugin.schema.json`. The version segment is not pinned, and the step still records a plugin that targets a later version of the standard. Codex documents its `.codex-plugin/plugin.json` as the compatibility fallback beside that layout. A plugin may have both manifests, and each is a row. The bundle's own skills, commands, subagents, hooks and settings stay with their own mechanisms, through the `.claude/plugins/*/` rows and the rows with a plugin placeholder as their first segment. A plugins row records that the repository has a plugin at all. A `PLUGIN_FILES` path with no directory, Copilot CLI's `marketplace.json`, is read at the root alone, and a path that starts with a placeholder, such as an Antigravity plugin's `plugin.json`, is read under every root of that kind.
- **LSP servers**: the paths that `LSP_FILES` names, including `.github/lsp.json`, a `.github/lsp.json` below the root (`NESTED_LSP_FILES`), a Claude plugin's `.lsp.json`, portable Copilot components and the files that a manifest selects. The detector checks the alternatives of a Copilot plugin in order against the LSP schema, and an invalid file lets the next alternative apply. Other LSP heuristics count a file by its path without that schema check, except OpenCode's configuration, which counts when its `lsp` key is `true` or an object (`json_enabled:lsp`) and not when it is `false`. A Claude Code manifest with a server under `lspServers` that has a `command` and an `extensionToLanguage` map is an LSP row itself, as DataDog/datadog-agent's gopls plugin configures its server in the manifest alone.
- **A plugin's parts**: a row with a path that starts with a placeholder such as `<claude-plugin>` is read under every directory that `paths.plugin_roots` finds for that kind, and nowhere else. `plugins/modelopt/agents/*.md` is therefore a subagent, because `plugins/modelopt/.claude-plugin/plugin.json` exists. Because `tool_for_path` resolves no tool for a path of that kind, `plugin_part_tools` lists each part with its plugin's tool, and `artifact_tools` adds the tool for a configuration artifact at or below a part. `plugin_part_tools` lists each plugin's manifest the same way, with the tool read off the rows of its placeholder, because `tool_for_path` reads `.github` only at the root, and a Copilot CLI plugin under `plugins/lint/.github/plugin/plugin.json` would otherwise get no tool. `paths.plugin_components` returns the places of a plugin that its tool reads: the default places; from a list of alternatives such as `hooks.json|hooks/hooks.json`, the first that satisfies the component predicate; the places that a manifest key names; and a root `SKILL.md`. It returns none for a Codex or a Copilot CLI plugin with a root `plugin.json` that declares the Agent Plugins schema, because both tools read such a plugin through that manifest. `_anchored` yields the default place of a placeholder row only where `plugin_components` keeps it, and a Claude Code `agents` key or a Copilot CLI `skills` string drops the default folder. Each detector adds what a manifest names, resolved into what the default row reads: a skill folder, a file, a hooks, MCP or LSP file held to the content test of the default row, or an agent folder read at the depth of its heuristic, including a Copilot plugin `README.md` with description front matter. An Antigravity plugin's `skills` key selects skills as the entries of its `skills.json` do, beside its `skills/`, and `detect_skills` reports a selected skill in the plugin root or a folder above it as a root skill, named for its folder. jasonxudeveloper/jengine's skill folders under `.claude-plugin/skills` are therefore skills rather than `other` rows. [The parts of a plugin](../heuristics.md#the-parts-of-a-plugin-wherever-the-repository-puts-it) gives the vendors' layouts and what Copilot CLI was observed to read.
- **Other**: every file that no other detector returned inside a spec directory or a place of a `nested:` row below the root, ignore files matched by basename at any non-vendored depth, and root-only files such as `.worktreeinclude`.

A Copilot plugin's `README.md` with description front matter is an agent in the default
directories, in the directories that a manifest selects and in the components of a portable
plugin, because the exclusion of README files at the repository level does not apply to plugin
agents. A skills directory that a Copilot plugin's manifest names and that contains a `SKILL.md`
is one skill, and the detector reads no skill below it. A skill below it counts only where the
manifest names that skill in an entry of its own.

## Error handling & edge cases

| Scenario | Behavior |
|----------|-----------|
| `data/validated/repos.csv` missing | Logs `ERROR detection: Validated list not found` and returns exit code `1` |
| The validated list missing a metadata column | Logs `ERROR` naming the absent columns and the header that it read, and returns exit code `1`. A `DictWriter` would have filled the name with a blank in every output CSV |
| `data/validated/` missing or without a repository directory | Logs `ERROR` and returns exit code `1` |
| An `@eaDir` directory or a `.DS_Store` in a repository directory, such as after File Station showed the tree after the collected file cleanup | Left out of every mechanism CSV and of `other.csv` |
| Repository directory present but absent from the validated list | Detected in full. It contributes rows with every metadata column but `repo_name` blank to every mechanism CSV but never reaches `output/repos.csv`, which the step writes by iterating the list. The step logs a line with the count and then, for each such repository, the line `<owner/repo> has a directory in data/validated and no row in data/validated/repos.csv`, with the paths that the module constants give |
| `file_history.csv` has no row for a configuration artifact, under its mechanism or any other | The <!--s:parameters.agentcontext.heuristics.HISTORY_COLUMNS:words-->four<!--/s--> git columns are written blank, the row is counted in a `WARNING`, and the first ten are named. `agentcontext/steps/file_history.py` measures them |
| `file_history.csv` absent | Every row of every CSV is counted that way, and the output CSVs are written with the git columns blank |
| `ai_authorship.csv` absent, or without a row for a context file at its `head_sha` | The <!--s:parameters.agentcontext.heuristics.AI_COLUMNS:words-->four<!--/s--> AI columns are blank, and an `INFO detection` message gives the number of such context files |

| A configuration artifact that cannot be opened, such as a file that the step may not read | A warning naming the file, and `language`, `line_count`, `is_reference` and `referenced_file` are blank |
| A `head_commit_date` of the validated list that is not an ISO 8601 timestamp, such as a date of a damaged repository | Blank in `output/repos.csv`, in every mechanism CSV and in `excluded.csv`. A `WARNING detection:` line names the count, one of the values and every repository, and the step goes on |

| A `created_at` of `file_history.csv` that does not parse, which the cache keeps as git printed it for a creation commit such as one of the year 10000 | Blank in the mechanism CSV, with the other git columns of the row as the cache has them. A `WARNING detection:` line names the count, one of the values and every repository |
| A `commit_timestamp` of a shard that does not parse, such as `10000-01-01T00:30:00Z`, which git prints in UTC for a commit of the year 10000 | Blank in the restricted commit CSV, with a `WARNING detection:` line that names the CSV, the count, one of the values and every repository |
| A file name with a space, `#`, `?` or a character outside ASCII | `github_link` percent-encodes it, and the column always contains a URL |
| A configuration artifact under <!--s:parameters.agentcontext.steps.detection._LANGUAGE_MIN_CHARS-->50<!--/s--> characters once leading and trailing whitespace is stripped | `language` is `n/a`. The marker of a context file that is a link is the usual case |
| A skill, an agent, a command or a rule that is a link to a file of the collected tree | Reported at the link's path, with the `language` of the file that the marker names (`measured_artifact`) |
| A context file that is a link to a file of the collected tree, held as a marker or as a real symlink, such as gomlx/gomlx's `.agents/CLAUDE.md` | Reported at the link's path as a reference to its target: `line_count` counts the marker's one line, `is_reference` is `TRUE` where a pattern captures the target, and `language` is `n/a` for a path under <!--s:parameters.agentcontext.steps.detection._LANGUAGE_MIN_CHARS-->50<!--/s--> characters |

## The mechanism CSVs

There is one CSV per mechanism, `output/<mechanism>.csv`, and `heuristics.csv_header`
builds the header of each. Every CSV opens with the <!--s:parameters.agentcontext.heuristics.META_COLUMNS:words-->five<!--/s--> metadata columns `repo_name`,
`scanned_at`, `branch`, `head_sha` and `head_commit_date`, followed by
the configuration artifact's path under the mechanism's own name and `tool`. Whatever else the mechanism records
about the configuration artifact comes next, then `github_link` and `dataset_version`, and then
`created_at` and `#commits`. The CSV ends with `language` where the mechanism has it, and
with `first_commit_sha` and `last_commit_sha`.

| CSV | Columns | Beyond those |
|---|---:|---|
| `settings.csv`, `hooks.csv`, `mcp.csv`, `plugins.csv`, `lsp.csv` | <!--s:schema.settings.columns-->13<!--/s--> | nothing |
| `other.csv` | <!--s:schema.other.columns-->14<!--/s--> | `link_path` |
| `commands.csv`, `rules.csv` | <!--s:schema.commands.columns-->15<!--/s--> | `name`, `language` |
| `subagents.csv` | <!--s:schema.subagents.columns-->16<!--/s--> | `name`, `memory`, `language` |
| `skills.csv` | <!--s:schema.skills.columns-->18<!--/s--> | `name`, `scripts`, `references`, `assets`, `language` |
| `context-files.csv` | <!--s:schema.context_files.columns-->21<!--/s--> | `language`, the <!--s:parameters.agentcontext.heuristics.REFERENCE_COLUMNS:words-->three<!--/s--> columns of the reference heuristic, and the <!--s:parameters.agentcontext.heuristics.AI_COLUMNS:words-->four<!--/s--> AI columns |

The mechanism CSVs have one row per detected configuration artifact. The CSVs with `language` are context files, skills,
subagents, commands and rules, the <!--s:parameters.agentcontext.heuristics.LANGUAGE_MECHANISMS:words-->five<!--/s--> mechanisms with configuration artifacts that are prose documents
and not settings formats. `context-files.csv` is the widest because it has the columns of two more
heuristics. `line_count`, `is_reference` and `referenced_file` record whether a context file is a
pointer to another file, and `first_commit_ai_created`, `first_commit_ai_tool`, `#ai_commits` and
`ai_commit_tools` record which commits of the file's history the commit heuristics attribute to a tool. [dataset.md](../dataset.md) gives the current row counts.

Until 2.0.0, including the outputs from which release 1.0.0 was built (`3_data-collection/output`
at the tag), each mechanism had two files. The detection step wrote `output/<mechanism>.csv`, the
file history step wrote `output/<mechanism>-extended.csv` beside it with the same rows and the git
columns, and `context-files-ai.csv` was a third file over the context-file rows. The published
copies under `_dataset/` joined them into one CSV per mechanism. Two files meant two writers, two
line terminators and two key sets to keep consistent, and in those outputs the two files of every
mechanism disagreed on which keys they held. The detection step joins `file_history.csv` and
`ai_authorship.csv` and writes one CSV per mechanism, and `agentcontext/steps/file_history.py`
fills in place the git columns for which the cache had no row.

Rows with unavailable history remain in the dataset with blank fields. The file history
step retries missing measurements when fetching is allowed, and a failed retry must not
remove an existing configuration artifact from the dataset. `history.read_artifact_history`
reads the history of a file below a directory symlink at its target path. `snapshot.json`
records the totals of missing history, and [dataset.md](../dataset.md) explains the evidence
limits.

`agentcontext/steps/release.py` builds the published copies from `output/` directly. [The
release](release.md#context) describes how release 1.0.0 was built in `_dataset/`.

## The planning documents

The step writes the planning documents of each repository that it publishes to
`output/planning-documents.csv`, one row per file that `planning.planning_documents` matches in
the validated tree ([Planning documents](../heuristics.md#planning-documents)). A planning document is no
configuration artifact. It sets no tool or file flag, and a repository with planning documents
and no configuration artifact does not reach the step, because the collected file cleanup drops
it. A file that a detector returns, including the files that `_collect_known_files` counts as
known, stays a configuration artifact and gets no row. A planning document gets no row of
`other.csv`, also where it is inside a tool's directory, as a plan in `.cursor/plans/` or
`.claude/plans/` is. The anchors that the cloning step copied beside the documents, such as the
`.bmad-core/` file beside BMAD's `docs/prd.md`, are no planning documents and get no row. A
header anchor is read in the validated copy, which has the bytes that the cloning step read.

`framework` and `document` come from the first heuristic that matches the file. The git columns
are joined from `file_history.csv` under the key `planning_document`, which the cloning step
writes for every file that it copies, and `created_at` is in UTC as in the mechanism CSVs.
`line_count` counts the lines of every file that is text, as `classify` counts the lines of a
context file
([Columns read from the configuration artifact](#columns-read-from-the-configuration-artifact)).
A file with a NUL byte and no UTF-16 byte order mark, such as an image in a feature folder, has
`language` `n/a` and a blank `line_count` (`no_text`). A configuration artifact without text has
the same values, such as a CLAUDE.md that git-crypt encrypted, which opens with `\0GITCRYPT\0`
and also has a blank `is_reference` and `referenced_file`.

`language` is detected in a Markdown file (`.md`, `.mdc` or `.markdown`) alone and is `n/a` for
every other file. A specification, a plan or a task list is prose, which the same detector reads
as it reads a context file. The other files of a framework's folder are scripts, JSON, YAML and
templates, for which a language detector returns no meaningful result, as it does for the files
of the mechanisms without a `language` column. The extension of the file
determines whether the step detects the language, not the heuristic's `document`, because a
heuristic of a folder, such as Spec Kit's `contracts/`, covers Markdown and other files alike.

## Claude commands are reported as skills

Claude Code merged custom commands into skills after this pipeline was first
written: "Custom commands have been merged into skills. A file at
`.claude/commands/deploy.md` and a skill at `.claude/skills/deploy/SKILL.md`
both create `/deploy` and work the same way. Your existing `.claude/commands/`
files keep working"
([skills](https://code.claude.com/docs/en/skills)).

`agentcontext/steps/detection.py` follows the merge: every `*.md` under `.claude/commands`
is reported in `skills.csv`, not `commands.csv`. The `scripts`, `references`
and `assets` columns of a command file are `FALSE`, because a command file is a skill
without a supporting directory, and the skill form adds that directory. A folder of
`.claude/commands` with a `SKILL.md` is that form inside the commands directory. Rows with a path
that ends in `SKILL.md` are the directory form, and rows under `.claude/commands` are the
flat form, and the two forms therefore remain distinguishable.

Only Claude Code merged the two mechanisms. `.cursor/commands` and
`.gemini/commands` remain separate features of their own tools and stay in
`commands.csv`.

If a repository has both `.claude/commands/deploy.md` and
`.claude/skills/deploy/SKILL.md`, both are recorded. In Claude Code the skill takes precedence, but
this step records the configuration artifacts present, not which file a session would run.

**Effect when the change was introduced.** Running this step again over the collected
repositories moved the rows of `.claude/commands` from `commands.csv` to `skills.csv`. The
share of each tool's repositories with commands dropped for every tool, because a repository
counted there afterwards only if it also used Cursor or Gemini commands. A Codex repository
that kept its prompts in `.claude/commands` counts as Skills since the change.
[dataset.md](../dataset.md) gives the current counts, and `CHANGELOG.md` lists changes of the
heuristics.

After you review the changes of the outputs, regenerate the RQ2 and RQ3 analyses with
`mise exec -- python3 4_data-analysis/run_analysis.py` and the website with
`_website/build_site.py` ([the website](../../_website/0_README.md)), from the same release
inputs. The values of earlier papers are not requirements for a release.

The regression suite of the detection step runs `main` with separate shards for the six tools and for the other tools. It checks that both commit CSVs contain only published repositories and keep their own tool attributions. Omitting the rebuild of the other tools' CSV, or reading the shards of the six tools for it, makes the test fail.

A Cursor worktree setup in `.cursor/worktrees.json` counts as settings and sets the Cursor tool flag, and it therefore does not appear in `other.csv`.

The tests check the retention of a repository with one configuration artifact of each named
mechanism in isolation. The unclassified files alone do not keep a repository.

The regression tests of the detection step check the rows of LSP files and symlink markers
through the published CSVs: their mechanism and tool flags, and their absence from
`other.csv`. Antigravity paths and Copilot plugin manifests each have an explicit
expected tool attribution, and changing the tool of one heuristic must make its test fail.

A file detected only because a context or rule declaration names it takes the declaring tool,
and its parent directory or a plugin that contains it adds no other tool. A file that another
mechanism also reads keeps that mechanism's attribution in that mechanism's row and takes the
declaring tool in the row of the declaration. A `.cursor/rules/*.mdc` that OpenCode's
`instructions` name, as in AnswerOverflow/AnswerOverflow, is therefore Cursor's rule and OpenCode's
context file. The SKILL.md of a Claude Code and Cursor plugin that a Gemini extension names as its
context file, as in obsei/obsei, is a skill of both plugin tools and Gemini's context file. Support files that only the collection copies, such as
`README.md`, do not identify a tool. The regression tests of the detection step and of the
rebuild of `output/repos.csv` check the same published tool flags, including for a declared
context file that is also a Copilot MCP file in its own right.

The rules and subagents of a Cursor plugin can have the extension `.md`, `.mdc` or `.markdown`,
and its commands can also have `.txt`. Where a manifest overrides the location of a component,
the detection step reads the override instead of the default location, and it reads both default
MCP files when no override is set. Project subagents accept the same Markdown extensions, and
project commands are the `.md` files at any depth under `.cursor/commands`, as [Detection heuristics (per mechanism)](#detection-heuristics-per-mechanism) states. The detection step records Cursor's project plugin settings in
`.cursor/settings.json` as settings.

The match mode determines the depth at which the detector finds skills ([Detection heuristics (per mechanism)](#detection-heuristics-per-mechanism), Skills). A skill that a manifest declares explicitly remains a skill inside a
default container even when it is deeper than the mode reads.

A followed symlink marker for the directory of a plugin component is part of the known set: its
target is reported once, and the marker does not appear in `other.csv`. Ordinary markers and
plugin markers go through the same check that the target is inside the repository.

`detect_other` reads the directory that a marker in a spec directory leads to as it reads the
spec directory itself. A file there that no detector returns is an `other` row at its own path,
and `link_path` gives the path at which the tool reads it, which `unmatched paths` groups and
tests the file by. utooland/utoo links `.claude/agents` to `agents/`. The performance reports
there have a heading above their `---` horizontal rules and no front matter, and they are therefore
subagents of neither Claude Code nor Cursor. Without this reading, they would be in no CSV. A marker with a target that contains the marker itself adds nothing,
because the collector never copies such a target. `link_path` is blank for every other row.

The `agents.md` file flag also covers `AGENTS.override.md`. The override sets the Codex tool flag
too and therefore cannot make a repository `no_specific_tool`. In a directory with an
`AGENTS.override.md` or an `AGENTS.md`, a name in `project_doc_fallback_filenames` makes no file
a context file, because Codex reads one file per directory and tries these two names first.

The `json_plugin_mcp` predicate accepts the server maps of a Claude Code or Codex plugin with or without an `mcpServers` wrapper, with a server that the plugin's tool loads (`_plugin_mcp_servers`). Codex infers the transport from a `command` or a `url`, and Claude Code loads a server with a `command` and no `type` or the type `stdio`, or a server with a `url` and the type `http`, `streamable-http`, `sse` or `ws`, with the fields that the schema of its type declares in their types (`paths.claude_loads_a_server`). The predicate applies to the default `.mcp.json` and to the files that a manifest selects, and a plugin part gives its tool to the file only where that tool loads a server of it (`_part_loads`). The other tools keep their own MCP predicates.

When a declared component path of a Claude plugin fails the path checks, the detection step rejects all parts of the plugin, and a valid default directory does not make the invalid declaration loadable.

The MCP files of Antigravity workspaces and plugins may contain comments and trailing commas, and
every other JSON file keeps the format of its heuristic. A root `REVIEW.md` is context for Claude
Code Review and Copilot code review, and a nested copy does not match that heuristic.

The components of a Claude plugin can come from an entry of a local marketplace without a
separate manifest. When the entry and a manifest conflict, the step detects none of the
components.

For a registration of Antigravity rules, the step reads the rule file that an entry names, or
the Markdown files directly in the entry's directory. A path resolves against the directory that
contains the registration file's customization root, or against its plugin's root, and against
the workspace root where nothing exists there. `include_only` names the items to read, nested
ones among them, and `exclude` names items to leave out, each by name and not by pattern. The
lists of an `inherits` object apply to everything that the inherited chain selects
([Configuration artifact detection](../heuristics.md#configuration-artifact-detection)). An inherited registration file
remains a configuration artifact of `rules` where it sets `entries`, `inherits` or `exclude`. An
inherited file that sets none of them, such as a package.json, or that Antigravity does not
read, such as a `README.md` or a file that does not parse, is no configuration artifact. A
registered rule counts only with a trigger and a registered agent only with a name and a
description in its front matter, and a `.` entry at the workspace root therefore selects no
README.md. The step reads a registration file through a linked customization root, such as an
`.agents` that links to `config/agents`, resolves the paths of the file against the directory
that contains the link, and reports the file at its path in the repository.

A registration file's top-level `exclude` leaves items out of the default places as well.
`paths.antigravity_left_out` names the files of Antigravity's default places that it leaves
out: the rules, workflows and subagents of a customization root in the file's directory or below,
the skills of `.agent/skills`, `_agents/skills` and `_agent/skills`, and the subagents, skills and
rules of a plugin that the plugin's own registration file excludes. The detectors skip such a
file in that place, and it is therefore an `other` row in a customization root unless another
tool reads it, as Claude Code does through a linked directory. A skill in `.agents/skills` stays,
because Codex, Copilot, Cursor and OpenCode read that directory too. A plugin that the
top-level `exclude` of a `plugins.json` leaves out is no plugin (`paths.plugin_roots`).

An Antigravity registration file in JSON is a configuration artifact of the mechanism that it declares. The detection step records each selected component once and attributes to Gemini the files that only a declaration names. A selected plugin directory contributes its usual component files. A selected skill is named after its folder, and a skill at the repository root after the repository, as a plugin's root skill is. A root skill, with the registration file that selects it in its own folder (`paths.registered_root_skills`), adds its `SKILL.md` and support directories to the known set of `detect_other`, and not the whole folder. A file of the package that no detector returns therefore stays an `other` row.

A `description` in front matter can be a quoted string with a trailing YAML comment or with
indented continuation lines. An empty string, a sequence or a mapping does not count.

The name of an agent that a manifest declares drops the same `.agent.md` or `.chatmode.md`
suffix as the name of an agent in a default directory. The keys of a Claude command map supply
the published skill name of a command file. If several keys name one source file, its row uses
the first key in alphabetical order, declarations in local marketplaces included. A key that
does not encode as UTF-8 names no file, as [Key decisions](#key-decisions) states.

A Codex manifest can replace the paths of skills, MCP and hooks. A non-empty inline component
counts under the path of its manifest, and with empty inline hooks the step does not count the
default hooks file. The hooks of a portable plugin are attributed to Codex. Its `skills/` and
`mcp.json` are attributed to Codex where `.codex-plugin/plugin.json` is beside the portable
manifest or a Codex marketplace lists the folder, and to Copilot where a Copilot CLI manifest is
beside it or a Copilot CLI marketplace lists the folder. The manifest of another vendor that Codex
or Copilot CLI reads in a folder that the tool's marketplace lists and that has no manifest of the
tool's own and no portable manifest, such as the `.claude-plugin/plugin.json` of
Azure/azure-sdk-tools's `plugins/azure-sdk-tools`, is a row of that tool as well.

A Cursor manifest's `mcpServers`, or the `mcpServers` of its entry in `.cursor-plugin/marketplace.json`,
takes a path, an inline object or a list of either as well, and the file that holds the object counts
as an MCP row of Cursor, as shadcn-ui/ui's `.cursor-plugin/plugin.json` does.

A Claude Code manifest's `mcpServers`, `lspServers` and `hooks` take a path, an inline object or
a list of either, and the inline servers and hooks load together with the default file. The
manifest counts under the mechanism where its inline object, or an object in its list,
configures a server with a `command` or a `url`, a language server with a `command` and an
`extensionToLanguage` map, or a hook in a matcher group (`paths.plugin_components`, kind
`inline`), and the default file still counts. patrickchugh/terravision's `.claude-plugin/plugin.json`
and `.codex-plugin/plugin.json` give the same server inline, and each is an MCP row of its
tool. A plugin without a manifest takes the entry of its marketplace as the manifest, and the
marketplace file, such as firebase/firebase-tools' `.claude-plugin/marketplace.json`, is then
the row. Beside a manifest, an entry's servers do not apply.

The detection step passes `heuristic_rows` to the helpers for declarations and plugins, and
`heuristics.MECHANISM_CSVS` supplies the output filenames and path columns.
