# Build the publication

## Context

`output/` contains what the pipeline computes, and `release/` contains what a person downloads. The release step joins `output/repos.csv`, which detection writes, to the sampling frame and the classification labels, renames <!--s:parameters.agentcontext.steps.release.DETECTED_RENAMES:words-->two<!--/s--> columns and withholds <!--s:parameters.agentcontext.steps.release.WITHHELD:words-->three<!--/s--> CSVs. It adds the heuristics and the provenance records, compresses the <!--s:parameters.agentcontext.steps.release.RELEASE_FILES.compressed_csvs:words-->two<!--/s--> large CSVs, packs the deletion log, and writes a README, a citation file and a checksum manifest, which `output/` does not contain.

Until AgentTorrent 1.0.0, the publication was built in `_dataset/`, a directory that was both the publication and the place where its inputs were staged. `_prepare_dataset.py` read its input files by bare name from that directory. A person published by copying them in by hand from the outputs of other stages, and the script ended by deleting the copies. Running the script twice was an error. Running it once had stopped working, because it read `repos_detected.csv`, a name that nothing has written since the detection step began writing `output/repos.csv`. `_generate_readme.py` then wrote a README from whatever CSVs were in the directory. The committed README therefore described the data of AgentConfigs 1.0.0 under the column names of that release, although both scripts had been updated for AgentTorrent 1.0.0.

This script is one step that stages nothing. It reads each input where the step that wrote it put it, writes `release/`, and deletes nothing.

The step removes `checksums.sha256` before it rebuilds the first CSV. Otherwise, a run that raises an exception partway through would leave the CSVs of this run beside the manifest of the previous run, and `sha256sum -c` would then find mismatches in a directory that nobody had edited. An unfinished release therefore has no manifest. Every comparison of the inputs runs before the manifest is removed, so that a refusal leaves the previous release as it was, with its manifest.

## Key decisions

- **Language:** Python 3.14 (single script `agentcontext/steps/release.py`), with the standard library only and the `7zz` binary on `PATH`. The step does not use pandas. Pandas reads the string `n/a` as a missing value, and `subagents.csv` uses `n/a` in `memory` for tools without memory per agent. Read with pandas, those cells would be published blank
- **One tuple, four consumers:** `RELEASE_FILES` is what the step builds, what the checksum manifest covers, what the README describes, and what the tests check. Four separate lists, as the scripts that this step replaces had, can differ without any check failing. Those scripts kept the files that their README overview named apart from the files that their build wrote and copied
- **A copied file has the time at which it was written, not the time of its source.** The step copies with `shutil.copyfile` rather than `copy2`. The runner tells whether a step wrote a declared output from the mtime, inode and size of the file before and after the step, and `copy2` of an unchanged source gives the destination the mtime of the source. Over a release already on disk, the runner would then find that this step wrote nothing, and it would stop the run
- **`output/` is inventoried, not globbed:** `OUTPUT_INVENTORY` lists every entry of that directory with what it is. The run stops on a file that is in neither the inventory nor the release, because nobody decided whether to publish or withhold it. `TestEveryStepOutputIsInTheInventory` checks against the inventory every file that a step of the runner declares under `output/`, because a declared output without an entry would stop a real run at this step. The test also checks every file tracked under `output/`, because a checkout contains each of them. The name of the tracked unmatched attributions, `all_ai_commits-unmatched-<YYYY-MM-DD>.csv.7z`, and the name of the CSV that extracting the archive writes contain the day on which their collection started. `OUTPUT_INVENTORY_DATED` therefore matches both names by that pattern
- **What is withheld is named:** `WITHHELD` lists `other.csv`, `excluded.csv` and `unmatched-commits.csv` with the reason, and the README gives each. `output/` also holds files that serve to build and check the dataset, such as `consistency-report.csv` and the regression manifest, and `OUTPUT_INVENTORY` states what each of them is. The README lists the withheld CSVs without a count and points to `OUTPUT_INVENTORY` for the other unpublished files of `output/`, so that every omission has a stated reason
- **The release contains what shows how the data was built, and no list that names people, within the limits of the rule of [What the archive keeps](../checks/unmatched.md#what-the-archive-keeps):** The maintainer decided on 2026-11-06 to publish more files, so that a dataset user can audit how the data was built without the repository of the pipeline. These are the negatives `not_configuration.csv`, `not_ai_commits.csv` and `not_planning_documents.csv`, the record of the documentation watch, `doc_hashes.json` and `doc_quotes.json`, and the records of the collection, `unmatched-paths.csv`, `deletions.csv`, `deletion.csv.7z`, `ai_commits-repos.csv` and `commit-reclassification.json` ([The records of the collection](#the-records-of-the-collection)). The maintainer also decided on 2026-11-06 that the lines of the unmatched attributions that name a bot or a tool go into the release, as `unmatched-attributions.csv`, which the step builds from the full list by the rule of `unmatched reduce` ([What the archive keeps](../checks/unmatched.md#what-the-archive-keeps)). The rest of the attributions that no commit heuristic explains stay out: `unmatched-commits.csv` and the full list, `all_ai_commits-unmatched.csv`. Most of their tokens are the names of the co-authors of commits that no heuristic matched, and some give an address. Such a commit has no row in the commit CSVs, and most of these names and addresses are therefore in no file of the release. `all_ai_commits-mentions.csv` and the commit logs in `collect_commits/` stay out for the same reason. These files stay in the handover of each run, where the check of the run reads them. `commits.csv` keeps its verbatim messages by design, so that the co-authors of credited commits stay published
- **The licenses:** The README states CC BY 4.0 for the dataset, the MIT license for the code of the pipeline, and that the collected files and the commit messages keep the licenses of their repositories
- **The deletion log is published as an archive alone:** `deletion.csv` is a record that a reader opens for an audit, and the release contains it once, as `deletion.csv.7z` (kind `build`). The step packs the log that the collected file cleanup wrote beside `output/`, not the archive that git tracks beside it in a checkout, which holds the log of the collection that [docs/dataset.md](../dataset.md) names and is only rebuilt when a regeneration is brought into the checkout. Without the log, the step refuses before anything is written, because `RELEASE_FILES` and the README name the archive
- **The collected_files_archive step writes into `release/` directly:** The archive therefore has one name, `repos_data.7z`, rather than a second name in the stage directory. It is the one entry of `RELEASE_FILES` that this step checks rather than writes
- **Timestamps off in both compressions:** 7zz records the modification time of the source file, and every run writes the source anew. With the times recorded, the manifest would change on every run while the data had not. With `-mtc=off -mtm=off -mta=off`, the archive has the same bytes whenever its content is the same
- **Every count in the README is computed here:** Nothing in the published README is typed by hand, and a README therefore cannot describe a release other than the release beside it
- **The model that labeled the sample comes from the record of the classification:** `classification_record` reads `repos_annotated.json` beside the labels. The classification writes that record, and `repos_annotated.7z` contains it for the labels of the development dataset. The README names the models of the record in its description of the classification step, and in its description of the `justification` column when the record names one model. With several, the column describes the justification as the response of the model that labeled the repository, and the sentences after the description of the classification step name the repositories that the second model labeled. With a model name written into this script, the README of a release after a run of the classification stage with another model, such as `gpt-6-luna`, would name the wrong model. The record also lists under `higher_temperature_labels` each labeled repository that the classifying model labeled at its higher temperature after a failed response, under `second_model_labels` each one that the second model labeled, because the classifying model left it without a decision after its retry rounds and a failed response, and under `second_model_failures` each repository that the second model left without a decision too (`2_classification/classify-repos-spec.md`). After the description of the classification step, the README names the classifying model, states how many such repositories there are and names each, grouped by the reason for the repositories that the classifying model labeled at its higher temperature and with its reason for the others (`fallback_sentences`), so that the published dataset itself lists them without a column of its own. The record also lists under `backup_provider_labels` each labeled repository with a label that a backup provider served, wholly or in part, while the pinned provider of a model failed, and the next sentences state how many there are and how many of them the backup providers served wholly, and point to that list, which names each with its backup providers (`backup_sentence`). The release does not contain the record, and the sentences name the archive `data/classification/repos_annotated.7z` of the pipeline's repository, which holds it with the labels that the release was built from. Through an outage of a pinned provider, a backup provider can serve most of the repositories of a run, which no sentence of the README could name. The provider is no classification parameter, and such a label was made under the same parameters as the others. A record that lists none, or has no such list, adds no sentence. Before anything is written, the step exits 1 on a missing record and on a record that names no model or has no description, as it does on a sampling frame without its provenance
- **The README defines the criteria that a justification names:** The classification appends to the model's justification a verdict that names the criteria that decided the label, each by its key, such as `inactive` or `fork` (`published_justification` of `2_classification/1_classify_repos.py`). For a fork or a mirror, the verdict also states the finding from GitHub's data that decided the label: that the fork is not independent of its upstream, or that no pull request was merged in the mirror since the sampling window began. The README describes the `justification` column as the model's justification followed by that verdict and lists the meaning of each key from `CRITERION_MEANINGS`. `test_classify_repos.TestTheReleaseDefinesEachCriterion` fails when the classification's `CRITERIA` and the keys of `CRITERION_MEANINGS` differ. A label made before the classification removed a criterion still names it, as the labels of run `2026-10-23T093036Z` name `closed_to_contributions`, which was removed on 2026-10-31 (`2_classification/classify-repos-spec.md`). `REMOVED_CRITERION_MEANINGS` gives the meaning of such a criterion with the date of its removal, and the README lists it after the current criteria when a published verdict names it (`named_criteria`). `build_repos` reads the keys that each published verdict names (`verdict_criteria`) and refuses a key that neither list defines, before anything is written, so that no published justification names a criterion that the release leaves undefined
- **The README states why a repository in the sampling frame has no published label:** The classification lists in `repos_excluded.csv` beside the labels each repository that it did not label, with the reason, such as `readme_non_english` or `no_readme_found` (`2_classification/readmes.py`), and under `copy` each repository that it labeled `true` and left out of the sample, because the sample keeps another repository at the same head commit. The README therefore says that a copy has no published label rather than that the classification did not label it. With copies, it counts the engineered projects among the annotated repositories (`engineered_sentence`). A copy is labeled `true` but has no published label, so the count of the annotated repositories and the labels that the README states for `engineered_project` leave it out, and a count of the engineered projects without that scope would read as the count of every repository labeled `true`. `exclusion_reasons` reads `repos_excluded.csv` before anything is written, and `unlabeled_by_reason` counts the published rows with a blank `engineered_project` by reason. The README states these counts in its description of the classification step and refers to them in its description of `engineered_project`, which also names each label with its count and states when the classification gives `false`, `unclear` and `true` (`labels_of`), so that a reader does not take the rows labeled `unclear` for `false`. Without the counts by reason, a reader could not tell why the sampling frame has more rows than the labels. The step exits 1 before anything is written on a missing file and on a row without a label and without a reason, because the README would count the row without saying why it has no label. Such a row arises when the labels and the exclusions come from different runs. A reason that `EXCLUSION_REASONS` lacks is named as the classification wrote it
- **No DOI in `CITATION.cff`:** Zenodo assigns the DOI at deposit. A DOI written here would be a DOI that nobody assigned
- **The citation names the version of the rows:** `CITATION.cff` and the Citation section of the README cite the `dataset_version` that `output/provenance.json` records, which the detection step writes with the rows. A version written into this script would cite the version of the code that built the release rather than the version of its rows. The step exits 1 before anything is written when `provenance.json` records no version
- **The run stops on a repository with detection rows and no row in the sampling frame:** The join is by repository name. A left join would drop the repository without a warning, the published row count would still be that of the sampling frame, and nothing would record that a repository is missing
- **A temporary file of an earlier run is removed first:** `write_csv` and `build_commits` write `<name>.<random>.tmp` beside the file that they replace and remove it after an exception. A SIGKILL leaves the file, and so does SIGTERM with its default handling, which a Stop sends. `consistency_problems` reports every entry of `release/` that is not a file of the release, and the run then exits 1. `publish` therefore deletes `<name>.*.tmp` for each name of `RELEASE_NAMES` before its checks, as `caches.replace_file` and the `write_table` of the file history step do for their files. Without the removal, every Start after such a Stop would fail in this step until a person deleted the file
- **The release publishes no files that disagree:** Before anything is written, the step compares the inputs with one another, and on any difference it logs every difference and returns 1. The detection heuristics have to match the SHA-256 that `output/provenance.json` records, and so do the heuristics of the planning documents, `vendored_dirs.txt` and `local_state_paths.csv`, which the release publishes beside them. Where `output/snapshot.json` records `classified_by`, the commit heuristics have to be the heuristics that the snapshot records as having classified the commits. The repositories in `release/repos_data.7z` have to be the repositories that `output/repos.csv` lists, and `release/` may contain only the files of `RELEASE_FILES`. `imported_sources` resolves in the imported tree every target that `output/imports.csv` places in `imported_files.7z` and adds the targets that the tree lacks or holds only as a stub to these differences. Without these checks, a `--heuristics` file other than the file that the detection ran with would be published beside the checksum of the file that it ran with. The README would describe an archive packed from another tree as the files of the repositories that the CSVs list, and a stray file in `release/` would be beside a manifest that does not cover it. The check of `release/` and the inventory of `output/` both leave out `FILE_MANAGER_ENTRIES`: Finder's `.DS_Store` and the `@eaDir` in which Synology DSM keeps the extended attributes and thumbnails of the files of a directory. These entries appear when a person opens either directory on the NAS, and treating them as problems would make every later Start fail in this step. `build_repos` and `build_context_files` build the rows of `repos.csv` and `context_files.csv` before anything is written, too, and the step keeps the rows for the writes. Building them compares the detection rows and the labels with the sampling frame and the columns of both inputs with the published columns, and `unlabeled_by_reason` compares the rows without a label with the exclusions. `copied_csv_rows` reads every CSV that the release copies and refuses one without a `repo_name` column, such as an empty file. `commit_csv_problems` compares the columns of each commit CSV with the columns that the cloning step writes. It also compares every id that the `matched_heuristics` of the CSV names with the rows of the commit heuristics that the release publishes beside it. The step reads each commit CSV twice, once for the comparison and once for the write, and a commit CSV that it extracts from its archive stays in a temporary directory until then. Each of these refusals leaves the previous release with its manifest, as the refusals of `consistency_problems` do
- **`id` is GitHub's in every release:** A sampling frame that the sampling stage writes records `_metadata.input_source.github` and has GitHub's id, and the classification copies that id into the labels as `github_id`. The sampling frame of March 2026 has GHS's database id, which AgentConfigs 1.0.0 published as GitHub's. For a sampling frame without that record, `id` therefore comes from the labels. `createdAt` has no other source, and the README describes it as the sampling frame records it
- **The README gives the switch that keeps the links:** `repos_data.7z` contains symbolic links with a target outside their directory. 7-Zip extracts such links only with `-snld` and otherwise writes them as empty files, and `7z x <archive> -y` is therefore not enough for that archive
- **The imported files that `repos_data.7z` lacks go into an archive of their own:** `imports.csv` places each found target in `repos_data.7z` where the validated tree has the same bytes at the path, and in `imported_files.7z` otherwise ([import detection](import_detection.md)). This step packs `imported_files.7z` from the imported tree, `--imported-dir`, with exactly the targets that `output/imports.csv` places there, under `imported/<owner§repo>/<path>`. It packs them as the collected_files_archive step packs `repos_data.7z`: from a copy in a staging directory, with the times of the files and of their directories. Each target is the file that the tool read, and the step therefore packs a link of the imported tree as the file that the link leads to. `repos_data.7z`, its file count and the other CSVs are the same as without imports, which `tests/test_steps_release.py` checks. The run stops on a target that the imported tree lacks, because its row would describe a file that the release does not contain. It also stops on a target for which the imported tree holds only a stub that the list of the stubs contains (`imports.read_stubs`), because the bytes of the stub are not the bytes of the file. `imported_sources` resolves the targets before anything is written, so that either target leaves the previous release with its manifest as it was, and `build_imported_archive` packs the files that it resolved after the copies

## `agentcontext/steps/release.py`

### Architecture

#### `RELEASE_FILES`

`RELEASE_FILES` contains one `ReleaseFile` per published file, with the fields `name`, `kind`, `source`, `section` and `description`.

`kind` is how the file is produced:

| `kind` | Meaning |
|--------|---------|
| `build` | Assembled here from one or more inputs |
| `copy` | Taken unchanged from `output/` or from the heuristics |
| `compress` | A 7z of a release file built earlier in the same run |
| `collected_files_archive` | Written by the collected_files_archive step, and this step checks that it is there |
| `generated` | Written from the constants in this file |

`section` is the part of the README that describes the file: `CSVs` (the overview table, with row counts), `archives` (the archive table, with sizes) or `provenance` (the record of how the data was produced). `ReleaseFile.__post_init__` raises `ValueError` for any other value of `kind` or `section`, and a typo therefore fails at import rather than producing a README with a file missing from every table.

The tuple is in build order. `repos.csv.7z` comes after `repos.csv`, and `checksums.sha256` comes last because it covers everything before it.

#### The inventory

`OUTPUT_INVENTORY` maps every name that `output/` may contain to what it is. `OUTPUT_INVENTORY_DATED` does the same by pattern, for the two names that contain the day on which their collection started and for the compressed commit CSVs, unsplit or in numbered volumes. `inventoried` looks a name up in both. `OUTPUT_REQUIRED` lists the files without which the release cannot be built: `repos.csv`, `excluded.csv`, `provenance.json`, `snapshot.json`, `imports.csv`, `planning-documents.csv`, the mechanism CSVs, `other.csv` among them, and the records of the collection. `inventory_problems` reports a file that the inventory does not contain and a required file that `output/` lacks, and the run stops on either. `commit-reclassification.json` is one of the records. A run without `--with-commit-reclassification` over a data root without it therefore stops at the release, and the problem names the flag (`OUTPUT_REMEDIES`). The container and the subsample run pass the flag.

The inventory takes the mechanism CSVs from `heuristics.csv_filenames()` rather than listing them by hand. A mechanism added to the heuristics therefore enters the inventory without an edit here. The mechanism still has to be added to `RELEASE_FILES` or to `WITHHELD`, which `test_steps_release` checks.

#### `repos.csv`

`repos.csv` has one row per repository in the sampling frame, in the order of the sampling frame, and <!--s:parameters.agentcontext.steps.release.REPOS_COLUMN_ORDER.length-->54<!--/s--> columns in the order of `REPOS_COLUMN_ORDER`. It draws on three sources:

1. **`data/sampling/ghs_filtered.json`:** `GHS_SCALAR_FIELDS` verbatim, plus `languages` and `topics` serialized as JSON strings. `pushedAt`, `updatedAt`, `lastCommit` and `lastCommitSHA` are in the sampling frame but not selected. They describe the repository on the day on which the sampling frame was downloaded, which is neither the day of the scan nor today, and a reader cannot tell the day from the value
2. **`data/classification/repos_annotated.csv`:** `engineered_project`, `justification`, `default_branch`, which falls back to the `defaultBranch` of the sampling frame, and `github_id`, which is the published `id` when the sampling frame did not query GitHub. The record beside the labels, `repos_annotated.json`, supplies the models that the README names and the lists that `fallback_sentences` reads: the repositories that the classifying model labeled at its higher temperature, those that the second model labeled and those that the second model left without a decision too. `repos_excluded.csv` beside them supplies the reasons for the repositories without a label, which the README counts
3. **`output/repos.csv`:** every column, with `branch` published as `scanned_branch` and `copilot-instructions` as `copilot_instructions` (`DETECTED_RENAMES`), and `other` discarded (`DISCARDED_DETECTED_COLUMNS`)

The step computes `github_link` again rather than copying it: `https://github.com/<repo_name>/tree/<scanned_branch or default_branch>`, with the branch percent-encoded by `repos.url_path`. Every row of the sampling frame then has a link, not only the scanned rows.

A repository that was not scanned has blank detection columns. These blanks distinguish the three provenance levels in the published file, and the README computes its counts per level from them.

The detection step leaves `head_commit_date` blank where git printed the committer date of `head_sha` in a form that does not parse, such as for a commit of the year 10000 (`repos.to_utc_or_blank`). The README says so in the description of the column, here and in the mechanism CSVs, and counts the rows of `repos.csv` with a `head_sha` and a blank `head_commit_date` among its evidence limits. A repository that was not scanned has neither and is not counted.

In a sampling frame that the sampling stage writes, `id` is GitHub's repository id and `createdAt` the creation time in UTC. That stage reads both from GitHub and records the query in `_metadata.input_source.github`, which `queried_github` reads. A label with a `github_id` that differs from the `id` of such a sampling frame was made over another sampling frame. The run then stops and logs the first <!--s:parameters.agentcontext.steps.release.NAMED_DIFFERENCES:words-->five<!--/s--> such labels. The sampling frame of 2026-03-17 has no such record, and it has GHS's database id and GHS's hour on a 12-hour clock. For that sampling frame, `id` is the `github_id` of the labels, blank for a repository that the classification did not label or that GitHub did not find. The README describes `createdAt` as GHS's time, with the correct date and the hour modulo 12.

#### `sampling.json`

`sampling.json` is the `_metadata` of the sampling frame as the filter wrote it: the GHS retrieval that the sampling frame came from, its sampling window and query, when GitHub was queried for its repositories, the parameters of the filter and what each step removed. `sampling_provenance` reads it before anything is written. The run stops on a sampling frame without `_metadata.input_source`, because the release could not state where its sample came from.

A GHS download that fails, or that refuses a retrieval with far fewer rows than the retrieval before, keeps the previous sampling frame. The filter does not run again over the same retrieval, and `sampling.json` therefore does not show that the window did not move. Before anything is written, `download_report` reads the report of the download, `ghs_retrieval_report.json` beside the sampling frame (`--retrieval-report`). When the report records the outcome `fallback` to the retrieval that `_metadata.input_source` names, the README states among its evidence limits:

- the retrieval
- the retrieval that the download that fell back attempted (`failed_retrieval_id`)
- the reason of the download
- the repositories of a GHS search result that the size check refused (`failed_item_count`)
- how many downloads in a row fell back to that retrieval (`fallback_limit`)

The report outlives the run that wrote it, and a later Start can run the release again without a download, such as after an image update. The limit therefore names the retrievals rather than "this run".

A download with `--accept-smaller` (`--step-arg ghs_download:--accept-smaller` in the container) takes a GHS search result that the size check refuses, and its report records the outcome `retrieved` with the reason `accepted_smaller`. The filter then builds the sampling frame from a retrieval with far fewer rows than the retrieval before, which `sampling.json` does not show either. When the report names the retrieval that `_metadata.input_source` names, the README states among its evidence limits:

- the retrieval with its repositories (`item_count`)
- the retrieval before it (`previous_retrieval_id`)
- that the sampling frame can lack repositories that the earlier retrieval had
- the reason, which states the counts that the size check compared (`smaller_limit`)

The README states no limit for a report of a retrieval that the size check let pass or of a retrieval other than the retrieval of the sampling frame, and none for a data root without a report. The report describes only the last download. A later download that falls back to such a retrieval therefore replaces its `accepted_smaller` with the fallback. The run stops on a report that cannot be read, because the README could not state whether the window moved. The runner also records the release by the report, and a new report publishes again.

#### `context_files.csv`

`context_files.csv` is `output/context-files.csv` with its columns in `CONTEXT_FILES_COLUMN_ORDER`, the `tool` column after the path. The step renames and drops nothing, and a column that is in the CSV and not in the list, or in the list and not in the CSV, is an error.

The detection step leaves `line_count`, `is_reference` and `referenced_file` of a context file blank where the file is not text, such as a file that git-crypt encrypted, or could not be read, and its `language` is `n/a` for a file that is not text ([detection](detection.md)). In the mechanism CSVs, `language` is also blank for a link to a file that the collection did not copy. The README describes these blanks in the descriptions of the columns, because a reader who converts a blank `is_reference` with `str(v).upper() == "TRUE"` would count it as FALSE. Its descriptions of `line_count` in `context_files.csv` and `planning-documents.csv` and of `target_line_count` in `imports.csv` state that a line ends at LF, CRLF or CR (`LINE_BREAKS`), as the detection step counts lines ([detection](detection.md#columns-read-from-the-configuration-artifact)). Python's `str.splitlines` also ends a line at a form feed or U+2028, and a reader who counted the lines of such a file with it would get more lines than the column.

The detection step reads a context file that is a symbolic link as the one-line file that names its target, whether the validated tree holds the link or that file (`detection.artifact_text`). Its row counts one line, is a reference to a target path that ends in `.md`, with that path in `referenced_file`, and has the language detected in the path, `n/a` for a short path such as `AGENTS.md`. The collected_files_archive step stores such a link in `repos_data.7z` as a link, and a reader who counts the lines of the extracted link reads its target. The README's descriptions of `line_count`, `is_reference`, `referenced_file` and `language` in `context_files.csv` therefore state how a link is described.

#### `commits.csv`

`commits.csv` is `output/all_ai_commits.csv`, streamed, with every commit message verbatim and a carriage return in a message written as a newline inside the quoted field, as RFC 4180 specifies. The step exits 1 before anything is written on an input with columns other than the columns that the cloning step writes, such as a CSV written before the heuristics had ids, and names `commit-reclassification`, which rewrites the CSV from the per-repository commit records. The cloning step already writes every line break of a commit message as a newline, and <!--s:collection.commit_messages_with_carriage_return:words-->zero<!--/s--> messages of the commit CSV contain a carriage return for the conversion to change. The step keeps the conversion, because the published file has to keep the line breaks of RFC 4180 whatever the input. `build_commits` also counts the rows with a blank `commit_timestamp`, which the detection step leaves where git printed the date in a form that does not parse, such as for a commit of the year 10000. The README says so in the description of the column and counts these rows of `commits.csv` and `other_commits.csv` among its evidence limits.

#### `other_commits.csv`

`other_commits.csv` is `output/other_ai_commits.csv`, the commits of the tools outside the six, built the same way as `commits.csv`. A collection that read its commit histories before this CSV existed, such as the collection of the March sample, has no such file. The release then includes the CSV with its header alone, and the step logs a warning, so that the release has the same files whichever collection built it. The release also includes `ai_commit_patterns.csv` and `other_ai_commit_patterns.csv` beside `config_path_patterns.csv`, because `matched_heuristics` in each commit CSV names rows of its own heuristics file by id. Without the heuristics file, a reader of the release could not look up what the column names.

#### `planning-documents.csv`

`planning-documents.csv` is `output/planning-documents.csv`, copied unchanged, with `planning_document_patterns.csv` among the provenance files. The section of the README on the file defines a planning document and states that planning documents are not configuration artifacts and are counted in no figure of the configuration artifacts. It also gives the number of repositories that have them and describes each column. The step exits 1 on a `planning_document_patterns.csv` with a SHA-256 other than the SHA-256 that `output/provenance.json` records under `planning_heuristics_sha256`, because the CSV would otherwise be published beside heuristics that did not write it.

#### The records of the collection

The README defines the columns or the fields of each record. These records are copied unchanged, except for the deletion log and the unmatched attributions:

| File | Written by | What a reader finds in it |
|------|------------|---------------------------|
| `ai_commits-repos.csv` | The cloning step, and the commit reclassification for the repositories that it leaves out | For each repository of the collection, whether the commit history was read and how many commits went into each commit CSV. The column `no_signal_shas` holds commit hashes |
| `commit-reclassification.json` | The commit reclassification | The outcome for every repository of the collection and the count of each outcome |
| `unmatched-paths.csv` | `unmatched_paths_report` | The path globs that no heuristic explains, ranked by repositories. A path glob in one repository is below the step's `--min-repos`, so that the list names places that several projects share |
| `unmatched-attributions.csv` | This step, from the full list `all_ai_commits-unmatched.csv` and the commit logs | The attributions in commits that no commit heuristic matched, limited to the lines that name a bot or a tool and no person. An account named for a login can remain, because its form does not separate it from the account of a project. The rule also drops every line that it cannot tell from a person, so the file does not list every bot or tool, and the absence of a name says nothing about the commits. The tracked archive that `unmatched reduce` writes holds the same lines |
| `deletions.csv` | `deleted_files_report` | The rows of the deletion log per reason and repository, the path globs under the repositories that the cleanup removed, and the findings of the assertions of the check ([deletions](../checks/deletions.md#the-csv)) |
| `deletion.csv.7z` | This step, from the `deletion.csv` that the collected file cleanup writes | Every file, empty directory and repository that the cleanup removed, with the reason |

The runner runs the release again when one of them changes. `release` consumes `unmatched_paths_report` and `deleted_files_report`, and the cloning step and the commit reclassification reach it through the collected file cleanup and the detection step.

#### The generated files

`render_citation` writes `CITATION.cff` from `CITATION_TITLE`, `CITATION_AUTHORS`, `CITATION_LICENSE` and the version that `provenance.json` records. `CITATION_AUTHORS` lists the authors of this release in the order of its Zenodo deposit and of the MSR 2027 data showcase paper that describes it, and the Citation section of the README cites the release with the same authors, title and version. The AIware 2026 dataset paper, which described AgentConfigs 1.0.0, has other authors in another order.

`render_readme` writes `0_README.md` with these parts:

- the overview table from the `CSVs` entries, with the row counts that this run measured
- the provenance table from the `provenance` entries
- the withheld list from `WITHHELD`, followed by the statement that the release publishes none of the other files of `output/`, which `OUTPUT_INVENTORY` names
- the archive table with sizes, and the file count of the archive of collected files, read from the last summary line of `7zz l`, which ends in `N files, M folders`, or in `N files` alone for an archive without folders
- the provenance counts, read off the published rows: the rows, the rows with a label, the engineered projects and the repositories that the collection scanned, with the rows without a label counted by the reason that `repos_excluded.csv` gives. With rows of that file under the reason `copy`, the README counts the engineered projects among the rows with a label
- the definitions of the columns and fields of the negatives, of the record of the documentation watch and of the records of the collection, under File Descriptions
- the Citation section, which cites the release as `CITATION.cff` does
- the usage examples, which read `engineered_project` as text. pandas reads a column that holds `true` and `false` alone as booleans, as in a release without the label `unclear`, and a comparison with the string `"true"` would then select no row

Every sentence that states a count agrees with it in number, with the singular for a count of 1 (`by_number`). This holds in the description of the levels, in the archive table and in every evidence limit, which `evidence_limits` writes.

The README takes from `collection.counts` of `output/snapshot.json` the number of repositories in the sample that were cloned and scanned and the number that git could not clone. `collection_counts` reads them before anything is written, with the outcome `missing_tree` of the `commit_reclassification` section of the snapshot: a cloned repository with a per-repository commit record and no directory in the collected tree, from which the detection step read no file. The number of repositories that were cloned and scanned is not the count of the detection. It is every repository in the sample that git could clone, less the repositories without their collected tree, which the README states separately.

The opening of the README states where the repositories of the release come from and when they were scanned (`origin_sentence`): the GHS retrieval and the end date of the sampling window that `sampling.json` records, and the `scanned_at_window` of the snapshot. A sampling frame without a retrieval id, such as the sampling frame of March 2026, is named by the day on which its GHS search result was downloaded. The opening then states that this dataset succeeds AgentConfigs, the dataset that the AIware 2026 dataset paper describes, and that an earlier version of the pipeline built AgentConfigs 1.0.0. It points to the documents of the pipeline at `PIPELINE_REPOSITORY` for how this release was built. The earlier version of the pipeline differed in how it sampled, classified and collected the repositories and in how it attributed the commits, and a README that called the paper the description of this release would give a reader the method of that version. The Associated Papers section of the README lists the AIware 2026 dataset paper first, with its own authors, `AIWARE_DATASET_PAPER_AUTHORS`, and states that it describes AgentConfigs 1.0.0. It cites each paper with the venue and the DOI that its Crossref record gives. In the README, the tool flags name the tool rather than one of its programs, because files that Copilot in VS Code also reads set `copilot`, and files of the Codex app set `codex`.

The README lists what the filter of the sampling stage removed from the GHS retrieval, one item for each step that `sampling.json` records with a `removed` count above 0, in the order of the steps, and points to `sampling.json` for the counts (`filter_removals`). `FILTER_STEP_REMOVALS` gives the words for a step by its key, and the items of `cleanup`, `licenses`, `languages` and `activity` name the flags, the number of allowed licenses, the kept languages and the thresholds that the values of the step record. The item of `duplicates` also names the rows of a name that GitHub resolved to two repositories when the step counts such names under `shared_names`. The kept languages are the `languages` of the values of the step `languages` (`kept_languages`). The filter keeps the most common languages of each retrieval, so the list can differ between releases, and the filter's steps and parameters can differ too. A list written in this script would describe one sampling frame in the README of every release. A step without a key, such as each step of the sampling frame of March 2026, or with a key that `FILTER_STEP_REMOVALS` lacks is named by the description that the filter recorded for it. `FILTER_STEP_REMOVALS` also contains `mirrors`, the key of a step that the current filter lacks and that the sampling frame of the development dataset records ([filter](../../1_sampling/filter-ghs-spec.md)).

The filter's step `languages` ranks only the languages that the end date of the sampling window covers. It records under `left_out` each language that it passed over because the end date left it out, with the crawl date of the language or null (`1_sampling/filter-ghs-spec.md`). The sampling frame contains none of the repositories of such a language, which the list of kept languages does not show. The README therefore names each such language among its evidence limits, with its crawl date, the end date and the number of languages that the step keeps (`left_out_languages`, `left_out_limit`). For a sampling frame without such a language or without the record, such as the sampling frame of March 2026, it states no such limit.

The README gives `7z x -snld` for `repos_data.7z`, for the links that the key decisions above describe. The `7z` of p7zip keeps such links and refuses the switch, and the README gives p7zip users the command without the switch. It gives `7z x <archive>` for `repos.csv.7z`, `commits.csv.7z`, `imported_files.7z` and `deletion.csv.7z`. `build_imported_archive` copies each imported file with `shutil.copy2`, which copies the file that a link leads to, and `imported_files.7z` therefore contains no link.

`compress` runs 7zz in `release/` and passes it the bare file names, because 7zz stores a relative path as it is given. A relative `--release-dir` would put `release/repos.csv` inside `repos.csv.7z`. The deletion log lies outside `release/`, and `compress` gets its absolute path, which 7zz stores under the bare name.

`render_checksums` writes `checksums.sha256` over every other release file, sorted by name, in the format that `sha256sum -c` reads.

### Output

The step writes `release/`, one file per entry of `RELEASE_FILES`. Two runs over the same inputs write byte-identical CSV and JSON files and byte-identical compressions, `imported_files.7z` included, and therefore the same manifest. `repos_data.7z` belongs to the collected_files_archive step, which packs the same bytes over the same validated tree, and it changes when that tree changes.

## Current input archives

A commit CSV can be a plain CSV, an unsplit `.7z` archive or a set of numbered volumes. When a commit CSV is absent, the step reads its tracked archive through `commits_source`, and `agentcontext.csv_archive` selects `.7z.001` when it is present. The archive of the commits of the six tools is split into numbered volumes, and `other_ai_commits.csv.7z` is unsplit. 7-Zip requires every volume, and the step fails when a volume is absent. Both commit CSVs go through this reader, and an archived CSV of the other tools therefore cannot become an empty release CSV only because nobody extracted it. The step extracts into a temporary directory ([dataset storage](../dataset.md#storage-and-regeneration)), and the output inventory accepts numbered volumes. `commit-reclassification.json` records how far a development reclassification reached. That record does not replace validated commit classifications.

The runner regenerates the snapshot before the publication. A development release built from incomplete archived commit evidence must state that limitation in its provenance and must not be presented as fully reclassified.

The generated README derives a section on the evidence limits from `snapshot.json`. The section follows the limit of a sampling frame from a GHS download that fell back or that took a smaller retrieval with `--accept-smaller` ([`sampling.json`](#samplingjson)), and it states:

- an incomplete commit reclassification, explicitly, with the number of repositories for each incomplete outcome (`RECLASSIFICATION_GAPS`), such as missing commit logs or commit histories that the cloning step could not fetch or read. It counts only the repositories in `output/repos.csv`, the clone failures and the repositories without their collected tree (`missing_tree`). The limit of each outcome ends with the names of its repositories, which the `repositories` of the `commit_reclassification` section of the snapshot lists by outcome (`named_repositories`). `output/repos.csv` lists these repositories among the configured repositories without marking them, and without their names a reader could not leave them out of a count of AI commits per repository. `collection_counts` refuses a snapshot that names fewer or more repositories than it counts for an outcome with a limit (`LIMITED_OUTCOMES`). The first sentence of these limits states that every commit in `commits.csv` and `other_commits.csv` was classified with the current commit heuristics. The commit reclassification leaves out of the commit CSVs every shard that other commit heuristics classified (`commit_reclassification.left_out_shards`), and `consistency_problems` refuses a snapshot that records a classification under other commit heuristics
- in the limit of each incomplete outcome, the number of its repositories in `output/repos.csv` with commits that the commit reclassification left out of the commit CSVs, from `left_out` in the `commit_reclassification` section of the snapshot, which counts these repositories by outcome (`gap_limit`). Neither `commits.csv` nor `other_commits.csv` contains any of their commits, while the count of an outcome covers only the missing evidence. A limit of their own would name these repositories a second time, and a reader would add the two counts. A repository without a row, such as a repository without its collected tree, is counted under its outcome alone. The README therefore names each repository in one limit. A repository without a per-repository commit record (`missing_record`) has no shard, and none of its commits is published. The limit of `missing_record` states this for every such repository (`gap_limit`).
- when `population_complete` is false, the number of repositories with a recorded clone or collection failure, with their names
- the rows of `context_files.csv` with blank AI columns and the number of their repositories, which `publish` counts in the published CSV. The detection step leaves the AI columns of a context file blank where `ai_authorship.csv` has no row for the file at its commit, such as for a file in a repository with commits that the commit reclassification could not classify again under the current commit heuristics. A reader who converts `first_commit_ai_created` with `str(v).upper() == "TRUE"` would count a blank value as `FALSE`. The descriptions of `first_commit_ai_created` and `#ai_commits` say that the value can be blank
- missing commit metadata of configuration artifacts, as a count of the rows of the published mechanism CSVs without `other.csv`, which the release withholds. The count covers the rows with a history that was not read, and the rows with a `created_at` or `head_commit_date` that the collection left blank because git printed a date that does not parse, such as for a commit of the year 10000 (`rows_without_commit_metadata`, [snapshot](../checks/snapshot.md))
- the rows of `planning-documents.csv` with missing commit metadata, counted apart from the snapshot's `planning_documents` section, because planning documents are not configuration artifacts
- from the published CSVs, the repositories in `repos.csv` with a blank `head_commit_date` ([`repos.csv`](#reposcsv)) and the commits in `commits.csv` and `other_commits.csv` with a blank `commit_timestamp` ([`commits.csv`](#commitscsv))
- the rows of the GHS retrieval that the filter's step `gone` removed because the GitHub query got no response for them in any round, the `unresolved` of the values of that step in `sampling.json`. The step runs before the other steps of the filter, and the README states that the count includes rows that those steps would have removed. The count is therefore not the number of repositories that the sampling frame lost. `sampling.json` records only the count, and the README cannot count the rows that would have passed the other steps. A sampling frame without the step, such as the sampling frame of March 2026, states no such limit
- the rows that the same step removed because GitHub found their repositories without an id, the `without_id` of the values of that step (`rows_without_id`), with the same remark on the other steps, because GitHub has these repositories and the sampling frame leaves them out. A sampling frame without the count states no such limit
- the languages that the filter's step `languages` left out because the end date of the sampling window does not cover them, the `left_out` of the values of that step ([The generated files](#the-generated-files))
- the repositories in the sampling frame that the classification left without a decision after its retry rounds and, where the second model applied, after the second model, which the record of the classification, `repos_annotated.json`, counts as `undecided`, because they are not in the sample. The second model labels only some of them, and the sentence of `second_model_failures` names those that it left without a decision. A record without the count states no such limit

A successful build alone does not establish that the commit classifications have been validated against the current heuristics.

In the code, the joined population of repositories is called `sampling_frame`, because it is the sampling frame, a larger population than the classified sample and the configured repositories.
