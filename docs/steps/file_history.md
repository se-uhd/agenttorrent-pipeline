# File history: the git columns missing after detection

## Context

The mechanism CSVs from `agentcontext/steps/detection.py` identify the configuration artifacts in each repository. Their <!--s:parameters.agentcontext.heuristics.HISTORY_COLUMNS:words-->four<!--/s--> history columns give each file's creation date, commit count, and first and last commits. Detection clones nothing; it joins these values from `file_history.csv`, which the cloning step fills before deleting each clone. For a sample collected in one pass, the file history step has nothing left to measure. The file history step measures the rest: a tree that arrived without a cache, a repository with a history that could not be read the first time, or a handover with incomplete history records. Each repair costs a clone per repository, and its result never changes, because the history of a commit is fixed.

The scripts that this step replaces did not treat the result as fixed. They cloned the same repositories more than once to read the same history, and each wrote the result into a CSV rather than caching it. `4_add_git_data.py` cloned every repository and read every file at whatever HEAD it found. Its output was copied by hand into `output/cached/` so that `_sync_extended_csvs.py` could reconcile it against the current CSVs and clone again for the new rows. `_fix_extended_blanks.py` then cloned a third time for whatever the second pass had left blank. `4_add_git_data_consolidated.py` combined the sequence into one pass. It removed the copying by hand but not the repeated clones, because it still measured every row again on every run.

This step reads `file_history.csv` instead. It keys every measurement on `(repo_name, head_sha, mechanism, artifact)` and writes it back. A measured row is never measured again, and a run over a sample that the cache already covers makes no network request at all. A row that this step measures goes into the cache and, in place, into the CSV that the detection step wrote. The row's <!--s:parameters.agentcontext.heuristics.AI_COLUMNS:words-->four<!--/s--> AI columns go into `ai_authorship.csv` and `context-files.csv` as well, because they are derived from the same commits as the git columns. A file with a history that the cloning step could not read has both sets of columns blank, and no other step clones for it.

The step fills `output/planning-documents.csv` the same way. Its rows go into `file_history.csv` under the key `planning_document`, in the column that holds the mechanism for the mechanism CSVs (`HISTORY_TABLES`), and the step measures the planning documents of a repository in the same clone as its configuration artifacts. The step writes no second CSV beside each `output/<mech>.csv`, such as the `output/<mech>-extended.csv` of the replaced scripts, because a second CSV would mean two writers, two line terminators and two key sets to keep consistent.

With `--offline`, the step fetches nothing and exits 1 when the cache cannot fill a row, with the number of such rows and the CSVs that contain them. In a checkout without credentials, such a run shows whether the CSVs are complete, and with the committed cache it rewrites every output CSV byte-identically.

## Key decisions

- **Language:** Python 3.14 (`agentcontext/steps/file_history.py`, with `history.py` for all the code that runs git, `caches.py` for the cache, `heuristics.py` for the mechanism CSVs and their headers, and `repos.py` for the `owner§repo` naming, where `history.py` clones through `auth.py` and `bounds.py`), with no third-party packages. This step opens no configuration artifact. `language` belongs to the detection step, which reads it from `data/validated/`, and `is_empty` is not published at all
- **The cache is the only source of the values of a row that an earlier collection measured, because the measurement cannot be repeated.** Such a measurement can contain a `created_at` later than the head commit date, and checking out `head_sha` does not reproduce it. `#commits` counts the union of the <!--s:parameters.agentcontext.git.history.PATH_QUERIES:words-->three<!--/s--> `git log` queries over the path, including the query over every ref of the clone (`--all`). The `--all` query reaches the tip of the cloned branch rather than `head_sha`, and a clone made after the collection can count more commits than the collection did
- **New measurements require the collected commit and complete history.** `head_sha` must be a complete commit hash, and the checkout must resolve and verify that commit. When the revision is unavailable, the measurement returns `revision_unavailable`. When the history fetch fails or its result is indeterminate, it returns `bound_exceeded` if the time bound or the size bound stopped fetching the history, and `git_unavailable` otherwise. None of these outcomes adds entries to the history cache or the AI-authorship cache, and none prunes the repository. Dates and branch tips cannot substitute for the collected commit
- **This step fills the git columns of the output CSVs and the AI columns of `context-files.csv`, and removes the rows of a repository that it prunes.** It fills the <!--s:parameters.agentcontext.heuristics.HISTORY_COLUMNS:words-->four<!--/s--> git columns, joins the AI columns from `ai_authorship.csv` ([Sources of the columns](#sources-of-the-columns)), and prunes as the bullet on pruning below describes. Every other column belongs to the detection step and stays as it was read, and a CSV with nothing to measure is written back with the same bytes. `plan_table` checks every mechanism CSV before any CSV is written and rejects a header that lacks a column that the lookup reads. An exception inside the loop that writes the CSVs would leave the CSVs that the loop reached rewritten and the rest unchanged, an output that is neither the old one nor the new one. After the CSVs are written, `verify_tables` compares each header against `heuristics.csv_header` and fails the run when a header is not what the heuristics declare
- **The caches keep the rows of the current collection.** This step is the last step of a run that writes `file_history.csv` and `ai_authorship.csv`. Before it plans the first CSV, it removes from both caches every row at a head that is in neither the collected list (`--collected-csv`) nor the validated list (`current_heads`, `retain_heads`). No step reads a row at a head that a repository has moved past, because the next collection takes a repository over only at the head that the collected list names. If the caches kept such rows, the tracked caches would grow with every collection. [Collection caches](../caches.md#the-rows-that-the-two-caches-keep) gives the reason for each case
- **No pandas.** `_sync_extended_csvs.py` read the mechanism CSVs with the default NA handling of pandas, which turns the string `n/a` into NaN. The subagents rows with `memory` set to `n/a` were therefore published blank. The CSV reader of the standard library has no list of such strings
- **No reordered columns.** `_output_columns` in the script that this step replaces moved `repo_name` and the configuration-file column to the front for every mechanism but `other`, and no published CSV has those columns first. This step composes no header. It writes back the columns that it read, which are the columns that the heuristics declare
- **One line terminator, LF.** Every writer of the pipeline ends its lines with LF, the detection step and this step among them, so that the rewrite of a CSV changes only the rows that changed
- **Pruning with deletion, once per run:** When git fails the clone of a repository with "repository not found", "does not appear to be a git repository" or one of GitHub's two closure messages, "Repository unavailable due to DMCA takedown." and "Access to this repository has been disabled by GitHub staff.", the step removes the repository's rows from every output CSV and its directory from `data/validated/`. The runner's step list declares this deletion with `mutates=("collected_file_cleanup",)`. A repository that is gone is a fact about the repository, not about the CSV that missed the cache. No clone runs for the output CSVs that the cache fills, and pruning only the CSVs with cache misses would leave the other CSVs with rows for a repository after the run had deleted its directory from the validated tree. Only `collected_file_cleanup` restores the directory, by deriving `data/validated/` again from the unchanged collected tree
- **A failure of the run is not a finding about the repository.** A clone stopped by a timeout, a size bound or a network failure leaves the row with what the last run published, and only a repository that is gone leads to pruning. A recorded branch that no longer exists does not prune the repository, because the clone falls back to the default branch, and a collected commit that the branch does not reach is `revision_unavailable`. git's "Remote branch ... not found in upstream origin" is therefore not among the phrases read as gone. The same distinction applies to each query over a path. `GitFileMetadata` returns a falsy default when a `git log` raises, and that default cannot be distinguished from "this file has no history". The step compares the two failure counters before and after every configuration artifact, and it leaves a row measured through a failed query blank rather than recording `0` commits. The repository's outcome is then `git_unavailable`, so that the step measures it again

## `agentcontext/steps/file_history.py`

### Architecture

#### Sources of the columns

| Columns | Source |
|---|---|
| everything else in the CSV | `output/<mech>.csv`, verbatim, as this step read it |
| `created_at`, `#commits`, `first_commit_sha`, `last_commit_sha` | the cache, or a clone on a cache miss |
| `first_commit_ai_created`, `first_commit_ai_tool`, `#ai_commits`, `ai_commit_tools`, in `context-files.csv` | `ai_authorship.csv`, filled by the same clone on a cache miss, or as the detection step wrote them where `ai_authorship.csv` has no row |

`FILLED_COLUMNS` is `heuristics.HISTORY_COLUMNS`, the <!--s:parameters.agentcontext.heuristics.HISTORY_COLUMNS:words-->four<!--/s--> git columns. This step joins the <!--s:parameters.agentcontext.heuristics.AI_COLUMNS:words-->four<!--/s--> AI columns from `ai_authorship.csv` as the detection step joins them, and an offline run over the committed caches reproduces them byte for byte. `record_ai_authorship` adds the rows of every file that this run measured, through `ai_authorship_from` over the commits that `measure_repo` returns. Without these rows, a file with a history that the cloning step could not read, as in `microsoft/windows-rs` in the collection of September 2026, would be published with the git columns that this step measured and blank AI columns, because no other step writes them. `language`, `line_count`, `is_reference` and `referenced_file` belong to the detection step, which reads them from `data/validated/`.

#### The lookup

`_plan_misses` splits the rows of a CSV into the rows that the cache fills and the rows that the step has to fetch. The step looks a row up as the detection step does (`detection.preferred_facts`): first the cloning step's complete row of the path at the commit, then the row for the mechanism. The cloning step writes only complete rows, and this step measures a row only where the cache has none for the commit. Where both rows exist, the cloning step's row is therefore the later measurement, and this step removes the other row before it plans (`without_superseded`). A row for the mechanism that took precedence over the cloning step's later row published `created_at` values that the commit named by the row's own `first_commit_sha` does not have. Where both lookups miss, `FileHistoryCache.for_artifact` returns the entry of the same `(repository, commit, path)` under any other mechanism, because a path that a heuristic reclassifies keeps its history. The heuristics of AgentTorrent 1.0.0 reclassified rows into other mechanisms. `for_artifact` returns nothing where two mechanisms recorded different values, the case for which `mechanism` is part of the key.

#### Measuring

`history.py` contains all the code that runs git:

- `GitFileMetadata`
- the clone and its retries
- `read_artifact_history`, which lists every commit that touched one path
- `measure_artifact`, which derives the <!--s:parameters.agentcontext.heuristics.HISTORY_COLUMNS:words-->four<!--/s--> git columns from that history
- `measure_repo`, for a repository that this step has to clone itself
- `_failures`, which distinguishes a command that raised from a command that returned a result

The code is a module of its own rather than a section of this step, because the cloning step clones the same repositories and reads the same history from the clone that it already has.

The clone is partial (`--filter=blob:none`). It falls back to a full clone only when git reports that the server refused the filter (`clone.is_filter_unsupported`), and to the default branch only when the recorded branch is gone. After any other failure, such as an early EOF, the step tries the partial clone again after the backoff. A full clone would fetch every version of every file and could reach the size bound or the time bound, which end the retries.

Reading the history of a path takes <!--s:parameters.agentcontext.git.history.PATH_QUERIES:words-->three<!--/s--> `git log` queries, each read oldest first:

- with `--follow` up to the checkout, where the first record is the commit that created the file under whatever name it had then, with its date. Where a commit deleted the path and a later commit added it again as a copy of another file, the query with `--follow` stops at that copy, and the creation commit is the first commit of the query without `--follow`, which lists the path before the deletion ([git](../git.md#the-git-client))
- without `--follow` up to the checkout, where the last record is `last_commit_sha`
- with `--all` over every ref of the clone

Because the clone is `--single-branch`, its refs are the recorded branch, or the default branch where the recorded branch is gone, and the tags that point into its history. `#commits` counts the union of the <!--s:parameters.agentcontext.git.history.PATH_QUERIES:words-->three<!--/s--> queries: every commit of that branch that touched the file under any of its names, and no commit of another branch. Every other column keeps the bound of its own query. A commit that the branch gained after the recorded commit therefore enters the count and no other column. The same records give the <!--s:parameters.agentcontext.heuristics.AI_COLUMNS:words-->four<!--/s--> AI columns of `context-files.csv`, through `ai_authorship_from` in `agentcontext/commits.py`.

`build_all` plans every mechanism CSV, measures the missing rows grouped by repository, and writes the results. Grouping the rows by repository avoids a second clone of a repository with configuration artifacts in several mechanisms.

`measure_repo` clones a repository once, requires complete history, verifies the collected commit through `_checkout`, initializes only the requested submodules and reads the missing configuration artifacts. A submodule's history must also be complete before the step measures the submodule's paths. `measure_repo` compares `_failures` before and after the setup and before and after each configuration artifact. A submodule fetch that timed out or a history query that raised therefore leaves the row blank rather than recording a value. `measure_missing` returns the error per repository, so that a later CSV with a row of the same repository still missing does not start the <!--s:parameters.agentcontext.git.history.CLONE_RETRIES:words-->three<!--/s--> clone attempts again. Each measurement goes into the cache under every mechanism that requested it. The step saves both caches at these points:

- once it has measured, before it removes the repositories that git reports as gone, because a stop or a removal that fails can end the step there
- after it writes each CSV
- when the run stops on an exception, including a stop during the first save

It saves `ai_authorship.csv` first. A row of `file_history.csv` without its AI row would leave the AI columns of the path blank until the next collection of the repository, because a later run finds the git row and does not measure the path. A missing git row, in contrast, makes the next run measure the path again and write both rows.

`fill_table` takes `plan` and `attempted` from that pass. When the tests call it without them for one CSV, it plans and measures on its own. It writes the CSV back through a temporary file and one `os.replace`, with the terminator that the file already had and the row order that the detection step gave it. The step syncs the temporary file before it renames the file and the directory after it renames the file, as `write_retained` does for the commit CSVs. This step rewrites the detection step's CSVs before the runner records this step. If a power loss came after the new name reached the disk and before the data did, the CSV would be empty. The step would fail to read that CSV in every later run, while the runner keeps the detection step recorded as complete.

### Output

The step writes these files:

- `output/<mech>.csv`, one per mechanism, with the git columns filled for every row that the cache or this run filled, the AI columns of `context-files.csv` filled wherever `ai_authorship.csv` has them, and every other column as it was read
- `file_history.csv` (`--cache`) and `ai_authorship.csv` (`--ai-authorship`), with the rows that the run measured, and without the rows at a head that is in neither the collected list nor the validated list. Both default to the directory above `--output-dir`, as `--validated-dir` and `--collected-csv` do, and that directory is the stage directory when `--output-dir` is not given. If the stage's caches were the default, a run over a scratch output directory would write its measurements into the tracked caches
- `output/repos.csv`, derived again from the CSVs after pruning: the mechanism flags from which CSVs still contain a row of the repository, the file flags from its context files through the detection step's `file_flags_of`, and the tool flags as the union of the `tool` column of its rows, which the detection step wrote from the tree. A repository with no row left is dropped

Computed from the paths and the validated tree instead, the tools of a workflow would be wrong: The path lookup gives the tool of the last `workflow_uses:` row for all of `.github/workflows`, whatever action a workflow runs. Reading the `tool` column keeps the flags equal to the tools of the rows, which `output_cross_check` checks.

The step logs a table with a row for each CSV: its mechanism, or `planning_document`, its rows, the rows that the run fetched, the rows that it pruned and the rows without a history. The first column is as wide as its longest name, so that the counts of every row stand under their headers.

## Error handling & edge cases

| Scenario | Behavior |
|---|---|
| The row is in the cache | Written from the cache, without a clone |
| The row is in the cache under another mechanism, and the mechanisms agree | Written from the cache, without a clone |
| The row is in the cache under two mechanisms that disagree | Fetched, because there is no single value |
| The row is not in the cache and `--offline` is set | The run stops, naming the number of rows and the CSVs that contain them, and no CSV is written |
| The row is not in the cache and `--offline-except` names its repository | Fetched, and every other row missing from the cache stops the run as under `--offline`. The subsample run passes the repository for which it made the cloning step's history fetch fail. This step then measures the rows of that repository alone, and a cloning step that stopped measuring still stops the run |
| The row is recorded with blank values | Fetched again, unless `--keep-blank` or `--offline` is set |
| A retry of blank rows finds the repository gone | The rows stay as they were, and the repository stays in the sample. Pruning it would take a repository out of a sample collected when it existed, which is not the purpose of a retry. A repository with rows that missed the cache is pruned as below |
| The recorded commit is missing, invalid or cannot be checked out | `revision_unavailable`, with the repository and the requested revision in the log. Rows and previous measurements remain, and neither cache receives a new measurement |
| Full history could not be established | `bound_exceeded` when the time bound or the size bound stopped fetching the history, and `git_unavailable` otherwise, even if Git failed without raising an exception. No path measurement starts |
| The clone times out, exceeds the size bound, or fails on the network | The rows keep what the last run published, and the summary counts them in its `no history` column. After the time bound or the size bound stopped a clone, the step does not attempt it again in the run, because every attempt runs under the same bounds. It attempts a clone that failed otherwise up to <!--s:parameters.agentcontext.git.history.CLONE_RETRIES:words-->three<!--/s--> times |
| A `git log` raises, or exits non-zero, rather than returning a result | The step leaves that configuration artifact's row blank and logs it, rather than recording `0` commits or <!--s:parameters.agentcontext.heuristics.HISTORY_COLUMNS:words-->four<!--/s--> blanks. A non-zero exit does not count as an empty history, because on a blobless clone that exit means that the blob fetch that `--follow` needs failed on the network |
| A worker raises | Logged, and the repository's rows keep what the last run published, as for a timeout. The failure of one repository does not end the run |
| Git identifies the repository as gone: not found, no repository at the path, or closed by GitHub for a DMCA takedown or by its staff | Its rows are pruned from every output CSV and its directory is removed from `data/validated/`, once per run. A missing branch or collected commit alone does not establish that the repository is gone |
| DSM writes an `@eaDir` into the directory of a gone repository while the step removes it | Removed with the directory (`paths.remove_tree`), and the step goes on. A removal with `shutil.rmtree` would fail with ENOTEMPTY and end the step with exit 1 after its clones |
| A path is inside a submodule | The step requires complete history in that submodule, and the submodule's checkout remains the commit that the parent pins. When fetching the full history fails, no path is measured |
| A CSV is missing `repo_name`, its configuration-file column, `head_sha`, `head_commit_date` or `branch` | The run stops before any CSV is written and names the columns and the header |
| A `created_at` or `head_commit_date` that is not an ISO 8601 timestamp, such as a date of a damaged repository | Blank in the CSV that the step writes (`to_utc`, through `repos.to_utc_or_blank`). A `WARNING file_history:` line names the CSV, the count, one of the values and every repository, and the step goes on. `file_history.csv` keeps git's text for `created_at`, and its row therefore records a history that was read. A blank there would mark a history that was not read, for which a run clones again and which an offline run refuses. `verify_tables` passes a `created_at` that the run left blank on a measured row, and fails the same blank on any other row |
| A `created_at` or `head_commit_date` with an offset of 24 hours or more, such as `+25:00` | The instant of the commit's epoch seconds, as for any other offset (`repos.utc_instant`) |
| A `created_at` or `head_commit_date` of an instant outside the years 1 to 9999 that `datetime` holds, such as `9999-12-31T23:30:00-01:00`, which git prints for a commit of the year 10000 in the offset `-0100`, or a value with the year 10000, such as `10000-01-01T00:30:00+01:00` | Handled as a value that is not an ISO 8601 timestamp: blank, with the warning, and the step goes on |
| A CSV's header differs from the header that the heuristics declare | Verification fails and the run exits 1, naming both headers |
| A CSV contains only its header | Written back with only its header |
| `file_history.csv` cannot be opened or read | One `ERROR file_history:` line and exit 1, the same as every other input failure |
| The collected list or the validated list is absent | One `ERROR file_history:` line that names the list and the step that writes it, and exit 1, before any cache or CSV changes. Without the list, the step cannot tell which rows of the caches a later step reads |
| The collected list or the validated list lacks `repo_name` or `head_sha` | `ValueError` naming the list and its header, and exit 1, before any cache or CSV changes |
| A cache has rows at a head that is in neither list | Removed before the first CSV is planned, and the first save writes the caches without them, also in a run that measures nothing |
| A mechanism CSV without a `tool` column, from a dataset version before the column existed | `ValueError` naming the CSV, exit 1. Without the column, every tool flag would be rewritten to FALSE |
| A `tool` value that the detection step cannot write, such as a blank, an unknown tool or `cursor\|claude` out of column order | `ValueError` naming the CSV, the repository and the path, exit 1 |
| `output/repos.csv` with a header that lacks a flag that the rebuild computes | `ValueError` naming the flag, exit 1. The writer drops a field that the header lacks and would leave the column out silently, and `verify_tables` does not check the header of this file |
| `output/repos.csv` with a row longer than its header | `ValueError` for that row, exit 1 |
| A mechanism CSV with a row longer than its header | `ValueError` naming the CSV and the row, before any CSV is written, exit 1. `write_table` also rejects such a row and a row with a field that no column names, and this check covers the commit CSVs. Without the check, the writer would drop the fields beyond the header's columns, and the run would exit 0 |
| git cannot measure repositories of the pass, `git_unavailable`, as during a spell of failures of GitHub's git service or an outage of the network | `WARNING history:` with git's last line for each clone that failed every attempt. The step saves the caches and measures those repositories again after each pause of `guards.RETRY_PAUSE_SECONDS`, in up to `guards.RETRY_ROUNDS` rounds, as the cloning step does (`retry_unavailable`). When repositories are still `git_unavailable` and the probe of `guards.PROBE_URL` fails too, the step probes again after each wait of `guards.PROBE_WAITS` (`wait_out_an_outage`), and once the probe responds, it measures those repositories again. When no probe responds, the caches keep what the pass measured, one `ERROR file_history:` line names the outage, and the step exits 4. The runner then does not record the step, and the step measures the rows when the next Start runs it again. With exit 0, the runner would record the step complete, and the release would publish the rows blank. When only the repositories fail, the probe responds, and the rows stay as they are |
| The time bound or the size bound stopped a clone or the fetching of the complete history, `bound_exceeded` | The rows keep what the last run published. The step measures the repository neither in a retry round nor after a wait, because an attempt under the same bounds would be stopped again |
| Ctrl+C or SIGTERM | `main` installs a handler for both signals. The handler cancels the submitted clones rather than awaiting them and kills the running git commands, because the pool runs threads and a worker thread cannot be terminated. It then lets the interruption propagate to the code that saves what the run measured to the cache, and it ends with `os._exit` and the exit code 130. An exception alone would leave the process waiting for a clone until its timeout, `GIT_TIMEOUT_SECONDS` (<!--s:parameters.agentcontext.git.history.GIT_TIMEOUT_SECONDS-->3,600<!--/s--> seconds) |
| Clones that a stopped run left in `--clone-dir` | `os._exit` ends the threads inside `measure_repo` before their `finally` removes their clones. The next run first removes every directory in `--clone-dir` with a name that starts with `history.CLONE_PREFIX` (`file_history_`) and logs their number. It keeps a symbolic link with such a name and every other entry, such as the cloning step's clones. Without `--clone-dir`, the clones are in the interpreter's temporary directory, which other processes share, and the step removes nothing there. The runner passes `--clone-dir` |
| Nothing has to be measured | Every CSV is written back with the same bytes, and the run logs 0 fetched for every mechanism |

The regression suite exercises history failures through `build_all`, the entry point that the step uses. The tests check that an unavailable history keeps the previously published git values, and that a worker exception keeps the rows of its repository while the other repositories finish.

The reconciliation of `output/repos.csv` also restricts `output/all_ai_commits.csv`, `output/other_ai_commits.csv` and `output/planning-documents.csv` to the repositories that the rewritten list contains. A pruned repository therefore loses its commit rows and its planning documents, and so does a repository left with planning documents and no configuration artifact. The step reads that list of repositories from the mechanism CSVs, not from the repositories that this run found gone. Suppose that a run stopped between writing the mechanism CSVs and writing the commit CSVs. If the step pruned the commit CSVs by the repositories found gone, the next run would find no repository gone, and the commit rows would stay. The commit rows that remain keep their columns and values. A missing commit CSV stays absent, and a commit CSV with nothing to drop is not rewritten. The step first removes the temporary files of an earlier rewrite that was killed, also when nothing is dropped, because the release step stops the run at a file in `output/` that its inventory does not list. The step reads and writes the commit CSVs a row at a time (`rows_to_drop`, `write_retained`), with the bytes that `write_table` would write. The CSVs grow with every collection, and in memory with their messages they would take many times their size.

The reconciliation reads the tool attribution that the detection step wrote into each row ([detection.md](detection.md)). Its regression test checks that both steps publish the same tool flags, including for a context file that is also a Copilot MCP file in its own right. It also checks that the flags are the tools of the rows rather than of their paths for an agent workflow, a Copilot plugin's skill and a skill read through a symlink marker.

A repository with both a cached blank row and an uncached row is pruned when its clone is permanently unavailable. A retry of blank rows alone keeps the repository.

The cloning step writes its history rows with an empty mechanism, because it reads the history of a file before the detection step assigns the file to a mechanism CSV. The checks over the current data therefore look such a row up by repository, collected commit and path, as `detection.preferred_facts` does. The step's tests use the lookup described above and verify that an offline run reproduces the current CSVs. A missing history value stays blank, and no value from an earlier release replaces it.

`heuristics.MECHANISM_CSVS` supplies the output filenames and the configuration path columns of the files that this step measures.

## Recovery

| Failure or warning | Recovery and output interpretation |
|---|---|
| `git_unavailable`, `bound_exceeded`, timeout, size limit or failed history query | Read the `history:` lines of the step's log, `run_logs/file_history.log`, for the operation that failed and its cause, such as git's line `Git could not clone <repository> in 3 attempts (...)`. Existing values remain, and a missing measurement does not mean zero commits. Resolve the cause and run `python3 -m agentcontext file-history` again. `--offline` prevents fetching, and `--keep-blank` prevents retrying cached blank measurements |
| `revision_unavailable` | Recover the collected commit in a working copy and retry. A missing commit does not prove that the repository is gone. The step reuses existing nonblank cache values. Review the measurements from earlier images that allowed a fallback checkout before you accept them |
| Permanently unavailable repository | Pruning depends on why the measurement was requested. A missing cache entry can remove the repository's rows and its validated directory, while a retry of cached blank values alone keeps them. Review the logged outcome. An authentication or connectivity failure alone does not prove that the repository was removed permanently |
| An `--offline` run stops on rows that the cache lacks | Restore the matching cache, or run the step without `--offline` in a working copy. The step fails before it writes any output CSV |
| Step interrupted or saving fails | Some CSVs may already have been replaced. Keep the caches and the step log, fix the storage or permission failure, then run `python3 -m agentcontext file-history` again. Do not publish a mixture of partially processed outputs |

To run the step again alone in the working copy, run `python3 -m agentcontext file-history`. To run it again through the runner, pass `--from file_history`, the step key with an underscore. The step reads the validated tree that it prunes. Before the runner runs this step or another step that reads the tree after this step pruned it, the runner runs the collected file cleanup again, also after a run of this step that failed or was stopped. It logs that run of the cleanup in an `INFO runner:` line. The cleanup rebuilds the validated tree from the collected tree before the detection step and this step run again. [The runner](../runner.md#steps-that-modify-an-earlier-steps-output) gives the details.

The recovery of the file history step does not restore a full commit log that is missing. Before you claim complete attribution, check the [commit reclassification](commit_reclassification.md#recovery) separately.
