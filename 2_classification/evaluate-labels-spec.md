# Evaluate the labels against a second model

## Context

`2_evaluate_labels.py` measures how far the classification's labels can be trusted without people labeling the whole sampling frame. A second model, GLM-5.3 by default (`endpoints.SECOND_MODEL`), labels the evaluation sample with the same prompt, tools and README. The evaluation sample is a simple random sample of the repositories that the first model, DeepSeek V4.1 Flash by default, labeled. People review only the repositories that the two models label differently. The prototype of the classification agreed with the batch labels on nearly all repositories (`../docs/history/2026-09-classification-mcp-pilot.md`).

## Key decisions

- **Language:** Python 3.14, with the standard library, `label_cache.py`, `1_classify_repos.py` for the criteria, `readmes.py` for the READMEs of the review, and `agentcontext.logs`
- The second model labels through the classification itself, `1_classify_repos.py --model z-ai/glm-5.3 --repository-list ../data/classification/evaluation/<id>/evaluation_sample.csv`. Its labels are therefore made with the same prompt, tools and README, and the cache of labels keeps them under the second model. The second model is GLM-5.3 on Morph's fp8 endpoint (`endpoints.SECOND_MODEL`), the default of `compare --second-model`. DeepSeek V4.1 Flash summarizes the linked pages for the second model as it does for the first. `compare` reads the labels of both models under the evaluation's classification parameters, which `evaluation_sample.json` records. The second model labels with the settings of its own record, `endpoints.SECOND_MODEL`: reasoning effort high, temperature <!--s:parameters.2_classification.endpoints.SECOND_MODEL_TEMPERATURE-->1.0<!--/s-->, top_p <!--s:parameters.2_classification.endpoints.SECOND_MODEL_TOP_P-->0.95<!--/s-->, seed <!--s:parameters.2_classification.endpoints.SEED-->7<!--/s--> and an output limit of <!--s:parameters.2_classification.endpoints.HIGHER_MAX_OUTPUT_TOKENS-->262,144<!--/s--> tokens. Z.ai's `generation_config.json` sets the temperature and the top_p. The reasoning effort and the seed are those that the maintainer set for both pinned models, and the output limit is that of the attempts of DeepSeek V4.1 Flash at its higher temperature (`HIGHER_MAX_OUTPUT_TOKENS`), the least value that DeepSeek's model card recommends. The parameters name the classifying model with its endpoint and the settings of its requests in the block `classifying_model` (`classify-repos-spec.md`). The parameters of the second model therefore differ from the evaluation's in that block alone. `compare` reads the labels of the second model under the evaluation's parameters with its pinned endpoint and the settings of its requests in that block, the block that `1_classify_repos.py --model <second model>` records without an endpoint or settings on its command line (`second_model_parameters`). Labels of the same model on another endpoint or with other settings, such as another reasoning effort, can be in the same cache of labels. A comparison that took the latest label of the model under any such block would mix the labels of two endpoints, and its record would not show it. `compare` refuses a second model without a pinned endpoint, such as Kimi K3, and records the SHA-256 of the parameters of the compared labels and their block in `agreement.json`. The review page and `draw-check` read the labels of the second model under the recorded parameters (`compared_parameters`), so that they show and choose from the compared labels also after the pinned endpoint or the settings change, and they refuse an `agreement.json` without them. The classification did not always record the classifying model among the parameters. The parameters of the evaluations `2026-10-07T021344Z`, `2026-10-11T060023Z` and `2026-10-28T214115Z`, recorded before it did, name no classifying model, and both models labeled under the same parameters, which are then the parameters of the second model as well. `compare` exits 1 while a repository lacks a label under these parameters. It leaves out a repository with a README that changed between the two labels, because a disagreement on that repository does not come from the models alone. If `compare` took the reference model's labels from its latest finished run, it would compare labels made under two sets of classification parameters after a check of new parameters with that model

- The evaluation sample is drawn from the repositories that the reference model labeled in its latest finished run over the whole sampling frame, under that run's classification parameters, and `evaluation_sample.json` records the run. The draw does not take the latest finished run of any scope, which can be a check over part of the sampling frame. The run has to have labeled the sampling frame that the draw reads, from the same retrieval. The population is the repositories that the run's labels file lists as labeled (`labeled_in`). A repository that the classification excluded before sending it to a model, such as a repository without a README or with a README that the language check found not to be in English, has no label and is not in the population. Neither is a repository that the run excluded, found gone or left without a decision while an earlier run under the same classification parameters labeled it. The second model's run over the evaluation sample would give such a repository no label, and `compare` would exit 1 at every attempt
- The draw leaves out the calibration sample. Its <!--s:calibration.sample_repositories-->2,282<!--/s--> repositories, drawn on 2026-10-05, are the repositories on which the classification's reading rules were measured and set ([the reading rules](0_README.md#the-reading-rules)). A draw of <!--s:evaluation_2026_10_28.sample_size-->1,040<!--/s--> repositories, the size of evaluation `2026-10-28T214115Z`, from the whole sampling frame that the calibration sample was drawn from would contain about <!--s:evaluation.expected_calibration_overlap-->52<!--/s--> of them, and each would test a label on a repository that the rules were fitted to. The draw also leaves out the evaluation sample of every evaluation in `--evaluation-dir` (`default_exclusions`), because the prompt was revised on the reviewed disagreements of each: the evaluations `2026-10-07T021344Z`, `2026-10-11T060023Z` and `2026-10-28T214115Z` and the pilots `2026-10-30T222453Z`, `2026-10-31T094615Z` and `2026-10-31T210357Z`. The prompt was also revised on the check samples of `2026-10-07T021344Z` and `2026-10-11T060023Z`. `--exclude` takes the CSVs with an `id` column that lists the repositories to leave out, in place of the calibration sample and these evaluation samples. `evaluation_sample.json` records each file with its SHA-256, by its path in the repository or else by its name. A file that cannot be read stops the draw. The draw also leaves out every repository in the sampling frame that the prompt names, such as `mrexodia/ida-pro-mcp` and `elizaOS/elizaos.github.io`, with or without `--exclude` (`named_in_prompt`). The prompt names such a repository as an example of how a criterion applies, so an evaluation that drew it would test a label that the prompt states rather than one that the model derives. For the same reason, the draw leaves out every repository whose description, README or other text the prompt quotes, while the prompt contains the passage, whether or not the prompt names the repository (`QUOTED_IN_PROMPT`). The prompt quotes the description of `coreutils/coreutils` and the READMEs of `bcgit/bc-java` and `bcgit/bc-csharp`, for example. Other passages in double quotes quote no single repository, and `QUOTED_FROM_NO_REPOSITORY` records what each of them is. Among them are the profile descriptions of Microsoft, GoogleChromeLabs and KDE, which describe all of the owner's repositories, and the words of the JDK's README, which the repositories of the OpenJDK projects carry as downstreams of `openjdk/jdk`. The draw leaves out no repository for these passages, so that `openjdk/loom`, for example, can be drawn, because such a passage states a rule for every repository that it describes or that writes it rather than how a criterion applies to one repository. A test of `test_evaluate_labels.py` requires every passage in double quotes of the prompt to be in one of the two lists, so that a new quotation in the prompt fails the test until it is decided. `evaluation_sample.json` records the prompt with its path and SHA-256, the number of these repositories and the names of the quoted repositories under the key `named_in_prompt`
- The draw leaves out every repository that the second model labeled in the reference model's run, because the classifying model left it without a decision after the retry rounds and a failed response (`labeled_by_second_model`, `classify-repos-spec.md`). The second model labels the evaluation sample, and it cannot check its own labels. The draw reads the decisions that the labels of the run name, a decision that the run reused from an earlier run included, and records the number and the names of these repositories under the key `labeled_by_second_model` of `evaluation_sample.json`
- The sample size is the size that a proportion needs at the requested margin and confidence in the worst case, corrected for the finite population: n0 = z^2 p (1 - p) / e^2 with p = <!--s:parameters.2_classification.2_evaluate_labels.worst_case_proportion-->0.5<!--/s-->, and n = n0 / (1 + (n0 - 1) / N). At e = <!--s:parameters.2_classification.2_evaluate_labels.MARGIN-->0.03<!--/s--> and <!--s:parameters.2_classification.2_evaluate_labels.CONFIDENCE.percent-->95%<!--/s-->, the size is <!--s:evaluation_2026_10_28.sample_size-->1,040<!--/s--> for the <!--s:evaluation_2026_10_28.population-->40,674<!--/s--> repositories from which evaluation `2026-10-28T214115Z` drew, and its `evaluation_sample.json` records the population, the margin, the confidence and the size
- The draw is reproducible. `evaluation_sample.json` records the seed, which is chosen at random when `--seed` gives none, and the ids of the evaluation sample are sorted
- `agreement.json` contains the agreement with its interval, Cohen's kappa and the whole confusion of the two labels, and the classification parameters of the compared labels of the second model with the block that names its endpoint and the settings of its requests, or null for parameters that name no classifying model. The interval is Wilson's, with z scaled by the finite population correction, sqrt((N - n) / (N - 1))
- The reviewer decides the disagreements in the browser, and `review` writes each decision into `disagreements.csv` as soon as it is made. `review` serves `review_disagreements.html` on 127.0.0.1, so that nothing leaves the machine. For each disagreement, the page shows the repository's GitHub link and the files and the README at the revision that both models read. For each model, it shows the label, the justification, the criteria that applied with the model's own judgment of the evidence of software engineering practices and, when that judgment differs from the label, a sentence stating that a criterion that applies makes the label `false`, the checklist with the facts and the evidence for each criterion, whether the software is maintained and used by others, the purpose with its quotation and, for a quotation from a page's purpose sentence, the page, the model's count of the words of the README by language and whether the classification finds the README mainly English by that count, and the description. It also shows the fork heuristic's verdict with the heuristic's whole result and, for a repository described as a mirror, the merges since the start of the sampling window. A sentence beside each of the two states that the classification decides it after the model's response. Last, the page shows the limits that the decision reached and every tool call with its whole output. The page takes these fields from the decisions under the evaluation's classification parameters in the cache of labels, which are the decisions that `compare` compared. If the page took each model's decisions from its latest finished run, it would show other labels and criteria than the rows that the reviewer decides on, after a check of new parameters. The page renders the README itself, read through GitHub's API at that revision, and shows a README with another blob than the blob that the models labeled with a warning. The sentence on the fork heuristic addresses the reviewer's question of 2026-10-11, why `gpt-6.1-sol` labeled `mrhenry/polyfill-library` `false` with a justification that no exclusion applies
- The reviewer chooses one of the three labels and writes a free-text note. With `false`, the reviewer also selects the criteria of the classification that apply (`CRITERIA` of `1_classify_repos.py`). A review therefore records which criterion a model missed or applied wrongly. Choosing a criterion on the page sets the label to `false`, and the server refuses a criterion with another label. The label, the note and the criteria are written into the CSV through a temporary file, so that a stop never leaves half a review. `compare` keeps the decisions already in the file when it writes the file again
- When a label that both models agreed on contradicts the reviewer's criteria, the reviewer's label replaces it as the expected label. On 2026-10-09, five labels that both models had agreed on under the earlier prompt contradicted the criteria that the reviewer had set since, such as the rule that a repository described as in maintenance mode is `inactive`, and the check counted them as misses. `reviewed_agreements.csv` contains the reviewer's label, criteria and note for each of these repositories, in the columns of the review, and `draw-check` expects the reviewer's label
- When the classification removes a criterion that a reviewer's label applied, the label that the current criteria give replaces it, in `disagreements.csv` with a note that names the removal and as the expected label of `check_sample.csv`. Otherwise `check` would count the label of the current criteria as a miss. The reviewer labeled microsoft/Teams-AdaptiveCards-Mobile `false` in evaluation 2026-10-07T021344Z, because its README calls it "a semi private repo" that accepts no pull requests and issues. That reading was the criterion `closed_to_contributions`, which was removed on 2026-10-31 (`classify-repos-spec.md`), and the label is `true`
- New classification parameters are checked against a reviewed evaluation. `draw-check` chooses every disagreement, with the reviewer's label as the expected label, and a seeded random sample of the repositories that both models agreed on. For an agreed repository, the expected label is the agreed label, or the reviewer's label when `reviewed_agreements.csv` lists the repository. A fork that the reviewer left `unclear` and that the fork heuristic found not independent (`forks.json`) is expected to be `false`. `draw-check` writes the chosen repositories to `check_sample.csv` and the seed to `check_sample.json`. Each model labels the repositories of `check_sample.csv` through the classification under the new parameters, with `--repository-list` set to that file, and `check` compares each model's labels with the expected labels. `check` leaves out a repository that the current sampling frame no longer contains, because no run over that sampling frame labels the repository again, and lists these repositories under `not_in_sampling_frame` in `check.json`. `check.csv` contains one row per repository with each model's label and criteria. Per model and group, `check.json` counts the labels that came out as expected and the changes that the other labels made. A reviewer's `unclear` expects no particular label and is not counted. The agreed repositories show whether the new parameters change labels that nobody disputed, which the disagreements alone cannot show
- `check` exits 1 for a model with a latest finished run under classification parameters that match the evaluation's own in everything but the classifying model, because the labels of that run are the evaluation's own and test no new parameters. Otherwise, it would report the second model's run over the evaluation sample as a check. `check` also exits 1 for a check that leaves out every repository, such as a check over a sampling frame that contains GHS's ids, rather than reporting 0 of 0
- New classification parameters are compared with the current parameters in runs of the same day, not with one earlier run. The reference model labels the check sample in several runs under each set of parameters, on the same day and over the same sampling frame, and the comparison uses the mean number of repositories that the runs label otherwise than expected. One run cannot separate the change from the variation between runs, because the model's label of one input varies from one run to the next, and a run reads the linked pages, the languages of the outline and GitHub's facts when it requests them. `prompt_check_<date>.csv` in the evaluation's directory records every run of such a comparison with its variant and classification parameters
- `check --runs N` makes such runs for one model, its endpoint and its reasoning effort, for a comparison of models: The model labels the check samples of the named evaluations, such as `2026-10-07T021344Z`, `2026-10-11T060023Z` and `2026-10-28T214115Z`, in several runs on the same day. Each run labels the repositories of every named check sample that the sampling frame contains, through `1_classify_repos.py` with `--repository-list`, into a cache of labels of its own, `../data/classification/checks/<date>/<variant>/run-<n>/` (`check_runs`). In one cache, the second run under the same model and classification parameters would reuse every label of the first, and the runs would show no variation. `.gitignore` leaves the caches out, and the records of the runs are tracked. `check_runs` resolves the endpoint of the runs once (`endpoints.endpoint`): A model with a pinned endpoint that the check names without `--provider`, `--quantization` and `--hugging-face-id`, such as GLM-5.3, labels on that endpoint (`endpoints.PINNED`), as in the classification. The runs get the options of the endpoint, and the name of the variant and the columns `provider` and `quantization` of the record name it. The record then shows which endpoint labeled, because the caches that would show it are not tracked, and a check that names the pinned endpoint and one that does not are one variant
- A check measures one model, and every run of `check --runs` passes `--no-second-model` to `1_classify_repos.py`. A repository that the model leaves without a decision after the retry rounds and a failed response stays without a label in the run, and the record counts it under `undecided`, rather than counting a label of the second model as the model's. Every run passes `--no-backup-provider` too, so that a request that the endpoint of the check fails goes to no backup provider, whose labels and summaries the record would count as the endpoint's under the `provider` that it names. The classification parameters are the same with and without the second model, so that the record of a check names the digest of a run of the classification. The runs keep the higher temperature of the model's settings, and a label that the model made at it counts as the model's label in the check. Each row names the higher temperature of its runs under `higher_temperature`, empty for runs without one, such as runs at the endpoint's defaults, and counts the labels of its run made at it under `higher_temperature_labels`, because the variant names only the temperature of the requests before a failed response, and two rows with the same parameters and variant can otherwise hold labels of other temperatures without showing it. A label that the second model of a run made names the run's classifying model as its `model`, and `check`, `compare` and the review read it as no label of that model (`own_label`): `check` then refuses the model for the repository, as for a repository without a label, and `compare` refuses an evaluated model that has only such a label for a repository of the evaluation sample. The commands that label a check sample for `check` pass `--no-second-model` too (`0_README.md`)
- `check --runs N --endpoint-default-temperature` passes the option of the same name of `1_classify_repos.py` to each run, whose requests then send an OpenRouter model neither a temperature, a top_p nor a seed, also after a failed response, so that the endpoint applies its own defaults (`classify-repos-spec.md`). A check then compares the labels at the settings of the model with the labels at the endpoint's defaults. The classification parameters of such runs leave out all three, and the name of its variant ends in `endpoint-default-temperature`. An OpenAI model's requests send none of them in any run, and the check refuses the option for an OpenAI model before a run starts. The runs label at the reasoning effort of the model's settings unless the check names one with `--reasoning-effort`, and the variant and the record name the effort of the runs
- The comparison writes one row per run and evaluation to `prompt_check_<date>.csv` in the evaluation's directory, with the columns of the earlier records, from `variant` to `differing_labels`, followed by the endpoint and the criteria of decision 4 of the decision record, and then by `higher_temperature` and `higher_temperature_labels` (`PROMPT_CHECK_COLUMNS`). The rows of `prompt_check_2026-11-02.csv` of the variants at reasoning effort medium were written by code without a higher temperature, before the record had these two columns, and have `higher_temperature` empty and `higher_temperature_labels` 0. The <!--s:prompt_check_2026_11_02.effort_high.runs-->5<!--/s--> rows of the variant at effort high were written by `check --runs` with the higher temperature: They have `higher_temperature` <!--s:prompt_check_2026_11_02.effort_high.higher_temperature-->1.0<!--/s-->, and their runs labeled <!--s:prompt_check_2026_11_02.effort_high.higher_temperature_labels-->37<!--/s--> repositories at it. `varying_repositories` counts the repositories of the check sample with more than one label among the runs of the variant, which is the spread between the runs. `responses` and `failed_responses` count the responses of the decisions that the run's labels name, over every retry round, and their failed responses, with their `failed_share`. A failed response, as `classify-repos-spec.md` defines it, stopped at the output limit before the model called `submit_classification`, was a final response that did not call `submit_classification` with its schema, or called another tool in a request that offered only `submit_classification`. The records written before the classification took this definition, those of 2026-11-02 included, also counted a round of tool calls with a call that the classification could not read. `undecided` counts the repositories that the run left without a decision, which count as labeled otherwise than expected. `repositories_with_tool_rounds` and `linked_pages` count the decisions with a round of tool calls and the linked pages that they read. They show whether a model reads the pages that the README links to, as `gpt-6-luna` and `gpt-6.1-sol` did in the pilot of 2026-10-30 and none of the open-weight models did. `cost_usd` gives the cost of the runs that made the decisions that the run's labels name, from the cost records of those runs (`costs.cost_record`), and `cost_per_repository_usd` gives that cost divided by the number of repositories that the latest run labeled. A run that a stop, a refusal or the longest wait for credit ended exits the check with its code, and the next check with the same `--check-date` resumes the run. Each check hands every run to the classification, which reuses the decisions under the same model and classification parameters without a request to the model, in a run of its own that decides no repository, and labels again otherwise. The name of a variant leaves out the summary model and the code that the parameters record, so a check of the same date and variant after such a change labels again instead of reporting the labels of the earlier parameters. The record takes the latest finished run and counts once the decision that each of its labels names. It adds the cost of the runs that made those decisions, and for a carried decision the cost of the run that made the original decision, however many runs carried it in between. A run that only reused decisions therefore keeps the responses, the tool use and the cost of the run that made them, a run that carried every label to changed code counts each decision once, and the log names a run that decided no repository (`run_record`). Two checks of one date and variant over different evaluations share the caches of labels, and the cost of the second then includes the cost of the runs that made its reused decisions, also for the repositories of the first. The rows of a variant replace its earlier rows of the same date. A record of the date with a header of the first columns of `PROMPT_CHECK_COLUMNS`, written before the code added the others, gets the missing columns, empty in its earlier rows. A record of the date with other columns, such as `prompt_check_2026-10-29.csv`, is left alone, and the check exits 1 after its runs. Once the record has the columns of `PROMPT_CHECK_COLUMNS`, the check run again with the same `--check-date` reuses the decisions of the runs without a request to the model, while another date labels the check sample again in new caches of labels
- Two checks of the same date and evaluation, such as the runs of two models at once, write the same record, each when its runs end. Each takes an exclusive lock of the lock file beside the record, `prompt_check_<date>.csv.lock`, before it reads the record, and holds it until the new record replaces the old one in one step (`replace_variant_rows`). The second check therefore waits for the first and keeps the rows of the first, and if the new record cannot be written, the old record stays as it was. The kernel releases the lock of a process that dies, and the lock file stays beside the record, untracked
- An evaluation's directory under `../data/classification/evaluation/` is named by the UTC second of its draw, or by the first second after it that no evaluation has. Git tracks `../data/classification/evaluation/`, because the disagreements with the reviewers' labels are the evaluation's result. The directory of an evaluation also holds records that no command of the script writes, such as `probe_runs_2026-10-30/` of evaluation `2026-10-28T214115Z`, which holds the caches of labels of the runs of 2026-10-30 behind the stricter rule of `read_linked_page` and describes them in its `0_README.md`, and `failed_responses_2026-11-02.csv` of the same evaluation, which lists each decision with a failed response that a run of the check of 2026-11-02 names. It was read from the caches of labels of that check, which are not tracked, and it shows which repositories the failed responses of `prompt_check_2026-11-02.csv` came from. `rounds_2026-11-02.csv` of the same evaluation records, for `IBM/ansible-storage-protect` in run `2026-11-02T053902Z`, the requests and the output tokens of each round of the run, which the decision does not record, as the differences between the progress lines of the run's log before and after the round, with both lines as the log wrote them

### Function structure

**`sample_size(population, margin, confidence)`**, **`kappa(pairs)`**, **`wilson(successes, n, confidence, population)`**: the statistics

**`sampling_frame_repositories(path)`**, **`latest_labels(cache_dir, model)`**, **`sampling_frame_run(cache_dir, model)`**, **`labeled_in(cache_dir, run)`**, **`labeled_by_second_model(cache_dir, run)`**, **`default_exclusions(evaluation_dir)`**, **`excluded_ids(paths)`**, **`named_in_prompt(repositories, prompt, quoted)`**, **`QUOTED_IN_PROMPT`**, **`QUOTED_FROM_NO_REPOSITORY`**: the inputs that the commands read, the repositories that the second model labeled in the reference model's run, the repositories that the prompt names or quotes, and the passages of the prompt that quote no single repository

**`read_disagreements(out)`**, **`write_disagreements(out, rows)`**: `disagreements.csv`, written whole through a temporary file

**`Review`**, **`github_readme(credentials_path)`**, **`review_server(review, port)`**: the review, that is, the disagreements with both models' decisions, the README at the revision and the reviewer's decisions, and the page with its four requests, `GET /`, `GET /api/items`, `GET /api/readme?id=` and `POST /api/decision`. Unlike the client of an unattended run (`readmes-spec.md`), the review's client for GitHub does not check the configured GitHub access tokens again once GitHub has rejected every one, because a reviewer is waiting for the page, which shows the error at once

**`labels_under(cache_dir, model, parameters)`**, **`second_model_parameters(cache_dir, parameters, model)`**, **`compared_parameters(out, agreement)`**: a model's labels under given classification parameters, matched by their keys, the digests without the provider of a model (`label_cache.ParameterKeys`), so that the labels that any provider served under the same weights, quantization and settings count, the parameters under which the second model labels the evaluation sample with the weights, the quantization and the settings of the requests of its pinned record and without the provider of any model, and the parameters of the compared labels of the second model that `agreement.json` records

**`draw_check(args)`**, **`check(args)`**, **`check_command(args, label)`**: the check of new classification parameters against a reviewed evaluation, for each evaluation that `check` names

**`check_runs(args, label)`**, **`label_check(arguments)`**, **`ENDPOINT_DEFAULT_TEMPERATURE`**, **`variant_name(args, found, effort)`**, **`finished_run(cache_dir, model)`**, **`run_record(cache_dir, row)`**, **`check_counts(rows, labels)`**, **`replace_variant_rows(path, variant, lines)`**, **`CHECK_DIR`**, **`PROMPT_CHECK_COLUMNS`**: the runs of `check --runs`, each through `1_classify_repos.main` into a cache of labels of its own, the part of the name of a variant whose runs send neither a temperature, a top_p nor a seed, the name of their variant, the finished run of a cache, what the comparison reads of it, the counts of the earlier records for one run and evaluation, the rows of a variant written into the record under its lock, where the caches are kept and the columns of the record

**`draw(args)`**, **`compare(args)`**, **`review(args)`**, **`main(argv)`**: the other commands

### Output

`draw` writes `../data/classification/evaluation/<id>/evaluation_sample.csv`, with the columns `id` and `repo_name`, and `evaluation_sample.json`. The JSON file contains the evaluation's id, the retrieval of the sampling frame, the run of the reference model that the sample is drawn from, the reference model and classification parameters, the repositories labeled, the files of repositories left out, the repositories that the prompt names or quotes and those that the second model labeled, how many were left out, the population, the sample size, the margin, the confidence and the seed. `compare` writes `disagreements.csv`, with `id`, `repo_name`, `github_url`, `readme_path`, `readme_sha`, each model's label, the criteria that applied joined with `|`, its justification and tools, and empty `human_label`, `human_criteria` and `human_note`. It also writes `agreement.json`, which contains the models, the classification parameters, under `second_model_parameters` the classification parameters of the compared labels of the second model and under `second_model_endpoint_and_settings` their block `classifying_model`, the repositories compared and agreed on, the agreement and its interval, kappa, the confusion, and the repositories left out because the README changed. `draw-check` writes `check_sample.csv`, with `id`, `repo_name`, `group`, `expected_label` and `expected_criteria`, and `check_sample.json`. That file contains the evaluation, its classification parameters, the two models, the disagreements, the agreed repositories and how many were chosen, the seed, the record of forks and the reviewed agreements. `check` writes `check.csv`, with the columns of `check_sample.csv` followed by each model's label and criteria, and `check.json`. That file contains the evaluation, the classification parameters of `check_sample.json`, the retrieval of the sampling frame and the repositories that the sampling frame no longer contains. Per model, it contains the model's classification parameters and, per group, the repositories, the repositories with a definite expected label, the repositories labeled as expected, and the changes. `check --runs` writes `prompt_check_<date>.csv` in the directory of each evaluation that it names, with the columns of `PROMPT_CHECK_COLUMNS`, one row per run, and keeps the cache of labels of each run under `../data/classification/checks/`.

## Error handling & edge cases

| Scenario | Behavior |
|----------|-----------|
| No finished run of a model in the cache, or none of the reference model over a sampling frame | `SystemExit` with a message that names the model |
| The reference model's latest run over a sampling frame labeled the sampling frame of another retrieval | `ERROR evaluate_labels: ...`, exit 1 |
| No repository in the sampling frame has a label of the reference model | `ERROR evaluate_labels: ...`, exit 1 |
| A repository in the evaluation sample lacks a label of either model under the evaluation's classification parameters, those of the second model on its pinned endpoint with the settings of its requests | `ERROR evaluate_labels: ...`, exit 1, nothing written |
| `compare` with a second model without a pinned endpoint, such as an OpenRouter model outside `endpoints.PINNED` | `ERROR evaluate_labels: <model> has no pinned endpoint, on which the comparison takes the labels of the second model (...).`, exit 1, nothing written |
| `review` or `draw-check` with an `agreement.json` that does not name the classification parameters of the compared labels of the second model | `SystemExit` with a message that names `agreement.json` and says to run `compare` again, and nothing written |
| The README of every repository in the evaluation sample changed between the two labels | `ERROR evaluate_labels: ...`, exit 1 |
| A cache file changed since it was written | `ERROR evaluate_labels: The cache of labels cannot be used, because ...`, exit 1 |
| `review` before `compare` ran, or after a `compare` that found no disagreement | `SystemExit` with a message that names `agreement.json` or `disagreements.csv`, rather than a `FileNotFoundError` with its traceback |
| `review` without a GitHub access token that GitHub accepts | `SystemExit` with a message that names where the GitHub access tokens are read |
| A decision with a label outside the three, or for an id that the file lacks | HTTP 400 with the reason, and the CSV is not written |
| GitHub returns no response for a README | The page shows the error, and the review goes on |
| `draw-check` with an undecided disagreement, or with fewer agreed repositories than requested | `ERROR evaluate_labels: ...`, exit 1 |
| `check` for a model with a latest run that is not finished | `ERROR evaluate_labels: ...`, exit 1, nothing written. Otherwise `check` would report an earlier finished run in its place |
| `check` for a model without a label for every repository of `check_sample.csv` | `ERROR evaluate_labels: ...`, exit 1, nothing written |
| `check` for a model with a latest finished run under the evaluation's classification parameters | `ERROR evaluate_labels: ...`, exit 1, nothing written |
| `check` over a sampling frame that contains no repository of `check_sample.csv` | `ERROR evaluate_labels: ...`, exit 1, nothing written |
| `check --runs` with a run that exits without a finished run, such as after a stop, a refusal or the longest wait for credit | `ERROR evaluate_labels: Run N of <variant> ended with exit C. Run the check again with --check-date <date> to resume it.`, the exit code of the run, and no record written |
| `check --runs` with an OpenRouter model that lacks part of its endpoint and has no pinned endpoint, or an OpenAI model with an endpoint | `ERROR evaluate_labels: ...` with the reason of `endpoints.endpoint`, exit 1, and no run starts |
| `check --runs --endpoint-default-temperature` with an OpenAI model | `ERROR evaluate_labels: ... applies only to an OpenRouter model.`, exit 1, and no run starts |
| `check --runs --endpoint-default-temperature` with `--temperature` or `--seed` | The usage and the error of the command line, exit 2, and no run starts |
| `check --runs` with a record of the date that has other columns | `ERROR evaluate_labels: ... has other columns than the record of a check .... Give the record these columns and run the check again with --check-date <date>, whose runs reuse their decisions without a request to the model`, exit 1, and the record is left as it is |
| `check --runs` with a record of the date that has the first columns of `PROMPT_CHECK_COLUMNS` only | The record gets the missing columns, empty in its earlier rows, and the rows of the runs |

## Known limitations

- Agreement between two models shows how often they decide alike, which is a different question from how often either is right. The reviewers' labels on the disagreements show which model was right there, and nothing shows how often both were wrong together
