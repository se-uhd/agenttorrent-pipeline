# The classification's tools

## Context

`classification_tools.py` is the MCP server with the tools that give the classification model more than the description and the README (`classify-repos-spec.md`). The classification reads `get_issues_and_pull_requests`, `get_repository_metadata` and `get_file_tree` itself before the first request and puts their results in the input, and the model calls `read_linked_page`. The batch classification computed the same context, namely Linguist's output and the linked pages, for every repository before the model saw any of it. The model needed it for few repositories (`../docs/history/2026-09-classification-mcp-pilot.md`). The server applies the [reading rules](0_README.md#the-reading-rules), which were set from measurements over the calibration sample ([the record](../docs/history/2026-10-classification-calibration.md)). The code refers to each rule by its number in that list.

## Key decisions

- **Language:** Python 3.14, in the single script `classification_tools.py`, with `mcp` for the server, `pydantic` for the results, `requests`, `html2text` and `zlib` for a web page, the connection classes of `urllib3`, which `requests` uses, for the deadline, `openai` for the summaries, `readmes.Client` and `agentcontext.github_api.TokenPool` for GitHub's API, and `agentcontext.credentials` for the GitHub access tokens and the OpenAI API key
- The server is a real MCP server over stdio, and any MCP client can therefore reproduce the context that a label was decided on. `mcp_bridge.py` starts the server for the classification (`mcp-bridge-spec.md`), and the classification fills in every parameter except the `url` of a page
- **`get_file_tree(repo_name, revision, max_chars)`** returns an outline of the files from GitHub's API, without a clone (rule 11). It sends two requests. The git trees API lists the tree recursively at the commit at which the README was read, or at `HEAD` without such a commit. The languages API, which takes no commit, returns the languages of the default branch. The outline gives the number of files, directories and submodules, the deepest path and the languages by share. It lists every top-level directory with its number of files and its <!--s:parameters.2_classification.classification_tools.OUTLINE_FILE_TYPES:words-->three<!--/s--> most common file types, the files at the root, and every file that shows a practice that the prompt names (`PRACTICES`): tests, CI, build and packaging, documentation, contribution, changelog and releases, containers and deployment. A contribution guide, a security policy or a governance file counts only when it is a document, that is, a file without an extension or with a document extension such as `.md`, `.rst` or `.txt`. Otherwise, `app/middleware/security.py` of `spoo-me/spoo` and `spaceward/src/pages/Governance.tsx` of `warden-protocol/wardenprotocol` would count as contribution guidelines, as they did in the check sample. The outline states when GitHub listed only part of the tree. Over the calibration sample, a clone for Linguist took up to <!--s:calibration.linguist.max_clone_minutes-->36<!--/s--> minutes and <!--s:calibration.linguist.max_checkout_gb-->4.9<!--/s--> GB, and Linguist's output listed no file that shows a practice
- The outline leaves nothing out (rule 12) unless it is longer than `max_chars`, the number of characters that the classification has left in the request (rule 1). The tool shortens a longer outline by listing the same number of files in each list of files per practice, the largest number that fits, which it finds by bisection, and it ends each list with `and N more`. When no number fits, the tool cuts the outline after `max_chars` characters. `note` states whether the lists were shortened or the outline was cut. A `max_chars` of 0 means no limit
- **`read_linked_page(url, repo_name)`** returns a summary of the page and never its text (rule 10). The summary model, at low reasoning effort, writes the summary with `prompts/page-summary-prompt.md` as the instructions and the page as the input, enclosed as `<page url="...">...</page>`. The prompt contains the repository's name and states that instructions in the page are not instructions to the model. A page over <!--s:parameters.2_classification.classification_tools.MAX_SUMMARY_INPUT_CHARS-->960,000<!--/s--> characters is cut before the summary, so that the summary request stays under the <!--s:parameters.2_classification.1_classify_repos.REQUEST_TOKENS-->272,000<!--/s--> input tokens above which OpenAI charges the long context price for its models, by the estimate of <!--s:parameters.2_classification.1_classify_repos.CHARS_PER_TOKEN-->3.57<!--/s--> characters per token of rule 1. The summary prompt has the summary model end the summary with a line that copies, word for word, the page's own sentence that says what the project is or does, and write none for a page about another project, such as one that the repository is based on, credits or depends on. For a page of GitHub of a repository whose name differs from that of the classified repository, including a page that a web link redirects to, as `git.openjdk.org/jdk/blob/master/doc/building.md` redirects to `github.com/openjdk/jdk` (`page_repository`), the server requests both repositories from GitHub's API. It names the page's repository as `other_repository` only when GitHub returns different ids, because GitHub resolves the earlier name of a renamed or transferred repository to the repository itself (`other_repository`). Without an id for one of them, the server compares the names. The prompt names the kinds of repository that a page can state, among them a read-only copy of another repository, a toy project and software that its author wrote for their own use. The server takes the line that copies the page's sentence, or the label at the end of the summary's last sentence, out of the summary and returns the sentence as `purpose_sentence` only when the page's text contains its words in their order, with at least <!--s:parameters.2_classification.classification_tools.PURPOSE_MIN_WORDS:words-->three<!--/s--> of them (`purpose_of`, `in_page`). Before it compares the words, it drops the targets of Markdown links, HTML tags, web addresses and soft hyphens from both texts and splits words at underscores, because html2text writes an emphasized word as `_word_` and a README writes links inside its sentences (`_words_of`). A sentence that the summary model changed or made up is left out, and the note says so, because a purpose quoted from the sentence counts as stated (`classify-repos-spec.md`). The result contains the summary's input and output tokens and the model that the API reports, and the input tokens that the API read from and wrote to its prompt cache with the service tier that its response reports, which decide what OpenAI bills for the summary. The request names no service tier, and the project's tier serves it. The classification counts the tokens and the tier for the run's cost record without showing them to the classifying model (`costs-spec.md`). The fields of the result are no classification parameters, because the model is offered the parameters of a tool and not its result
- The summary model is the classifying model, DeepSeek V4.1 Flash on Morph's fp8 endpoint by default (`SUMMARY_MODEL`, `endpoints.PRODUCTION`), at low reasoning effort, the effort of the two pilots of the classification from which the maintainer chose it on 2026-10-31. In the experiment of 2026-10-06, `gpt-6-luna` summarized pages drawn at random from the readable pages of the calibration sample. Every request succeeded, every summary stayed under the length that the prompt requests, and read beside its page, each summary reported the content of the page without its navigation ([rule 10 of the record](../docs/history/2026-10-classification-calibration.md#rule-10-the-model-receives-a-page-as-a-summary-decided), which gives the sample and the cost). No other model was tried on these pages. The summary model, the Hugging Face id of its weights, its quantization and its reasoning effort are classification parameters, and its provider is none (`classification_parameters` in `1_classify_repos.py`, `endpoints-spec.md`). A label is reused only under the same parameters. A run with another summary model therefore labels every repository again
- A summary model that OpenRouter serves is given as an OpenRouter model id with the provider slug of its endpoint, the quantization and the Hugging Face id (`--summary-provider`, `--summary-quantization`, `--summary-hugging-face-id`). The summary request then goes to OpenRouter's Responses API with the provider routing of that endpoint and without fallbacks, and the result names the provider that served it as its service tier, which sets its price in the cost record and which the decision records (`endpoints-spec.md`). The summaries use the first API key of the summary model's service
- `--summary-backup-provider` names the backup provider of an OpenRouter summary model, which serves the same weights in the same quantization (`endpoints.backup_of`), and the classification passes `deepinfra/fp8` for DeepSeek V4.1 Flash unless `--no-backup-provider` is given or the check before the first request found that it serves no summary (`1_classify_repos.backup_for`). The maintainer decided on 2026-11-04 on a backup provider for each model. A summary request that the pinned provider failed for the service after the SDK's retries (`service_failure`), or whose response the service ended (`SummaryEnded`), goes to the backup provider at once, unchanged but for the provider routing, and the backup provider serves every summary from then on, with a `WARNING`. While it serves, one request every <!--s:parameters.2_classification.endpoints.PINNED_CHECK_SECONDS.minutes:words-->ten<!--/s--> minutes tests the pinned provider, and its first response ends the switch, with an `INFO` line (`endpoints.Providers`). A summary has no pause and no attempt of its own, and the failure of the pinned provider would fail the tool call, so the backup provider takes the first failure. A failure of the backup provider fails the summary as a failure of the pinned provider does without it, and so does OpenRouter's refusal of a request because the requests in flight fill their budget (`endpoints.in_flight`), which belongs to the API key and not to the provider. A summary request that tests the pinned provider goes without the retries of the SDK (`endpoints.TEST_RETRIES`). The provider is no classification parameter, and the result names the provider of each summary in its `service_tier`, an existing field of its output schema, which the classification parameters record
- **`get_repository_metadata(repo_name)`** returns what GitHub records about the repository, from `GET /repos/{owner}/{repo}`: its description, homepage, topics, license, whether GitHub marks it as a template repository, which lets others create repositories from it, whether issues are enabled, and its creation and last push. It also returns the profile description of the repository's owner, an organization's `description` from `GET /orgs/{org}` or a user's `bio` from `GET /users/{user}` (`owner_description`), because an owner can describe all of its repositories, as KDE's organization calls each "Official read-only mirror of the KDE project" while `KDE/liquidshell` itself does not. The server keeps each owner's description for the run that it serves, so that the repositories of one owner cost one request for it, and requests it again after a failure other than 404. It returns neither the stars nor the forks, which the classification does not give the model (`classify-repos-spec.md`). The classification sends the description with every README, so that the model sees a missing description. The classification reads the metadata of every repository, and the model reads the template flag and whether issues are disabled there. GitHub's template flag only lets others create repositories from the repository, and owners set it on libraries and applications too. In run `2026-10-10T035814Z`, `gpt-6-luna` applied `example_or_template` to `theimpossibleastronaut/rmw`, `lschoe/mpyc` and `lob/lob-typescript-sdk` because GitHub marks them as templates, while their READMEs describe a utility, multiparty computation software and an SDK. The tool's description and the prompt therefore state what the flag does and that the flag does not make a repository a template. Because the classification fills in the repository, the tool reads only the repository being labeled
- **`get_issues_and_pull_requests(repo_name)`** returns the activity of the repository's issues and pull requests, from one query of GitHub's GraphQL API, which costs one of its points. The activity gives how many pull requests are open, merged and closed without a merge, how many issues are open and closed, and whether issues are enabled. It also lists the issues pinned at the top of the issue tracker, at most <!--s:parameters.2_classification.classification_tools.PINNED_ISSUES:words-->three<!--/s--> on GitHub, and the <!--s:parameters.2_classification.classification_tools.ACTIVITY_ITEMS-->10<!--/s--> most recently updated pull requests and issues, newest first. Each of these has its number, title, link, state, dates, its author's association with the repository, who merged it, and the first <!--s:parameters.2_classification.classification_tools.COMMENT_CHARS-->300<!--/s--> characters of its last comment, after the association of that comment's author. The reviewer of the evaluation of 2026-10-11 proposed a tool for issues and pull requests that the model calls sparingly. The tool returns more than the counts, because the counts alone are misleading. The README of `openssl/openssl` describes the repository as a mirror and invites pull requests on GitHub. The repository closes most of its pull requests without a merge and merges few, while its maintainers review the open pull requests on GitHub ("It needs rebase"). `mlichvar/chrony`, a mirror, closes pull requests with "This was merged with some fixes". The classification reads the activity of every repository before the first request and puts it in the input (`classify-repos-spec.md`), and the prompt instructs the model to read the pinned issues before it decides whether the repository is inactive, moved or a mirror. A pinned issue can state what the README does not, such as issue #676 of `oliviertassinari/react-swipeable-views`, "Deprecate package, do not use". For a mirror, the classification decides from the repository's merges whether the mirror is developed on GitHub (`classify-repos-spec.md`). In run `2026-10-10T035814Z`, this applied to the <!--s:classification_2026_10_10.described_as_mirror-->530<!--/s--> of the <!--s:classification_2026_10_10.model_decisions-->44,286<!--/s--> repositories that `gpt-6-luna` labeled and that were described as mirrors. The counts are not part of the metadata, which comes from the REST API, because the REST API returns them only page by page and does not list the pinned issues. A GraphQL query counts against a rate limit of its own and not against the rate limit of the REST API. The classification fills in the repository and lets the model read an issue or a pull request of the repository with `read_linked_page`, as it reads a link of the README
- `read_linked_page` reads a github.com link through GitHub's API (rule 4): a repository as its README, a `blob` or `raw` link as the file, a `tree` link as the directory's listing, `releases` as the list of releases with tag, date and name, and an `issues` or `pull` link as the issue's repository, number, title, state, author and body. An issue comes with the comments of the repository's owner, members and collaborators on the first page of <!--s:parameters.2_classification.classification_tools.ISSUE_COMMENTS-->100<!--/s--> comments. The text gives the issue's repository, as in "Issue #7 of up/stream", because a README can link to an issue of another repository, such as its upstream, with an owner and members who are not this repository's maintainers. GitHub renders an issue's web page with scripts, and the web page therefore contains no text of the issue. In the evaluation of 2026-10-11, the README of `streamlink/streamlink-twitch-gui` pointed to issue #1045 for its development status, and neither model could read the issue. When the contents API returns a file without content, that is, a file over <!--s:github_api.contents_json_limit_mb-->1<!--/s--> MB, the tool fetches the file again as raw. GitHub returns 404 for a file or a directory at a branch that was renamed, and responds to `GET /repos/{owner}/{repo}/branches/{branch}` with a redirect to the branch's new name. After a 404 at a branch, the tool therefore requests the branch and reads the file once more at the branch that GitHub names (`renamed_branch`). It does not request a commit or `HEAD` as a branch. A README can link a file of its upstream at `master`, which the upstream has since renamed, and a link of the repository being labeled reaches the tool at the README's commit (rule 5). The tool reads no other github.com page, such as a wiki or an account. It also reads no link with a `.` or `..` segment in its path, even when the segment is percent-encoded once or more or separated by backslashes. The HTTP client would resolve such a segment against the segments before it, and `https://github.com/o/r/blob/main/../../../../user` would then request `https://api.github.com/user`, the account of the server's GitHub access token, and pass the account's data to the summary model and the cache of labels. The classification resolves a relative link of the README first, and the link reaches this tool without such a segment, a file or a directory of the repository as the `blob` link at the commit at which the README was read (rule 5) and another page as its github.com link (`classify-repos-spec.md`)
- The tool reads any other link from the public internet only. The stage runs in a container on a network with other machines, and a README can link to any address. Every address that the host resolves to therefore has to be global (`ipaddress.ip_address(...).is_global`). The tool reads only http and https links. The request sets `Accept` to text types, and the tool reads a body only of a text type, `text/html`, `application/xhtml+xml`, `text/plain`, `text/markdown` or `text/x-markdown`, or of a response without a content type (rule 3). The tool follows redirects and meta refreshes itself, at most <!--s:parameters.2_classification.classification_tools.MAX_REDIRECTS:words-->five<!--/s--> together, and checks each address in the same way (rules 6 and 7)
- Connecting may take <!--s:parameters.2_classification.classification_tools.PAGE_TIMEOUT.connect-->10<!--/s--> seconds and each read <!--s:parameters.2_classification.classification_tools.PAGE_TIMEOUT.read-->30<!--/s--> (rule 8). The whole reading of a page, over its redirects, ends after `PAGE_DEADLINE` seconds, with a note that states the deadline. A server that sends a few bytes within each read keeps every read under its timeout, and without the deadline it would keep the tool and the worker that labels the repository waiting. Between two checks of the deadline, the client waits for the whole status line and headers, or for a whole chunk of the body. A timer therefore shuts down the connections of the page's session at the deadline, which ends a read that is waiting (`deadline_session`, `shut`). A connection that the connect timeout lets finish after the deadline shuts itself down as it connects, because the timer has already run. The timer starts before the tool reads the clock for the deadline. The tool therefore counts the deadline as passed once the timer has run, even when the clock has not reached it yet, and never takes a body without a length that the shutdown ended for the whole page. The deadline is far above the times that rule 8 measured. It is not one of the classification parameters, because a change of any of them sends every repository to the model again
- The download stops at <!--s:parameters.2_classification.classification_tools.MAX_PAGE_BYTES.mb-->2<!--/s--> MB, and the note states the cut (rule 9). The request offers the content codings gzip and deflate (`ACCEPT_ENCODING`). The tool reads the body as the connection delivers it and decodes it itself, into no more than the bytes that are left of the limit of rule 9 (`raw_chunks`, `BodyDecoder`). urllib3 decodes each chunk that it reads in full, without a limit on what the chunk decodes to and through any number of stacked codings. With urllib3's decoding, a small body in a stacked or a zstd coding would fill the memory of the tool server before the limit is checked, and the host's out-of-memory killer would end the server and with it the labeling. The tool decodes gzip and deflate as urllib3 does, gzip with further members and deflate with or without the zlib header. A body in another coding or in more than one, or a body that does not decode, is a page that cannot be read
- html2text turns HTML into text without links or images (`converted_text`). Its output grows with the square of the depth of nested lists. The conversion therefore stops once its text is longer than `PAGE_TEXT_CHARS` by more than `CONVERSION_MARGIN`, and the text is cut at `PAGE_TEXT_CHARS`, one character more than the summary reads. Only the last characters of a conversion that stops can differ from the whole conversion. The summary therefore reads the same text that the whole conversion gives, and the note states that the page was cut
- The server logs at the level `WARNING`, in the format of `agentcontext.logs`, because its stderr is the classification's log (`../docs/logs.md`). At `INFO`, the SDK would write a line for every tool error and the OpenAI client a line for every summary request. When the server is built, the SDK also configures the root logger with a format of its own. `main` therefore calls `logs.capture_libraries`, which takes over the root logger, after building the server
- A failure of GitHub or of the summary model shows nothing about the repository. A tool raises such a failure as a tool error that begins with the failure's name in brackets (`failure`), and the classification raises the error rather than passing it to the model (`Classifier.tool` in `classify-repos-spec.md`). The names are:
  - `no_github_access_token` when GitHub refuses every GitHub access token of the server
  - `summary_refused` when the API refuses every request of the summary model (`refusal`): a rejected key (HTTP 401), a project or a key without access (HTTP 403), or a model that the API does not offer. A top-up does not end these refusals. OpenRouter's HTTP 403 for a page that its moderation or a guardrail blocked (`endpoints.blocked`) is none of these. The page is unavailable, with a note that gives the reason, as for a page that the API refuses with HTTP 400
  - `summary_no_credit` when the service of the summary model refuses the summary for spent credit (`endpoints.credit_refusal`): OpenRouter's HTTP 402, its HTTP 403 for a spent budget or key limit, or OpenAI's `insufficient_quota` or `billing_hard_limit_reached`. A top-up ends this refusal
  - `github_failed` when GitHub returns no usable response or a response that is not the JSON that it documents
  - `network_failed` when a page's host does not resolve, the request reaches no server, the body cannot be read or the deadline ends the page, and this machine cannot connect to GitHub's API either (`network_down`, `NETWORK_PROBE`), as during a failure of its own network or name resolution
  - `summary_failed` for any other failure of the summary
- When the API refuses the summary request with HTTP 400 for the page that it contains, such as with `context_length_exceeded` or `invalid_prompt`, the tool does not report a failure. The API refuses that page the same way in every attempt. As a failure of the summary, the refusal would fail every call of the tool and every retry round, each after the paid requests of the classifying model. The page reaches the model as unavailable, with a note that gives the code. A refusal that a new request does not receive again (`TRANSIENT_REFUSALS`) stays a failure of the summary
- The classification stops on `no_github_access_token` and `summary_refused`. On `summary_no_credit`, the requests to the summary model's service wait for the credit, which is every worker when the classifying model is on that service too, and the call is made again once the credit is back (`CreditPause` in `classify-repos-spec.md`). A 402 of OpenRouter for the budget of the requests in flight, which a wait ends without a top-up, is a `summary_failed`. On the other failures, it makes the call again after each wait of its `TOOL_WAITS`, so that the model's conversation goes on, and fails the repository after the last wait (`classify-repos-spec.md`). If the tools reported these failures to the model as an unavailable outline or page, a retired summary model or an empty pool of GitHub access tokens would make every outline or page unavailable, and the cache of labels would keep the labels decided without them. The classification logs the failure under its step with the repository, and the server logs nothing. A response of a page or a repository, such as a 404 or a type that is not text, describes the repository or the page, and the decision records it in the tool's output
- When a GraphQL response for the issues and pull requests lacks the repository, the tool reports a repository that GitHub did not find if the errors give `NOT_FOUND` or if the response has no errors. GitHub also returns other errors with HTTP 200 for its own failure, and with such errors the response is a failure of GitHub. If the tool took such a response for a repository that GitHub did not find, the model would receive GitHub's failure as a fact about the repository. Errors that are not objects, such as a proxy's text, count as other errors, and `github_api.graphql_errors` reads them as their messages. A body, a `data` or a repository that is not an object is a response that is not the JSON that GitHub documents. GraphQL sets a field that it could not resolve to null and reports the failure in the errors, with the path from the query's root, in which the second element is the field of the repository. A repository with a null field, such as a count, or with a list of pull requests or issues that is null or holds a null, is therefore a failure of GitHub too when the path of an error names the field (`unresolved_fields`). Read as a value, the null would reach the model as a count of zero or as no recent pull request. An error without a path could have left any field null, and it counts for every null field. A null that no error names is GitHub's value, such as `pinnedIssues` beside an error deep in the comments of an issue. GitHub's schema declares `pinnedIssues` nullable, and GitHub returns it as null for a repository with issues disabled. The summary of the classification counts the repositories that the classification leaves without a decision for such errors (`field_errors`)
- The server has its own pool of GitHub access tokens. The pool drops a GitHub access token only when GitHub returns HTTP 401 for it and again for a request to `/rate_limit` with it (`readmes-spec.md`). Once GitHub has refused every GitHub access token, the next tool call checks the configured GitHub access tokens again after each wait of `readmes.RECHECK_WAITS` and continues with the GitHub access tokens that GitHub accepts again. A period in which GitHub rejects valid GitHub access tokens then does not stop the classification. Only after the last wait does the call fail as `no_github_access_token`. The bridge waits for a call longer than these waits (`mcp-bridge-spec.md`)
- The server checks the input from the model. A repository name is `owner/repo` with GitHub's characters, no part is `.` or `..`, and the owner does not start with `-`. GitHub allows a repository's name to start with `-`, as `Hackerprod/-SKYNET-Steam-Emulator` in the sampling frame does, and the tools put the name only into the addresses of API requests. A revision is 40 hex digits or empty, and `max_chars` is 0 or more. The server refuses other input with a `ToolError`, and the SDK passes its text to the model
- The server ends itself once the process that started it is gone (`exit_with_parent`, checked every `PARENT_CHECK_SECONDS`). The MCP SDK starts the server in a session of its own, and the stop that the runner forwards to the classification does not reach it. Without this check, a stop of the classification would leave the server running until its tool calls ended, which can take hours when a call waits for GitHub's rate limit. The server would hold the runner's pipe of the step's output open, the runner would wait for the pipe, and stopping the container would end in SIGKILL, without a handover
- The description of `read_linked_page`, the one tool of the server that the model is offered, is part of the classification parameters that a label is recorded under, because the wording of a description changes how often the model calls a tool. The prototype's model called a tool for few repositories under one wording and for most under another (`../docs/history/2026-09-classification-mcp-pilot.md`). The model reads neither the descriptions nor the output schemas of the other three tools. Because the input holds their results, the classification parameters record their output schemas as the server lists them, the constants that limit their results or select what they contain, such as `ACTIVITY_ITEMS`, `COMMENT_CHARS`, `PINNED_ISSUES`, `ACTIVITY_QUERY`, `PRACTICES` and `OUTLINE_FILE_TYPES`, and a digest of the code that writes them (`classify-repos-spec.md`)

## Script: `classification_tools.py`

### CLI interface

```
python3 classification_tools.py [--summary-model MODEL] [--summary-effort EFFORT]
                                [--summary-provider SLUG --summary-quantization Q
                                 --summary-hugging-face-id ID] [--credentials PATH]
```

| Flag | Default | Description |
|------|---------|-------------|
| `--summary-model` | `deepseek/deepseek-v4.1-flash` (`endpoints.PRODUCTION`) | The model that summarizes pages: an OpenAI model, or an OpenRouter model, whose id names its author |
| `--summary-effort` | `low` | The reasoning effort of the summary model |
| `--summary-provider`, `--summary-quantization`, `--summary-hugging-face-id` | none | The provider slug of the endpoint, its quantization and the Hugging Face id of the weights of an OpenRouter summary model, all three required for a model outside `endpoints.PINNED` and refused for an OpenAI model. A model of `endpoints.PINNED` without them is called on its pinned endpoint |
| `--credentials` | `credentials.csv` at the repository root, or `AGENTCONTEXT_CREDENTIALS` | The file of the GitHub access tokens and of the API key of the summaries, OpenAI's or OpenRouter's, read after the environment. The classification and the comparison of its labels pass their own `--credentials` |

### Function structure

**`checked_repo_name(repo_name)`**: the name, or `InvalidInput`

**`failure(kind, message)`**, **`failure_of(output)`**, **`refusal(error)`**: a tool error that the classification raises rather than passing it to the model, the name and message of such an error read back, and the reason why the API refuses every request of a project. The classification applies `refusal` to its own requests too. `MODEL_NOT_OFFERED` is the reason for a model that the API does not offer, and `TRANSIENT_REFUSALS` lists the refusals that a new request does not receive again

**`outline(tree, languages, max_chars)`**, **`github_client()`**, **`file_tree(client, repo_name, revision, max_chars)`**: the outline, as a `FileTreeResult`

**`repository_metadata(client, repo_name)`**, **`activity(client, repo_name)`**, **`unresolved_fields(body, found)`**, **`field_errors(message)`**: what GitHub records about the repository, as a `RepositoryMetadataResult`, and the activity of its issues and pull requests, as an `ActivityResult`. `unresolved_fields` returns the fields of a repository in a GraphQL response that the response's errors left null, and `latest_merge` of `1_classify_repos.py` reads it too. `field_errors` returns whether the message of a failure of GitHub states such fields (`IN_PLACE_OF_FIELDS`), which the summary of the classification counts

**`public_address(host)`**, **`page_text(body, content_type)`**, **`converted_text(html)`**, **`deadline_session(sockets, expired)`**, **`shut(sockets)`**, **`raw_chunks(response)`**, **`BodyDecoder`**, **`read_web(url, session, clock)`**: a web page's text, the address that it was read at, and a note. The page is read in a session in which the timer of the deadline shuts down the connections. The body is read without urllib3's decoding and decoded into at most the limit of rule 9, and the conversion of HTML stops at `PAGE_TEXT_CHARS`

**`github_link(url)`**, **`issue(client, owner_repo, number)`**, **`renamed_branch(client, base, ref)`**, **`read_github(client, url)`**: what a github.com link refers to, an issue with its repository and its maintainers' comments, the new name of a renamed branch, and the text of a link through the API, without a request for a link with a `.` or `..` segment in its path

**`Summarizer`**, **`SummaryEnded`**, **`ended_summary(response)`**: the summary of a page's text, with its tokens, the tokens that it read from and wrote to the prompt cache, its model and its service tier, from OpenAI or from the provider that served an OpenRouter model, its pinned endpoint (`endpoint`) or its backup provider (`backup`). Its request sends no output limit, unlike a request of a model that labels (`MAX_OUTPUT_TOKENS` of `endpoints.py`), and the endpoint applies its own: A summary is a short text at reasoning effort `low`, and a higher limit would only let a summary that never ends cost more. A response with an error, with the status `failed` or without a list of output items is one that the service ended (`ended_summary`), and the summary raises `SummaryEnded`, which the tool reports as `summary_failed`. OpenRouter reports a failure after the status 200 in a Response with the status `failed`, an error and the `error_type` at the top level, without `output` or with an empty one (openrouter.ai/docs/api_reference/errors-and-debugging), and the `output_text` of such a Response is empty. Read as the summary, it would make an available page say nothing, and the cache would keep the label that the model decided from it

**`build_server(github, session, summarizer)`**, **`main(argv)`**: the server, in which a caller can replace GitHub, the web and the summarizer, and `from_github` in it, which raises GitHub's failures as failures for the classification

## Error handling & edge cases

| Scenario | Behavior |
|----------|-----------|
| GitHub returns a status other than 200 for the tree | `available: false` with a note, because the status does not describe the repository |
| GitHub returns no response, after the client's attempts, or a response that is not the JSON that it documents, for the tree, the languages, the repository's metadata, the issues and pull requests or a github.com link | A `github_failed` tool error, after which the classification makes the call again and then fails the repository |
| GitHub refuses every GitHub access token of the server | The tool checks the configured GitHub access tokens again after each wait of `readmes.RECHECK_WAITS`, and the call continues with the GitHub access tokens that GitHub accepts again |
| GitHub refuses every GitHub access token of the server after the last wait | A `no_github_access_token` tool error, which stops the classification |
| GitHub returns a status other than 200 for the repository's metadata | `available: false` with the status |
| The GraphQL query for the issues and pull requests returns a status other than 200, or does not find the repository | `available: false` with a note |
| The GraphQL query returns errors other than `NOT_FOUND` and no repository, also errors that are not objects | A `github_failed` tool error |
| The GraphQL query returns the repository with a null field, or a list of pull requests or issues that is null or holds a null, and an error with a path that names that field or an error without a path | A `github_failed` tool error |
| The GraphQL query returns a null field that no error names, such as `pinnedIssues` beside an error deep in another field | GitHub's value: the activity reaches the model |
| An `issues` or `pull` link without a number, such as `issues/new` | Not read, with a note |
| The API refuses every request of the summary model | A `summary_refused` tool error, which stops the classification |
| The service of the summary model refuses the summary for spent credit | A `summary_no_credit` tool error, after which the requests to the summary model's service wait for the credit and the call is made again |
| The API refuses the summary request with HTTP 400 for the page, with a code that is not in `TRANSIENT_REFUSALS` | `available: false` with a note that gives the code, and the page is not summarized |
| OpenRouter blocks the summary request for the page's content with HTTP 403 (`endpoints.blocked`) | `available: false` with a note that gives OpenRouter's reason, and the page is not summarized |
| The pinned provider of an OpenRouter summary model fails the summary request for the service, or ends its response, and the summary model has a backup provider | The same request goes to the backup provider, which serves every summary until the pinned provider responds again to a test, with a `WARNING`. A refusal for the budget of the requests in flight fails the summary instead |
| The summary request fails otherwise, or the service ends its response, with an error, with the status `failed` or without output items | A `summary_failed` tool error, after which the classification makes the call again and then fails the repository |
| Reading a page takes more than `PAGE_DEADLINE` seconds, also on a server that sends its headers or its body a few bytes at a time, and on a body without a length that the shutdown at the deadline ends | `available: false` with a note that states the deadline, returned within the deadline |
| A page's host does not resolve, the request reaches no server, the body cannot be read, or the deadline ends the page | While this machine connects to GitHub's API, `available: false` with a note, and otherwise a `network_failed` tool error, after which the classification makes the call again and then fails the repository |
| A link, a redirect or a meta refresh to an address that is no URL, such as an IPv6 address without its closing bracket | `available: false` with the note that the address is not a valid URL |
| A charset that Python does not know or cannot decode with replacements, such as `undefined` or `idna` | The body is read as UTF-8 |
| The languages API returns a status other than 200 | The outline contains `Languages: none detected` |
| An address off the public internet, also after a redirect or a meta refresh, and also when a backslash before an `@` makes `urlsplit` read another host than the request connects to, such as `http://10.0.0.5\@docs.example/` | `available: false`, and no request is sent to it |
| A github.com link with a `.` or `..` segment in its path, also percent-encoded or separated by backslashes | `available: false` with a note, and no request is sent |
| GitHub returns 404 for a file or a directory at a branch, and redirects `GET /branches/{branch}` to another branch | The file or the directory is read at that branch. With no other branch, `available: false` with the note of the 404 |
| A page in a content coding other than gzip or deflate, in more than one, or with a body that does not decode | `available: false` with the note that the page could not be read, and no summary is made |
| A body that decodes to more than the limit of rule 9 | The tool holds no more of it than the limit, and the note states the cut |
| HTML with a text longer than `PAGE_TEXT_CHARS` | The conversion stops, and the summary reads the same text and states the cut, as for the whole conversion |
| A page that is not text, returns another status, has no text, or redirects more than <!--s:parameters.2_classification.classification_tools.MAX_REDIRECTS:words-->five<!--/s--> times | `available: false` with a note, and no summary is made |
| A file that contains a null byte in its first <!--s:parameters.2_classification.classification_tools.binary_check_bytes-->8<!--/s--> KB | `available: false`, because the file is not text |
| A malformed repository name, revision or `max_chars` | `ToolError` with the reason |

## Known limitations

- The address is resolved before the request and again by the request itself, and a request to a host for which the second lookup returns another address than the first reaches that address
- Because the timer of the deadline shuts down a connection only once it is made, it does not end a TLS handshake that a server sends a few bytes at a time, or a request through a proxy that the environment names. The bridge gives up on such a call after its `CALL_SECONDS`
- A top-level directory that contains only submodules is counted among the directories but not listed under `Top level`
- `PRACTICES` falsely counts an application directory named `Test`, as in firefly-iii, as tests
