# Label the sampling frame


A hash that names a prompt or a set of parameters in this specification, such as `2f8e5d6b`, is a commit of the private repository `se-uhd/agenttorrent-pipeline-internal`, as `config/parameter_digests.csv` records it, and no check resolves it.

## Context

`1_classify_repos.py` is the script of the labeling step of the classification stage. It decides for every repository in the sampling frame, `../data/sampling/ghs_filtered.json`, whether the repository hosts an engineered software project. The model decides from the repository's README and its description on GitHub. For every repository, it also reads the activity of the repository's issues and pull requests, with the pinned issues, what GitHub records about the repository and an outline of the repository's files, which the classification reads before the first request. When it requests one, it reads a summary of a page that the description, the homepage or the README links to. The engineered project selection keeps the repositories labeled `true` (`agentcontext/steps/engineered_project_selection.py`).

A batch classification labeled the sampling frame of March 2026. Nine scripts cloned every repository and sent one request per repository with its README, its Linguist output and summaries of its linked pages to the OpenAI Batch API. A prototype of this script ran on repositories drawn at random. Its model requested more than the README for few of them, and its labels agreed with the batch labels on nearly all (`../docs/history/2026-09-classification-mcp-pilot.md`). Computing the Linguist output and the link summaries for every repository was the expensive part of the batch, and the prototype shows that the model rarely needs them. The [reading rules](0_README.md#the-reading-rules) bound what the classification reads, and measurements over a random sample of the sampling frame set them. This spec names each rule by its number there.

## Key decisions

- **Language:** Python 3.14, with `openai` for the Responses API of OpenAI and of OpenRouter, `asyncio` for deciding several repositories at once, and the modules `readmes.py`, `label_cache.py`, `forks.py`, `mcp_bridge.py`, `classification_tools.py`, `endpoints.py` and `changed_labels.py` beside it
- The classifying model and the summary model are OpenAI models, called through OpenAI's API, or open-weight models that OpenRouter serves, called through OpenRouter's OpenAI-compatible Responses API on one pinned endpoint without fallbacks (`endpoints-spec.md`). A model with an id that names its author, such as `deepseek/deepseek-v4.1-flash`, is an OpenRouter model, and it needs `--provider`, the provider slug of its endpoint such as `morph/fp8`, `--quantization` and `--hugging-face-id`. A request to an OpenRouter model adds OpenRouter's provider routing (`order`, `allow_fallbacks: false`, `quantizations`, `require_parameters: true`), the reasoning effort as OpenRouter's `reasoning` parameter, and no service tier. A run whose pinned endpoint stops responding pauses as a run on the flex tier does (`ServicePause`, below), and where a failure would use an attempt, the backup provider of the model serves the same request (below)
- OpenRouter's Responses API "is stateless" and rejects a request with a non-null `previous_response_id` with HTTP 400 ([the Responses API](https://openrouter.ai/docs/api/reference/responses/overview)). For an OpenRouter model, each request therefore sends the whole conversation: the first input as a message of the user, every output item of each response as the response gave it, its reasoning items with their `encrypted_content` included, and the outputs of each round of tool calls (`Classifier.opening`, `Classifier.follow`, `as_input`). A request to OpenAI continues from the last response through `previous_response_id`. Both bill the input tokens of the earlier requests again in each request, and the prompt cache discounts the repeated part
- The script reads the README through GitHub's README API at the commit that the sampling frame recorded, `lastCommitSHA`, which is the HEAD of the default branch that GitHub's query returned. A label therefore records the revision that it was decided on (`readmes-spec.md`). No repository is cloned for its README

- A page has to be an absolute or relative link of the README, a web address of the description or the homepage that the metadata gives (`described_links`), the homepage read over https when GitHub keeps it without a scheme, such as `angryip.org`, also when the model passes it without a scheme, or an issue or a pull request of the repository, which `get_issues_and_pull_requests` lists. A web address may contain balanced parentheses, as `lambdaloop/anipose` links its paper at `https://www.cell.com/cell-reports/fulltext/S2211-1247(21)01179-7`. The model may pass a link with its markup, a link reference definition or a reStructuredText target definition whole, or a reference to a definition by its label or name. `[Install]` names the definition `[Install]: doc/install.md` in the README of `herumi/xbyak`. `pism-contributing_`, also in `` `Contributing to PISM <pism-contributing_>`_ ``, names the definition `.. _pism-contributing: http://www.pism.io/docs/contributing` in the README of `pism/pism`, and GitHub renders that reference as a link to the address. The specification of reStructuredText states that "Reference names are whitespace-neutral and case-insensitive", as GitHub renders `MPI_` of the same README as a link to the target of `.. _mpi:`, and `reference_definitions` reads a name in that way. A target definition may write its target indented on the next line, as `` .. _`Next steps`: `` in the README of `celery/celery`, and GitHub renders `` `Next steps`_ `` as a link to that target. The text of a reference may contain angle brackets, as `` `Pydantic (>=2.0) <https://github.com/pydantic/pydantic>`_ `` in the README of `tfranzel/drf-spectacular`, which GitHub renders as a link to the address. The first definition of a name counts, as for a link reference definition. A chained target, such as `.. _first:` directly above `.. _second: docs/guide.rst`, and an indirect target, such as `.. _first: second_`, read as no link. `resolve_link` takes a github.com link to a file or a directory of the repository, at any branch, tag or commit, as the README's link to the same path. The tools read such a link, and a relative link of the README, through GitHub as the `blob` link at the commit at which the README was read (rule 5). GitHub returns 404 for a file at a branch that was renamed. In run `2026-10-23T093036Z`, which read a github.com link of the README as the README wrote it, GitHub returned 404 for <!--s:classification_2026_10_23.own_links_not_found-->50<!--/s--> calls in <!--s:classification_2026_10_23.own_links_not_found_repositories-->50<!--/s--> repositories with a link of the repository at a ref other than its default branch and the commit of the sampling frame, such as `blob/master/CONTRIBUTING.md` of `android/android-test`, which renamed `master` to `main`. A link to a file of another repository at a renamed branch is read at the branch's new name (`classification-tools-spec.md`)
- `_from_repository` resolves a relative link as GitHub renders it, from the README's page under `/<owner>/<repo>/blob/<ref>/`. GitHub renders `../master/CONTRIBUTING.md` of `skuschel/postpic` as `/skuschel/postpic/blob/master/CONTRIBUTING.md`, which the tools read as that path at the README's commit (rule 5). It renders `../../../jackson#participation-contributing` of `FasterXML/jackson-core` as `/FasterXML/jackson#participation-contributing`, and the tools read that repository's README as a page of another repository (`classification-tools-spec.md`). `../../wiki` of the same README names a page that the tools do not read, and the tool's note says so. The function returns no link for a branch without a path, such as `../master`, for a path above GitHub's root, and for a path from the repository's root that leaves it, such as `/../other`. `resolve_link` writes the path of a github.com link of the repository in that last form, and such a path must not reach another repository
- `resolve_link` takes any other web address as the README's link to the same page, which has the same scheme and host, apart from their letter case, the same path, apart from its trailing slashes, and the same query, where an empty query counts as none, whatever the fragment (`_page_of`). `https://drf-spectacular.readthedocs.io` names the page that the README of `tfranzel/drf-spectacular` links as `https://drf-spectacular.readthedocs.io/`, and `https://github.com/OhMyGuus/BetterCrewlink-mobile` names the page that the README of `OhMyGuus/BetterCrewLink` links only with fragments, such as `#web`. The README of `common-workflow-language/cwlviewer` writes `<https://doi.org/10.7490/f1000research.1114375.1?>`, GitHub renders a link with the `?`, and `readme_links` reads the address without it, so that the address as the README writes it names that link. The URL that reaches the tool is the address that the README writes, the first in sorted order when it writes several, so that every run reads and records the same address (`_known_link`). Because the tool fetches what the link names, a link from the model reaches no host, repository or page that the description, the homepage or the README does not link. A link without a scheme names a file or a directory of the repository that the README links first, as GitHub renders it, and only then a web address of the README, the description or the homepage with that host, in the letter case of the address. In a README that writes `[c](CONTRIBUTING.md)` and `https://contributing.md/`, as the README of `MrBear2-Rus/Bear2Wave` does, `CONTRIBUTING.md` names the file and `contributing.md` names the site. In a README that writes only the address, `CONTRIBUTING.md` is refused as a file that the README mentions without a link. A github.com address without its scheme names the path at the README's commit, as it does with its scheme (rule 5)
- When `resolve_link` finds no such link, the tool returns `REFUSED_LINK`, which names the link forms that the tool reads. A refusal that stated only that the README has no such link would be wrong where the README writes the link in a form that the tool does not read. In run `2026-10-10T035814Z`, the tool returned the refusal for <!--s:classification_2026_10_10.refused_rst_links-->75<!--/s--> calls with links of README.rst files, because it found no such link in the README. The current code reads links of these forms, such as links written as `` `guide <CONTRIBUTING.rst>`_ `` or as a target definition such as `.. _HISTORY: HISTORY.rst`. It also reads the links of refused calls for README.md files, such as `https://github.com/akash-network/node/blob/main/CONTRIBUTING.md` for the README's relative link to `CONTRIBUTING.md`, and of refused calls for README.adoc files. Since it reads link reference definitions, it also reads the links of refused calls that the README writes as such a definition, such as `[contributing]: CONTRIBUTING.md`, and of refused calls with a web address that contains parentheses. The other refused calls name files that the README mentions without a link, as in "See CONTRIBUTING.md", or pages that it does not link, such as a file inside a directory that the README links. In run `2026-10-23T093036Z`, the tool returned the refusal for <!--s:classification_2026_10_23.refused_links-->350<!--/s--> calls, and for some of them the README wrote the link as a link reference definition
- The classification fills in the repository, the commit and the room of the outline in each tool call without showing them to the model. The outline is therefore always the outline of the repository at its revision
- The repository's name goes first, enclosed in `<repository>` tags, and the instructions name no repository, so that the first request of every repository starts with the same instructions, tools and response format, which the API can read from its prompt cache. The repository's description on GitHub goes before the README, enclosed in `<description>` tags. For a repository without a description, a line that states its absence takes its place. A missing description is no evidence on its own. The description comes from the sampling frame, which records GitHub's response to the sampling stage's GitHub query. For a sampling frame without GitHub's descriptions, the script stops before any request (`SystemExit`). The decision records the description, and the script compares it with the current description before it reuses the label
- The repository's activity goes with the description, enclosed in `<activity>` tags: its commits, contributors, releases, issues and pull requests, in total and open, its creation and its last commit, as the sampling frame records them (`activity_of`). The sampling frame takes the creation and the last commit from GitHub's response to the sampling stage's query of GitHub, and the counts from GHS. The research criterion tests whether code that accompanies a paper is maintained beyond the paper and used by others, which these counts show and a README seldom states. The counts cost no request. The decision records them, so that `changed_labels.py` can repeat a label with the same counts
- The model reads neither the stars nor the forks, in the activity or from `get_repository_metadata`. Both measure popularity, which no criterion of the prompt names as evidence of maintenance or use. A star threshold finds engineered projects precisely but misses most of them (Munaiah et al., Empirical Software Engineering 22, 2017). Stars can be bought (He et al., "Six Million (Suspected) Fake Stars in GitHub", ICSE 2026), and forks also count the copies of templates, tutorials and course material, which the exclusion criteria remove. Labels that followed the star count would also raise the adoption rate that the dataset publishes, because the share of the sample with a configuration artifact rises with the star count. Over the sampling frame of retrieval `2026-10-05T101430Z`, the share labeled `true` rose more steeply with the star count in run `2026-10-10T035814Z`, which read the counts, than in run `2026-10-06T140917Z`, which did not, although the prompt changed between the two runs too

- A criterion with an exception has separate fields in the model's response, and the classification combines them (`CRITERION_FACTS`, `CRITERION_APPLIES`). - How a repository takes contributions excludes it from nothing. Development by a core team, or through Gerrit, a mailing list or another repository, makes a project no less engineered, and closed source is the criterion `no_source_code`. The criterion `closed_to_contributions`, which excluded a repository that refused pull requests and issues from the public, was removed on 2026-10-31, after it excluded `vmware/packer-plugin-vsphere`, whose contribution guide limits pull requests to collaborators and issues to the maintainers' work. The profile description of the repository's owner, which the metadata gives, describes the repository when it describes all of the owner's repositories as mirrors or as read-only, as KDE's organization does for `KDE/liquidshell`, whose description and README do not. The owner's profile description decides no other field, because it says what the owner publishes. - Whether the software is maintained and used by others is one field of the response (`MAINTENANCE_AND_USE`), and two criteria use it. Research code, software that its author wrote for their own use and a single script are excluded unless the software is both maintained and used by others. The reviewer settled this exception for code that accompanies a paper on 2026-10-08 and extended it to the personal criterion on 2026-10-09. A response in the format ends the streak, so that `FORMAT_STREAK` failed responses in a row have to follow before the next pause, but the pauses count on and their waits keep growing until the endpoint has recovered: until responses in the format for <!--s:parameters.2_classification.1_classify_repos.FORMAT_STREAK_REPOSITORIES-->5<!--/s--> repositories have followed each other without a failed response between them (`FormatStreak.passed`). Only then does the next pause begin with the shortest wait, while a pause that holds runs to its end. An endpoint that fails most responses returns one in the format now and then. If each such response made the next pause the first again, the run would never stop, would pay for the failed attempts at every repository, and would take the labels of the higher temperature or of the second model. A run of responses in the format for as many repositories as the streak needs to tell an endpoint from a repository is rare at such an endpoint and common at a working one. While a streak is open (`FormatStreak.open`), that is, once it has paused every worker and until the endpoint has recovered, the failed responses of the repositories that failed an earlier round count as well, and the pass of the second model waits out the pause that holds and takes over the pauses of the streak (`FormatStreak.take_over`, `ServicePause.wait_for`). The failed responses of the second model then count toward a streak of its own, which pauses the workers of the pass and ends the pass after the last pause, as a refusal of the second model does. An outage that begins at the end of the main round, whose last repositories use up their attempts during the pauses, thus pauses the retry rounds and the pass of the second model too, instead of failing every attempt of the retry rounds within minutes and leaving the repositories to the second model or, when it fails during the same outage, without a decision. An endpoint that ignores the JSON schema fails every response, also after the pauses. On 2026-10-30, OpenRouter's endpoint `siliconflow/fp8` of Qwen3.8 2.4T-A95B returned YAML, XML or Markdown for every repository once tools were in the request, and the run paid for every attempt at each repository before a person stopped it. A working endpoint can fail a burst of responses as well: On 2026-11-03, Morph's endpoint of DeepSeek V4.1 Flash returned such a streak shortly after a progress line that counted no failed repository, and a stop at the streak would end a run that the endpoint could finish. The number of pauses is a policy, as `PAUSES_BEFORE_ATTEMPTS` is for the pauses of the service. With waits that double from `PAUSE_FIRST_SECONDS`, the pauses let an unattended run of several days ride out an endpoint that fails the format for hours instead of stopping: the request after a pause costs only the requests that the workers send, whereas a stop costs the hours until a person starts the run again. An endpoint that ignores the schema stops after about one more request per worker and pause. A working endpoint fails a few responses of a run, and the responses of the other workers that follow the format end each streak. While no streak is open, the responses of a repository that an earlier attempt round of the run left without a decision do not count (`Classifier.failed_earlier`), nor in a resumed run those of a repository that the model failed in an earlier invocation (`model_failures`), nor those of a repository that the model, or the second model after it, failed in the latest finished run under the same model, classification parameters, retrieval and scope (`failed_in_finished_run`). A retry round, the main round of a resumed run, and the main round of the run that tries again the repositories that a finished run left without a decision, which reuses every other decision, can hold nothing but such repositories. The `WARNING` of a pause names the endpoint, the streak, the reason of the last failure and the pause, the `ERROR` of the stop names the endpoint, the reason of the last failure and how many of the final responses after the first pause failed the format, and the decisions so far are kept. The text of every failed response reaches the log, in the `INFO` line of its failed attempt (`Classifier.label`)

### Function structure

**`read_sampling_frame(path)`**, **`read_repository_ids(path)`**, **`activity_of(item)`**, **`activity_text(activity)`**: the repositories to label with their activity and GitHub's mirror flag, and the thresholds that a fork's own development has to reach

**`plain(text)`**, **`_resolved(text)`**, **`quoted(quote, *sources)`**: a text in the form in which a quotation of it is compared, the text with each reference to an AsciiDoc attribute that it sets replaced, and whether a description or a README contains a quotation

**`classification_parameters(prompt, function_tools, classifying, settings, summary, summary_effort, output_schemas)`**, **`run_parameters(args, prompt, function_tools, output_schemas)`**, **`read_first_code()`**, **`link_resolution()`**, **`purpose_sentence_check()`**: what a decision is recorded under, with the endpoints of the classifying model and the summary model and the settings of the classifying model's requests, the parameters of a run with a command line, the digest of the code that writes the results of READ_FIRST, the digest of the code that reads the links of the README and resolves a link from the model, and, beside the output schema of `read_linked_page`, the fewest words of a page's purpose sentence, the pattern of its line in the summary and the digest of the code that compares its words with the page and of the code that names the page of another repository, because a purpose quoted from the sentence decides a label

**`checked_response(response, name, limit)`**, **`stopped_at_limit(response, limit)`**, **`checklist_calls(response)`**, **`argument_text(arguments)`**, **`kept_arguments(arguments)`**, **`message_text(response)`**, **`kept_message(response)`**, **`printable(value)`**, **`response_details(response)`**, **`service_ended(response, limit)`**, **`named_error(response)`**, **`error_body(response)`**, **`as_input(item)`**: the model's final response as the checklist for the repository, or `ModelFailure` with the kind `output_limit` or `response_format`, whether a response stopped at its output limit by either of the two signals that OpenRouter gives, the calls of `submit_classification` in a response, the arguments of such a call as text, their length, start and end, the text of the messages of a response without such a call, its length, start and end, a value from the API escaped for one line of the log, the status, the reason of the `incomplete_details`, the types of the output items, or no output items for an empty output or none, the output tokens and the length and the start of the text of the messages of a response, why the service ended a response, or an empty string, the code, the message and the `error_type` of the error of a response, the `ServiceEnded` of a Response that holds an error and no output items, or None, and an output item of a response as an input item of the next request through OpenRouter

**`room(used_tokens)`**, **`readme_input(name, path, text, other_chars, description, activity)`**, **`readme_links(text, name, path, revision)`**, **`reference_definitions(text, name, path, revision)`**, **`_page_of(link)`**, **`_known_link(link, links)`**, **`resolve_link(link, links, name, path, revision, definitions)`**, **`REFUSED_LINK`**, **`READ_FIRST_CALL`**, **`LINKED_PAGE_LIMIT`**, **`TOOL_ROUND_LIMIT`**: the room that a request has left, the README as the model reads it, its links, its link reference definitions and reStructuredText target definitions by label, the page that a web address names, the link of the README that names the same page, the page that a link from the model names, the refusal of a link that is not among them, and the messages for a call of a tool of READ_FIRST and for a call past a limit

**`recorded_results(decision)`**: the calls of READ_FIRST that a decision recorded for its first request

**`Classifier`**: one repository's label, through these methods:

- `create`: one request with the instructions after the pause of every worker and the pause for the credit of the classifying model's service, with the provider routing of the provider that serves the model for an OpenRouter model (`endpoints.Providers`), and the same request again after a pause that its failure, a response that the service ended among them, or a refusal for spent credit begins or joins, or at once to the backup provider (`again`), counting each response that carries usage toward the requests of its repository and naming the provider that served it
- `again`: whether a request that the service failed is sent again rather than using an attempt, and whether it goes to the backup provider at once, with the switch of every request of the model to the backup provider once the pinned provider has failed the requests of two repositories, and never for a refusal for the budget of the requests in flight
- `opening` and `follow`: the input of the first request, and the request after a round of tool calls, through `previous_response_id` for OpenAI and with the whole conversation for OpenRouter
- `tool`: one tool call, again after each wait of `TOOL_WAITS` when GitHub or the summary model fails it, raising a failure that the server marks
- `outline`: the outline, fetched to its room
- `read_first`: the input of the first request with the results of READ_FIRST, which it takes from the decision that `changed_labels.py` repeats where the decision recorded them
- `page`: a summary without its cost

### Output

The run writes `../data/classification/repos_annotated.csv` and `../data/classification/repos_excluded.csv` (`0_README.md`). `repos_excluded.csv` lists under the reason `undecided` a repository that the run left without a decision, and under the reason `copy` a repository labeled `true` at the head commit of another one labeled `true` that the sample keeps instead (`first_of_copies`). Its `detected_language` column is the language that Lingua detected for a README that the check excluded. `../data/classification/repos_annotated.json` contains the run, the classification parameters, the retrieval, the models and response models of the labeled decisions, the second model among them when it labeled a repository, under the key `undecided` the number of repositories that the run left without a decision, under the keys `higher_temperature_labels` and `second_model_labels` each repository of `repos_annotated.csv` that the classifying model labeled at its higher temperature or that the second model labeled, with its name, its GitHub id, the model, the classifying model, the temperature of a label of the higher temperature and the reason, and under the key `second_model_failures` each repository that the second model left without a decision too, with its name, its GitHub id, the second model, the classifying model and the reason, and under the key `backup_provider_labels` each repository of `repos_annotated.csv` with a label that a backup provider served wholly or in part, with its name, its GitHub id, the model that labeled it, the classifying model, the backup providers and whether they served it wholly (`backup_served`). Outputs that a later invocation completes for a finished run read the second model and the reason from the run's labels (`second_model_failure`). The script reads the response models off the decisions, because a reused label keeps the response model, the dated snapshot, of the run that made it.

The run writes its index row, its decisions file, its labels file, its tokens file, its cost record and the classification parameters that it names into `../data/classification/labels/`. A decision of the model keeps every tool call with its arguments and its whole output, as the model read it.

A run over the whole sampling frame then compares its labels with the labels of the previous run. It labels each changed repository again on the service tier of the run to determine why it changed, and writes `../data/classification/label_changes.csv` beside its other outputs (`compare_with_previous_runs`, `changed-labels-spec.md`). An invocation can leave a comparison unfinished at any point. The next run over a sampling frame then finishes that comparison before it compares the latest run, and the next invocation over the same sampling frame finishes it without a new run (`complete_finished_run`). An earlier run that was never compared stays uncompared. `label_changes.csv` contains every comparison that the invocation made or wrote again from the cache of labels, oldest first, each after the comparisons of the earlier runs over the same retrieval that lead to its run (`earlier_comparisons`). The comparison of a finished run that left repositories without a decision thus stays in the file before the comparison of the new run that tries them again, also when a later invocation compares the new run or writes its comparison again.

The script writes each of these outputs through a temporary file, syncs it to disk before the rename and syncs the directory after it (`caches.replace_file`), because an empty `repos_annotated.csv` after a power loss would stop the engineered project selection.

## Known limitations

- A run on the standard tier (`--openai-service-tier default`) costs the full price of the model, whereas the batch classification paid the price of the Batch API
- The pause for GitHub begins with the second repository that GitHub fails since its last response, also in a retry round. An outage of GitHub that begins in the last retry round therefore leaves the first repository that it fails without a decision, and a retry round that holds a single repository begins no pause
- Because `gpt-6-luna` names no dated snapshot, the model behind it can change between two runs under the same classification parameters. The model that each response reports is recorded, and is not part of the reuse key
- The purpose check does not find a sentence that a README writes across the rows of a table with more than one column, because the flattened README alternates the cells of each row. The README.rst of `MetPX/sarracenia` writes its English and its French description side by side, and run `2026-10-23T093036Z` recorded the model's quotation of the English description as refused (`purpose_quote_refused`)
- A label is reused for an unchanged README even when the repository changed otherwise, such as its files. A README that states nothing new about a repository that became something else keeps its label
- Rule 1 holds for the first request. The README is cut only when the request with the README, the issues and pull requests and the metadata would cross the boundary, and the outline, read after them, gets little room after a README that nearly fills the request. A request after a round of tool calls is not sized again, and the summaries of the round can take it over the boundary by their length, up to <!--s:calibration.summaries.max_chars-->997<!--/s--> characters each
- The characters per token are an estimate. Text that tokenizes at fewer than <!--s:parameters.2_classification.1_classify_repos.CHARS_PER_TOKEN-->3.57<!--/s--> characters a token, as <!--s:calibration.readmes_below_chars_per_token-->11<!--/s--> of the <!--s:calibration.token_count_readmes-->100<!--/s--> READMEs of the calibration sample with counted tokens do, can push a request that the estimate keeps under the boundary over it
