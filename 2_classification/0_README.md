# Classification

This stage labels every repository in the sampling frame as an engineered software project or not. A model, DeepSeek V4.1 Flash through OpenRouter on Morph's fp8 endpoint by default, reads the repository's description on GitHub and its README and fills in a checklist. The checklist gives the fields of each exclusion criterion as `true`, `false` or `unclear` with the evidence, the upstream if the repository is described as a fork, the purpose quoted from the description or the README, and the model's judgment of the evidence of software engineering practices, `true` or `unclear`. The classification derives the label from this response. The label is `false` when a criterion applies, when the README is not mainly in English, when no purpose is stated, or when a fork has not become a project of its own, which the fork heuristic in `forks.py` decides from GitHub's data. The label is `unclear` when none of these conditions holds and one of them is unclear. Otherwise the label is the model's judgment, with a justification.

For every repository, the classification reads three results from the tools of an MCP server and puts them in the model's input: the activity of the repository's issues and pull requests with the pinned issues, which shows the project's status or whether it takes pull requests, an outline of the repository's files from GitHub's API, and what GitHub records about the repository. Before the model submits the checklist, it calls the server's tool for a summary of a page that the description, the homepage or the README links to, when the page could change a field that the input does not state outright or that rests on an inference. [The reading rules](#the-reading-rules) bound what the classification reads, and measurements over a random sample of the sampling frame set them. The cache of labels under `../data/classification/labels/` keeps each label, and the classification reuses it while the README's wording, the description, the model and the classification parameters are unchanged. A monthly run therefore sends to the model only the repositories that are new or have a changed README or description.

The last step of the stage, `engineered_project_selection`, keeps the repositories labeled `true` as the sample, which the collection clones. The scripts, the prompts and the review page, `review_disagreements.html`, are in this directory. Everything that the stage reads and writes is in `../data/classification/`, beside the sampling frame in `../data/sampling/`.

## Running the classification stage

Run the stage from this directory with `run_classification.py`, which runs the two steps of the stage through `../agentcontext/runner.py`. `--list` prints the steps without running them. `../run_pipeline.py` runs the same steps after the sampling stage and before the collection.

```shell
python3 run_classification.py --list
python3 run_classification.py
```

Before the first step starts, the pre-checks test for the credentials and the packages. The labeling, `repository_labeling`, labels the repositories in the sampling frame. A run over the whole sampling frame ends by comparing its labels with the labels of the previous run. The selection, `engineered_project_selection`, then writes the sample to `../data/classification/repos_annotated_included.csv`. The runner records the labeling with its inputs: the sampling frame, the two prompts and the modules that `1_classify_repos.py` imports. Under `../run_pipeline.py`, it records the repositories in the sampling frame and the values of its `_metadata` that the labeling reads, in place of the whole file (`run-classification-spec.md`). It runs the labeling again after a new sampling frame or a changed prompt or module, and a run over an unchanged sampling frame reuses the cached labels. After a changed module, such as the cost record, the labeling over the same sampling frame completes its finished run instead, without a new run and without a README request, when the current rules derive each of its labels unchanged. The sample then stays, and so does the collection of the sample. `--new-run` labels the sampling frame in a new run, which requests every README again and drops from the sample each repository that GitHub no longer serves. The runner writes the log of each step to `../data/classification/run_logs/<step>.log`, or to `run_logs/<step>.log` at the data root when `../run_pipeline.py` runs the step.

## 1. Label the sampling frame (`repository_labeling`)

`1_classify_repos.py` reads the README of each repository in the sampling frame through GitHub's README API. It reads the README at the commit that the sampling frame recorded as the HEAD of the default branch, and it sends the ETag of the latest decision on the repository. GitHub returns 304 for a README that did not change, and the script reuses the decision. The script also keeps the label of a README that changed only in badges, images, link targets, reference definitions, HTML comments and tags, bare URLs, whitespace or numbers. When the description of the repository changed, the model labels the repository again. The script derives a reused decision again under the current rules of the criteria, the language check and the purpose check, so a fix to them needs no request to the model. When GitHub no longer has the commit of the sampling frame, as after a force push, the script reads the README at the default branch. It also requests there the facts of GitHub that a reused decision needs again, such as the commit counts of the fork heuristic.

A README that is missing or empty is an exclusion. So is a README that the language check, which runs Lingua over the prose of the README, finds not to be in English. Any other README goes to the model with `prompts/classification-prompt.md` as instructions. Before the README, the model reads the repository's name, its description on GitHub, or a line that states that it has none, and the activity that the sampling frame records for the repository. After the README, it reads the three results that the classification read for it. The model's response gives every exclusion criterion with its evidence. For a criterion with an exception, and for the two cases of `no_source_code`, the response gives separate fields, each `true`, `false` or `unclear`, and the script combines them. The response also counts the README's words of prose by language, names the upstream of a fork, states the purpose and judges the evidence of software engineering practices. The script derives the label as the opening paragraph of this file describes. A fork has not become a project of its own when it tracks its upstream, or when it is not developed on its own, with fewer of its own authors than the contributor minimum of the GHS query or no commit of its own in the sampling window (`forks-spec.md`). Each decision records the criteria that applied.

The script sizes a request to stay under <!--s:parameters.2_classification.1_classify_repos.REQUEST_TOKENS-->272,000<!--/s--> input tokens, above which OpenAI charges the long context price for its models. It estimates the tokens at <!--s:parameters.2_classification.1_classify_repos.CHARS_PER_TOKEN-->3.57<!--/s--> characters per token, which the calibration measured with OpenAI's token counting. The script cuts the README only when, by that estimate, the request with the README, the activity of the issues and pull requests and what GitHub records about the repository would cross this boundary. The outline of the files, which the classification reads after the other results, gets the room that is left. The script shortens the lists of files of the outline first and cuts the rest of the outline after them. A model with another tokenizer can count more tokens than the estimate. In the check of 2026-11-02, DeepSeek V4.1 Flash counted <!--s:decisions_2026_11_02.largest_single_request_input_tokens-->334,012<!--/s--> input tokens for the one request of `libvirt/libvirt`, and it responded to the request. The price that `config/model_prices.csv` quotes for its pinned endpoint has no long context rate, so such a request costs no more per token.

Each model labels with the settings of its requests that its record in `endpoints.py` gives (`endpoints-spec.md`), which the maintainer set on 2026-11-02. Each labeling request of an OpenRouter model sends an output limit, reasoning included, because a request without a limit gets the endpoint's own, which no page of OpenRouter or of the provider states. DeepSeek V4.1 Flash sends <!--s:parameters.2_classification.endpoints.MAX_OUTPUT_TOKENS-->65,536<!--/s--> tokens at its configured temperature, so that a response that reasons until its limit ends sooner, and <!--s:parameters.2_classification.endpoints.HIGHER_MAX_OUTPUT_TOKENS-->262,144<!--/s--> tokens in its attempts at the higher temperature, the least that DeepSeek's model card recommends, with K counted as 1024 as DeepSeek's API reference counts it. GLM-5.3 and a model without settings of its own send <!--s:parameters.2_classification.endpoints.HIGHER_MAX_OUTPUT_TOKENS-->262,144<!--/s--> tokens. After a failed response at a repository, which `classify-repos-spec.md` defines, the next attempts at the repository use the higher temperature of the model's record, <!--s:parameters.2_classification.endpoints.HIGHER_TEMPERATURE-->1.0<!--/s--> for DeepSeek V4.1 Flash. When the model still leaves the repository without a decision through the retry rounds, the second model, GLM-5.3 on its pinned endpoint (`endpoints.SECOND_MODEL`), labels it with the same inputs and prompt and the settings of its own record. Each decision records the temperature and the top_p of the requests that decided it, a decision of the higher temperature or of the second model records it, the reason and the requests and tokens that the classifying model spent on its failed attempts, and `repos_annotated.json` lists these repositories. A run reuses such a label only under the same higher temperature and second model, also in an invocation in which the second model cannot label, as when its endpoint is unserved. A run of the second model itself and a run with `--no-second-model`, which every run of `check --runs` passes, label without the second model under the same classification parameters and reuse no label of it. A failure of GitHub, of a tool or of the API's service, or a README that the API refuses, is no reason for another temperature or the second model, which would get the same failure. When the API refuses the second model, its pass ends, and its repositories stay without a decision for the next run.

The script appends every decision to the partial file of the run as it makes the decision, and the next invocation resumes a stopped run where it stopped. A resumed run first derives the decisions of its earlier invocations again under the current rules, as it does for a reused decision. A new image that changed a rule therefore leaves no labels of the earlier rules in the outputs. When the model's service or GitHub returns no usable response for a repository through the retry rounds, and the second model does not label it either, the run leaves the repository without a decision, lists it as `undecided` in `repos_excluded.csv`, and the next run tries it again. The run finishes and exits 0 while these repositories number no more than the ceiling that the cloning step applies to clone failures among as many repositories. With more, it exits 1. A run that did not finish also writes its decisions, so that a run over another sampling frame reuses them. A later run also reuses the decisions in the partial file of a run that a kill ended. When the API rejects the API key, denies the key or the project access, or does not offer the model, the run stops. Fix the cause, and the next invocation resumes the run.

When OpenAI or OpenRouter refuses the requests for spent credit, the run waits for credit instead of stopping. Such a refusal is OpenRouter's HTTP 402, its HTTP 403 for a spent budget or key limit, or OpenAI's `insufficient_quota` or `billing_hard_limit_reached`, for the classifying model or the summary model. The requests to that service pause, which for the classifying model's service is every worker, and the refusal uses no attempt at a label and fails no repository. Only a response of that service ends the pause. A `WARNING` names the service and what to do: add credits at https://openrouter.ai/settings/credits or raise the credit limit of the OpenRouter API key, or raise the quota or the billing limit of the OpenAI project. The pipeline execution state shows the wait under `running_step_status` while it lasts ([the runner](../docs/runner.md)). Every <!--s:parameters.2_classification.1_classify_repos.CREDIT_CHECK_SECONDS.minutes:words-->ten<!--/s--> minutes (`CREDIT_CHECK_SECONDS`), the run checks the credit: for OpenRouter through `GET https://openrouter.ai/api/v1/key`, which spends nothing, and otherwise with one request, which costs nothing when it is refused. Once the credit is back, the run continues by itself and logs how long it waited. After <!--s:parameters.2_classification.1_classify_repos.CREDIT_WAIT_SECONDS.days:words-->three<!--/s--> days (`CREDIT_WAIT_SECONDS`), which cover a weekend, the run stops with its decisions kept, and the next invocation resumes it. Before its first request, a run through OpenRouter logs the credit that the key has left beside the estimated cost of the repositories left, and a `WARNING` with the shortfall when the credit covers less.

Before its first request, the script checks each GitHub access token, and only HTTP 401 rejects one. When a check fails on the network or with a server error, the script checks again. When GitHub rejects every GitHub access token, the run checks them again after waits that grow from minutes to hours, as the sampling stage's query does, and stops only when GitHub accepts none after the last wait.

When GitHub has returned no usable response for two repositories since its last response, every worker pauses, for waits that grow in the same way, and then tries the repository again. When GitHub fails again after the last wait, the run stops, and the next invocation resumes it. While GitHub responds to the README request that it served last, a repository that GitHub failed earlier in the run fails again on its own and starts no pause. The repositories for which GitHub fails every request therefore end without a decision instead of pausing every worker. When GitHub returns no usable response to that README request either, the failure counts toward the pause, so that the run waits out an outage that begins in a retry round. When GitHub or the summary model fails a tool call, the script makes the call again after waits of minutes, before the first request or in the same conversation. The script writes the model's response to the partial file before it requests the facts of GitHub that the response needs, so neither a failed request for the facts nor a stop pays the model again.

The log has the format of the log of the cloning step: a progress line after every <!--s:parameters.2_classification.1_classify_repos.PROGRESS_EVERY-->100<!--/s--> repositories or <!--s:parameters.agentcontext.logs.PROGRESS_SECONDS.minutes:words-->ten<!--/s--> minutes, with the rate, the time left and the requests and tokens spent, a warning for each repository left without a decision, and a summary at the end.

Run the labeling on its own from this directory, with the default model, DeepSeek V4.1 Flash on Morph's fp8 endpoint through OpenRouter:

```shell
python3 1_classify_repos.py
```

The endpoint that serves an OpenRouter model sets its price, and its requests name no tier. An OpenAI model that a command names, such as a reference model of the pilots, sends its requests to OpenAI's flex tier, which costs half the standard price and responds more slowly, or with `--openai-service-tier default` to the standard tier. When the service fails the requests of two repositories, as for a lack of capacity, every worker pauses, for longer after each pause that ends without a response, and then sends its request again in the same conversation. The run stays on its tier. After the first pauses without a response, each such failure uses an attempt at the label of the repository, so that repositories with requests that fail every time end without a decision. Once the pauses since the last response have taken `PAUSE_TOTAL_SECONDS`, the run stops, and the next invocation resumes it. The comparison with the previous run sends the requests for its repeated labels to the endpoint or the tier of the run.

Each model of OpenRouter has a backup provider of the same weights in the same quantization in `endpoints.py`: `deepinfra/fp8` for DeepSeek V4.1 Flash, the classifying model and the summary model, and `gmicloud/fp8` for GLM-5.3, the second model, which the maintainer chose from a check on 2026-11-04. Where a failure of the pinned provider would use an attempt, after the pauses or as the failure of one repository while the others succeed, the same request goes to the backup provider with the same settings. Once the pinned provider has failed the requests of two repositories, the backup provider serves every request of the model, a `WARNING` says so, and one request every <!--s:parameters.2_classification.endpoints.PINNED_CHECK_SECONDS.minutes:words-->ten<!--/s--> minutes tests whether the pinned provider serves again. Its first response ends the switch, with an `INFO` line. A failure of the backup provider pauses and uses attempts as a failure of the pinned provider did without it, and so does OpenRouter's refusal for the budget of the requests in flight of the API key at either provider. A streak of responses that fail the response format that ends with a response of the backup provider retires the backup provider for the rest of the invocation, with a `WARNING`, instead of stopping the run. The summary model fails over to its backup provider on the first failed summary. A backup provider that OpenRouter's endpoint list shows unable to serve the requests of its role is left out with a `WARNING`. A pinned endpoint that the list does not name, as while its provider takes it down, starts the model on its backup provider, with a `WARNING`, where it would otherwise stop the run at its start. `--no-backup-provider` sends every request to the pinned provider. The provider is no classification parameter: The maintainer decided on 2026-11-04 that the model, the weights, the quantization and every setting of the requests are parameters and the provider is none. A label that the backup provider served is a label under the same parameters, and its decision names the provider of each response under `served_by` and of each summary under `summary_provider`. A run that started under parameters recorded with the provider resumes under the same parameters without it and keeps its decisions.

When <!--s:parameters.2_classification.1_classify_repos.FORMAT_STREAK-->20<!--/s--> final responses in a row, for <!--s:parameters.2_classification.1_classify_repos.FORMAT_STREAK_REPOSITORIES-->5<!--/s--> repositories or more, fail the response format, every worker pauses as well, for waits that grow in the same way. Responses in the format for <!--s:parameters.2_classification.1_classify_repos.FORMAT_STREAK_REPOSITORIES-->5<!--/s--> repositories in a row show that the endpoint has recovered and make the next pause the first again, whereas a single response in the format only ends the streak. When the endpoint keeps failing through <!--s:parameters.2_classification.1_classify_repos.FORMAT_PAUSES:words-->seven<!--/s--> pauses without recovering, it does not hold the model to the schema of `submit_classification`, and the run stops with its decisions kept. Until the endpoint has recovered, the failed responses of the retry rounds count as well, and the pass of the second model takes over the pauses, so that an outage at the end of the main round pauses them too. An unattended run thus rides out an endpoint that fails the format for hours rather than stopping. The failed responses still make the next attempts at their repositories use the higher temperature. A response that the service ended, with an error or with the status `failed`, is a failure of the service rather than of the response format, whether or not it calls `submit_classification`, and the next attempt keeps its temperature. When the provider fails after the headers, OpenRouter responds with status 200 and a Response with the status `failed` that holds only an error, without output or with an empty output, which counts as a response that the service ended as well, whatever the code of the error. The log names the error with its `error_type`, which states the reason. Such a Response carries no usage and counts as no response of its repository, and no code of its error makes the workers wait for credit. A summary of a linked page that the service ended in the same way fails the tool call, which the classification makes again and then leaves the repository for a retry round, rather than reaching the model as a page that says nothing. A response with the status `incomplete` for another reason than the output limit, such as a content filter, is a failed response, and so is a response that stopped at its output limit before the call of `submit_classification` or in the arguments of the call, which pauses no worker. The log names each failed attempt with its error, which for a failed response states how the response ended, and the `failed` line of a repository that the model left without a decision keeps the start and the end of the arguments of each malformed checklist and of the text of each message that the model wrote instead of the checklist. A label made after a failed response also keeps the start and the end of the text of its message, in the record of the higher temperature or of the second model, or under `first_failed_response` for a label that a model made at its own settings, such as a label of the second model or of a run with `--endpoint-default-temperature` (`classify-repos-spec.md`). The timeout of the requests applies to connecting and to each read of a response, not to the whole request. OpenRouter sends the headers of its response when the provider accepts the request, and the bodies of its responses to the requests, which are not streamed, begin with blank lines, the more the longer the model generated, so that a request can take far longer than the timeout.

The classifying model and the summary model are DeepSeek V4.1 Flash, an open-weight model that OpenRouter serves, by default (`endpoints.PRODUCTION`). For another OpenRouter model, or the default model on another endpoint, pass the model's OpenRouter id, which names its author, to `--model`. Pass the provider slug of the pinned endpoint, which OpenRouter's endpoint list gives in `tag`, to `--provider`, the endpoint's quantization to `--quantization` and the Hugging Face id of the model's weights to `--hugging-face-id`. Each request goes to that endpoint alone, without fallbacks and only to an endpoint that supports every parameter of the request. OpenRouter's Responses API keeps no conversation, so each request sends the whole conversation with the reasoning items of the model's responses. A run whose endpoint stops responding pauses as a run on the flex tier does. DeepSeek V4.1 Flash labels at reasoning effort high, temperature <!--s:parameters.2_classification.endpoints.TEMPERATURE-->0.6<!--/s-->, top_p <!--s:parameters.2_classification.endpoints.TOP_P-->0.95<!--/s--> and seed <!--s:parameters.2_classification.endpoints.SEED-->7<!--/s-->, which `--reasoning-effort`, `--temperature`, `--top-p` and `--seed` change, and `--endpoint-default-temperature` sends neither a temperature, a top_p nor a seed. Its model card recommends `| temperature | 1.0 |`, the higher temperature <!--s:parameters.2_classification.endpoints.HIGHER_TEMPERATURE-->1.0<!--/s--> of the attempts after a failed response, and the model card of DeepSeek-R1 recommends 0.6 for that model against endless repetitions. In the check of 2026-11-02, the runs at 0.6 labeled closer to the reviewer and had fewer failed responses than the runs at 0.2 and at the endpoint's default temperature (`classify-repos-spec.md`). The settings of a pinned model apply to its weights on any endpoint. An OpenAI model labels at the effort medium and takes none of the other settings, and the summary model's requests send its effort alone. The model id, the Hugging Face id of its weights, its quantization and the settings that its requests send are classification parameters, and a change of any of them, but not of the provider, makes the next run label every repository again (`endpoints-spec.md`):

```shell
python3 1_classify_repos.py --model deepseek/deepseek-v4.1-flash --provider morph/fp8 \
    --quantization fp8 --hugging-face-id deepseek-ai/DeepSeek-V4.1-Flash --no-second-model \
    --repository-list ../data/classification/evaluation/<id>/check_sample.csv
```

**Output:**

- `../data/classification/repos_annotated.csv` (`repo_name`, `github_id`, `default_branch`, `engineered_project`, `justification`), one row per labeled repository, in the order of the sampling frame

## 2. The labels that changed since the previous run (`changed_labels.py`)

A run over the whole sampling frame ends by comparing its labels, by GitHub id, with the labels of the previous run over a sampling frame. For each repository with a changed outcome, it records why the outcome changed. The model labels a repository again only where the README, the model or the classification parameters changed, and the model's response varies from one request to the next. A changed README alone therefore does not establish why a label changed. The classifier of the run labels the current README of each changed label again, at the higher temperature or with the second model where the current label records it. When the repeated label equals the new label, the classifier also labels the previous README at the previous revision. The cause is model variation when one input has two labels, an input change when the labels follow their input, and a classifier change when a new model or new classification parameters give the previous input the new label. The cause of a change between a label and an exclusion follows from the README or the language check, without a request to the model. Trials and the runs of a label evaluation cover part of the sampling frame and are never the previous run. The first run over a whole sampling frame in the cache of labels has no previous run to compare with.

The index of the cache records a run as finished before the run writes its outputs and compares its labels. The comparison can fail, or a stop can end the invocation before the outputs and the comparison are complete. The next invocation over the same sampling frame then writes the missing outputs from the labels of the run and compares the run. It starts a new run instead when the current rules derive one of the labels of the run differently or need GitHub to check it. When the run left repositories without a decision and no collection over its sample has begun, the invocation also tries them again in a new run after the comparison, unless OpenRouter's lists show that OpenRouter serves no request of the classifying model or the summary model. Otherwise it starts no new run and requests no README. When the next run is over another sampling frame, that run finishes the comparison that the invocation left unfinished. `label_changes.csv` then contains both comparisons, and each row names its previous run. The cause stays `undetermined`, with the error, in these cases:

- GitHub or the model fails a repeated label through the retry rounds
- the API refuses a repeated label as malformed, and no retry round sends it again
- the current code cannot repeat the label, because it would send other classification parameters than the run recorded
- the second model made the current label and labels nothing in the invocation, as while its endpoint is unserved

`changed-labels-spec.md` gives every case. Run on its own, `changed_labels.py` compares any finished run with any earlier run:

```shell
python3 changed_labels.py --run 2026-11-05T080000Z --previous 2026-10-06T140917Z
```

**Output:** `../data/classification/label_changes.csv` (`repo_name`, `cause`, `previous`, `now`, `changed`, `repeat_label`, `previous_input_label`, `previous_run`, `justification`, `previous_justification`), one row per repository with a changed outcome in each comparison that the invocation made or wrote again from the cache of labels and, before it, in the comparisons of the earlier runs over the same retrieval that lead to its run (`changed-labels-spec.md`), the repeated labels in `../data/classification/labels/`, the tokens of the repeated labels in the tokens file of the run, with the cost record of the run written again, and the counts by cause in the log.

## 3. Select the sample (`engineered_project_selection`)


## 4. Evaluate the labels (`2_evaluate_labels.py`)

A second model, GLM-5.3 on Morph's fp8 endpoint by default (`endpoints.SECOND_MODEL`), labels the evaluation sample with the same prompt, tools, summary model and README. The evaluation sample is a simple random sample of the repositories that the first model labeled in its latest run over the sampling frame. A disagreement is therefore a difference between the two models, and a reviewer reviews only the disagreements. The evaluation sample leaves out the <!--s:calibration.sample_repositories-->2,282<!--/s--> repositories of the calibration sample, on which the reading rules were set, and every repository that the prompt names, or whose description, README or other text it quotes, as an example. The repositories that a quoted text describes as a group, such as the repositories of an owner whose profile description the prompt quotes or the repositories with the JDK's README, can still be drawn. The evaluation sample also leaves out the repositories that the second model labeled in the first model's run, because the first model left them without a decision, and the second model cannot check its own labels. `evaluation_sample.json` records them under `labeled_by_second_model`. The evaluation sample also leaves out the repositories of every earlier evaluation sample in `../data/classification/evaluation/`, because the prompt was revised on the disagreements of each of these evaluations. The earlier evaluations include the second pilot, `2026-10-30T222453Z`, the six-model test, `2026-10-31T094615Z`, and the pilot of the prompt revisions, `2026-10-31T210357Z` (`evaluate-labels-spec.md`). Its size is what an agreement of ±<!--s:parameters.2_classification.2_evaluate_labels.MARGIN.percent-->3%<!--/s--> at <!--s:parameters.2_classification.2_evaluate_labels.CONFIDENCE.percent-->95%<!--/s--> confidence needs. Evaluation `2026-10-28T214115Z` drew <!--s:evaluation_2026_10_28.sample_size-->1,040<!--/s--> of the <!--s:evaluation_2026_10_28.population-->40,674<!--/s--> other repositories that `gpt-6-luna` labeled in run `2026-10-23T093036Z`.

Draw the sample, label it with the second model, compare the labels of the two models and review the disagreements. `draw` creates the directory of the evaluation, `../data/classification/evaluation/<id>/`, and its log names the evaluation sample in it. Replace `<id>` in the commands below with the name of that directory:

```shell
python3 2_evaluate_labels.py draw --reference-model deepseek/deepseek-v4.1-flash
python3 1_classify_repos.py --model z-ai/glm-5.3 --repository-list ../data/classification/evaluation/<id>/evaluation_sample.csv
python3 2_evaluate_labels.py compare ../data/classification/evaluation/<id>
python3 2_evaluate_labels.py review ../data/classification/evaluation/<id>
```

`review` serves a page on 127.0.0.1 and opens it in the browser, unless you pass `--no-browser`, and its log names the address. Stop the server with Ctrl+C. The page shows each disagreement with its GitHub link, the rendered README that both models read, and for each model the label, the criteria that applied, the checklist, the purpose, the result of the fork heuristic, the justification and the tool calls with their outputs. As the reviewer decides each disagreement, `review` writes the reviewer's label, the criteria that apply when the label is `false`, and a note into `disagreements.csv`.

To check new classification parameters, such as a revised prompt, against a reviewed evaluation, draw a check sample, label it with both models and compare their labels with the expected labels. `draw-check` chooses every reviewed disagreement and a seeded random sample of the repositories that both models agreed on:

```shell
python3 2_evaluate_labels.py draw-check ../data/classification/evaluation/<id> --agreements 200
python3 1_classify_repos.py --no-second-model --repository-list ../data/classification/evaluation/<id>/check_sample.csv
python3 1_classify_repos.py --model z-ai/glm-5.3 --repository-list ../data/classification/evaluation/<id>/check_sample.csv
python3 2_evaluate_labels.py check ../data/classification/evaluation/<id> --models deepseek/deepseek-v4.1-flash z-ai/glm-5.3
```

To compare a model with others on the reviewed check samples, `check --runs` labels the check samples of several evaluations with one model, endpoint and reasoning effort in several runs. Each run labels into a cache of labels of its own under `../data/classification/checks/<date>/<variant>/`, so that no run reuses the labels of another. The command writes one row per run to `prompt_check_<date>.csv` in each evaluation's directory, with the numbers of reviewed disagreements labeled as the reviewer did, of agreed labels kept, of repositories labeled differently between the runs, of failed responses and of repositories left without a decision, the cost per repository, the higher temperature and the labels made at it. A check measures one model, and its runs label without the second model (`--no-second-model`), so a repository that the model fails counts as left without a decision. `check --models` counts a label that a run's second model made as no label of the run's model, and so does `compare` for the second model of an evaluation. A check that a stop or the longest wait for credit ended resumes with the same `--check-date`:

```shell
python3 2_evaluate_labels.py check ../data/classification/evaluation/2026-10-07T021344Z \
    ../data/classification/evaluation/2026-10-11T060023Z \
    ../data/classification/evaluation/2026-10-28T214115Z \
    --runs 5 --model deepseek/deepseek-v4.1-flash --provider morph/fp8 --quantization fp8 \
    --hugging-face-id deepseek-ai/DeepSeek-V4.1-Flash
```

**Output:** in `../data/classification/evaluation/<id>/`:

- `evaluation_sample.csv` and `evaluation_sample.json`, the evaluation sample and what drew it
- `disagreements.csv`, one row per repository that the two models labeled differently, with each model's criteria and empty `human_label`, `human_criteria` and `human_note` columns for the review
- `forks.json` in the evaluation of 2026-10-07, the results of the fork heuristic for its forks
- `check_sample.csv` and `check.csv`, with their records in `check_sample.json` and `check.json`, the check of new classification parameters against the review
- in evaluation 2026-10-11T060023Z, `prompt_check_2026-10-17.csv` with every run of the comparison of the reworded prompt with the earlier prompt, `prompt_check_2026-10-18.csv` and `prompt_check_2026-10-19.csv` with every run of the checks of the later changes to the prompt, and `prompt_check_2026-10-21.csv` with every run of the check of the classification without the star and fork counts
- `prompt_check_<date>.csv` of each evaluation that `check --runs` names, one row per run of a model with the columns of `PROMPT_CHECK_COLUMNS` (`evaluate-labels-spec.md`)
- `agreement.json`, the agreement with its interval, Cohen's kappa and the confusion matrix of the two labels, and the classification parameters of the compared labels of the second model with its weights, its quantization and the settings of its requests

Git tracks the cache, and a run adds files to it without changing the earlier files, except its own tokens file and cost record, which its comparison writes again. `label-cache-spec.md` describes the cache.

## The cost of a run

Every response of a model reports its tokens, the input tokens that the API read from its prompt cache or wrote to it, and the service tier that served the request, and OpenAI bills by all of them. OpenRouter bills by the tokens at the prices of the endpoint that served the request, the pinned endpoint or the backup provider, and the run counts the tokens of an OpenRouter model under the provider slug of that endpoint in place of the tiers. A request that a service refuses costs nothing and is not counted. As each invocation of a run ends, the run adds the tokens of its responses to `<id>.tokens.csv` in the cache of labels, by the role and the model, the tier that the requests named and the tier that the responses reported. The tokens of the page summaries count as well, although their requests name no tier. When the run ends, finished or stopped, it writes its cost record, `<id>.cost.csv`, and logs one line with the total in USD and the file. The comparison with the previous run adds the tokens of its repeated labels and writes the record again. The runs of a label evaluation and the trials write records of their own. The scripts of `diagnostics/` write none.

The record has one row per role of the model, model, service tier and rate: uncached input, cached input, cache writes and output, which includes the reasoning tokens. Each row gives the tokens, the price in USD per million tokens, the cost in USD, and the page and the date of the price. `config/model_prices.csv` contains the prices, read from OpenAI's pricing page and, for each pinned endpoint of an OpenRouter model, from OpenRouter's list of the model's endpoints, and the weekly documentation watch reads these pages again (`.github/workflows/doc-watch.yml`). After a change of a price, update its row and its `doc_verified` date, and record the hash of the page from the repository root:

```shell
python3 -m agentcontext docs --heuristics 2_classification/config/model_prices.csv --label-columns model,service_tier --update
```

`costs.py` writes the cost record of any run in the index from the tokens that the cache records. For the tokens that the index counts and no tokens file records by tier, such as those of a run from before the tokens file, it assumes the tier of `--openai-service-tier`, else the tier that the requests of the tokens file named, else the default of the labeling, and the notes of the record state each assumption (`costs-spec.md`):

```shell
python3 costs.py --run 2026-10-23T093036Z --output /tmp/cost.csv
```

## The reading rules

The classification bounds what the model reads by the rules below, which the code and the specs
name by number. Each rule was set from a measurement over the calibration sample, a random sample
of <!--s:calibration.sample_repositories-->2,282<!--/s--> repositories in the sampling frame of
retrieval `2026-10-05T101430Z`, or from a documented constraint of the model.
[The record of the calibration](../docs/history/2026-10-classification-calibration.md) gives the
measurements, and `../data/classification/calibration/` contains their results. The
`calibration_*.py` scripts of `diagnostics/` measure them again. The label evaluation draws its
sample from the other repositories in the sampling frame, so that it does not test the rules on
the repositories that they were set from.

| Rule | What the model reads | Where |
|---|---|---|
| 1 | A request is cut only where it would cross <!--s:parameters.2_classification.1_classify_repos.REQUEST_TOKENS-->272,000<!--/s--> input tokens, the boundary above which OpenAI charges the long context price for its models, estimated at <!--s:parameters.2_classification.1_classify_repos.CHARS_PER_TOKEN-->3.57<!--/s--> characters per token of OpenAI's token counting: first the outline's lists of files per practice, then the README, each cut marked by a line | `1_classify_repos.py` |
| 2 | The language check reads the README that GitHub shows by default. It excludes a README that it finds not to be in English without a request, and the classification labels `false` every other README that is not mainly English by the model's count of its words by language (`readme_words_by_language`) | `readmes.py`, `1_classify_repos.py` |
| 3 | A page is read only when its `Content-Type` is HTML, XHTML, plain text or Markdown, or is absent | `classification_tools.py` |
| 4 | A github.com link is read through GitHub's API: a repository as its README, a file as the file, a directory as its listing and the releases as their list. A file or a directory at a branch that was renamed is read at the branch's new name. No other page of github.com is read, and no link with a `.` or `..` segment in its path | `classification_tools.py` |
| 5 | A relative link of the README is resolved as GitHub resolves it from the README's page. A relative or github.com link of the README to a file or a directory of the repository at any branch, tag or commit is read as rule 4 reads a file or a directory, at the commit that the sampling frame recorded | `1_classify_repos.py`, `classification_tools.py` |
| 6 | A meta refresh counts as a redirect | `classification_tools.py` |
| 7 | At most <!--s:parameters.2_classification.classification_tools.MAX_REDIRECTS-->5<!--/s--> redirects per link | `classification_tools.py` |
| 8 | <!--s:parameters.2_classification.classification_tools.PAGE_TIMEOUT.connect-->10<!--/s--> seconds to connect and <!--s:parameters.2_classification.classification_tools.PAGE_TIMEOUT.read-->30<!--/s--> seconds per read | `classification_tools.py` |
| 9 | At most <!--s:parameters.2_classification.classification_tools.MAX_PAGE_BYTES.mb-->2<!--/s--> MB of a page | `classification_tools.py` |
| 10 | A page reaches the model as a summary, which the summary model writes from the text of the page, cut at <!--s:parameters.2_classification.classification_tools.MAX_SUMMARY_INPUT_CHARS-->960,000<!--/s--> characters | `classification_tools.py`, `prompts/page-summary-prompt.md` |
| 11 | The repository's files are shown as an outline from GitHub's list of files and its bytes per language, without a clone | `classification_tools.py` |
| 12 | The outline has no limits of its own, and only rule 1 shortens it | `classification_tools.py` |
| 13 | At most <!--s:parameters.2_classification.1_classify_repos.LINKED_PAGES-->5<!--/s--> linked pages per repository | `1_classify_repos.py` |
| 14 | At most <!--s:parameters.2_classification.1_classify_repos.MAX_TOOL_ROUNDS-->5<!--/s--> rounds of tool calls. A tool call past a limit returns a note that the limit is reached, and after a round past the limit the next request offers the tool of the checklist alone, so that the model decides without reading more | `1_classify_repos.py` |

The decision keeps each tool output whole, within the bound of rule 1. A page is read only from
an address on the public internet, because the stage runs in a container on a network with other
machines. The numbers of attempts of the requests to GitHub and to the model come from the
sampling stage's query of GitHub and from the prototype of this stage, and no measurement set
them.

## The prompts

`prompts/classification-prompt.md` keeps the definition of an engineered software project from the batch classification that labeled the sampling frame of March 2026. It requests the decision in two steps. The first step covers whether the software is maintained and used by others, every exclusion criterion with its evidence, and the upstream of a fork. The second step covers the purpose and the evidence of software engineering practices. The forms that a criterion names are examples, and the list of them is not complete. The reviews of the label evaluations added criteria and revised their wording, and `classify-repos-spec.md` records each revision with the review that it rests on. The criteria include the material of a paper or a book in any field, localization, deployment configuration, no source code, work in progress, a stated purpose, and inactivity, such as maintenance mode or a retirement notice. The prompt distinguishes a website, which presents content to its visitors, from a web application, with which its users do something, and a collection of material from a repository in which several programs are developed. It excludes a theme as a template, the packaging of software developed elsewhere as configuration and a program written for a course as teaching material, and it keeps a program that contains or loads a dataset. It counts as inactive the end of the platform that the software extends when the README recommends alternatives, and compatibility releases while a rewrite is developed in another repository, but not a port that adds no features beyond its original or the promotion of a newer product. The model reads the pinned issues before it decides the criteria that they can describe. Ansible modules and plugins are software, and Ansible roles and playbooks are a collection, also when they are published as an Ansible collection. A repository with its own code that generates, updates or customizes the components that it assembles is software. API stubs are no source code, the source of one particular website is a website, current data that scripts keep publishing for users is no dataset, and a script suite that a team runs together is software. `no_source_code` has a field for each of its two cases. A repository that is described as a mirror, or that GitHub marks as one, counts as a mirror unless its README invites pull requests there or pull requests were merged in it since the start of the sampling window. Pull requests that GitHub Apps such as Dependabot or Renovate opened do not count. The classification queries GitHub's API for the merges. Such merges also keep the repository from counting as moved.

The input is the description, the activity that the sampling frame records, the README and the results of three of the four tools, which the classification reads for every repository: the activity of the issues and pull requests, what GitHub records about the repository and the outline of its files. The model calls the fourth tool for a summary of a linked page. The batch prompt instead described three sections that every request contained. `classify-repos-spec.md` lists every change, and [the record of the calibration](../docs/history/2026-10-classification-calibration.md#the-prompts) gives the review of the prompts against OpenAI's guidance in 2026-10. `prompts/page-summary-prompt.md` contains the instructions of the model that summarizes a linked page. [The record of the prompt iterations](../docs/history/2026-03-classification-prompt-iterations.md) keeps the revision of the batch prompt.

A commit that `config/parameter_digests.csv` or a record under `../data/classification/evaluation/` names, such as the column `prompt_commit` of a pilot, is a plain value that names a commit of the private repository `se-uhd/agenttorrent-pipeline-internal`, and no check resolves it.

The classification parameters and their SHA-256 change with the classifying model, its weights, its quantization or a setting of its requests, with the summary model, its weights and its quantization, and with a prompt, a tool description, the response format, the format of the input or of a result that it holds, a limit, a message that replaces the result of a tool call or the code that decides which page a link from the model names. After such a change, the next run labels every repository in the sampling frame again and pays the model for each. The provider that serves a model changes neither, by the maintainer's decision of 2026-11-04, and a digest recorded before with the provider counts as the digest of the same parameters without it (`label_cache.ParameterKeys`). `config/parameter_digests.csv` records each digest of the classification parameters in order, with the commits that made it and what changed. A test of `test_classify_repos.py` computes the digest of the classification parameters that the code builds, with the tool definitions and the output schemas that the real MCP server lists, and fails when that digest is not the last entry. Record a new digest there on purpose, in the commit that changes the parameters.
