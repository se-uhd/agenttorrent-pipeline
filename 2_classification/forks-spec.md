# Decide whether a fork is independent

## Context

`forks.py` is the fork heuristic, which decides whether a repository that its README or description calls a fork of another project has become a project of its own. Before the heuristic, the prompt required the label `false` for every repository described as a fork. The reviewer of the evaluation of 2026-10-07 marked <!--s:evaluation_2026_10_07.fork_disagreements-->16<!--/s--> of its disagreements as forks, each with a label that depends on how independently the fork evolved. The reviewer labeled `hiqdev/yii2-hiart`, which "was started as fork from Yii2 Elasticsearch", `true`. GitHub's own forks never reach the classification, because the sampling stage drops every repository that GitHub marks as a fork (`exclude_forks` in `../1_sampling/config/ghs_filter.yaml`). In the classification, a fork is a repository created on its own that started from another project. The model names the upstream (`fork_of`), and the heuristic decides from GitHub's data, so that the decision does not depend on the model's reading of how close two projects are.

## Key decisions

- **Language:** Python 3.14, in the single module `forks.py`, with `readmes.Client` for GitHub's REST API, as for the classification's other GitHub requests, and `agentcontext.github_api.blocked` for GitHub's block of a repository
- A fork is independent when it does not track its upstream and is developed on its own: It has at least the GHS query's `contributorsMin` own authors, <!--s:parameters.1_sampling.config.ghs_download.query.contributorsMin:words-->two<!--/s-->, without bots, and at least one own commit since the start of the sampling window. Its own authors are the authors of the commits on its default branch made since GitHub created it, or of all its commits when it took over none of its upstream's history, counted at the revision that the sampling frame recorded. The sampling frame records both thresholds (`thresholds_of`), and the heuristic needs no threshold of its own. A fork that someone made and changed a little has one author or no commit in the window, which is the case that the reviewer raised. Until 2026-10-31, the fork's own commits also had to reach the commit minimum of the filter's activity step, <!--s:classification_2026_10_23.fork_commit_minimum-->359<!--/s--> in the sampling frame of retrieval `2026-10-23T074035Z`, as if the fork had to enter the sampling frame by its own commits. In the second pilot of the classification, that minimum alone excluded `jaroslawhartman/withings-sync`, "Based on withings-garmin", which does not merge its upstream and has two authors and commits in the window, and `quictls/quictls`. The reviewer labeled `withings-sync` `true`: A fork with independent development is a project of its own however few its own commits are
- A fork tracks its upstream when the upstream is on GitHub and has commits in the sampling window, the upstream's newest commit from before the window is newer than GitHub's creation of the fork, and the fork's revision contains that commit. The fork then keeps merging the upstream, and its commits since its creation are mostly the upstream's. Nearly all of the commits of `ferrocene/ferrocene` since its creation are Rust's, and the repository describes itself as "a proper downstream" of Rust. Such a fork is a downstream whatever the number of its own commits. The heuristic decides from GitHub's comparison of the revision with the commit whether the fork contains the commit, and a status of `behind` or `identical` means that it does. The request puts the revision first, because GitHub compares from the merge base of the two commits to the second commit, and the comparison is empty when the revision contains the commit. In the other order, GitHub compared every commit of the fork since the commit and broke the connection for `ferrocene/ferrocene` on 2026-10-09
- A fork contains every commit of its upstream that it started from, and an upstream commit from before GitHub created the fork therefore does not show that the fork keeps merging the upstream. `closeio/sync-engine`, "a fork of the Nylas sync-engine project", was created on GitHub on 2020-07-09 and developed on its own until 2026-10-29. It contains the newest commit of `nylas/sync-engine` from before the window, made on 2017-03-08, because it started from that history, and Nylas's only commit in the window is its archive notice of 2026-06-25. Before 2026-10-31, the heuristic found that the fork tracks its upstream, and the second pilot of the classification excluded it. The heuristic compares the commit's committer date with the creation time of the fork's repository on GitHub, which the repository record that the heuristic reads gives exactly for every fork. Comparing the commit with the fork's first own commit instead would need the comparison of histories that the heuristic makes only to count the authors, and the date of that first commit is set by its author or comes from an import. For a project that moved to GitHub with its history after it started from its upstream, the heuristic counts an upstream commit from before the move as one that the project started from, and decides by the project's own development. `openshift/sriov-network-device-plugin`, created in 2019, contains the newest commit of `k8snetworkplumbingwg/sriov-network-device-plugin` from before the window, made on 2026-03-31, and tracks its upstream
- A fork that does not contain its upstream's first commit took over none of the upstream's history. Every commit of the fork is its own, and the author of every commit counts among its own authors. `parthenon-hpc-lab/athenapk` describes itself as "a performance portable version based on Athena++", contains none of Athena++'s commits and has commits from before GitHub created its repository in 2022. The heuristic decides from GitHub's comparison of the fork's revision with the upstream's first commit whether the fork contains that commit, as it does for tracking. The check sends three requests, for the first and the last page of the upstream's commits and for the comparison. It sends them only when the fork's authors since its creation fall short of the minimum, the one case in which the result changes the verdict. Of the <!--s:classification_2026_10_10.upstreams_named-->2,739<!--/s--> repositories with an upstream that the model named in run `2026-10-10T035814Z`, <!--s:classification_2026_10_10.upstreams_on_github-->1,478<!--/s--> had an upstream on GitHub. On 2026-10-11, of the 11 forks with an upstream on GitHub in both evaluations, `athenapk`, `hiqdev/yii2-hiart`, `samfundev/KtaneTwitchPlays`, `ticketz-oss/ticketz` and `jhipster/jdl-studio` contained none of their upstream's history
- A fork of an upstream that is not on GitHub, or that GitHub no longer has or blocks, has no upstream's first commit to look for. The authors that the heuristic counts among a fork's commits since its creation are the fork's own authors. When the fork's oldest commit is by one of them, the fork started with its own commit and took over none of its upstream's history either, and every commit of the fork is its own. `Perlence/PyGuitarPro` states that "Initially PyGuitarPro is a Python port of AlphaTab which originally was a Haxe port of TuxGuitar". Its oldest commit is by its own author, and <!--s:forks_2026_10_19.pyguitarpro_since_creation-->279<!--/s--> of its <!--s:forks_2026_10_19.pyguitarpro_commits-->553<!--/s--> commits are from after GitHub created its repository. A fork that took over its upstream's history starts with the upstream's commit, as `LukeSmithxyz/dwm` starts with a commit of dwm's author. Run `2026-10-10T035814Z` had <!--s:forks_2026_10_19.off_github_short-->96<!--/s--> forks with an upstream off GitHub and fewer commits since their creation than the commit minimum of that time. Read from GitHub on 2026-10-19, some of these start with a commit of one of their own authors and reached that minimum with all of their commits, such as `ygrek/ocurl`, which its maintainer moved from SourceForge, and `EionRobb/purple-googlechat`, which continues its author's plugin for the old Hangouts. Counting the authors of every commit of a fork with an upstream off GitHub would count the upstream's authors for the forks that took over their upstream's history, such as `TianheMICALab/SimCXL` with gem5's. If the heuristic counted the authors of the commits that the fork's newest authors made before its creation, it would count the upstream's own developer for `RealityRipple/squirrelmail`, which imports SquirrelMail's commits. The check sends the two requests for the fork's oldest commit and reads the pages of its newest authors again only when the authors since the creation fall short of the minimum
- When an upstream cannot be tracked, the heuristic decides by the fork's own development. An upstream cannot be tracked when it is not on GitHub, such as KivyMD's on GitLab, when GitHub no longer has it or blocks it after a DMCA takedown or for a violation of its terms of service, or when it has no commit in the window. `samfundev/KtaneTwitchPlays`, for example, contains the last commit of its upstream, which stopped in 2018. If the heuristic failed a fork with a blocked upstream, the classification would leave the fork without a decision in every run and pay the model for its README again in each run
- When GitHub resolves the upstream to the repository itself, the repository is the upstream, and the heuristic counts it as independent. `calcom/cal.diy` is `calcom/cal.com` renamed, and GitHub's redirect for the old name returns the repository's own id
- The heuristic checks an upstream when the model gives a github.com link or names a repository on GitHub as `owner/repo`, which it resolves through GitHub as it resolves a link (`github_name`). A login on GitHub has no dot, so a host with a path, such as `gitlab.com/inkscape`, is no such name. A name such as `GNU/Linux` or `OS/2` that has the form is resolved like the others, and GitHub's 404 for such a name makes the upstream one off GitHub, at the cost of one request. The model gives the link that the README, the description or a page that the model read gives, the github.com link of a repository of the same owner on GitHub also when no page links it, or the name when none of this gives a link. In the second pilot of the classification, the models named `openjdk/jdk` without a link as the upstream of `openjdk/lilliput`, a repository of an OpenJDK project with the JDK's README that keeps merging the JDK, and the heuristic could not check that it tracks its upstream. The repositories of OpenJDK's projects that keep merging the JDK track it, and the update repositories, `jdk8u` to `jdk21u`, which do not merge it, are decided by their own development. `MirageNet/Mirage` names "Mirror" and `magemonkeystudio/fabled` names "SkillAPI" without a link. For these two forks, the heuristic decides by the fork's own development, because a name alone cannot be resolved to a repository without guessing. `ferrocene/ferrocene`, `criteo/py-consul` and `ticketz-oss/ticketz` link to their upstreams elsewhere in their READMEs
- The heuristic counts the fork's own authors, newest first, until it reaches the minimum or the fork's own commits end. It reads them from pages of <!--s:parameters.2_classification.forks.AUTHOR_PAGE_SIZE-->100<!--/s--> commits, the most that GitHub's list of commits returns: "The number of results per page (max 100)" ([list commits](https://docs.github.com/en/rest/commits/commits#list-commits), read on 2026-10-19). A fork with two authors among its newest commits costs one request. With a limit of ten pages, run `2026-10-10T035814Z` counted one own author for <!--s:forks_2026_10_19.single_author_forks-->15<!--/s--> forks in which one author made the newest ten pages of own commits, such as `psi-probe/psi-probe` with <!--s:forks_2026_10_19.psi_probe_own_commits-->9,460<!--/s--> own commits. Read to the end of their own commits on 2026-10-19, all of them but `NellielProject/Nelliel` have a second author, and `NellielProject/Nelliel` has one author in all its own commits. A fork with one author takes a page for each <!--s:parameters.2_classification.forks.AUTHOR_PAGE_SIZE-->100<!--/s--> of its own commits, against GitHub's rate limit of <!--s:github.rest_hourly_requests-->5,000<!--/s--> requests an hour for a GitHub access token ([rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api), read on 2026-10-19)
- A commit counts as a bot's when GitHub gives its author's type as `Bot` or a name contains `[bot]`. An author is a commit's GitHub account, else the address of the author in its git data. GitHub's REST API description declares that author as `nullable-git-user` ([description](https://raw.githubusercontent.com/github/rest-api-description/main/descriptions/api.github.com/api.github.com.yaml), read on 2026-10-18), and a commit that GitHub returns with a null author there counts by its account. If such a commit failed with an error that the classification does not handle, the labeling would stop at the same repository in every run, because the partial file keeps the model's response that waits for GitHub's facts. A commit with neither an account nor an address names no author. If the heuristic counted such commits, all of them together would add one author, the empty name, who could bring a fork with one author to the minimum
- The classification records the heuristic's result with the decision and reuses a fork's decision only under the same thresholds (`classify-repos-spec.md`). The result contains the upstream as the model named it, the repository that GitHub resolved it to, whether the upstream is active, its newest commit from before the window with that commit's date, whether the fork tracks it, and whether the fork shares history with it. It also contains the fork's own authors and its own commits in the window, the fork's creation, the thresholds, whether the fork is independent and the reasons when it is not
- The version of the heuristic is the SHA-256 of the code of `forks.py` without its comments, docstrings and layout (`HEURISTIC`, `code_digest`). The classification records the version with each verdict and queries GitHub again for a reused verdict of another version. Without the version, a reused decision under the same thresholds would keep the verdict of the code that made it, and a fix such as counting every commit of a fork that shares no history with its upstream would never reach that decision. A changed comment does not change the version, because querying GitHub again costs requests for every fork
- The thresholds were checked on the forks of the evaluation of 2026-10-07. `../data/classification/evaluation/2026-10-07T021344Z/forks.json` contains the heuristic's results for all <!--s:evaluation_2026_10_07.fork_disagreements-->16<!--/s--> forks, with the upstreams that their READMEs name. By these results, <!--s:evaluation_2026_10_07.forks_independent-->11<!--/s--> forks are independent, `ferrocene/ferrocene` and `clover-moe/lilium-voyager` track their upstreams, and `IBM/ibm-cos-sdk-js`, `criteo/py-consul` and `cculianu/asicseer-pool` had fewer own commits than the commit minimum of that time. The reviewer agreed with this outcome on 2026-10-08, and the file predates the removal of the commit minimum. The heuristic reads the fork's own commits rather than its issues and pull requests, which were considered first, because the commits show the fork's own development directly

## Module: `forks.py`

### Function structure

**`Thresholds`**, **`thresholds_of(metadata)`**: the thresholds, read from the sampling frame's `_metadata` as `input_source.query.contributorsMin` and `input_source.window.committed_min`, or None when one of them is missing

**`github_name(upstream)`**: the `owner/repo` of a github.com link or of a bare `owner/repo`. It returns None for another link and for another name. It also returns None for an owner or a repository of dots alone, such as `https://github.com/../user`, which in a request would leave the repository's path and query `/user` with the GitHub access token. It returns None as well for an address that is no URL, such as an address with a fullwidth slash in its host, which the model can copy from a README. If `github_name` raised the error of such an address, the error would count as GitHub's failure, and the repository would end undecided in every retry round

**`count(client, url)`**, **`own_authors(client, name, head, since, minimum)`**: the number of items of a paged list, read from the last page when one item is requested per page, and the number of distinct authors of the commits since `since`, newest first until `minimum` or the end of the commits

**`oldest_commit(client, name, head)`**, **`first_commit(client, name)`**: the oldest commit at a revision of a repository, and the SHA of the oldest commit on its default branch

**`independence(client, repository, revision, upstream, thresholds)`**: the counts and the comparison that the heuristic decides on, whether the fork is independent, with the reasons when it is not

**`code_digest(source)`**, **`HEURISTIC`**: the version of the heuristic

## Error handling & edge cases

| Scenario | Behavior |
|----------|-----------|
| The upstream is a name other than `owner/repo` or a link off GitHub | No request for it. The heuristic decides by the fork's own development. The authors of every commit count when the authors since the creation fall short of the minimum and the fork's oldest commit is by one of its newest authors |
| GitHub returns 404 or 451 for the upstream, or 403 with the block of a terms-of-service violation | The upstream counts as not on GitHub |
| The upstream has no commit in the window | No comparison for tracking. The heuristic decides by the fork's own development, after the comparison with the upstream's first commit when the fork's authors since its creation fall short of the minimum |
| An empty repository, 409, for a list of commits | No commits |
| A commit with a null author in its git data, or without its git data | It counts by its GitHub account, and names no author without one |
| Any other status than the documented statuses, also for the request of the upstream's last commit before the window, which the test for tracking needs | `Unexpected`, which fails the repository for the classification, and the next run decides it |

## Tests

See `test_forks.py`, which uses the standard library's `unittest`. A fake session behind the real `readmes.Client` stands in for GitHub. The fake session stores each repository as a history of commits and returns, as GitHub's REST API does, the repository, its commits filtered by `sha`, `since` and `until` in pages with a Link header, and the comparison of two commits. It breaks the connection when a comparison would send more commits than a limit. A fork and its upstream share the commits that the fork took over, and whether the fork contains a commit follows from the histories.

- **`TestIndependence`** (20): a fork that contains its active upstream's commit tracks it and is a downstream; an upstream named as owner and repository is resolved through GitHub; a fork that only started from its upstream's history does not track it; a failed request for the upstream's commit before the window is GitHub's failure; a fork that diverged with its own development is independent; a fork with few own commits and its own development is independent; a fork that shares no history with its upstream counts every author; a fork of an upstream off GitHub that starts with its own commit counts every author; one author besides bots is too few; the own authors are counted past a thousand commits of one author; a commit without its git author counts by its GitHub account; a commit that names neither an account nor an address counts no author; no own commit in the window is not a project of its own; an upstream that stopped cannot be tracked, and the fork's own development decides; an upstream named without a link to GitHub leaves the decision to the fork's own development; an upstream that GitHub no longer has or blocks leaves the decision to the fork's own development; an upstream that is the repository itself is no fork; the commits are counted at the sampling frame's revision; the own commits are counted across pages; a response of GitHub that is not documented fails
- **`TestPieces`** (3): the heuristic's version follows its code and not its comments; the thresholds come from the sampling frame's record; a GitHub link names its repository

Run with:

```shell
python3 -m unittest test_forks -v
```

## Known limitations

- The heuristic does not treat a repository as a fork when the repository calls itself a fork only outside its README and description, because the heuristic runs only for an upstream that the model names. `mrhenry/polyfill-library` has no description and a README that names no upstream but links to its `HISTORY.md`, which calls it a hard fork. The model names the upstream only when it reads that page, which the prompt has required since 2026-10-18. When the model does not read the page, it labels the repository `true`, while the reviewer of evaluation 2026-10-11 labeled it `false`
- A downstream that names its upstream only by a name other than `owner/repo`, without a github.com link, is judged by its own development alone, because such an upstream is not checked for tracking
- The heuristic selects commits by their commit date. A commit made before the fork's creation and pushed after it does not count as the fork's own, and an upstream's commit merged with a later date does
- One person who commits under two addresses counts twice, because the fork's own authors are counted from the commits' GitHub accounts or, without an account, their addresses
- The fork's own authors are counted from GitHub's creation of the repository when the fork shares history with its upstream, or when its upstream is not on GitHub and its oldest commit is not by one of its newest authors. A project that was moved to a new repository on GitHub with its history therefore counts only the authors of its commits since the move, unless its first author is among the authors of its newest commits. `Cxbx-Reloaded/Cxbx-Reloaded` has commits since 2015, but GitHub created its repository on 2026-04-19, and its first pull request there is from 2026-10-08. When gpt-6.1-sol named the original Cxbx as its upstream in the evaluation of 2026-10-11, the heuristic of that time counted 15 own commits and found the fork not independent, and the reviewer labeled it `true`. An upstream named without a link to GitHub has no first commit to compare with, and the oldest commit of `Cxbx-Reloaded/Cxbx-Reloaded` is not by one of its two newest authors. The heuristic therefore still counted 15 own commits on 2026-10-19. The prompt states that credits to the authors of earlier projects do not describe a repository as a fork, and the README credits the original Cxbx in this way
